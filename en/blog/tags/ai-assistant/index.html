Billing model. claude-cli uses your Claude subscription (Max/Pro) quota — there’s a daily/monthly usage cap but no per-token charge. API Key billing is per actual token usage with no hard cap, but costs can be higher.

Q: Why use Opus 4.6 [1M] over the standard window?

Section titled “Q: Why use Opus 4.6 [1M] over the standard window?”

  • Code analysis: Load entire project’s key files in a single context

The tradeoff is slightly higher time-to-first-token. If your use case doesn’t need long context, standard claude-opus-4-6 (200K) is faster.

Since v2026.3.28, when you reference the claude-cli backend in your config, the corresponding bundled plugin is automatically enabled — no more manual declaration in plugins.allow. This is part of the “CLI Backend Pluginization” improvement.

OpenClaw Permission Control Deep Dive: From 9-Layer Security to Production-Grade Hardening

Mar 29, 2026
Vibe Sparking

A comprehensive guide to OpenClaw’s tool permission system — combining official documentation and community best practices. Not just configuration templates, but a deep look at the trust model, audit mechanisms, and architecture trade-offs.

Why Permission Control Is OpenClaw’s Core Challenge

Section titled “Why Permission Control Is OpenClaw’s Core Challenge”

OpenClaw is not a chatbot — it’s an AI assistant platform with real system capabilities: file read/write, command execution, message sending, browser control, and more. A single prompt injection, if permissions aren’t locked down, could turn into an rm -rf or a bizarre email to your boss.

The fundamental question of permission control: How do you make AI powerful enough without letting it cross the line?

Part 1: Trust Model — The Foundation of All Configuration

Section titled “Part 1: Trust Model — The Foundation of All Configuration”

Personal Assistant Model, Not Multi-Tenant Platform

Section titled “Personal Assistant Model, Not Multi-Tenant Platform”

This is the most easily overlooked yet most important point:

OpenClaw’s security model is a personal assistant model — one Gateway instance = one trust boundary.

This means:

  • All users within a single Gateway share the same tool permissions. There’s no permission isolation between sessions; sessionKey is a routing selector, not an authentication token.
  • If multiple people share a bot (e.g., everyone in a Slack group can @it), every person can trigger all tool calls that agent is allowed to make.
  • Need real user isolation? Split your Gateways — use different Gateway instances for different trust boundaries, ideally running under different OS users or even different machines.

Real-World Consequences

Personal multi-channel (Telegram + WhatsApp)Same trust domain, acceptableEnsure DM pairing + group requireMention

Part 2: The 9-Layer Permission Security Model

Section titled “Part 2: The 9-Layer Permission Security Model”

Every time AI calls a tool (read files, execute commands, send messages…), it must pass through 9 gates in sequence — blocked at any gate means termination. Layers go from coarse to fine:

Three Iron Rules

Section titled “Three Iron Rules”
  1. deny is irreversible — once any layer denies a tool, no subsequent layer can restore it
  2. Only tightening — later layers only get stricter, never re-enable what earlier layers disabled
  3. Fine overrides coarse — agent-level config overrides global; sender-level overrides group-level

⚠️ Common pitfall: Using deny: ["exec"] at Layer 1 to disable command execution, then allow: ["exec"] at Layer 5 for a specific agent — doesn’t work, exec is already dead. You can only fix it at Layer 1.

minimal — Minimum Permissions

coding — Development Mode ⭐ Most Common

Section titled “coding — Development Mode ⭐ Most Common”
  • ✅ File read/write, command execution, session management, memory operations
  • Use case: Daily development, operations, project management

messaging — Messaging Mode

Section titled “messaging — Messaging Mode”
  • ✅ Chat session-related operations
  • ❌ No system files or commands
  • Use case: Customer service, message broadcasting, pure conversation bots

full — Full Access Mode

Section titled “full — Full Access Mode”
  • ⚠️ No restrictions whatsoever, admin use only
  • Official recommendation: Start with messaging or coding, open up as needed

Part 8: Future Evolution

Section titled “Part 8: Future Evolution”

Near-Term

Section titled “Near-Term”

  1. Dynamic runtime approval expansion — Currently only exec has ask mode; future may extend to browser, gateway, cron, and more tools with runtime approval prompts.

  2. Continuous auditing — Evolving from manual openclaw security audit to background continuous monitoring + real-time alerts via webhooks.

  3. Hot permission policy updates — Permission config changes taking effect immediately without Gateway restart.

Mid-Term Trends

Section titled “Mid-Term Trends”

  1. Conditional policy engine — Evolving from static JSON allow/deny to a policy language supporting conditional expressions (time ranges, IP ranges, call frequency, etc.).

  2. Per-user permission boundaries — Implementing user-level permission isolation without splitting Gateways, reducing operational cost for multi-user scenarios.

  3. Cross-Gateway federation management — Unified policy distribution and compliance auditing for multi-instance cluster scenarios.

Long-Term Outlook

Section titled “Long-Term Outlook”

  1. RBAC / ABAC model — Evolving from tool-level allow/deny to role/attribute-based access control, integrating with enterprise IAM systems.

  2. Audit log compliance export — Supporting audit log formats required by compliance frameworks like SOC2 / ISO27001.

  3. AI behavior analysis — Detecting anomalous tool usage behavior based on historical call patterns (e.g., sudden surge in exec calls).

Conclusion

Section titled “Conclusion”

OpenClaw’s permission control system is the most comprehensive among similar products, with the 9-layer model covering everything from global scope to individual senders. Core takeaways:

  1. Understand the trust model first — Personal assistant ≠ multi-tenant; shared bot = shared permissions
  2. deny irreversibility is by design — Guarantees the security chain only tightens
  3. Start from the hardened baseline — Lock everything first, open up as needed, not the other way around
  4. Regular auditing is not optional — openclaw security audit --deep should be a routine ops habit
  5. Small model + big permissions = high risk — The weaker the model, the easier it is to inject; permissions must be tightened accordingly

Permission configuration may look complex, but it boils down to one sentence: From outside to inside, from coarse to fine, only tighten, never loosen.

sliverp/qqbot adds developer tooling

Section titled “sliverp/qqbot adds developer tooling”
  • GitHub Actions E2E test workflow — automated testing baked into CI
  • CLI plugin management tool (bin/ directory)
  • Lean README: features, config, done

  • 30+ tag variant auto-correction — Write <qq-img> instead of <qqimg> and it still works.
  • Upload dedup caching — Same file sent twice doesn’t get uploaded twice.
  • Ordered queue delivery — Messages arrive in sequence.
  • Dedicated upgrade guide and structured changelogs in both English and Chinese.

These are features born from supporting a larger user base. The quoted context feature alone changes the conversation quality for group chats where users frequently reply to specific messages.
