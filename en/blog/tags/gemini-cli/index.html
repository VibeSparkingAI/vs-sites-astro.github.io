Claude Code 2.1.91 Deep Dive: Breaking Down All 13 Changes

Apr 3, 2026
Vibe Sparking

Analysis date: 2026-04-03 Source: Claude Code CHANGELOG.md

Claude Code 2.1.91 looks like a small patch release on paper, but it carries a surprisingly strong signal. These 13 updates span five themes at once: MCP maturity, enterprise safety, session reliability, token efficiency, and developer experience.

This article walks through each change, the problem behind it, practical use cases, caveats, related changes in earlier versions, and how it compares with Codex CLI and Gemini CLI.

Why 2.1.91 matters more than it looks

Section titled “Why 2.1.91 matters more than it looks”

At first glance, this is just a short changelog. In reality, it reveals several clear product directions:

  1. MCP is moving from “works” to “scales.”
  2. Enterprise controls are getting stricter and more explicit.
  3. Session durability remains a major engineering battlefield.
  4. Token economics are now being optimized at the tool-protocol level.

Let’s go change by change.

1. MCP large-result persistence override

Section titled “1. MCP large-result persistence override”

Change: Claude Code now supports _meta["anthropic/maxResultSizeChars"], allowing an MCP server to request a higher result retention cap of up to 500K characters.

Background

Section titled “Background”

Claude Code has default truncation limits for MCP tool results, roughly around 25K characters, to avoid flooding the context window. That works fine for small outputs, but it becomes painful when an MCP tool returns something genuinely important and naturally large, such as a database schema, a repository index, or a large search result.

Before this release, MCP server authors had no direct way to say: “this result is large, but it is also important—please keep more of it.”

Practical scenarios

Section titled “Practical scenarios”
  • Database schema inspection: a Postgres MCP server returns the full schema for 200+ tables
  • Code search: a repository-wide search returns many relevant code blocks that should remain intact
  • Document retrieval: an MCP-based RAG server returns several long but highly relevant documents

Technical detail

Section titled “Technical detail”

The MCP server can return metadata like this:

This is an Anthropic-specific vendor extension, built on top of the MCP _meta extension mechanism.

Caveats

Section titled “Caveats”
  • The cap is still finite: 500K is the upper bound
  • Larger results consume more context and may trigger compaction sooner
  • MCP servers must opt in explicitly

2. disableSkillShellExecution for enterprise safety

Section titled “2. disableSkillShellExecution for enterprise safety”

Change: A new setting disables inline shell execution in skills, custom slash commands, and plugin commands.

Background

Section titled “Background”

Skills are powerful, but that power comes with risk. If a skill can execute shell inline, then an untrusted or poorly audited skill can become a serious safety problem in enterprise environments.

This release finally adds a clean master switch.

Practical scenarios

Section titled “Practical scenarios”
  • Enterprise IT policy: centrally disable shell execution in third-party skills
  • CI/CD environments: reduce execution surface area in automated runs
  • Compliance-heavy organizations: ensure that all execution paths remain explicit and auditable

Caveats

Section titled “Caveats”
  • This only blocks inline shell execution inside skills/commands/plugins
  • It does not disable ordinary user-requested Bash tool calls
  • Existing skills that depend on inline shell execution may stop working

Practical scenarios

  • Recovering deferred tools in SDK or CI flows with missing state
  • Containerized remote sessions losing transcript integrity after restarts

  • async persistence timing
  • large-session durability
  • old-transcript compatibility
  • remote container lifecycle issues

This is not a glamorous fix, but it’s exactly the sort of thing power users feel every day.

Fallback

Section titled “Comparison”

Section titled “7. Fixed plan mode in remote sessions”

Change: Claude Code fixed plan mode losing track of its plan file in remote sessions after container restarts.

What was happening

Section titled “What was happening”

Once the plan file path was lost, two bad things followed:

  1. Editing the plan triggered unnecessary permission prompts
  2. The plan-approval modal showed up empty

Impacted environments

  • Remote Control sessions
  • Dev Containers
  • cloud IDEs such as Codespaces/Gitpod-like environments

8. Fixed schema validation for permissions.defaultMode: "auto"

Section titled “8. Fixed schema validation for permissions.defaultMode: "auto"”

Change: JSON schema validation now correctly accepts permissions.defaultMode: "auto".

This is a “small but important” fix. Even if the setting worked at runtime, a schema mismatch damages trust:

  • editors show red squiggles
  • teams doubt the docs
  • config rollout becomes noisier than it should be

For enterprise deployment, schema correctness matters more than many teams realize.

9. Fixed Windows rollback-copy cleanup

Section titled “9. Fixed Windows rollback-copy cleanup”

Change: Windows version cleanup no longer deletes the rollback copy of the active version.

This is classic reliability plumbing. Nobody notices it when it works, but when rollback is needed, it becomes critical.

Claude Code’s Windows installation model is heavier than npm-only tools like Codex CLI or Gemini CLI, so this kind of fix matters more in its ecosystem.

10. /feedback now explains why it is unavailable

Section titled “10. /feedback now explains why it is unavailable”

Change: /feedback no longer simply disappears; it now explains why it cannot be used.

This is a very good UX improvement. “Unavailable with explanation” is much better than “seems to have vanished.” That matters especially for:

  • enterprise deployments
  • third-party provider setups
  • proxy and managed environments

This reduces the chance that users interpret an intentional limitation as a broken product.

Caveats:

Cross-tool comparison:

  • Codex CLI: Has three modes (suggest / auto-edit / full-auto), no fine-grained hooks.

2.5 Memory Leak in Long Sessions

Section titled “2.5 Memory Leak in Long Sessions”

What changed: Fixed a memory leak caused by large JSON inputs being retained as LRU cache keys.

Problem context: The LRU cache used the full JSON string of input content as its key. When inputs were large (e.g., reading large file contents), these strings stayed in memory and were never garbage collected. In extended sessions (e.g., 8-hour coding marathons), the Node.js process memory would climb continuously.

Use cases: After several hours of continuous Claude Code use and reading multiple large files, process memory grows from 300MB to 2GB+, and the terminal starts lagging.

Caveats:

  • For long sessions, periodically using /clear or /compact is recommended.

Cross-tool comparison:

  • Codex CLI: Uses React/Ink rendering; also exhibits memory growth but manifests differently.

Use cases: In a TypeScript project, editing a massive .d.ts file causes tsserver to OOM and crash. Before the fix, you had to exit and reenter Claude Code; after the fix, the next LSP call auto-recovers.

2.8 CJK/Emoji Prompt History Loss

Section titled “2.8 CJK/Emoji Prompt History Loss”

Use cases: Chinese/Japanese/Korean users frequently using Claude Code would find their prompt history missing (pressing the up arrow couldn’t find previous commands).

Caveats:

  • This bug affected a large number of Asian users; the fix is significant.
  • Similar UTF-8 boundary bugs exist in many tools.

Cross-tool comparison:

5 Agent Skill Design Patterns Every ADK Developer Should Know

Section titled “5 Agent Skill Design Patterns Every ADK Developer Should Know”

The Format War Is Over

Section titled “The Format War Is Over”

Thirty agent tools now read the same file format. Claude Code, Gemini CLI, Cursor, and more — they all parse the same SKILL.md layout with YAML frontmatter, the same directory structure, the same spec.

So why do most skills still break in production?

Because developers fixate on getting the YAML right and structuring directories. The formatting problem is solved. The challenge now is content design. The spec explains how to package a skill, but offers zero guidance on how to structure the logic inside it.

A skill that wraps FastAPI conventions operates completely differently from a four-step documentation pipeline, even though their SKILL.md files look identical on the outside. Same frontmatter. Same directories. Different reliability.

By studying how skills are built across the ecosystem — from Anthropic’s repositories to Vercel and Google’s internal guidelines — five recurring design patterns emerge. Each one answers a different architectural question. Each one comes with working ADK code.

Pattern 1: The Tool Wrapper

Section titled “Pattern 1: The Tool Wrapper”

A Tool Wrapper gives your agent on-demand context for a specific library. Instead of hardcoding API conventions into your system prompt, you package them into a skill. Your agent only loads this context when it actually works with that technology.

It’s the simplest pattern. The SKILL.md file listens for specific library keywords in the user’s prompt, dynamically loads your internal documentation from the references/ directory, and applies those rules as ground truth. This is how you distribute team coding guidelines or framework best practices directly into developer workflows.

Here’s a Tool Wrapper that teaches an agent how to write FastAPI code:

When to use it: Your task needs context injection for a specific library, framework, or internal standard.

Pattern 2: The Generator

Section titled “Pattern 2: The Generator”

While the Tool Wrapper applies knowledge, the Generator enforces consistent output. If your agent generates different document structures on every run, the Generator solves this by orchestrating a fill-in-the-blank process.

It uses two optional directories: assets/ holds your output template, and references/ holds your style guide. The instructions act as a project manager — they tell the agent to load the template, read the style guide, ask the user for missing variables, and populate the document.

When to use it: You need consistent, predictable output — API docs, commit messages, project scaffolds.

Pattern 3: The Reviewer

Section titled “Pattern 3: The Reviewer”

The Reviewer separates what to check from how to check it. Rather than writing a long system prompt detailing every code smell, you store a modular rubric inside references/review-checklist.md.

When code arrives, the agent loads the checklist and scores methodically, grouping findings by severity. Swap out a Python style checklist for an OWASP security checklist, and you get a completely different audit using the same skill infrastructure.

When to use it: You need quality scoring against a checklist — PR reviews, security audits, compliance checks.

Pattern 4: Inversion

Section titled “Pattern 4: Inversion”

Agents want to guess and generate immediately. Inversion flips this. Instead of the user driving the prompt and the agent executing, the agent interviews the user first.

The key mechanism is explicit, non-negotiable gating instructions: “DO NOT start building until all phases are complete.” The agent asks structured questions sequentially, waits for answers, and refuses to synthesize output until it has a complete picture.

When to use it: You need thorough requirements gathering before any action — project planning, architecture design, onboarding flows.

Pattern 5: The Pipeline

Section titled “Pattern 5: The Pipeline”

For complex tasks, you cannot afford skipped steps. The Pipeline enforces a strict, sequential workflow with hard checkpoints.

Instructions serve as the workflow definition. Diamond gate conditions (like requiring user approval before advancing) ensure the agent cannot bypass steps or present unvalidated results. Different reference files load only at the step where they’re needed, keeping the context window clean.

When to use it: Complex multi-step tasks where order matters and validation is required at each stage.

Choosing the Right Pattern

Section titled “Choosing the Right Pattern”

Each pattern answers a different question:

QuestionPattern
Need to inject library/framework context?Tool Wrapper
Need consistent, template-based output?Generator
Need to score against a checklist?Reviewer
Need to gather requirements first?Inversion
Need strict multi-step workflow?Pipeline

Start with the question your task asks. If it spans multiple questions, compose the patterns.

Patterns Compose

Section titled “Patterns Compose”

These patterns are not mutually exclusive.

A Pipeline skill can include a Reviewer step at the end to double-check its own work. A Generator can rely on Inversion at the beginning to gather the necessary variables before filling its template. Thanks to ADK’s SkillToolset and progressive disclosure, your agent only spends context tokens on the exact patterns it needs at runtime.

This is the architectural advantage: instead of cramming complex, fragile instructions into a single system prompt, you decompose the behavior into composable building blocks. Each block is testable independently. Each block has a clear contract.

Practical Tips

Section titled “Practical Tips”

  1. Start with one pattern. Most tasks fit a single pattern cleanly. Don’t compose until you need to.

  2. Name the pattern in metadata. Adding metadata.pattern: tool-wrapper to your frontmatter makes the architecture explicit and searchable across your skill library.

  3. Keep references external. The power of Wrapper, Reviewer, and Pipeline patterns comes from loading context files on demand. Don’t inline large checklists or conventions into SKILL.md itself.

  4. Gate aggressively in Pipelines. Every checkpoint you skip is a validation you lose. The explicit “DO NOT proceed until…” instruction is the Pipeline’s most important line.

  5. Test patterns in isolation. A Generator with a broken template is a Generator problem, not a skill problem. Debug the pattern layer, not the SKILL.md layer.

Get Started

Section titled “Get Started”

The Agent Skills specification is open-source and natively supported across Google ADK. You already know how to package the format. Now you know how to design the content.

Stop formatting. Start architecting.
