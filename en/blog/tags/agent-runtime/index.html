OpenClaw 2026.4.2 逐项调研报告

生成时间：2026-04-03 10:30 CST 版本：v2026.4.2 (d74a122) 发布者：@steipete，2026-04-02

总体判断

Section titled “总体判断”

这是一个典型的 “架构收束 + 插件边界重划 + 安全补强 + 多渠道修复” 版本。

不是”功能炫技版”，而是：

  • 把原来散在 core 里的能力往 plugin-owned boundary 收
  • 把 background orchestration 正式拉回 Task Flow substrate
  • 把 provider transport / routing / auth / TLS / header 统一
  • 把 exec approval / host exec / node exec 的默认行为重新定型
  • 修复上一批版本里因为作用域、配对、路由、审批、流式输出带来的回归

2026.4.2 的主线，是 OpenClaw 从”能跑很多事”继续往”边界更清晰、可运维、可恢复、可插件化”演进。

  • 用 xAI 提供的 x_search

2) Plugins/web fetch：Firecrawl web_fetch 配置迁移

Section titled “2) Plugins/web fetch：Firecrawl web_fetch 配置迁移”

背景问题

Section titled “背景问题”

以前 Firecrawl 的 web_fetch 配置也走 core：tools.web.fetch.firecrawl.*

这会导致：

  • core 对某个具体 provider（Firecrawl）耦合太深
  • fallback 路径带有 Firecrawl 特判
  • 后续引入别的 fetch provider 不优雅

2026.4.2 具体变化

Section titled “2026.4.2 具体变化”

迁移到插件自有路径：plugins.entries.firecrawl.config.webFetch.*

同时 web_fetch fallback 不再走 “Firecrawl-only core branch”，而是通过新的 fetch-provider boundary

使用场景

Section titled “使用场景”
  • 使用 Firecrawl 做网页提取
  • 同时支持多种 fetch provider
  • 要求插件替换/禁用更可控

注意事项

Section titled “注意事项”
  • 同样建议 openclaw doctor --fix
  • 如果你有自动化脚本 grep 旧路径，会全部失效
  • 这也意味着后续 web_fetch 会成为 provider-agnostic 抽象

历次版本脉络

Section titled “历次版本脉络”
  • 之前：web fetch 在 core 里有大量 provider 特判
  • 现在：开始形成 fetch provider seam
  • 未来：可能出现更多 fetch providers 并存、路由、优先级链

竞品对比

Section titled “竞品对比”
产品Web Fetch 抽象
OpenClaw新 fetch-provider boundary，插件可替换
NanoClaw直接调 Anthropic SDK 内置能力
IronClawHTTP client + endpoint allowlist
PicoClaw内置 HTTP + 可选 provider
ZeroClawtrait-based fetch provider
NanobotMCP server 提供 fetch 能力

判断

Section titled “判断”

这条很重要。它不是单纯改路径，而是在说：

web_fetch 以后不再是 “Firecrawl 的别名”，而是 OpenClaw 的一个可插拔抓取抽象层。

二、Changes：逐项解析

Section titled “二、Changes：逐项解析”

3) Task Flow substrate 回归：managed / mirrored，同步模式、持久状态、revision、openclaw flows

Section titled “3) Task Flow substrate 回归：managed / mirrored，同步模式、持久状态、revision、openclaw flows”

背景问题

Section titled “背景问题”

OpenClaw 的后台任务、分布式编排、插件作者层逻辑，之前有点”上层花活很多，底层 substrate 不够强”。

常见痛点：

  • 后台任务状态丢失
  • orchestrator 和 runtime 状态不同步
  • 崩了以后难恢复
  • 任务流 inspection / recovery 工具不够

这次解决了什么

Section titled “这次解决了什么”

恢复 core Task Flow substrate，并支持：

  • managed vs mirrored sync modes
  • durable flow state
  • revision tracking
  • openclaw flows inspection/recovery

使用场景

Section titled “使用场景”
  • 背景任务编排
  • 长链路自动化
  • cron 触发后衍生多个子任务
  • 插件 authoring layer 想基于稳定底座构建流程

例子

Section titled “例子”

收到 Feishu 评论 → 创建任务流 → 拉文档上下文 → 生成答复 → 回帖 → 记录状态。中途 gateway 重启后仍能恢复 flow 状态。

注意事项

Section titled “注意事项”
  • 这标志着”流程”成为真正一等对象
  • 如果你自己写插件/authoring layer，应该尽量挂靠 taskFlow seam，而不是自己造状态机

版本脉络

Section titled “版本脉络”
  • 中间一些版本更偏”上层 authoring runtime”
  • 这版把 core substrate 重新做厚
  • 说明团队认识到：没有 durable orchestration substrate，agent 编排迟早变脆

竞品对比

Section titled “竞品对比”
产品后台编排能力
OpenClawTask Flow substrate (managed/mirrored, durable, revision, CLI inspection)
NanoClaw基础 cron/scheduled jobs，无 flow 抽象
IronClawRoutines (cron + event triggers + webhooks)
PicoClawSubTurn + Hooks + EventBus (v0.2.4+)
ZeroClaw不详，可能较轻量
Nanobot无内置 flow，靠 MCP server 外挂

判断

Section titled “判断”

这是本版最核心的架构演进之一。

4) Task Flow：managed child task spawning + sticky cancel intent

Section titled “4) Task Flow：managed child task spawning + sticky cancel intent”

背景问题

Section titled “背景问题”

父任务取消时，子任务可能已经在跑。常见两种糟糕状态：

  • 直接硬杀，导致系统不一致
  • 不硬杀，父任务却继续调度新任务

这次变化

Section titled “这次变化”
  • managed child task spawning
  • sticky cancel intent
  • 一旦决定取消，调度器立即停止继续排新活
  • 但已运行的 child task 可以收尾
  • 最后 parent flow 再 settle 到 cancelled

场景

Section titled “场景”
  • 多阶段流程
  • 有副作用的子任务（发消息、写文档、同步状态）
  • 需要”优雅取消”

例子

Section titled “例子”

一个 flow 已经发起 3 个子任务（拉上下文、调模型、写回渠道）。取消时不再调度第 4、5 个子任务，让已在跑的完成，然后整体标 cancelled。

注意

Section titled “注意”
  • sticky cancel 更接近工作流引擎语义，而不是”立即 SIGKILL”
  • 写插件时要区分：scheduler stop / child completion / parent settle

竞品对比

Section titled “竞品对比”
  • IronClaw 有 self-repair / stuck detection，但不明确有 parent-child cancel 语义
  • PicoClaw 的 SubTurn 有 steering 但非 durable flow cancel
  • 其他竞品无此级别编排

5) Plugins/Task Flow：api.runtime.taskFlow bound seam

Section titled “5) Plugins/Task Flow：api.runtime.taskFlow bound seam”

背景问题

Section titled “背景问题”

插件或 trusted authoring layer 之前如果想操作 flow，可能要显式传 owner id、host context 等，易错、啰嗦、边界不安全。

新变化

Section titled “新变化”

提供 bound seam api.runtime.taskFlow，由 host-resolved OpenClaw context 绑定，不必每次传 owner identifiers。

场景

Section titled “场景”
  • 插件内部发起/控制 flow
  • 受信 authoring layer 编排任务

例子

Section titled “例子”

Feishu 插件收到评论事件后，可直接在当前宿主上下文下开 flow，而不是拼一堆 owner/session 参数。

注意

Section titled “注意”
  • 这是插件作者福音
  • 也意味着 runtime boundary 更标准化
  • 不建议继续用旁门左道直接操宿主内部状态

6) Android/assistant：Assistant role + Google Assistant App Actions metadata

Section titled “6) Android/assistant：Assistant role + Google Assistant App Actions metadata”

背景问题

Section titled “背景问题”

Android 上 OpenClaw 作为”被系统语音助手触发”的入口不完整。

新变化

Section titled “新变化”
  • assistant-role entrypoints
  • Google Assistant App Actions metadata
  • Android 可从 assistant trigger 启 OpenClaw，并把 prompt 交给 composer

场景

Section titled “场景”

“Hey Google, ask OpenClaw to …”，手机侧快速唤起 agent。

注意

Section titled “注意”
  • 这不是完整 agent automation，只是系统入口打通
  • 真正体验还取决于 Android intent / app actions / OEM 行为

竞品对比

Section titled “竞品对比”
产品移动端入口
OpenClawAndroid Assistant + iOS companion
NanoClaw无原生移动端
IronClaw无原生移动端
PicoClawAndroid APK (v0.2.4+)
ZeroClaw无原生移动端
NanobotWeb UI 为主

判断

Section titled “判断”

移动端入口正在增强，但生态成熟度仍明显低于桌面/CLI/聊天渠道。

7) Exec defaults：gateway/node host exec 默认 YOLO（security=full, ask=off）

Section titled “7) Exec defaults：gateway/node host exec 默认 YOLO（security=full, ask=off）”

背景问题

Section titled “背景问题”

以前 host exec 的默认行为在不同 host/gateway/node、approval fallback、doctor/reporting 之间不一致，用户容易误判”到底会不会弹审批”。

新变化

Section titled “新变化”

默认请求 security=full + ask=off，并让 approval-file fallback、docs、doctor 报告都对齐这个”默认无提示”语义。

这是什么意思

Section titled “这是什么意思”

不是更安全，而是默认更直接执行。强调的是”host exec 的默认姿势是 YOLO”。

场景

Section titled “场景”
  • 本机自动化
  • 已高度信任的受控环境
  • 需要减少 approval friction

注意事项

Section titled “注意事项”

这是一个运维上必须重视的改动：

  • 对高信任单用户机器：更顺手
  • 对共享环境/远端节点/高风险宿主：风险升高
  • 必须结合你自己的 exec-approvals policy、sandbox、tool policy 使用

竞品对比

Section titled “竞品对比”
产品Exec 默认安全模型
OpenClaw默认 YOLO（security=full, ask=off），靠 policy 约束
NanoClaw容器隔离，bash 在容器内执行
IronClawWASM sandbox + endpoint allowlist
PicoClawCron security gating (v0.2.3+)
ZeroClawpolicy-based security
Nanobot无内置 exec，走 MCP server

版本脉络

Section titled “版本脉络”

最近几版一直在整理 exec approvals、host routing、node exec 行为；这版属于默认值定型。

判断

Section titled “判断”

这是本版另一个关键变化。OpenClaw 正在把默认执行体验做得更”像一个真正会动手的 agent”，代价是必须靠更强的边界和策略约束兜底。

8) Providers/runtime：provider-owned replay hooks

Section titled “8) Providers/runtime：provider-owned replay hooks”

背景问题

Section titled “背景问题”

不同 provider 的 transcript replay、cleanup、reasoning dispatch 逻辑不完全一样，统一放 core 很快会变得臃肿。

新变化

Section titled “新变化”

把 replay 相关表面开放给 provider 自己实现：transcript policy / replay cleanup / reasoning-mode dispatch。

场景

Section titled “场景”
  • 不同 provider 有不同 transcript/reasoning 格式
  • 恢复历史会话、转发上下文、处理 reasoning tokens

判断

Section titled “判断”

说明 OpenClaw 正从”统一 adapter”往”provider 主权更高的 runtime seam”演化。

9) Plugins/hooks：before_agent_reply

Section titled “9) Plugins/hooks：before_agent_reply”

背景问题

Section titled “背景问题”

插件做完 inline action 后，有时已经知道最终该回什么，没必要再走 LLM，省钱、省时、减少不可控性。

新变化

八、结论
