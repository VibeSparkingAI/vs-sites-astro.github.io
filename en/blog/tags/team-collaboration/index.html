OpenClaw + Feishu + Scrum: Running a Complete R&D Closed Loop with an AI Agent Team

Section titled “OpenClaw + Feishu + Scrum: Running a Complete R&D Closed Loop with an AI Agent Team”

This is not another article about AI helping you write code. Everyone’s done that. This is about something different: giving AI agents actual team roles — Product Owner, Developer, QA Engineer, Scrum Master — and letting them collaborate with each other and with humans in a Feishu group chat, running a real Sprint from backlog to release.

The gap nobody talks about

Section titled “The gap nobody talks about”

Most teams use AI as a personal productivity tool. You open a chat window, ask it to generate code or write tests, copy the result. The AI never talks to your teammates. It doesn’t know what the PO defined or what QA found broken. The moment cross-role collaboration starts, AI exits the room.

We wanted to change that.

The idea: create five AI agents on OpenClaw, each bound to a separate Feishu bot account, each assigned a specific Scrum role. Put them all in one Feishu group chat. Let them read each other’s messages, challenge each other’s work, and collaborate through shared workspace files.

Architecture overview

Section titled “Architecture overview”

Stack:

  • OpenClaw — local AI gateway, manages multi-agent + multi-Feishu-bot accounts
  • Feishu — IM collaboration platform, connected via enterprise custom apps
  • Scrum — development framework that constrains agent behavior boundaries

Role design: tension by intent

Section titled “Role design: tension by intent”

Adversarial roles

Section titled “Adversarial roles”

“Adversarial” is not a negative word here. These three roles have natural goal tension. They check each other and produce better outcomes.

RoleAgent IDFeishu BotCore Responsibility
POvs-po@vs-poRequirements, acceptance criteria, priority ranking, story splitting
Devvs-dev@vs-devTechnical design, implementation, unit tests, tech debt management
QAvs-qa@vs-qaTest case design, defect discovery, regression verification, quality gates

PO pushes for feature completeness and business value. Dev pushes for implementation simplicity and maintainability. QA pushes for system stability and edge coverage. The three naturally push against each other, driving requirements toward clarity and code toward robustness.

Facilitative roles

Section titled “Facilitative roles”
RoleAgent IDFeishu BotCore Responsibility
SMvs-sm@vs-smProcess guardian, blocker removal, team rhythm, ceremony facilitation
Projectproject-a@project-aProgress tracking, risk management, cross-team sync, release coordination

Design principles

Section titled “Design principles”

1. Clear role boundaries, no overstepping

Section titled “1. Clear role boundaries, no overstepping”
  • PO does not write code — only defines “What”
  • Dev does not define requirements — only decides “How”
  • QA does not pass substandard features — regardless of schedule pressure

Each agent’s SOUL.md and AGENTS.md files define the role and refusal policies.

2. Shared workspace is the collaboration hub

Section titled “2. Shared workspace is the collaboration hub”

All agents collaborate by reading and writing the shared/ directory. Sprint Board, Bug list, and requirement documents all live there. Humans can inspect and edit at any time.

3. Humans are the final decision makers

Section titled “3. Humans are the final decision makers”

AI agents propose approaches, surface risks, and execute tasks, but critical decision points need human confirmation:

  • Requirement priority changes
  • Release timing windows
  • Security-related policy calls

4. Scrum Master guards the process

Section titled “4. Scrum Master guards the process”

The SM agent does no business work — only:

  • Detects blockers and escalates
  • Maintains Sprint rhythm
  • Facilitates ceremonies (standup, retrospective, review)

Why this pattern works

Section titled “Why this pattern works”

It’s not about replacing people. It’s about:

  1. Amplifying decisions — AI handles information gathering, drafting, test case generation, and status tracking. Humans focus on judgment and decisions.
  2. Enforcing process discipline — Agents don’t skip steps. Requirements always have acceptance criteria. Tests always have cases.
  3. 24/7 responsiveness — Code committed at 2 AM gets initial QA feedback from the QA agent immediately.
  4. Knowledge accumulation — Each agent’s workspace builds context over time. No dependency on individual memory.

What’s next

Section titled “What’s next”
  • Scheduled heartbeat for SM agent to auto-trigger daily standups
  • GitHub Webhook integration: auto-trigger @vs-qa verification on PR merge
  • Shared workspace synced with Git for Sprint Board versioning
  • Sprint Retrospective: SM facilitates agent team retrospective at Sprint end

OpenClaw provides the multi-agent infrastructure. Feishu provides the collaboration surface your team already uses. Scrum provides the framework that keeps AI agents focused, bounded, and accountable. Together, AI stops being your private assistant and starts being an actual working member of your team.
