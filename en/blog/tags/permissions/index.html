Claude Code 2.1.97 Deep Dive: 50+ Changes Fully Analyzed

Apr 9, 2026
Vibe Sparking

Release date: 2026-04-09 Changes: 50+

Version Overview

Section titled “Version Overview”

2.1.97 is a major maintenance and feature release containing approximately 50+ changes, covering new features, permission systems, MCP, session recovery, NO_FLICKER rendering, enterprise integration, and numerous reliability fixes. The overall signal is clear: this version isn’t about single-point innovation, but about polishing Claude Code’s core execution surface to be more stable and better suited for high-frequency real-world development usage.

I. New Features

Section titled “I. New Features”

1. Focus View Toggle (Ctrl+O) in NO_FLICKER Mode

Section titled “1. Focus View Toggle (Ctrl+O) in NO_FLICKER Mode”

Change Content

  • Added Focus View in NO_FLICKER mode
  • Display includes: user prompt, one-line summary of tool calls, edit diffstats, final response

Problem Background

  • NO_FLICKER mode solves the traditional terminal flickering problem, but introduces another issue: information hierarchy can become mixed in long sessions
  • Users often don’t want to see all raw tool outputs, but want to quickly understand “what I asked, what it did, how much was changed, what was the final answer”

Use Cases

  • Quick review after long refactoring tasks
  • Recapping an agent’s work process to colleagues
  • Reviewing results after numerous Bash, Read, Edit, Write tool calls
  • Need to quickly locate operation summaries for failed tasks

Example

  • User asks Claude to refactor auth module
  • Focus View only shows:
    • prompt: “Refactor auth to JWT middleware”
    • tool summary: Read 4 files, Edit 3 files, Bash npm test
    • diffstats: +84 -27
    • final response: “JWT middleware refactor completed, tests pass”

Notes

  • Only available in NO_FLICKER mode
  • Better suited for summary browsing, not for replacing full step-by-step debugging
  • If you need to see detailed shell output step by step, still return to full view

Historical Context

  • 2.1.89 introduced CLAUDE_CODE_NO_FLICKER=1
  • 2.1.90 to 2.1.97 continuously fixed multiple NO_FLICKER rendering, scrolling, copying, and shortcut issues
  • This addition of Focus View indicates NO_FLICKER is transitioning from “experimental rendering layer” to “usable workflow interface” stage

Competitor Comparison

  • Codex CLI
    • Typically more focused on raw streaming output
    • Lacks this hierarchical focus review view
  • Gemini CLI
    • Emphasizes structured output and extension ecosystem
    • Also lacks this session summary view oriented toward long coding sessions

Future Trend Prediction

  • More view toggles may appear later, such as diff-only, tools-only, errors-only
  • Claude Code may gradually evolve terminal sessions into a “navigable work record interface” rather than just a text stream

2. refreshInterval Status Line Setting

Section titled “2. refreshInterval Status Line Setting”

Change Content

  • Added refreshInterval status bar setting
  • Allows status bar commands to automatically rerun every N seconds

Problem Background

  • Previously, status bar was more like static information or low-frequency updates
  • For real-time changing information like current branch status, task queues, backend service health status, single render wasn’t enough

Use Cases

  • Real-time display of git branch, worktree, repo status
  • Real-time display of local dev server, test watcher, CI status
  • Display current machine status or session information during remote development

Example

  • Execute a status command every 5 seconds, showing:
    • Current branch
    • Current worktree
    • Whether background tests pass
    • Whether current directory has uncommitted changes

Notes

  • Too frequent refreshing increases performance overhead
  • Status bar commands should be lightweight to avoid causing lag
  • Be especially careful with heavy git/status commands in large monorepos

Historical Context

  • 2.1.94 added richer status/UI information management
  • 2.1.97 simultaneously added workspace.git_worktree, these two changes are clearly complementary

Competitor Comparison

  • Codex CLI status UI is relatively simple, lacking this obvious customizable status bar refresh mechanism
  • Gemini CLI has footer/UI improvements, but support for “custom status command timed refresh” isn’t as development-workflow oriented as Claude Code

Future Trend Prediction

  • Status bar may later support more dynamic contexts like token usage, agent count, task status, network status
  • Long-term may evolve into customizable development cockpit

3. workspace.git_worktree Injected into Status Bar JSON

Section titled “3. workspace.git_worktree Injected into Status Bar JSON”

Change Content

  • When current directory is in a linked git worktree, status bar JSON input adds workspace.git_worktree

Problem Background

  • Git worktree is high-frequency advanced development usage, especially suitable for parallel bug fixing, parallel feature development, parallel agent execution
  • Many tools only recognize repo root, not current worktree identity, leading to misleading status

Use Cases

  • Opening multiple worktrees in one repository for different branch tasks
  • One Claude main session + multiple subagents each bound to different worktrees
  • Quickly confirm through status bar that you’re not in main working directory but in some linked worktree

Example

  • Main repository at /repo
  • Current directory at /repo-feature-auth
  • Status bar can display worktree=feature-auth

Notes

  • Only has value in linked worktree scenarios
  • Custom status scripts need to handle empty field cases

Historical Context

  • 2.1.92 improved --resume to directly restore sessions from other worktrees in same repo
  • This version fixes subagent worktree isolation leaking to parent Bash tool
  • Indicates Claude Code is systematically completing worktree-first development experience

Competitor Comparison

  • Codex CLI worktree experience is currently more “you handle paths yourself”
  • Gemini CLI also lacks this explicit worktree status exposure capability

Future Trend Prediction

  • May later add branch, dirty state, ahead/behind, repo root identity fields
  • Worktree may become default isolation unit for multi-agent parallel programming

4. Added ● N running Indicator in /agents

Section titled “4. Added ● N running Indicator in /agents”

Change Content

  • In /agents list, when an agent type has active subagent instances, displays ● N running

Problem Background

  • Claude Code’s subagent/agent system is gradually strengthening, but observability has been a barrier
  • Users often don’t know which agents are running, whether they’re dead or busy

Use Cases

  • Multiple subagents concurrently executing code search, testing, documentation summarization
  • Checking if an agent type already has instances running to avoid duplicate launches
  • Debugging agent stuck issues

Example

  • In /agents output see:
    • code-research ● 2 running
    • refactor-helper ● 1 running
    • docs-agent

Notes

  • This is visibility enhancement, doesn’t mean agent orchestration logic itself changed
  • If agent instance state synchronization is delayed, may still need to combine with specific session judgment

Historical Context

  • 2.1.89 added named subagents to @ mention typeahead
  • 2.1.92 fixed tmux changes causing permanent subagent spawning failure
  • This version also fixes subagent cwd/worktree leakage

Competitor Comparison

  • Codex CLI current mainstream usage is still more single-agent oriented
  • Gemini CLI has rich extension ecosystem, but native multi-subagent interaction management isn’t as deep as Claude Code

Future Trend Prediction

  • May later add agent CPU/time/token visualization
  • May eventually form interactive panel similar to “job manager / task supervisor”

5. Cedar Policy File Syntax Highlighting

Section titled “5. Cedar Policy File Syntax Highlighting”

Change Content

  • Added syntax highlighting for .cedar and .cedarpolicy files

Problem Background

  • Cedar is increasingly important DSL in permission policy domain, especially growing in cloud permissions, fine-grained authorization, and policy-as-code
  • Lack of syntax highlighting significantly reduces readability

Use Cases

  • Enterprise permission policy debugging
  • Developing internal authorization systems
  • Analyzing Cedar-based access policies

Example

  • When writing Cedar rules for “whether user can access certain resource”, keyword, condition, entity reference highlighting helps reduce misreading

Notes

  • Only syntax highlighting, not policy validator
  • Doesn’t mean Claude Code itself starts natively executing Cedar permission models, but has signaling significance

Competitor Comparison

  • This item is more about editing experience enhancement, competitors may not particularly emphasize it

Future Trend Prediction

  • May indicate Claude Code values policy-as-code scenarios more
  • Combined with continuous permission system hardening, has flavor of evolving toward enterprise security development tools

II. Permission & Security Fixes

Section titled “II. Permission & Security Fixes”

6. Fixed --dangerously-skip-permissions Silent Downgrade Issue

Section titled “6. Fixed --dangerously-skip-permissions Silent Downgrade Issue”

Problem Background

  • This parameter, as the name suggests, is very dangerous, meaning skip permission restrictions
  • Previously, after approving one write operation to protected path, would be silently downgraded to accept-edits mode
  • Worst part: users didn’t know it changed

Why This is Serious Problem

  • In automated scripts or controlled CI, this “I thought still fully allowed, actually already semi-allowed” behavior creates unpredictability
  • Not transparent security-wise, unreliable engineering-wise

Use Cases

  • Unattended automatic environment modifications
  • Large-scale migrations in trusted local sandboxes

Notes

  • Even after fix, not recommended for daily use of this parameter
  • Only use when you completely trust environment, explicitly accept risks

Historical Context

  • 2.1.90 started continuously strengthening permission model
  • Multiple permission fixes this version indicate permission system moving from “usable” to “predictable and consistent”

Competitor Comparison

  • Codex CLI has clearer full-auto/semi-auto mode distinction, but usually more straightforward in explainability
  • Gemini CLI YOLO/accept-edits is also clear
  • Claude Code fixing “mode semantic instability” problem is fundamentally crucial

7. Bash Tool Permission Hardening

Section titled “7. Bash Tool Permission Hardening”

Change Content

  • Strengthened env-var prefix checking
  • Strengthened network redirection related checking
  • Simultaneously reduced false positives for common commands

Problem Background

  • Bash permission control is difficult because shell syntax is too complex
  • Attacks or bypasses often hide in:
    • Environment variable prefixes
    • Wrapper commands
    • Redirections
    • Compound commands

Typical Problem Scenarios

  • FOO=bar curl ...
  • LANG=C rm foo
  • timeout 5 mkdir out
  • cmd > /sensitive/path

This Fix Value

  • On one hand plugging vulnerabilities, on other hand reducing false positives
  • Shows team isn’t just tightening, but balancing “high security + low friction”

Notes

  • Shell permission systems always have edge cases
  • High-risk environments should still rely on outer sandbox, not just trust CLI’s own rules

Historical Context

  • 2.1.89 fixed hook if condition failing to match env prefixes and compound commands
  • 2.1.90 strengthened PowerShell permission checking
  • 2.1.97 further improved Bash permission checking

Competitor Comparison

  • Codex CLI tends to use more outer isolation and mode control
  • Gemini CLI yolo/shell/accept-edits model easier to understand, but granularity may not be as high as Claude Code

Future Trend Prediction

  • May later introduce more formal shell command normalization layer
  • Long-term may develop into declarative command risk classification system

8. Permission Rule Name Colliding with JS Prototype Properties Causing settings.json to be Ignored

Section titled “8. Permission Rule Name Colliding with JS Prototype Properties Causing settings.json to be Ignored”

Problem Background

  • If permission rule name is JavaScript prototype property name like toString, settings.json would be silently ignored

Root Cause

  • Typical JS object key handling error
  • When using plain objects as maps, prototype pollution or prototype key collision is classic pitfall

Use Cases

  • When enterprises/teams define permission rule names themselves, accidentally hitting these reserved properties

Why Important

  • Worst part is “silent ignore”
  • Users think rules are effective, but entire permission configuration may not be effective

Notes

  • This type of problem exposes configuration system robustness was insufficient
  • For enterprise administrators, this silent failure is much more dangerous than explicit errors

Competitor Comparison

  • This is implementation layer quality issue, not feature comparison point
  • But from product maturity perspective, Claude Code is paying down this enterprise-level edge reliability debt

9. Managed-settings Allow Rules Still Effective After Removal Until Restart

Section titled “9. Managed-settings Allow Rules Still Effective After Removal Until Restart”

Problem Background

  • Administrator remotely removed allow rules, but old rules continued effective in local process until restart

Impact

  • Management policies cannot be immediately revoked
  • In security governance, this is serious consistency problem

Use Cases

  • Enterprise administrator urgently revoking access to certain directory, command, or network capability

Notes

  • Immediate effectiveness is very important for enterprises
  • Once this type of problem exists, significantly weakens managed settings credibility

Historical Context

  • 2.1.92 added forceRemoteSettingsRefresh, emphasizing fail-closed semantics
  • This version fixes hot update not revoking problem, belongs to same governance chain completion

10. permissions.additionalDirectories Mid-session Modifications Not Effective

Section titled “10. permissions.additionalDirectories Mid-session Modifications Not Effective”

Problem Background

  • Additional allowed directories in settings not applied when modified during session runtime

Scenario

  • Temporarily opening sibling repo, shared config directory, external script directory during development

Impact

  • Users modify configuration but still need to restart session, breaking flow

11. Error Removing --add-dir Permissions When Removing Directory from additionalDirectories

Section titled “11. Error Removing --add-dir Permissions When Removing Directory from additionalDirectories”

Problem Background

  • Directory exists both through settings and --add-dir
  • After removing from settings, should still retain access rights from --add-dir
  • Previously both were revoked together

Root Cause

  • Multi-source permission merging logic error
  • Didn’t correctly do source-aware permission bookkeeping

Why Important

  • Multi-layer permission sources is enterprise environment norm
  • Permission system must support “precise addition/removal by source”, cannot brutally override

III. MCP Related Fixes

Section titled “III. MCP Related Fixes”

12. MCP HTTP/SSE Reconnection Memory Leak, ~50MB/Hour

Section titled “12. MCP HTTP/SSE Reconnection Memory Leak, ~50MB/Hour”

Problem Background

  • MCP heavily relies on HTTP/SSE long connections
  • When server repeatedly reconnects, buffers not released
  • Long sessions or unstable network environments steadily consume memory

Use Cases

  • Long-term connections to databases, browsers, remote knowledge bases, internal tool MCP servers
  • Environments with average network quality where server actively disconnects and reconnects

Example

  • 8 hours workday, if leaking 50MB/hour, that’s 400MB
  • Combined with other caches and transcript, quickly becomes noticeable performance issue

Notes

  • This is typical stability pain point for “long-running agent tools”
  • Significantly impacts those using Claude Code as all-day development partner

Historical Context

  • 2.1.90 fixed SSE transport quadratic complexity issue for large streamed frames
  • 2.1.92 fixed plugin MCP stuck connecting
  • 2.1.97 fixes buffer unreleased, indicating MCP communication stack still being polished

Competitor Comparison

  • Codex CLI native MCP ecosystem not as heavy as Claude Code
  • Gemini CLI also pushing MCP/extensions, but Claude Code deeper in real IDE-like agent integration, so these problems exposed earlier

Future Trend Prediction

  • MCP will increasingly become “AI tool bus”
  • Stability, reconnection, backpressure, memory recycling will become next phase core engineering competition points

13. MCP OAuth oauth.authServerMetadataUrl Token Refresh Not Effective After Restart

Section titled “13. MCP OAuth oauth.authServerMetadataUrl Token Refresh Not Effective After Restart”

Problem Background

  • Enterprise identity providers like ADFS rely on this metadata URL
  • Token refresh after restart didn’t correctly honor this setting

Use Cases

  • Enterprise SSO login
  • Self-hosted OAuth or ADFS-compatible MCP services

Impact

  • Initial login may succeed, subsequent refreshes fail
  • Causes most annoying enterprise problem: “seems usable, suddenly breaks after some time”

Notes

  • These problems typically only appear heavily in enterprise environments, high compliance environments
  • Ordinary individual users may not encounter, but once encountered almost judged as unusable

IV. Rate Limit & API Reliability

Section titled “IV. Rate Limit & API Reliability”

14. Fixed 429 Retry Too Fast Exhaustion Problem

Section titled “14. Fixed 429 Retry Too Fast Exhaustion Problem”

Problem Background

  • Server returns small Retry-After
  • Client uses this small value as primary basis, causing too fast retries
  • All retries exhausted in about 13 seconds

Why This is Bad Experience

  • Users encounter recoverable rate limiting, but due to overly aggressive client strategy, directly becomes failure
  • Makes people mistakenly think “service completely unavailable”

Fix Content

  • Exponential backoff now applied as minimum lower bound
  • Even if server gives small Retry-After, won’t blindly densely retry

Use Cases

  • API temporary congestion
  • Enterprise proxy layer, Cloudflare, gateway layer rate limiting
  • High concurrency subagents triggering burst

Historical Context

  • 2.1.90 fixed rate-limit options dialog infinite loop
  • 2.1.94 fixed 429 long Retry-After causing appearance of hanging
  • 2.1.97 fixes small Retry-AAfter retry exhaustion problem

Historical Context

  • 2.1.90 fixed rate-limit options dialog infinite loop
  • 2.1.94 fixed 429 long Retry-After causing appearance of hanging
  • 2.1.97 fixes small Retry-After retry too fast

Competitor Comparison

  • All three tools encounter rate limiting
  • Claude Code has many fix records in this area, indicating they’re fine-tuning strategies at more granular level for real production traffic

Future Trend Prediction

  • May later add smarter per-model, per-endpoint, per-plan retry strategies
  • May also deeper integrate with UI, clearly telling users “I’m backing off and retrying, not stuck”

15. Context Compaction Causing Rate-limit Upgrade Options to Disappear

Section titled “15. Context Compaction Causing Rate-limit Upgrade Options to Disappear”

Problem Background

  • After being rate limited, system may suggest upgrade options or alternatives
  • But after context compaction, these prompts disappeared

Root Cause

  • UI state and session state not uniformly persisted

Impact

  • Users handling limit issues, then prompts disappear themselves, breaking experience

V. /resume & Transcript Persistence Fixes

Section titled “V. /resume & Transcript Persistence Fixes”

This group is one of the most important areas in this version, because they directly relate to whether Claude Code can become a “long-term continuous work agent”.

16. Multiple /resume Picker Issues Fixed

Section titled “16. Multiple /resume Picker Issues Fixed”

Issues Involved

  • --resume <name> not editable after opening
  • Ctrl+A reload clears search
  • Empty list swallows navigation
  • task-status overwrites conversation summary
  • Cross-project stale data

Problem Background

  • Resume picker has evolved from simple list to actual session index interface
  • Once UI state, search state, session metadata synchronization isn’t done well, experience becomes fragile

Use Cases

  • Finding specific work among large history sessions
  • Switching sessions across projects
  • Need to quickly continue previous day’s tasks

Future Significance

  • If Claude Code wants to become daily main development environment, resume experience must be as reliable as “workbench recovery”, not “try luck whether can reconnect”

17. Edit Diffs for Files Larger Than 10KB Disappear in --resume

Section titled “17. Edit Diffs for Files Larger Than 10KB Disappear in --resume”

Problem Background

  • Large file edits not showing diff after resume

Impact

  • After recovery you know changes were made, but don’t know what changed
  • Especially bad for refactoring or generative modifications

Scenario

  • Modifying large config files, large TS files, large Markdown documents

18. --resume Cache Miss and Attachment Message Transcript Loss

Section titled “18. --resume Cache Miss and Attachment Message Transcript Loss”

Problem Background

  • Attachment messages not saved to transcript
  • Causing missing context blocks during resume

Use Cases

  • Users dragging images, screenshots, design drafts for Claude analysis
  • Resuming session after disconnection

Significance

  • Multimodal sessions cannot only store text, otherwise resume isn’t complete

19. Messages Input While Claude Working Not Persisted

Section titled “19. Messages Input While Claude Working Not Persisted”

Problem Background

  • User inputs additional messages while Claude is working
  • These inputs not saved to transcript

Impact

  • During session recovery, those critical supplementary instructions lost
  • May even cause users thinking they already said, but Claude completely unaware after recovery
