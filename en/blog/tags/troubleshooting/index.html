Symptoms

Root Cause

Section titled “Root Cause”

This is not a Docker container sandbox issue — it’s OpenClaw’s filesystem security boundary (the fs-safe module) at work.

OpenClaw assigns each agent a workspace root directory, and all file I/O tools (read, write, edit) are restricted to this directory. The logic works as follows:

  1. Resolve the file’s absolute path
  2. Check whether it falls within the workspace root (isPathInside check)
  3. If not → throw SafeOpenError("outside-workspace")

This is a hardcoded security mechanism, not a configuration option. There are no allowedPaths or extraReadPaths whitelist settings to bypass it.

Non-Solutions

Section titled “Non-Solutions”

The following approaches are not available in the current version:

  • ❌ sandbox.allowedPaths — There is no path whitelist mechanism

This restriction is intentional security design:

  1. Prevent file leaks from prompt injection — Malicious prompts cannot make the agent read sensitive files outside the workspace

  3. Multi-agent isolation — Agents with different workspaces don’t interfere with each other

Why the prompt appears

Section titled “Why the prompt appears”

OpenClaw has a device pairing mechanism. The rule is straightforward:

  • 127.0.0.1 / localhost → local loopback, trusted, no prompt
  • Everything else → external device, pairing required

Two Macs on the same LAN have IPs like 192.168.x.x. To the Gateway, that’s indistinguishable from a random machine on the internet — not localhost, so pairing kicks in.

Multiple GitHub issues confirm this behavior: non-localhost connections always trigger pairing. There’s no “same subnet = auto-trust” logic.

Section titled “What should be fixed upstream”

Three suggestions for the OpenClaw Docker setup:

  1. Set allowedOrigins before starting the gateway. The race condition is the biggest pain point. The setup script should write the config before the first docker compose up.

  2. Include both localhost and 127.0.0.1 in the default allowlist. Developers use both interchangeably. Blocking one is a paper cut.

  3. Auto-approve the first Control UI device pairing. If the user just completed onboarding, the first browser connection is clearly legitimate.
