Matt Pocock Skills Deep Dive: 17 AI Agent Skills Fully Dissected

Apr 7, 2026
Vibe Sparking

Source: mattpocock/skills Survey date: 2026-04-07 Total: 17 skills covering planning, development, tooling, and writing

I. Planning & Design

Section titled “I. Planning & Design”

1. write-a-prd

Section titled “1. write-a-prd”
  • Install: npx skills@latest add mattpocock/skills/write-a-prd
  • What it does: Generates a complete Product Requirements Document (PRD) through interactive interviews + codebase exploration, submitted as a GitHub Issue
  • Core workflow:
    1. Gather detailed problem and solution descriptions from the user
    2. Explore the codebase to verify current state
    3. Drill into every decision branch until consensus is reached
    4. Design module boundaries, pursuing “deep modules” (small interfaces, large implementations)
    5. Generate PRD from template (problem statement, solution, user stories, implementation decisions, module design)
  • Use cases:
    • Want to add a notification system but haven’t thought through the details — run this skill to turn vague ideas into structured documentation
    • Replace “let’s have a meeting to discuss” when kicking off new features

2. prd-to-plan

Section titled “2. prd-to-plan”
  • Install: npx skills@latest add mattpocock/skills/prd-to-plan
  • What it does: Breaks a PRD into multi-phase implementation plans using tracer bullet vertical slices, output to ./plans/
  • Core workflow:
    1. Confirm PRD is in context
    2. Explore codebase to understand architecture
    3. Identify durable architectural decisions (routing, schema, auth patterns, etc.)
    4. Split by vertical slices — each phase cuts through all integration layers (schema → API → UI → tests)
    5. Confirm granularity with user, iterate until satisfied
    6. Write to ./plans/ Markdown files
  • Use cases:
    • PRD is ready, need to schedule and phase the implementation
    • Ensure every development phase can demo independently, not “it only works on the last day”

3. prd-to-issues

Section titled “3. prd-to-issues”
  • Install: npx skills@latest add mattpocock/skills/prd-to-issues
  • What it does: Splits a PRD into independently claimable GitHub Issues, annotated with dependencies and HITL/AFK types
  • Core workflow:
    1. Get PRD (GitHub Issue number)
    2. Optionally explore codebase
    3. Split into vertical slices, label HITL (needs human decision) / AFK (can be done autonomously)
    4. Confirm granularity, dependencies, and categories with user
    5. Create GitHub Issues in dependency order
  • Use cases:
    • Multi-person team collaboration, turning large requirements into assignable tickets
    • Let AI agents autonomously execute AFK-type issues

4. grill-me

Section titled “4. grill-me”
  • Install: npx skills@latest add mattpocock/skills/grill-me
  • What it does: Ruthlessly interrogates your proposal, walking through every branch of the decision tree until consensus
  • Core workflow:
    • One question at a time
    • Each question comes with a recommended answer
    • Questions answerable by exploring the codebase are answered by reading code, not asking you
  • Use cases:
    • Planning to split a monorepo into microservices but unsure about boundaries — let it grill you
    • Stress-testing any major technical decision
    • Running a “devil’s advocate” pass before writing an RFC

5. design-an-interface

Section titled “5. design-an-interface”
  • Install: npx skills@latest add mattpocock/skills/design-an-interface
  • What it does: Based on John Ousterhout’s “Design It Twice” principle, uses parallel sub-agents to generate 3+ radically different interface designs, then compares them
  • Core workflow:
    1. Gather requirements (problem, callers, key operations, constraints)
    2. Launch 3+ parallel sub-agents, each with different constraints (minimalist, flexible, common-case optimized, etc.)
    3. Present each design (signatures, usage examples, hidden complexity)
    4. Multi-dimensional comparison (interface simplicity, generality, implementation efficiency, module depth)
    5. User selects or mixes
  • Use cases:
    • Designing cache module APIs, plugin systems, SDK interfaces, and other critical modules
    • Avoiding the “first idea is the final idea” trap

6. request-refactor-plan

Section titled “6. request-refactor-plan”
  • Install: npx skills@latest add mattpocock/skills/request-refactor-plan
  • What it does: Generates a detailed refactoring plan through interviews, broken into tiny safe commits, submitted as a GitHub Issue
  • Core workflow:
    1. Gather problem description and initial proposal
    2. Explore codebase to verify
    3. Discuss alternatives
    4. Define precise scope (what changes, what doesn’t)
    5. Check test coverage
    6. Split commit plan following Martin Fowler’s “each step as small as possible” principle
    7. Create GitHub Issue (problem, solution, commit list, decision documentation)
  • Use cases:
    • Want to unify scattered state management to Zustand but afraid of breaking things
    • Any large-scale refactoring spanning multiple files and modules

II. Development

Section titled “II. Development”

7. tdd

Section titled “7. tdd”
  • Install: npx skills@latest add mattpocock/skills/tdd
  • What it does: Strict red-green-refactor TDD cycles, progressing one vertical slice at a time
  • Core philosophy:
    • Tests verify behavior (through public interfaces), not implementation details
    • Horizontal slicing strictly forbidden (writing all tests before any code)
    • One test → one implementation → refactor → next (vertical slicing)
    • Good tests read like specifications and survive refactoring
  • Use cases:
    • Adding refund functionality to a payment module, progressing step by step
    • Writing a failing test before fixing a bug
    • Building TDD habits in AI agents

8. triage-issue

Section titled “8. triage-issue”
  • Install: npx skills@latest add mattpocock/skills/triage-issue
  • What it does: Automatically investigates bug root causes, explores the codebase, generates GitHub Issues with TDD fix plans
  • Core workflow:
    1. Get problem description (asks only one question)
    2. Deep codebase exploration: locate bug, trace code paths, find root cause, check related code
    3. Determine fix approach (minimal changes)
    4. Design TDD fix plan (ordered RED-GREEN cycles)
    5. Create GitHub Issue
  • Use cases:
    • User reports “page occasionally goes blank” — nearly hands-free automatic investigation
    • Open-source issue triage, auto-generating fix proposals

9. improve-codebase-architecture

Section titled “9. improve-codebase-architecture”
  • Install: npx skills@latest add mattpocock/skills/improve-codebase-architecture
  • What it does: Organically explores the codebase, discovers architectural improvement opportunities, focusing on deepening shallow modules and improving testability
  • Core concept: Deep Modules (John Ousterhout) = small interfaces hiding large implementations, more testable, more AI-friendly
  • Core workflow:
    1. Organically explore codebase, record friction points
    2. Present candidate improvements (coupling clusters, dependency types, test impact)
    3. User selects candidates
    4. Propose multiple refactoring approaches using design-an-interface methodology
    5. Create GitHub Issue RFC
  • Use cases:
    • Project growing large, small files everywhere with tangled dependencies, “something feels wrong but can’t articulate it”
    • Regular architecture health checks

10. migrate-to-shoehorn

Section titled “10. migrate-to-shoehorn”
  • Install: npx skills@latest add mattpocock/skills/migrate-to-shoehorn
  • What it does: Migrates as type assertions in test files to @total-typescript/shoehorn
  • Migration patterns:
    • as Type → fromPartial() (passing partial data)
    • as unknown as Type → fromAny() (intentionally passing wrong data)
    • When large objects only care about a few properties, no more faking entire objects
  • Use cases:
    • TypeScript projects with as assertion sprawl in tests, wanting better type safety
    • Note: This is Matt Pocock’s own library, suited for the Total TypeScript ecosystem

  • Core specs:
    • Section: XX-section-name/, Exercise: XX.YY-exercise-name/

  • Use cases:
    • Batch-generating exercise scaffolding for TypeScript/programming tutorials

VI. Design Philosophy Summary

Section titled “VI. Design Philosophy Summary”

Matt Pocock’s skills system is built on several core principles:

  1. Vertical Slicing (Tracer Bullet) — Threading through the complete chain of write-a-prd → prd-to-plan → prd-to-issues → tdd, every step emphasizes end-to-end thin slices over horizontal layering
  2. Deep Modules — From John Ousterhout’s A Philosophy of Software Design, small interfaces hiding large implementations, central to design-an-interface and improve-codebase-architecture
  3. Design It Twice — Don’t fall in love with your first design; explore multiple approaches in parallel
  4. Tiny Commits — Martin Fowler’s refactoring philosophy, keeping code runnable at every step
  5. Behavior Tests Over Implementation Tests — The core of the TDD skill; tests should read like specifications and survive refactoring

Recommended combination path: grill-me → write-a-prd → design-an-interface → prd-to-plan → prd-to-issues → tdd

Skill Vetter Guide: Build a Vet-Before-Install Security Workflow for OpenClaw

Apr 5, 2026
Vibe Sparking

Third-party skills are not something you should fear.

But in an agent environment like OpenClaw—where skills can influence file access, command execution, network behavior, and workflow automation—you should absolutely review first and install second.

Why Skill Vetter deserves its own workflow

Section titled “Why Skill Vetter deserves its own workflow”

When people first encounter OpenClaw skills, they often think of them as lightweight prompt packages or convenience wrappers. That is partly true, but not enough.

A skill can shape what an agent reads, writes, executes, and reaches over the network. In practice, installing a third-party skill means giving an agent a new behavioral protocol. If that protocol is unsafe, automation only amplifies the risk.

That is the point of Skill Vetter:

Never install a skill without vetting it first.

Skill Vetter is not a standalone CLI. It is a safety-first review protocol for agents. Before installation, the agent should inspect the full skill, look for red flags, assess permission scope, produce a structured report, and only then decide whether the skill should be installed.

What Skill Vetter actually checks

Section titled “What Skill Vetter actually checks”

You can think of Skill Vetter as a pre-install security reviewer. Instead of trusting a README or a single SKILL.md, it pushes the agent to inspect all files in the skill.

Typical review points include:

  • Whether the source is trustworthy
  • Whether the skill reaches out to unknown external services
  • Whether it reads sensitive directories or private context files
  • Whether it uses risky patterns such as eval, exec, obfuscation, or base64 decode pipelines
  • Whether it requests tokens, credentials, or elevated permissions
  • Whether its file, command, and network access match the principle of least privilege

In other words, Skill Vetter forces three questions before installation:

  1. What does this skill really do?
  2. What permissions does it need?
  3. Are those permissions justified?

Recommended install scope: make it global

Section titled “Recommended install scope: make it global”

If Skill Vetter lives only inside one workspace, it helps only that one agent. A better pattern is to treat it as shared security infrastructure and install it globally:

That gives you three benefits:

  • Multiple OpenClaw agents on the same machine can reuse it
  • Security policy becomes more consistent across sessions
  • Auditing, upgrading, and recurring reviews become easier to manage

A useful mental model is:

Skill typeTypical locationBest for
Built-in OpenClaw skillsOpenClaw installation directoryOfficial bundled capabilities
User-global skills~/.agents/skills/Shared capabilities across agents
Workspace-local skillsProject or workspace directoryNarrow, project-specific behavior

Skill Vetter clearly belongs in the second bucket.

Section titled “The most practical usage pattern: vet first, install second”

In day-to-day OpenClaw usage, Skill Vetter is not usually something you invoke as a command. The easiest way to use it is to make the workflow explicit in natural language.

For example:

The critical thing is not the wording. It is the order.

A practical SOP for every third-party skill installation

Section titled “A practical SOP for every third-party skill installation”

If you want a repeatable standard, this six-step flow is enough for most OpenClaw environments.

1. Verify the source

Section titled “1. Verify the source”

Start by identifying where the skill comes from:

  • Official OpenClaw source
  • ClawHub
  • A GitHub repository
  • A personal or private share

Then check supporting signals: who maintains it, when it was last updated, whether other people use it, and whether its purpose is clearly documented.

Source quality is not everything, but it is a fast way to filter obvious junk.

2. Review every file

Section titled “2. Review every file”

This is the part people most want to skip, and the part they should skip least.

Common red flags include:

  • curl or wget calls to unfamiliar hosts
  • Silent outbound data transfer
  • Reads of ~/.ssh, ~/.aws, ~/.config, or similar sensitive locations
  • Access to files like MEMORY.md, USER.md, SOUL.md, or IDENTITY.md
  • base64 decode pipelines or other masking behavior
  • eval() or exec() paired with external input
  • Modifications outside the intended workspace
  • Hidden dependency installation
  • Requests for sudo or elevated permissions
  • Access to browser cookies, sessions, or credential stores

The rule here is simple:

Review code, not marketing.

A well-written README is not evidence of safety.

3. Assess the permission boundary

Section titled “3. Assess the permission boundary”

After code review, the agent should explicitly describe the capability envelope:

  • Which files does it read?
  • Which files does it write?
  • Which commands does it execute?
  • Does it need network access?
  • Are the network targets aligned with the stated function?
  • Can the permission surface be reduced further?

If a Markdown formatter wants broad access to personal memory files or system configuration, that mismatch is already a warning sign.

4. Assign a risk level

Section titled “4. Assign a risk level”

A simple but useful grading model:

Risk levelMeaningRecommended handling
LOWLocal formatting, text transforms, weather-like low-risk tasksUsually installable after review
MEDIUMFile operations, browser work, third-party API integrationInstall cautiously after full review
HIGHCredentials, system config changes, automated outbound actionsRequire human approval
EXTREMERoot access, security policy tampering, broad privacy accessDo not install by default

This matters because it turns “maybe we should pause” into an actual operating rule.

5. Produce a structured report

Section titled “5. Produce a structured report”

The report should be easy to audit and easy to compare over time. A practical format includes: skill name, source, author, version, metrics, red flags, permissions needed, risk level, verdict, and notes.

A standard layout makes recurring audits dramatically easier.

6. Record the installation

Section titled “6. Record the installation”

Do not leave the result only in chat. After installation, record at least: install date, skill name, source, risk level, review summary, and install path. Typical destinations include memory files or dedicated security audit folders.

This becomes even more valuable when you operate multiple OpenClaw instances.

Which OpenClaw files should be treated as highly sensitive

Section titled “Which OpenClaw files should be treated as highly sensitive”

In local agent workflows, the most overlooked risk is often not a shell command. It is context leakage.

Files that should normally be treated as highly sensitive include:

  • MEMORY.md
  • USER.md
  • SOUL.md
  • IDENTITY.md
  • TOOLS.md
  • openclaw.config.json
  • memory/*.md

These often contain personal context, private preferences, system-specific notes, internal rules, or memory summaries. If a third-party skill tries to read them, that should usually be treated as a high-risk signal.

Three best practices that pay off fast

Section titled “Three best practices that pay off fast”

1. Write the rule into AGENTS.md

Section titled “1. Write the rule into AGENTS.md”

If you only mention this workflow casually, it will drift. A stronger pattern is to add an explicit rule to the agent operating guide. That makes “vet before install” part of the system, not just a habit.

2. Require human confirmation for high-risk cases

Section titled “2. Require human confirmation for high-risk cases”

Pause and ask for approval whenever the skill touches credentials or tokens, outbound messaging or data transfer, system configuration changes, root or elevated permissions, private context files, or network calls to unfamiliar destinations.

Security workflows collapse when too many exceptions become informal.

3. Audit installed skills regularly

Section titled “3. Audit installed skills regularly”

Installation is not the finish line. A skill can be updated, replaced, or tampered with later. A practical cadence is fast recurring checks every four hours and deeper manual reviews weekly or monthly. Keep history instead of overwriting.

Prompt templates worth reusing

Section titled “Prompt templates worth reusing”

Template 1: Review only

Section titled “Template 1: Review only”

Ask the agent to review a skill using the Skill Vetter protocol without installing it. Have it check all files, output a standard report, and end with a clear verdict.

Template 2: Review and auto-install if safe

Section titled “Template 2: Review and auto-install if safe”

Tell the agent you want to install a skill, but it must perform a full vetting first. Only proceed with installation if the risk is LOW. Stop and wait for confirmation if HIGH or EXTREME.

Template 3: Audit all installed third-party skills

Section titled “Template 3: Audit all installed third-party skills”

Request a security audit of all third-party skills under ~/.agents/skills/. Have the agent label each as Normal, Needs Attention, or Problematic, and write the results to an audit file.

A clean operating model for real OpenClaw setups

Section titled “A clean operating model for real OpenClaw setups”

If you are managing multiple OpenClaw agents or instances, a practical rollout looks like this:

  • Install path: ~/.agents/skills/skill-vetter/
  • Policy file: AGENTS.md
  • Long-term records: MEMORY.md or a security audit folder
  • Automation: audit ~/.agents/skills/ every four hours
  • Mandatory pause conditions: credentials, outbound network access, privacy files, or system changes

That combination is light enough to maintain and strong enough to actually change behavior.

Closing thought

Section titled “Closing thought”

If I had to reduce the whole workflow to one line, it would be this:

Review third-party skills before installation, inspect all files, and stop when the risk is high.

In a framework as capable as OpenClaw, that is not overcautious. It is what professionalism looks like.

Impact: Multi-tenant OpenClaw deployments are at highest risk. Single-user setups are less exposed but should still upgrade.

Path traversal via alias fields is a classic web security issue. Jupyter Notebook and Code Server have both had similar vulnerabilities. This fix unifies all path fields under the same security check.

You’re Probably Using Your AI Assistant Wrong

Section titled “You’re Probably Using Your AI Assistant Wrong”

You wouldn’t hire a senior engineer and then hand them tasks one sentence at a time with no context, no process, no institutional knowledge. But that’s exactly what most of us do with our AI coding assistants.

Matt Pocock — the TypeScript educator behind Total TypeScript — just open-sourced his .claude directory. Inside: a collection of structured “skills” that turn Claude Code from a reactive chatbot into something closer to an opinionated team member who knows how your shop runs.

What Are Skills, Exactly?

Section titled “What Are Skills, Exactly?”

Claude Code supports a .claude directory where you define “skills” — structured workflow definitions the AI follows when invoked. Not prompts. Processes.

Think of them as runbooks for your AI assistant. Matt has been building his personal collection, and he just made it public on GitHub: mattpocock/skills.

What makes this worth your attention isn’t any single skill. It’s how the collection is architected.

The Three-Layer Architecture

Section titled “The Three-Layer Architecture”

Planning Layer

Section titled “Planning Layer”

Three skills handle the upstream work most developers rush through.

write-a-prd doesn’t generate a boilerplate document. It conducts an interactive interview, explores your actual codebase, designs module boundaries, and files the result as a GitHub issue. The AI becomes your product thinking partner.

prd-to-issues takes that PRD and decomposes it into independently-grabbable GitHub issues using vertical slices. Each issue is self-contained — pick it up, implement it, ship it. No dependency chains to untangle.

grill-me is the standout. It inverts the dynamic completely. Instead of you asking the AI questions, it interrogates you about your plan or design. Relentlessly. Until every branch of the decision tree is resolved. It’s like having a skeptical tech lead in your terminal who won’t let you start coding until your thinking is airtight.

Development Layer

Section titled “Development Layer”

This is where the engineering discipline shows.

tdd implements actual test-driven development. Not “write some tests after the fact.” The real thing — red-green-refactor, one vertical slice at a time. You tell it what feature to build or what bug to fix, and it drives the loop.

triage-issue investigates bugs by exploring the codebase, identifies root causes, and files GitHub issues with TDD-based fix plans already attached. Bug triage and fix planning in a single workflow.

improve-codebase-architecture scans for structural improvement opportunities. It focuses on deepening shallow modules and improving testability — the kind of refactoring work that’s always important and never urgent, which means it usually never happens.

Tooling Layer

Section titled “Tooling Layer”

Two skills build the safety nets.

setup-pre-commit configures Husky pre-commit hooks with lint-staged, Prettier, type checking, and tests. Standard tooling, but automated setup means no excuse to skip it.

git-guardrails-claude-code sets up Claude Code hooks that block dangerous git commands — push, reset —hard, clean — before the AI can execute them. Your AI assistant is powerful. It should also be constrained.

The Meta Layer

Section titled “The Meta Layer”

write-a-skill teaches the AI to create new skills with proper structure, progressive disclosure, and bundled resources. The system is self-extending. Skills create skills.

Why This Matters: Skills as Packages

Section titled “Why This Matters: Skills as Packages”

Think about the history of software development. We went from writing everything from scratch to sharing libraries. From ad-hoc scripts to package managers. From manual deployment to CI/CD pipelines.

Each transition followed the same pattern: something that was artisanal and individual became structured and shareable.

Skills are that transition for AI-assisted development. A tdd skill isn’t a prompt — it’s an entire methodology encoded as a workflow definition that any developer can install and run.

We’re watching the early days of a package manager for AI behavior. And like npm in 2012 or Docker in 2014, the developers building and sharing the best packages early will shape how everyone works later.
