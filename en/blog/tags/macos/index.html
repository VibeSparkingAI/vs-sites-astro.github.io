Fixing Garbled CJK Characters After SSH Login on macOS

Vibe Sparking

The Problem

Section titled “The Problem”

After SSH-ing into a macOS host, viewing Markdown files containing CJK (Chinese/Japanese/Korean) characters with more shows garbled text or a binary file warning:

Even when you choose to view it anyway, CJK characters display as garbled text.

Root Cause

Section titled “Root Cause”

Checking the locale settings on the remote host:

LANG is empty and all LC_* variables are set to C.

The C locale only recognizes single-byte ASCII characters. UTF-8 encoded CJK characters use 3 bytes each, which under the C locale are treated as illegal byte sequences. This causes:

  • more to misidentify the file as binary
  • cat to output garbled text (depending on whether the terminal emulator handles UTF-8 independently)
  • less may partially work (it has its own character encoding logic)

Why Does macOS Behave This Way?

Section titled “Why Does macOS Behave This Way?”

macOS Terminal.app has “Set locale environment variables on startup” enabled by default, so local sessions get LANG set to en_US.UTF-8 or zh_CN.UTF-8. However, when connecting via SSH:

  1. The SSH client may not forward locale variables (depends on SendEnv config)
  2. The remote sshd may not accept locale variables (depends on AcceptEnv config)
  3. The user’s shell config (.zshrc / .bashrc) doesn’t explicitly set LANG

If any of these conditions fails, the remote session falls back to the C locale.

Section titled “The Fix”

The most reliable approach: explicitly set the locale in the remote host’s shell config file.

This doesn’t depend on SSH locale forwarding and works regardless of how you connect.

Stop Babysitting SSH Tunnels: launchd + autossh Is the macOS Way

Vibe Sparking

Every morning, same routine. Open a terminal, fire a curl at localhost:18800, and get a connection refused. The s8-aws-tokyo tunnel is dead again. Ten seconds of actual work, two minutes of re-establishing state. Annoying enough that I finally sat down to fix it properly.

What Actually Killed It

Section titled “What Actually Killed It”

My first assumption was SSH — maybe the Tokyo server has an aggressive ClientAliveInterval, or the connection timed out overnight. I started there.

Came back: SSH_OK. SSH was fine. The key auth works, the server is reachable, nothing wrong on that side.

The real culprit showed up when I tried to reattach:

Not “session not found.” Not “connection lost.” The entire tmux server was gone. That’s a different failure mode.

Why tmux Doesn’t Survive on macOS

Section titled “Why tmux Doesn’t Survive on macOS”

tmux is a user-space process. When macOS sleeps — or you close the lid, or the machine restarts — the OS tears down user processes that aren’t managed by launchd. There’s no graceful shutdown, no state preservation. The tmux server just vanishes.

This is by design. macOS doesn’t treat tmux as a service. It doesn’t know that tmux was babysitting an SSH tunnel that something else depends on. From the OS’s perspective, it’s just another process attached to your terminal session.

On Linux with systemd you’d write a unit file and call it a day. On macOS, the equivalent is launchd — and most people never use it for personal tooling because it feels like overkill. It isn’t.

The Fix: launchd + autossh

Section titled “The Fix: launchd + autossh”

autossh wraps an SSH connection and restarts it when it drops. Combined with launchd, you get a tunnel that:

  • Starts automatically on login
  • Restarts if the SSH connection dies
  • Survives sleep and wake cycles
  • Doesn’t need a terminal window open to stay alive

Section titled “Setting Up the plist”

Create the launchd agent file at ~/Library/LaunchAgents/com.openclaw.tunnel-s8.plist. Name it whatever makes sense for your setup — the reverse-DNS prefix is convention, not requirement.

A few things worth explaining in the autossh flags:

  • -M 0 disables autossh’s own monitoring port. We’re relying on SSH’s built-in keepalives instead, which is cleaner.
  • ServerAliveInterval=30 and ServerAliveCountMax=3 mean SSH will detect a dead connection within 90 seconds and exit, letting autossh restart it.
  • ExitOnForwardFailure=yes tells SSH to bail if the port forward can’t be established — rather than connecting successfully but silently failing to set up the tunnel.
  • -N means no remote command; we just want the tunnel.

AI agents can write code, search the web, and manage files. What they can’t do is reach across your screen and actually use the apps you work in — Slack, Xcode, Finder, Terminal. That gap has existed not because desktop control is technically impossible, but because the obvious approach (screenshots + vision model) was always a workaround for a problem macOS already solved differently.

macos-use removes that wall.

What It Is

Section titled “What It Is”

macos-use is an MCP server written in Swift. It lets Claude — or any MCP-compatible model — control desktop applications through macOS Accessibility APIs.

Not screenshots. The accessibility tree.

Every UI element in every macOS app — buttons, text fields, menus, lists — is exposed through Accessibility APIs as structured, hierarchical data. VoiceOver has relied on this for decades. Automated testing tools use it. macos-use connects this tree directly to Claude via MCP.

Instead of analyzing a 1200×800 image and guessing coordinates, the AI reads: AXButton, label="Send", enabled=true. Unambiguous. Resolution-independent. No vision model required.

The screenshot approach has three hard problems.

Token cost. A 1080p screenshot dropped into context is expensive. macos-use returns compact JSON file paths — UI trees are saved to /tmp/macos-use/, not dumped into the model’s context window.

Unreliability. Pixel-based recognition depends on display resolution, scaling, dark mode, font rendering. Change monitors or toggle Dark Mode and coordinates shift. The accessibility tree is structural data — none of that matters.

Why the prompt appears

Section titled “Why the prompt appears”

OpenClaw has a device pairing mechanism. The rule is straightforward:

  • 127.0.0.1 / localhost → local loopback, trusted, no prompt
  • Everything else → external device, pairing required

Two Macs on the same LAN have IPs like 192.168.x.x. To the Gateway, that’s indistinguishable from a random machine on the internet — not localhost, so pairing kicks in.

Multiple GitHub issues confirm this behavior: non-localhost connections always trigger pairing. There’s no “same subnet = auto-trust” logic.

Why it keeps coming back after clicking Allow

Section titled “Why it keeps coming back after clicking Allow”

Common reasons:

  1. Device identity changed. Gateway token rotation, network switch, macOS update — any of these can alter the node’s device fingerprint. Changed fingerprint means the Gateway sees a new device or a device needing repair, retriggering pairing.
  2. Pending repair not cleared. When a device is stuck in “awaiting repair confirmation,” the UI Allow button doesn’t always resolve it fully. Many scenarios require CLI approval.
  3. Token churn loop. Recent macOS reports show tokens refreshing repeatedly, causing a pairing-required cycle.

The UI Allow button sometimes grants temporary passage without completing the full device lifecycle.
