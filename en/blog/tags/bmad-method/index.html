1. What is BMAD?

Section titled “1. What is BMAD?”

BMAD = Build More Architect Dreams — an AI-driven agile development framework (multi-agent system) covering the complete software development lifecycle from ideation, planning, architecture, coding to QA. 100% open source (MIT), installed via npx bmad-method install.

Core philosophy: Let AI agents collaborate through agile methodology (Epic → Story → Sprint → Review) in an orderly fashion, rather than letting LLMs freestyle.

3.2 In-Depth Product Comparisons

Section titled “3.2 In-Depth Product Comparisons”

📌 OpenSpec — “Fluid, Not Rigid”

Section titled “📌 OpenSpec — “Fluid, Not Rigid””

Core Philosophy: Reach spec consensus first, then write code.

Differences from BMAD:

  • OpenSpec focuses on single change spec lifecycle: propose → apply → archive
  • BMAD focuses on entire product development lifecycle: product brief → architecture → Epic/Story → Sprint → Code Review → retrospective
  • OpenSpec doesn’t preset workflow phases (“fluid not rigid”); BMAD has strict Phase 1-4
  • OpenSpec contains no agent role definitions; BMAD has Analyst/PM/Architect/Developer/QA

Good for:

  • Existing mature codebase needing spec governance for each change
  • Don’t want to introduce agile concepts, just want “write it down then do it”
  • Multi-person collaboration needing spec alignment

Not ideal for:

  • Building products from scratch (lacks architecture/product planning stages)
  • Needing Sprint management, retrospectives and other agile ceremonies

📌 Spec Kit (GitHub) — “Spec as Executable”

Section titled “📌 Spec Kit (GitHub) — “Spec as Executable””

Core Philosophy: Spec-Driven Development — specs themselves can generate implementations.

Differences from BMAD:

  • Spec Kit is GitHub official, deeply integrated with Copilot
  • Provides CLI + templates + prompts; flow is spec → plan → tasks → implementation
  • More “developer tool” oriented, doesn’t cover product management
  • Python ecosystem, requires pip install
  • Has relatively strict phase gates

Good for:

  • Deep GitHub ecosystem users (Copilot + Actions + PR)
  • Enterprise projects needing spec governance
  • Preference for structured templates

Not ideal for:

  • Need flexible iteration (OpenSpec claims to be lighter)
  • Non-Python environments where pip is inconvenient

📌 GStack (Garry Tan) — “One Person = One Team”

Section titled “📌 GStack (Garry Tan) — “One Person = One Team””

Core Philosophy: Use slash commands to turn Claude Code into a virtual development team.

Differences from BMAD:

  • GStack is role simulation: CEO/Eng Manager/Designer/QA/CSO and 28 other specialists
  • BMAD is a process framework: organizes work by Epic/Story/Sprint
  • GStack is tightly bound to Claude Code ecosystem (skill standard)
  • GStack includes actual browser QA (/qa opens real URLs in Chromium)
  • GStack is more “solo workshop,” BMAD is more “team collaboration”

Good for:

  • Solo developers / technical founders
  • Already heavy Claude Code users
  • Need end-to-end Think→Plan→Build→Review→Test→Ship pipeline
  • Enjoy “conversational reasoning” (like /office-hours’ 6 probing questions)

Not ideal for:

  • Multi-person collaboration (GStack is essentially a single-person tool)
  • Need to work across multiple IDEs/Agents (limited platform support)
  • Teams not using Claude Code

📌 GSD (Get Shit Done) — “The Ultimate Context Engineering Weapon”

Section titled “📌 GSD (Get Shit Done) — “The Ultimate Context Engineering Weapon””

Core Philosophy: Solve context rot — as context windows fill up, AI output quality degrades.

Differences from BMAD:

  • GSD’s core innovation is context engineering: each task plan executes in a fresh context window, 200K tokens purely for implementation
  • BMAD assumes one session handles one story, no explicit context management
  • GSD’s flow is simpler: new-project → discuss-phase → plan-phase → execute-phase
  • BMAD has richer agile ceremonies: Sprint Planning / Retrospective / Correct Course
  • GSD supports wave execution (parallel by dependency groups); BMAD is more serial
  • GSD explicitly opposes “enterprise theater” (sprint ceremonies, story points), positioned for individuals/small teams

Good for:

  • Long-context projects (context rot is a real pain point)
  • Preference for concise commands (4 core commands cover everything)
  • Multi-platform users (8 runtimes, one-click switch)
  • “Describe vision → AI executes” work mode

Not ideal for:

  • Need complete agile management (no sprint/retrospective/status tracking)
  • Enterprise teams needing document audit trails

Section titled “The Old Way: Step-File Architecture”

The original bmad-create-product-brief works like a form wizard. Step 01 through Step 06, strict sequence, no skipping. Each step needs user confirmation before the next one unlocks. One agent handles everything. No web research. State lives in frontmatter via stepsCompleted. It runs. It works. It’s predictable.

It’s also a script that happens to use AI. The structure is human-designed, human-paced, human-controlled.

The New Way: Prompt-Based Multi-Agent Orchestration

Section titled “The New Way: Prompt-Based Multi-Agent Orchestration”

The replacement, bmad-product-brief-preview, barely resembles its predecessor. Five stages instead of six steps, but that’s the least interesting change.

Four sub-agents run concurrently:

  • artifact-analyzer scans existing project documents
  • web-researcher pulls external market data
  • opportunity-reviewer evaluates business potential
  • skeptic-reviewer stress-tests assumptions

Three execution modes:

  • guided (default) for interactive use
  • yolo for autonomous execution with simulated expert input
  • headless for fully autonomous, no human in the loop

It can edit existing briefs, not just create new ones. It accepts parameters like --create, --edit, --optimize, --distillate, --inputs, and --headless. And it outputs an LLM distillate: a token-optimized version of the brief designed to feed downstream AI workflows like PRD generation.

The Pattern Behind the Pattern

Section titled “The Pattern Behind the Pattern”

I’ve been watching this shift across AI tooling. The first generation takes what humans do and adds AI at each step. A motor on a bicycle. The second generation asks: why does this need to be a bicycle at all?

The step-file architecture says: “Here are six things to do. Do them in this order. Wait for permission at each step.”

The prompt-based architecture says: “Here’s what we need to produce. Here are specialists who can help. Go.”

That’s not a version upgrade. That’s a paradigm change.

Why This Changes What’s Buildable

Section titled “Why This Changes What’s Buildable”

A step-file skill can’t run headless, because every step expects a human to press ‘C’ for Continue. A multi-agent skill can, because the agents negotiate among themselves.

A step-file skill can’t do web research in parallel with artifact analysis, because step 3 has to finish before step 4 begins. The new skill can, because sub-agents are concurrent by design.

The LLM distillate is maybe the most telling detail. The old skill produces output for humans to read. The new skill produces output for both humans and downstream AI agents to consume. It’s designing for AI-to-AI communication. A product brief that feeds a PRD generator that feeds a story creator that feeds a developer agent. The output format isn’t an afterthought; it’s an architectural decision about who (or what) the audience is.

The “Guided to YOLO to Headless” Maturity Curve

Section titled “The “Guided to YOLO to Headless” Maturity Curve”

Three execution modes aren’t just a feature. They describe a maturity curve:

  1. Guided: human drives, AI assists (training wheels)
  2. YOLO: AI drives with simulated expert input, human reviews (supervised autonomy)
  3. Headless: AI runs independently, produces output, moves on (full autonomy)

If your AI tools only support guided mode, they’re generation one. The jump from guided to headless isn’t incremental. It requires the tool to be architecturally capable of self-direction. Step-file tools can’t make that jump. Multi-agent tools can.

What This Means for Practitioners

Section titled “What This Means for Practitioners”

Stop evaluating AI tools by their feature checklists. Start evaluating their architecture.

A tool with three execution modes and concurrent sub-agents isn’t “better” than a step-file tool the way a faster car is better than a slower car. It’s different the way a car is different from a horse. The capabilities aren’t incremental; they’re categorical.

Next time you update a framework, don’t just check if your old workflows still run. Check if the framework has evolved past your mental model. The replaces-skill field in BMAD’s manifest wasn’t just deprecating a script. It was deprecating an entire way of thinking about how AI and humans collaborate.

For your own tools: ask whether you’re still building step-file architectures when the world has moved to agent orchestration.

The Problem with Vibe Coding

Section titled “The Problem with Vibe Coding”

“Vibe coding” - writing code “by feeling” and hoping the AI guesses your intentions - seemed efficient at first. You describe what you want, the AI generates code, you copy-paste. Fast, right?

But this apparent speed hides structural problems that inevitably emerge:

  • Context rot: As conversations lengthen, the AI “forgets” previous decisions and generates code inconsistent with what was done before
  • Emergent architecture (in the worst sense): Without an overall vision, code grows chaotically and quickly becomes impossible to maintain
  • Lack of traceability: Impossible to understand why certain technical decisions were made
  • Onboarding nightmare: New team members have no references to understand the system

Enter Spec-Driven Development

Section titled “Enter Spec-Driven Development”

Spec-Driven Development (SDD) is the professional answer. A methodology where specifications become first-class executable artifacts. You write the “spec” (structured documentation) first, then the AI generates code that respects that contract.

The spec becomes the source of truth for developers and AI agents, eliminating the ambiguities of vibe coding.

According to Thoughtworks, SDD is one of the most important engineering practices in recent years.

Ralph runs AI agents in automated loops until specifications are met. Each iteration spawns a new agent process with a clean context window. The agent reads specs from disk, takes a task, implements it, and exits.
