1. Goal

Section titled “1. Goal”

Set up an hourly automated task to monitor version updates in Claude Code CHANGELOG.md. When a new version is detected:

  1. vs-claude agent generates an in-depth research report (problem background, use cases, competitive comparison, trend analysis)
  2. vs-sites-astro agent invokes the wechat-official-account-article skill to convert the report into an Astro Blog post, generate a cover image, and publish a WeChat Official Account draft

One cron job, spanning two agent sessions, fully automating the entire pipeline from detection to publication.

2. Final Architecture

Section titled “2. Final Architecture”

3. State Management: Resumable Pipeline

Section titled “3. State Management: Resumable Pipeline”

The core design uses a JSON state file to enable pipeline checkpointing and resumption:

On each cron trigger, Step 0 reads the state:

  • publish == pending + report == done → jump to Step 5 (publish only)
  • report == pending + check == done → jump to Step 3 (generate report only)
  • Otherwise, start from scratch checking for new versions

This way, even if a run times out or a subagent fails, the next execution resumes from the last checkpoint.

4. The 7 Pitfalls We Hit (Lessons Learned the Hard Way)

Section titled “4. The 7 Pitfalls We Hit (Lessons Learned the Hard Way)”

The entire debugging process went through 7 iterations, roughly 1.5 hours.

Pitfall 1: Agent Routing Error

Section titled “Pitfall 1: Agent Routing Error”

Initially the cron job ran on vibesparking (the default agent), and the publishing subagent was also routed to vibesparking. But the wechat-official-account-article skill lives on vs-sites-astro — vibesparking couldn’t find it.

Fix: Set the cron’s agentId to vs-claude, and specify agentId: vs-sites-astro for the subagent.

cron: sessionTarget "main" is only valid for the default agent

Pitfall 4: Subagent Toolset Trimmed — Glob Not Found

Section titled “Pitfall 4: Subagent Toolset Trimmed — Glob Not Found”

The vs-sites-astro subagent called the Glob tool and got Tool Glob not found, looping through this error 60+ times in a single session.

The cause: maxSpawnDepth defaults to 1, and a depth=1 subagent has the leaf role, which lacks Claude Code built-in tools (Glob, Read, Write, etc.).

Fix: Set agents.defaults.subagents.maxSpawnDepth: 2 so depth=1 subagents become orchestrator (with full toolset).

But even after fixing the depth issue, Glob/Read/Write were still unavailable — these are Claude Code CLI built-in tools, not part of the OpenClaw agentTurn runtime.

Final solution: Explicitly state in the subagent’s task prompt:

❗❗ Do NOT use Glob/Read/Write tools! Use exec find/ls to find files, exec cat to read files, and exec tee to write files.

Pitfall 5: File Sandbox Isolation

Section titled “Pitfall 5: File Sandbox Isolation”

vs-sites-astro’s Read tool couldn’t access report files under the vibesparking workspace:

Path escapes sandbox root (~/vs-sites-astro/.openclaw/workspace): /Volumes/.../vibesparking/.../report.md

Fix: In Step 5a, use exec cp to copy the report to the vs-sites-astro Astro blog directory first, so the subagent can access it within its own sandbox.

Pitfall 6: Stale Sessions Blocking New Tasks

Section titled “Pitfall 6: Stale Sessions Blocking New Tasks”

After deleting an old cron job, its leftover session state remained running, blocking new cron executions. Tasks showed enqueued: true but never dispatched.

Fix: Manually clean up stale session states in sessions.json and restart the gateway.

Pitfall 7: Skill Path Resolution Strategy

Section titled “Pitfall 7: Skill Path Resolution Strategy”

The subagent searched for the skill using find ~/.agents/skills, but wechat-official-account-article was in vs-sites-astro’s workspace skills directory, not the global skills directory.

Fix: Define a prioritized search strategy:

  1. First check vs-sites-astro workspace skills: ~/WorkSpaces/.../vs-sites-astro/.openclaw/workspace/skills/<name>/SKILL.md
  2. Then check global skills: ~/.openclaw/skills/<name>/SKILL.md
  3. If neither found → exit with error

OpenClaw Multi-Agent Permissions ≠ User Isolation: A Dangerous Misconception

Mar 29, 2026
Vibe Sparking

Think assigning different Agents to different users makes you secure? The Gateway trust model says otherwise.

What the Misconception Looks Like

Section titled “What the Misconception Looks Like”

When people first encounter OpenClaw’s multi-agent configuration, a natural thought emerges:

“I’ll create 3 Agents—admin for myself, developer for colleagues, viewer for external users—each with separate permissions. That’s user isolation, right?”

The config looks clean enough:

Three Agents, three permission sets, each with a clear role. Perfect?

No. This is a dangerous security illusion.

Why It Doesn’t Work: The Gateway Trust Model

Section titled “Why It Doesn’t Work: The Gateway Trust Model”

Core Fact: One Gateway = One Trust Domain

Section titled “Core Fact: One Gateway = One Trust Domain”

The official OpenClaw documentation is explicit:

Inside one Gateway instance, authenticated operator access is a trusted control-plane role, not a per-user tenant role.

In plain English:

  • Anyone who can connect to the Gateway is an operator
  • Operators have no hierarchy—there’s no “super admin” vs “regular user”
  • All operators have equal access to the Gateway’s control plane

What This Means in Practice

Section titled “What This Means in Practice”

Anyone with Gateway authentication (token or password), regardless of which Agent they’re “assigned” to, can:

ActionPossible?Consequence
List all Agents’ sessions✅ YesKnow who’s using what
Read other Agents’ chat history✅ YesSee all of admin’s conversations
Send messages to admin Agent’s session✅ YesExecute tools with admin’s permissions
Access Gateway API endpoints✅ YesFull control-plane operations

You configured deny: ["*"] for the viewer, but they can send messages directly to admin’s session and execute anything through admin’s permissions.

It’s like giving an intern a keycard that only opens the conference room—while the building’s back door is wide open.

A More Visual Explanation

Section titled “A More Visual Explanation”

sessionKey Is Not an Auth Token

Section titled “sessionKey Is Not an Auth Token”

Another common misunderstanding:

“Different Agents use different sessionKeys—surely the other party can’t get in without knowing the key?”

The official docs are clear:

Session identifiers (sessionKey, session IDs, labels) are routing selectors, not authorization tokens.

A sessionKey tells the Gateway “which conversation context I want to interact with”—it’s an address, not a lock. Knowing your street address doesn’t mean having your house key, but in the Gateway trust model, all operators hold the same master key.

What Multi-Agent Permissions Actually “Separate”

Section titled “What Multi-Agent Permissions Actually “Separate””

Let’s clarify the capability boundary:

✅ What It Can Do

Section titled “✅ What It Can Do”
  • Restrict the AI’s tool invocation scope — The viewer Agent’s AI truly can only call read, not exec
  • Reduce accidental AI misuse — Different Agents stay in their lanes
  • Functional partitioning within a trust domain — Your development Agent and messaging Agent stay separate

❌ What It Cannot Do

Section titled “❌ What It Cannot Do”
  • Prevent people from accessing other Agents’ data — The control plane is shared
  • Block privilege escalation via other Agents’ sessions — You can send messages to high-privilege Agents
  • Provide OS-level or filesystem-level isolation — Same machine, same user
  • Serve as a multi-tenant security boundary — It was never designed for this

One-line summary:

Multi-agent permissions constrain what the AI can do, not what people can see. To isolate people, isolate Gateways.

When Multi-Agent Permissions Are Appropriate

Section titled “When Multi-Agent Permissions Are Appropriate”
ScenarioSecure?Notes
One person, multiple purposes✅ Perfectly fineDev Agent and support Agent separated, reducing AI overreach
Same trust-domain team⚠️ AcceptableColleagues trust each other; prevents accidents, not malice
Family members sharing⚠️ Depends on trustFine if you don’t mind family seeing your chat history
Untrusted collaborators❌ Not secureEither party can access the full control plane
Public-facing service❌ Not secureExternal users = operators, catastrophic consequences
Client / vendor separation❌ Not secureVendor can see all client data

The Right Way to Isolate Users

Section titled “The Right Way to Isolate Users”

Option 1: One Gateway Per Person (Recommended)

Section titled “Option 1: One Gateway Per Person (Recommended)”
  • Each trust boundary gets its own Gateway instance
  • Separate OS users (ideally separate hosts / VPS)
  • Independent credentials, filesystems, configurations
  • Physical isolation = real isolation

Option 2: Same Machine, Different OS Users (Minimum)

Section titled “Option 2: Same Machine, Different OS Users (Minimum)”
  • Multiple OS users on the same machine
  • Each with their own ~/.openclaw directory
  • File permission isolation (ensure 0700)
  • Different ports, different auth tokens

Option 3: Container Isolation

Section titled “Option 3: Container Isolation”
  • One container per user
  • Network and filesystem naturally isolated
  • Ideal for team deployments

If You’re Already Using Multi-Agent “Isolation”…

Section titled “If You’re Already Using Multi-Agent “Isolation”…”

Check Immediately

Section titled “Check Immediately”

  1. Run a security audit:

    Watch for security.trust_model.multi_user_heuristic — the audit tool detects “config looks like multi-user but is actually single Gateway” situations.

  2. Verify Gateway auth token distribution — Who has the token? If untrusted parties have it, your “viewer” permissions are meaningless.

  3. Review channel configuration — Who can trigger the bot in Telegram / Slack? Everyone who can trigger it is an operator.

Migration Path

Section titled “Migration Path”

If you find your current setup is insecure:

  1. Create independent Gateway configurations for each trust boundary
  2. Migrate respective Agent configs and credentials
  3. Update channel bindings (each Gateway binds to its own bot)
  4. Revoke the old shared token
  5. Run openclaw security audit again

Suggestions for the OpenClaw Team

Section titled “Suggestions for the OpenClaw Team”

The current trust model is clear, documented, and intentional—a personal assistant doesn’t need multi-tenancy. But as use cases expand, the community needs:

  1. Prominent warnings in Agent configuration docs — Currently, agent permission config and security docs are separate; it’s easy to read only the former and assume “this is enough”
  2. Enhanced multi-user detection in openclaw security audit — When multiple agents + multiple channel sources are detected, proactively warn about trust model limitations
  3. Long-term consideration for per-user permission layers — Supporting user-level access control without splitting Gateways, reducing operational overhead for multi-person scenarios

One-Line Takeaway

Section titled “One-Line Takeaway”

Multi-agent permissions govern what the AI can do, not what people can see. To isolate people, isolate Gateways.

Don’t let a tidy config file give you a false sense of security.

Based on analysis of official OpenClaw security documentation (docs.openclaw.ai/gateway/security). Last updated: 2026-03-29

BMAD 6.2.0: The Version Upgrade That Killed an Entire Architecture

Section titled “BMAD 6.2.0: The Version Upgrade That Killed an Entire Architecture”

I asked a simple question: “What’s the difference between these two BMAD skills?” The answer rewired how I think about AI development tools.

Both skills create product briefs. Both live in the same framework. One has six steps. The other has five stages, four sub-agents, three execution modes, and a replaces-skill field pointing at the first one like a death warrant.

Two Skills, Same Job, Different Universe

Section titled “Two Skills, Same Job, Different Universe”

BMAD 6.2.0 shipped with two skills in the analysis workflow folder: bmad-create-product-brief and bmad-product-brief-preview. Same job. Same framework. I assumed the second was a preview of a minor update. Then I opened bmad-manifest.json and found the replaces-skill field.

One was killing the other.

The Old Way: Step-File Architecture

Section titled “The Old Way: Step-File Architecture”

The original bmad-create-product-brief works like a form wizard. Step 01 through Step 06, strict sequence, no skipping. Each step needs user confirmation before the next one unlocks. One agent handles everything. No web research. State lives in frontmatter via stepsCompleted. It runs. It works. It’s predictable.

It’s also a script that happens to use AI. The structure is human-designed, human-paced, human-controlled.

The New Way: Prompt-Based Multi-Agent Orchestration

Section titled “The New Way: Prompt-Based Multi-Agent Orchestration”

The replacement, bmad-product-brief-preview, barely resembles its predecessor. Five stages instead of six steps, but that’s the least interesting change.

Four sub-agents run concurrently:

  • artifact-analyzer scans existing project documents
  • web-researcher pulls external market data
  • opportunity-reviewer evaluates business potential
  • skeptic-reviewer stress-tests assumptions

Three execution modes:

  • guided (default) for interactive use
  • yolo for autonomous execution with simulated expert input
  • headless for fully autonomous, no human in the loop

It can edit existing briefs, not just create new ones. It accepts parameters like --create, --edit, --optimize, --distillate, --inputs, and --headless. And it outputs an LLM distillate: a token-optimized version of the brief designed to feed downstream AI workflows like PRD generation.

Section titled “The Comparison Table”

Every row tells the same story. The old skill automates a human workflow. The new skill defines a goal and lets agents negotiate the approach.

The Pattern Behind the Pattern

Section titled “The Pattern Behind the Pattern”

I’ve been watching this shift across AI tooling. The first generation takes what humans do and adds AI at each step. A motor on a bicycle. The second generation asks: why does this need to be a bicycle at all?

The step-file architecture says: “Here are six things to do. Do them in this order. Wait for permission at each step.”

The prompt-based architecture says: “Here’s what we need to produce. Here are specialists who can help. Go.”

That’s not a version upgrade. That’s a paradigm change.

Why This Changes What’s Buildable

Section titled “Why This Changes What’s Buildable”

A step-file skill can’t run headless, because every step expects a human to press ‘C’ for Continue. A multi-agent skill can, because the agents negotiate among themselves.

A step-file skill can’t do web research in parallel with artifact analysis, because step 3 has to finish before step 4 begins. The new skill can, because sub-agents are concurrent by design.

The LLM distillate is maybe the most telling detail. The old skill produces output for humans to read. The new skill produces output for both humans and downstream AI agents to consume. It’s designing for AI-to-AI communication. A product brief that feeds a PRD generator that feeds a story creator that feeds a developer agent. The output format isn’t an afterthought; it’s an architectural decision about who (or what) the audience is.

The “Guided to YOLO to Headless” Maturity Curve

Section titled “The “Guided to YOLO to Headless” Maturity Curve”

Three execution modes aren’t just a feature. They describe a maturity curve:

  1. Guided: human drives, AI assists (training wheels)
  2. YOLO: AI drives with simulated expert input, human reviews (supervised autonomy)
  3. Headless: AI runs independently, produces output, moves on (full autonomy)

If your AI tools only support guided mode, they’re generation one. The jump from guided to headless isn’t incremental. It requires the tool to be architecturally capable of self-direction. Step-file tools can’t make that jump. Multi-agent tools can.

What This Means for Practitioners

Section titled “What This Means for Practitioners”

Stop evaluating AI tools by their feature checklists. Start evaluating their architecture.

A tool with three execution modes and concurrent sub-agents isn’t “better” than a step-file tool the way a faster car is better than a slower car. It’s different the way a car is different from a horse. The capabilities aren’t incremental; they’re categorical.

Next time you update a framework, don’t just check if your old workflows still run. Check if the framework has evolved past your mental model. The replaces-skill field in BMAD’s manifest wasn’t just deprecating a script. It was deprecating an entire way of thinking about how AI and humans collaborate.

Recommendation

Section titled “Recommendation”

For new projects: use bmad-product-brief-preview.

For your own tools: ask whether you’re still building step-file architectures when the world has moved to agent orchestration.

One Bot Token, Multiple Agents: OpenClaw Discord Channel-Level Routing

Mar 18, 2026
Vibe Sparking

A Discord server with a dozen channels, one bot handling everything. The coding channel and the casual chat channel get the same responses. Technical questions get vague answers. Creative discussions get stuffed with code snippets.

The problem isn’t the agent. The problem is one agent doing everyone’s job.

OpenClaw has a routing system that maps different channels to different agents. Same bot token, but #code-help runs a code review specialist, #creative-writing runs a writing assistant, and #support runs a troubleshooting guide. No code required — five CLI commands and one JSON edit.

Prerequisites

Section titled “Prerequisites”
  • OpenClaw installed and running
  • Discord bot created with a valid token (if not, see the previous post: OpenClaw Discord Bot Setup)
  • At least two agent configurations ready (otherwise routing has no point)

How Routing Works

Section titled “How Routing Works”

OpenClaw’s bindings array matches in order. First match wins. Specificity from high to low:

PriorityMatch ScopeUse Case
1peer — specific channel or userPer-channel customization
2guildId — entire serverServer-level differentiation
3accountId — bot accountAccount-level default
4No match conditionGlobal fallback

Same logic as firewall rules: narrow rules must come before broad ones.

Step 1: Register the Discord Bot Account

Section titled “Step 1: Register the Discord Bot Account”

Skip if you’ve already connected Discord.

Step 2: Create Your Agents

Section titled “Step 2: Create Your Agents”

Each agent gets its own workspace and configuration directory. System prompts, model parameters, tool chains — all managed separately per agent config directory.

Want the coding channel agent to follow documentation strictly and the writing channel agent to run at higher temperature? Adjust each in their respective config directories.

Step 3: Open Group Message Permissions

Section titled “Step 3: Open Group Message Permissions”

Easy to miss. OpenClaw defaults groupPolicy to allowlist — whitelist mode. The effect: every channel message gets silently dropped. No errors, no warnings, no logs.

If the bot joins a channel and ignores every message, check this first. It’s almost always the cause.

Step 4: Edit Routing Bindings

Section titled “Step 4: Edit Routing Bindings”

Manually edit ~/.openclaw/openclaw.json and add channel-level rules to the bindings array:

One rule per channel. The id field takes the Discord channel ID.

Two ways to get a channel ID:

  • Turn on Developer Mode in Discord settings, right-click the channel, copy ID
  • CLI query: openclaw directory groups list --channel discord --account <accountId>

Ordering matters. Channel-level bindings must appear before account-level bindings for the same bot. If the account-level rule sits higher in the array, it matches first and the channel rule never fires. Same principle as CSS specificity or iptables.

Step 5: Restart the Gateway

Section titled “Step 5: Restart the Gateway”

Routing doesn’t hot-reload. After editing config, restart is required.

What It Looks Like in Practice

Section titled “What It Looks Like in Practice”

Three channels, three agents:

  • #code-help -> code-review-agent (low temperature, strict documentation adherence)
  • #creative-writing -> writing-assistant (high temperature, free style)
  • #support -> troubleshoot-agent (medium temperature, guided troubleshooting)

Three binding rules, one bot token. Whichever channel a user sends a message in, the corresponding agent handles it. Channels without specific bindings fall through to the account-level or global default agent.

Troubleshooting

Section titled “Troubleshooting”

Bot doesn’t respond in channels at all Check if groupPolicy is set to open. The default whitelist silently drops all channel messages.

Channel-level binding not working — all channels respond the same way Check the order in the bindings array. Channel rules must come before account rules.

How to get channel IDs Discord Settings > App Settings > Advanced > Developer Mode. Then right-click any channel to copy its ID.

Multi-server scenarios Use guildId for server-level routing. Channel-level peer rules have higher priority and can layer on top: a server defaults to Agent A, but a specific channel within it routes to Agent B.

Comparison with Feishu and QQ

Section titled “Comparison with Feishu and QQ”

OpenClaw’s routing isn’t Discord-specific. Feishu group chats and QQ group chats support the same peer-level binding. The differences:

  • Discord channels are naturally separate conversation spaces — routing them to different agents feels intuitive
  • In Feishu group chats, a bot that suddenly changes response style confuses users
  • QQ group binding uses the same logic, but permission configuration differs

Discord’s channel model and multi-agent routing are a natural fit.

Next Steps

Section titled “Next Steps”
  • Tune each agent’s system prompt to sharpen their role in each channel
  • Use guildId bindings for multi-server isolation
  • Combine with ACP Thread Binding to switch agents within the same channel via threads (see the previous post)

One bot token. Five configuration steps. Channel-level isolation. The routing priority table has four rows — remember it: peer > guildId > accountId > default.

In the rapidly evolving landscape of AI development, context engineering has emerged as one of the most critical disciplines for building effective agent systems. Unlike prompt engineering, which focuses on crafting effective instructions, context engineering addresses the holistic curation of all information entering a model’s limited attention window.

Agent Skills for Context Engineering by Murat Can Koylan is a comprehensive, open-source collection designed to teach the art and science of curating context to maximize agent effectiveness across any platform.

What is Context Engineering?

Section titled “What is Context Engineering?”

Context engineering is the discipline of managing the language model’s context window. The fundamental challenge is that context windows are constrained not by raw token capacity but by attention mechanics.

The Core Problem

Section titled “The Core Problem”

As context length increases, models exhibit predictable degradation patterns:

  • Lost-in-the-Middle Phenomenon - Information in the middle of long contexts gets less attention
  • U-Shaped Attention Curves - Models focus more on beginning and end of context
  • Attention Scarcity - Limited “attention budget” must be allocated wisely

The Solution

Section titled “The Solution”

Effective context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of desired outcomes. This requires understanding what context is, how it degrades, and how to optimize it.

Key Concepts Deep Dive

Section titled “Key Concepts Deep Dive”

1. Context Fundamentals

Section titled “1. Context Fundamentals”

Understanding the anatomy of context in agent systems is essential:

Components of Context:

  • System prompts
  • Tool definitions
  • Retrieved documents
  • Message history
  • Tool outputs

Each component competes for limited attention. Effective agents prioritize high-signal information and compress or eliminate low-signal content.

2. Context Degradation Patterns

Section titled “2. Context Degradation Patterns”

Recognizing failure patterns helps prevent them:

Lost-in-Middle: Critical information placed in the middle of long contexts receives less model attention.

Context Poisoning: Bad or conflicting information corrupts the model’s understanding.

Context Distraction: Irrelevant information diverts attention from important content.

Context Clash: Contradictory instructions or data create confusion.

3. Multi-Agent Patterns

Section titled “3. Multi-Agent Patterns”

Three primary architectures for multi-agent systems:

Orchestrator Pattern: A central agent coordinates specialized sub-agents, managing task delegation and result aggregation.

Peer-to-Peer Pattern: Agents communicate directly without central coordination, suitable for collaborative tasks.

Hierarchical Pattern: Layered agent structures where higher-level agents manage groups of lower-level agents.

4. Memory Systems

Section titled “4. Memory Systems”

Effective agents require multiple memory types:

Short-term Memory:

  • Recent conversation context
  • Current task state
  • Immediate working memory

Long-term Memory:

  • Persistent knowledge stores
  • User preferences
  • Historical patterns

Graph-based Memory:

  • Relationship maps between concepts
  • Entity connections
  • Semantic networks

Recommended Use Scenarios

1. Building Production Agent Systems

Section titled “1. Building Production Agent Systems”

When developing agents for real-world deployment:

  • Start with fundamentals - Understand context anatomy before optimization
  • Design memory early - Memory architecture affects all downstream decisions
  • Plan for degradation - Build in monitoring and recovery mechanisms
  • Test at scale - Evaluation frameworks catch issues before production

2. Optimizing Existing Agents

Section titled “2. Optimizing Existing Agents”

For teams with existing agent systems:

  • Diagnose context issues - Use degradation patterns to identify problems
  • Apply compression strategies - Reduce token usage without losing signal
  • Implement caching - Avoid redundant context loading
  • Add instrumentation - Build visibility into context usage

3. Multi-Agent Architecture Design

Section titled “3. Multi-Agent Architecture Design”

When building systems with multiple coordinating agents:

  • Choose the right pattern - Orchestrator vs peer-to-peer vs hierarchical
  • Design communication protocols - How agents share context
  • Manage shared memory - Coordination without conflicts
  • Handle failures gracefully - Recovery when agents fail

Design Philosophy

Section titled “Design Philosophy”

The collection follows three key principles:

1. Progressive Disclosure

Each skill is structured for efficient context use. At startup, agents load only skill names and descriptions. Full content loads only when a skill is activated for relevant tasks.

2. Platform Agnosticism

These skills focus on transferable principles rather than vendor-specific implementations. The patterns work across Claude Code, Cursor, and any agent platform that supports skills or allows custom instructions.

3. Conceptual Foundation with Practical Examples

Scripts and examples demonstrate concepts using Python pseudocode that works across environments without requiring specific dependency installations.
