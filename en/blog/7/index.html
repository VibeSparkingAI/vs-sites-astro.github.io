Claude Code 2.1.77: Opus 4.6 Gets 128k Output Tokens, Everything Else Gets Fixed

Section titled “Claude Code 2.1.77: Opus 4.6 Gets 128k Output Tokens, Everything Else Gets Fixed”

Opus 4.6 can now output up to 128k tokens in a single response. The default is 64k, four times what most people were working with. That means generating an entire file, a full test suite, or a complete refactor in one shot without hitting the output ceiling.

But the token limit isn’t the real story of 2.1.77. The real story is the 25+ bug fixes underneath it.

The token ceiling

Section titled “The token ceiling”

Increased default maximum output token limits for Opus 4.6 to 64k tokens. The upper bound for both Opus 4.6 and Sonnet 4.6 goes to 128k tokens.

What this means in practice: if you’ve been hitting the output ceiling on large code generation tasks — full module rewrites, comprehensive test suites, detailed architectural documents — you now have room. The default quadruples, and if you push the upper bound, you get eight times what the previous default allowed.

allowRead sandbox setting

Section titled “allowRead sandbox setting”

A new allowRead filesystem setting that re-allows read access within denyRead regions. If you’ve locked down a directory with denyRead but need Claude to read specific files inside it, allowRead lets you punch targeted holes without removing the broader restriction.

/copy N

Section titled “/copy N”

/copy now accepts an optional index. /copy N copies the Nth-latest assistant response. Previously, /copy always grabbed the most recent response. If you wanted an earlier one, you had to scroll and manually select.

Compound bash permissions

Section titled “Compound bash permissions”

“Always Allow” on compound bash commands like cd src && npm test was saving a single permission rule for the full string instead of breaking it into per-subcommand rules. The result: dead rules that never matched again, and repeated permission prompts every time you ran the same compound command.

This was one of those bugs where the workaround (clicking “Allow” every time) trained you to stop noticing the problem. Fixed now — each subcommand gets its own rule.

Auto-updater memory bomb

Section titled “Auto-updater memory bomb”

The auto-updater was starting overlapping binary downloads when the slash-command overlay repeatedly opened and closed. Each open/close cycle could trigger a new download. In long sessions with frequent slash-command usage, this accumulated tens of gigabytes of memory.

If your Claude Code process was ballooning in memory during long sessions, this was likely the cause.

—resume silent truncation

Section titled “—resume silent truncation”

--resume was silently truncating recent conversation history. The root cause: a race between memory-extraction writes and the main transcript. The extraction process and the transcript save were competing for the same data, and the transcript sometimes won before extraction finished, losing recent entries.

This was subtle — you’d resume a session and your latest work would be missing, but there was no error message. Just gone.

Security: PreToolUse hooks bypassing deny rules

Section titled “Security: PreToolUse hooks bypassing deny rules”

PreToolUse hooks returning “allow” were bypassing deny permission rules, including enterprise managed settings. If an enterprise admin denied a specific tool via managed settings, a hook could override that denial by returning “allow.”

This is a security boundary violation. Hooks should be able to add restrictions, not remove them. Fixed — deny rules now take precedence regardless of hook responses.

Write tool CRLF handling

Section titled “Write tool CRLF handling”

The Write tool was silently converting line endings when overwriting CRLF files or creating files in CRLF directories. You’d edit a Windows-style file, and it would come back with Unix line endings. On teams with mixed OS environments, this created unnecessary diffs and merge conflicts.

Memory growth in long sessions

Section titled “Memory growth in long sessions”

Progress messages were surviving compaction in long-running sessions. Every status update accumulated and persisted through compaction cycles, growing memory usage over time. In sessions running for hours, this added up.

Cost tracking with non-streaming fallback

Section titled “Cost tracking with non-streaming fallback”

Cost and token usage were not being tracked when the API fell back to non-streaming mode. If your setup used a proxy or configuration that triggered the non-streaming fallback, your usage numbers were wrong.

CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS

Section titled “CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS”

The CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS flag wasn’t stripping beta tool-schema fields from requests. Proxy gateways with strict schema validation were rejecting these requests because they contained unrecognized fields.

Bash tool and temp directory spaces

Section titled “Bash tool and temp directory spaces”

The Bash tool was reporting errors for successful commands when the system temp directory path contained spaces. The command would execute correctly, but the error reporting code failed to parse the path, generating a false error.

Paste and typing

Section titled “Paste and typing”

Paste was being lost when typing immediately after pasting. The input handler was dropping the paste buffer when a keystroke arrived before the paste was fully processed.

Ctrl+D in /feedback

Section titled “Ctrl+D in /feedback”

Ctrl+D in /feedback text input was deleting forward (like Delete) instead of the second press exiting the session. Standard terminal behavior is: first Ctrl+D at end of line does nothing or signals EOF; second press exits. This was doing something else entirely.

0-byte image drag

Section titled “0-byte image drag”

Dragging a 0-byte image file into the prompt triggered an API error. The handler wasn’t checking for empty files before attempting to process them as images.

Claude Desktop OAuth collision

Section titled “Claude Desktop OAuth collision”

Claude Desktop sessions were incorrectly using the terminal CLI’s configured API key instead of OAuth. If you had both Claude Desktop and the CLI installed with different auth methods, Desktop was grabbing the wrong credentials.

Git subdir plugin cache collision

Section titled “Git subdir plugin cache collision”

Git-subdir plugins at different subdirectories of the same monorepo were colliding in the plugin cache. Two plugins pointing at different directories in the same repo would overwrite each other’s cached state.

Terminal rendering fixes

Section titled “Terminal rendering fixes”

A sweep of terminal rendering fixes:

  • Ordered list numbers not rendering in terminal UI
  • Worktree cleanup race where stale-worktree cleanup could delete an agent worktree just resumed from a previous crash
  • Input deadlock when opening /mcp or similar dialogs while the agent is running
  • Vim mode: Backspace and Delete keys not working in NORMAL mode; status line not updating when vim mode is toggled
  • Hyperlinks opening twice on Cmd+click in VS Code, Cursor, and other xterm.js-based terminals
  • tmux background colors rendering as terminal-default inside tmux with default configuration
  • iTerm2 crash when selecting text inside tmux over SSH
  • Clipboard copy silently failing in tmux sessions; copy toast now indicates whether to paste with Cmd+V or tmux prefix+]
  • Arrow keys accidentally switching tabs in settings, permissions, and sandbox dialogs while navigating lists
  • IDE auto-connect not working when Claude Code is launched inside tmux or screen
  • CJK characters visually bleeding into adjacent UI elements when clipped at the right edge
  • Teammate panes not closing when the leader exits
  • iTerm2 auto mode not detecting iTerm2 for native split-pane teammates

Performance

Section titled “Performance”

Two targeted performance improvements:

  • Faster startup on macOS (~60ms) by reading keychain credentials in parallel with module loading instead of sequentially
  • Faster —resume on fork-heavy and very large sessions — up to 45% faster loading and approximately 100-150MB less peak memory usage

Other improvements

Section titled “Other improvements”
  • Esc now aborts in-flight non-streaming API requests
  • claude plugin validate now checks skill, agent, and command frontmatter plus hooks/hooks.json, catching YAML parse errors and schema violations
  • Background bash tasks are killed if output exceeds 5GB, preventing runaway processes from filling disk
  • Sessions are auto-named from plan content when you accept a plan
  • Headless mode plugin installation now composes correctly with CLAUDE_CODE_PLUGIN_SEED_DIR
  • apiKeyHelper shows a notice when it takes longer than 10s, preventing it from silently blocking startup
  • Agent tool no longer accepts a resume parameter — use SendMessage({to: agentId}) to continue a previously spawned agent
  • SendMessage auto-resumes stopped agents in the background instead of returning an error
  • Renamed /fork to /branch (/fork still works as an alias)
  • [VSCode] Plan preview tab titles now use the plan’s heading instead of “Claude’s Plan”
  • [VSCode] When option+click doesn’t trigger native selection on macOS, the footer now points to the macOptionClickForcesSelection setting

What 2.1.77 signals

Section titled “What 2.1.77 signals”

Three new features, 25+ bug fixes, two performance improvements. The ratio tells the story.

The token ceiling raise is meaningful — 128k output tokens puts Opus 4.6 and Sonnet 4.6 in territory where a single response can contain a complete, production-ready module. That’s a capability shift for code generation workflows.

The security fix matters. Hooks bypassing enterprise deny rules is the kind of bug that erodes trust in managed deployments. It’s fixed, and the fix establishes a clear principle: deny rules are authoritative.

Everything else is the work of a team that reads its bug reports. The auto-updater memory bomb. The resume truncation race. The paste handler. The CRLF conversion. The CJK rendering. The tmux clipboard. Each of these was making someone’s workday worse in a small, specific way. Now they’re fixed.

If you skipped 2.1.76, update. If you’re already on 2.1.76, still update. This release makes the tool more reliable in the ways that matter for daily use.

Root cause: intents:content=limited — the Message Content Intent isn’t active. The bot receives messages but the content field is empty. It can’t detect @mentions in text that doesn’t exist.

OpenClaw v2026.3.13-1: Recovery Release Ships 70+ Fixes Across Agents, Security, Mobile, and Messaging

Mar 17, 2026

OpenClaw v2026.3.13-1: Recovery Release Ships 70+ Fixes

Section titled “OpenClaw v2026.3.13-1: Recovery Release Ships 70+ Fixes”

GitHub won’t let you reuse a published release tag. When v2026.3.13 shipped broken, the team couldn’t just fix and re-push. So they tagged v2026.3.13-1, kept npm at 2026.3.13, and packed 70+ fixes into what became one of the most community-driven releases in the project’s history.

Why v2026.3.13-1?

Section titled “Why v2026.3.13-1?”

The original v2026.3.13 tag and GitHub Release broke. GitHub’s immutable release system prevents overwriting published tags. The solution:

  • Git tag / GitHub Release: v2026.3.13-1
  • npm package version: 2026.3.13 (unchanged)

The -1 suffix exists only for Git and GitHub. If you install via npm, nothing changes.

Agent fixes: the big ones

Section titled “Agent fixes: the big ones”

The agent layer received the most attention this cycle.

Thinking block replay. Anthropic thinking blocks were being replayed incorrectly during agent conversations. Fixed — they’re now dropped on replay (#44843).

Memory file double-injection. On case-insensitive file systems (macOS, Windows), memory files could get injected twice into agent context. Path comparison now handles case folding (#26054).

Session reset preservation. lastAccountId and lastThreadId were getting wiped on session reset. They’re preserved now (#44773). The reset prompt was also reworded to avoid triggering Azure content filters (#43403).

Cross-agent workspace resolution. When an agent spawned a subagent targeting a different agent’s workspace, the target path resolved incorrectly. Fixed (#40176).

Custom provider keys. Blank local API keys for custom providers were getting overwritten during onboarding. They’re preserved now (#45631).

Post-compaction sanity check. The compaction system now uses the full-session token count instead of a partial count for its sanity check (#28347).

Security hardening

Section titled “Security hardening”

Docker token leak. Gateway tokens could leak through the Docker build context. The Dockerfiles now prevent this (#44956). All Dockerfiles also add apt-get upgrade for base image security (#45384).

Control-UI auth. The auth bypass for insecure control-ui connections was accidentally removed. Restored, with proper connect failure classification (#45512).

macOS PortGuard. PortGuard was killing Docker Desktop processes when running in remote mode. It no longer does (#13798).

Shared auth on insecure connects. Shared auth state is now maintained on insecure control-ui connections (#45088).

Gateway token requests. Unanswered client requests are now bounded to prevent resource exhaustion (#45689).

Messaging platform fixes

Section titled “Messaging platform fixes”

How it actually works

Section titled “How it actually works”

The interaction model is push-to-talk. Hold Space to record, release to stop and transcribe. This was a deliberate design decision — no always-on microphone in a terminal, no accidental activations while coding.

A few things that matter:

Input only. Claude responds with text, not audio. Voice is for your prompts, not Claude’s answers. If you want TTS responses, community hooks like claude-code-voice-hooks can add that.

Hybrid input. You can type half a prompt, hold Space to voice the middle section, then keep typing. The two modes coexist. Speak the architecture, type the exact variable names.

Developer vocabulary. The STT model is tuned for code. It handles camelCase, file paths, regex patterns, JSON keys, OAuth, and repo names. You say “getUserById” and it transcribes “getUserById”, not “get user by ID.”

Barge-in. You can interrupt Claude’s response mid-stream by holding Space and speaking.

Free. Voice transcription tokens don’t count against your rate limits.

MCP elicitation

Section titled “MCP elicitation”

This is the headline. Until now, MCP tool calls were strictly request-response: Claude Code sends a request, the server sends back data. If the server needed additional information from you — credentials, a configuration choice, a confirmation — it had no way to ask.

MCP elicitation changes that. An MCP server can now send an elicitation request during a tool call. Claude Code renders it as an interactive dialog: form fields for structured input, or a browser URL for OAuth-style flows. You respond, and the server continues with your answer.

Two new hooks accompany this:

  • Elicitation fires when an MCP server requests input, before the dialog is shown. You can inspect, modify, or auto-respond.
  • ElicitationResult fires after you respond, before the result is sent back to the server. You can override or log what’s being returned.

This matters because it turns MCP tools from passive data sources into interactive collaborators. A database tool can ask which schema to use. A deployment tool can request confirmation before applying changes. An auth tool can redirect you to a login page and wait for the token.

Deferred tools: schema loss after compaction

Section titled “Deferred tools: schema loss after compaction”

If you use ToolSearch to load tools on demand (deferred tools), their input schemas were silently dropped after conversation compaction. Array parameters and number parameters would be rejected with type errors. The tool appeared to work, then stopped working after compaction, with no obvious explanation.

The root cause: compaction serialized tool definitions without preserving their full schemas. The fix ensures schemas survive the round-trip.

If you’ve been hitting unexpected type errors on tools that worked earlier in a session, this was it.

Auto-compaction circuit breaker

Section titled “Auto-compaction circuit breaker”

Auto-compaction was retrying indefinitely after consecutive failures. If compaction failed three times in a row, it would keep trying, burning tokens and time. A circuit breaker now stops after 3 attempts.

Section titled “Session naming”

Pitfall 3: Messages Silently Disappear

Section titled “Pitfall 3: Messages Silently Disappear”

This one took the longest.

Configuration complete, gateway restarted, sent “hi” to the bot. No reply.

Logs showed:

WebSocket was connected. But zero im.message.receive_v1 events arrived.

The debug path:

  1. WebSocket connected — confirmed working
  2. Event log empty — messages weren’t being pushed at all, problem was on Feishu’s side
  3. Changed dmPolicy to open — still no messages
  4. Checked the Feishu developer console carefully — found it

im:message.p2p_msg:readonly was listed as “Not Enabled.”

This permission controls “read messages sent by users to the bot in DMs.” Without it, Feishu filters out the event at the server side. It doesn’t send it to the long connection, doesn’t return an error, doesn’t log a warning. The message just disappears.

Enabled the permission, published a new version, restarted the gateway. Messages started flowing immediately.

The worst part of this issue is the zero feedback. WebSocket is connected, config looks right, but messages vanish without a trace. If Feishu returned something like permission_denied when filtering events, it would save a lot of debugging time.

  • Feishu console: Latest app version published
  • openclaw gateway restart executed

OpenClaw Enterprise Architecture: A CTO's Guide to Multi-Project AI Agent Management

Mar 13, 2026
Vibe Sparking

You’re a CTO. You have five projects, three Slack workspaces, two QQ groups, a Telegram channel, and a dozen engineers who keep asking the same deployment questions. You’ve been thinking about AI agents — not the demo kind, the kind that sits inside your team’s workflow and handles real work.

You spin up OpenClaw. Create one agent. Connect it to Slack. It works. Then someone asks: “Can we get one for Project B too?” And another: “Can it also respond in our QQ group?” Suddenly you’re facing the real question: how do you architect this for an entire engineering organization?

The wrong instinct

Section titled “The wrong instinct”

Most CTOs start the same way. They think in channels. One agent for Slack. One for QQ. One for Telegram. This feels intuitive but it’s wrong. Channels are just doors — entry points for messages. Organizing agents around doors means duplicated logic, inconsistent responses, and a maintenance headache that grows with every new platform you add.

Understanding the real architecture

Section titled “Understanding the real architecture”

OpenClaw has four components that matter:

  • Gateway — The control plane. Routes messages, manages sessions and memory, connects everything.
  • Agents — The brains. Each one is an LLM with its own prompt, tools, and memory.
  • Channels — The doors. Slack, QQ, Telegram, Web, CLI. Just input surfaces.
  • Bindings — The routing rules. They decide which door leads to which brain.

Once you see this separation clearly, the architecture designs itself.

The enterprise blueprint

Section titled “The enterprise blueprint”

For a CTO managing multiple projects with a team of engineers, the recommended pattern is: Platform + Project Isolation + Multi-Channel Access.

Platform Agents handle shared concerns. A DevOps Agent that knows your CI/CD pipelines. A Code Review Agent with your team’s coding standards loaded. A Documentation Agent. These serve everyone, regardless of project.

Project Agents are scoped. Project-carehealth gets an agent loaded with its PRD, codebase structure, and issue tracker. Project-ragLabs gets its own. Each project agent knows its domain deeply and doesn’t leak context to other projects.

Personal Agents serve roles. The CTO Agent generates cross-project daily reports — CI status, code churn, open risks, customer escalations. The PM Agent tracks feature progress. The QA Agent monitors test coverage trends.

One Gateway is enough

Section titled “One Gateway is enough”

For teams under 30 people with fewer than 10 projects: one Gateway. Simpler to operate, agents share tools, configuration is centralized.

You only split to a second Gateway when you need hard isolation — like separating internal team agents from customer-facing service agents. Different data boundaries, different prompt security, different tool permissions.

Channels stay flat, routing gets smart

Section titled “Channels stay flat, routing gets smart”

One Slack channel type. One QQ channel type. One Telegram channel type. Don’t multiply channels by agents.

Use Bindings to route:

  • Mention routing: Type @devops in any channel, message goes to DevOps Agent. Type @project-carehealth, it goes to Project-carehealth Agent.
  • Channel routing: Messages in #project-carehealth automatically go to Project-carehealth Agent. Messages in #devops go to DevOps Agent.

Mention routing is more flexible when multiple agents share a channel. Channel routing is cleaner when teams have dedicated spaces.

Security is not optional

Section titled “Security is not optional”

Enterprise deployment means controlling what agents can do:

  • Tool whitelists per agent. DevOps Agent gets kubectl and terraform. Coding Agent gets repo and PR access. No agent gets shell root.
  • No production deploys from agents. No exceptions.
  • No secret reading. Agents should not access credentials stores directly.
  • Gateway stays off the public internet. More security incidents come from exposed admin panels than from prompt injection.

The Coordinator pattern

Section titled “The Coordinator pattern”

When you’re ready for the next level, add a Coordinator Agent. It sits above the others. When a request comes in that spans multiple domains — “What’s the risk status across all projects?” — the Coordinator decomposes it, dispatches sub-tasks to Project Agents and the DevOps Agent, collects responses, and synthesizes a unified answer.

This is multi-agent orchestration. It turns OpenClaw from a collection of chatbots into an AI-native operations platform.

The CTO Super Agent

Section titled “The CTO Super Agent”

Build yourself a CTO Agent with one command: /cto report. Every morning, it pulls CI status from all projects, checks open blockers, summarizes code review velocity, flags security alerts, and delivers a single digest. No more checking five dashboards.

Section titled “The complete picture”

This is your organization’s AI infrastructure. Treat it like one.

What is BMAD + Quick Dev Flow + YOLO Mode?

Section titled “What is BMAD + Quick Dev Flow + YOLO Mode?”

Three concepts combine to make this workflow possible.

BMAD stands for Business-Module-Architecture-Development. It is a structured development methodology that moves through four phases: define business requirements, design the module boundary, make architecture decisions, then execute development. The key value is that it produces a compact, machine-readable spec that an AI agent can consume without ambiguity.

Quick Dev Flow (/bmad-bmm-quick-dev) is the fast lane within BMAD. It reads the spec, analyzes the existing codebase for patterns and conventions, implements the feature, runs the tests, and fixes failures. One command kicks off the entire pipeline.

YOLO mode tells Claude Code to operate autonomously. No confirmation dialogs. No “should I proceed?” interruptions. It reads, writes, runs commands, and iterates until done.

The combination works because BMAD provides the guardrails — conventions, patterns, architecture constraints — while YOLO removes friction. The agent knows what to build (from the spec) and how to build it (from analyzing your codebase). You just let it run.

5. Test-first validates backend. User-first validates frontend. RSpec caught backend issues before they reached a browser. But frontend issues only surfaced when a human looked at the rendered page. This asymmetry is structural: backend behavior is fully testable through integration specs; frontend behavior depends on visual correctness, component library quirks, and interaction flows that automated tests do not cover well without dedicated E2E suites.

The memory leak

Section titled “The memory leak”

This is the headliner. On the Node.js/npm code path, streaming API response buffers were not released when the generator was terminated early. If you cancelled a generation mid-stream, the buffer stayed allocated. Do that enough times in a long session, and RSS grew without bound.

This is distinct from the native bash parser memory leak fixed in 2.1.72. That one accumulated during command parsing. This one accumulated during response streaming. Both contributed to the same symptom — a process that got heavier over time.

MCP OAuth: two separate problems

Section titled “MCP OAuth: two separate problems”

Port conflict hang. When the OAuth callback port was already in use, authentication would hang indefinitely. No error, no timeout, just a process waiting for a callback that would never arrive. The fix detects the conflict and fails with a clear message.

Token refresh failure. Some OAuth servers (Slack is the notable example) return errors with HTTP 200 status codes. The refresh logic treated any 200 response as success, so when a refresh token expired, it would silently fail to re-authenticate. The fix now inspects the response body, detects the error, and prompts for re-authentication.

If you’ve had MCP integrations that worked for weeks and then quietly stopped, this is probably why.

Click Allow. A few minutes later, it pops up again. And again. Close the window, reopen, still there.

This isn’t a bug.

Why the prompt appears

Section titled “Why the prompt appears”

OpenClaw has a device pairing mechanism. The rule is straightforward:

  • 127.0.0.1 / localhost → local loopback, trusted, no prompt
  • Everything else → external device, pairing required

Two Macs on the same LAN have IPs like 192.168.x.x. To the Gateway, that’s indistinguishable from a random machine on the internet — not localhost, so pairing kicks in.

Multiple GitHub issues confirm this behavior: non-localhost connections always trigger pairing. There’s no “same subnet = auto-trust” logic.

Why it keeps coming back after clicking Allow

Section titled “Why it keeps coming back after clicking Allow”

Common reasons:

  1. Device identity changed. Gateway token rotation, network switch, macOS update — any of these can alter the node’s device fingerprint. Changed fingerprint means the Gateway sees a new device or a device needing repair, retriggering pairing.
  2. Pending repair not cleared. When a device is stuck in “awaiting repair confirmation,” the UI Allow button doesn’t always resolve it fully. Many scenarios require CLI approval.
  3. Token churn loop. Recent macOS reports show tokens refreshing repeatedly, causing a pairing-required cycle.

The UI Allow button sometimes grants temporary passage without completing the full device lifecycle.

Run these on the Mac acting as Gateway:

Step 1: List devices and pending requests

Find entries with pending repair or pending pairing status. Note the requestId.

You can use reject instead of approve — the point is to clear the pending state. Don’t leave it hanging.

If pending isn’t cleared, the remove in step 4 will fail.

Step 3: Get the real device ID

Section titled “Step 3: Get the real device ID”

Output is JSON with each device’s hex device ID. The remove command needs this ID, not the display name (e.g., “FENG’s MacBook Pro”).

Step 4: Remove the device

  • The UI Allow button isn’t equivalent to CLI approve in all scenarios. When the prompt loops, go straight to CLI.

Bottom line

Section titled “Bottom line”

You can’t fix this by “turning off the prompt.” You need to clear pending repairs and remove stale paired devices. Otherwise it comes back. The simplest path: skip LAN cross-connection entirely, use localhost on each Mac.

Two plugins, one bridge: sliverp/qqbot vs tencent-connect/openclaw-qqbot

Vibe Sparking

Search GitHub for “QQ Bot OpenClaw plugin” and you get two results that look almost identical. Same feature tables. Same demo screenshots. Same QQ group invite code.

Behind the parallel READMEs is a story about how open source works in China’s developer ecosystem.

The two repos

Section titled “The two repos”

sliverp/qqbot — the community version. Built by a developer named sliverp. 241 commits, version 1.5.4. MIT license. Package name: @sliverp/qqbot.

tencent-connect/openclaw-qqbot — the official version under Tencent Connect. 299 commits, version 1.5.7. MIT license. Package name: @tencent-connect/openclaw-qqbot.

Both connect OpenClaw to QQ. Both handle private chat, group @messages, channel messages, rich media (images, voice, video, files up to 20MB), STT/TTS, scheduled push, typing indicators, Markdown, and multi-account bots.

The shared features make sense once you realize the official version forked from the community one.

Where they diverge

Section titled “Where they diverge”

The differences tell you about each project’s priorities.

sliverp/qqbot adds developer tooling

Section titled “sliverp/qqbot adds developer tooling”
  • GitHub Actions E2E test workflow — automated testing baked into CI
  • CLI plugin management tool (bin/ directory)
  • Lean README: features, config, done

This is a project built by someone who ships fast and tests properly. The E2E pipeline and CLI tooling suggest a developer who plans to maintain this long-term.

tencent-connect/openclaw-qqbot adds production hardening

Section titled “tencent-connect/openclaw-qqbot adds production hardening”
  • Quoted message context — When a user quotes a previous message in QQ, the platform sends only a cryptic REFIDX_xxx key. The official plugin resolves these from a persistent local store (~/.openclaw/qqbot/data/ref-index.jsonl) and injects the full quoted body into AI context. The AI actually understands what the user is replying to.
  • Remote one-liner install — curl | bash with --appid and --secret flags. Zero-clone setup.
  • 30+ tag variant auto-correction — Write <qq-img> instead of <qqimg> and it still works.
  • Upload dedup caching — Same file sent twice doesn’t get uploaded twice.
  • Ordered queue delivery — Messages arrive in sequence.
  • Dedicated upgrade guide and structured changelogs in both English and Chinese.

These are features born from supporting a larger user base. The quoted context feature alone changes the conversation quality for group chats where users frequently reply to specific messages.

Section titled “The pattern worth noticing”

The community version validated the demand. sliverp built the first bridge, proved it works, attracted users. The official version inherited that momentum and added enterprise polish.

  • You prefer a leaner package
