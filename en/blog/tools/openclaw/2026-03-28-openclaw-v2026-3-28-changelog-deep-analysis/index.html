1.1 Qwen Portal OAuth Removal (#52709)

Section titled “1.1 Qwen Portal OAuth Removal (#52709)”

Background: Qwen (Tongyi Qianwen) previously integrated with portal.qwen.ai via qwen-portal-auth OAuth — an early authentication method. Alibaba Cloud has since unified the Qwen API under the Model Studio platform, and the old OAuth flow is no longer maintained.

Use Case: Users running Qwen series models (qwen-turbo, qwen-plus, qwen-max, etc.) as OpenClaw inference backends.

Example: Previously, selecting Qwen during openclaw onboard would launch a browser-based OAuth authorization flow. Now it requires a direct Model Studio API Key input:

Notes:

  • ⚠️ Breaking — Existing Qwen users must reconfigure authentication after upgrading
  • You’ll need to obtain an API Key from dashscope.console.aliyun.com first
  • If any cluster instances use Qwen, prepare new keys before upgrading

Comparison with Similar Products:

ProductQwen SupportAuth Method
OpenClaw✅ Model Studio API KeyAPI Key
ZeroClaw✅ Via OpenRouter/direct configAPI Key
Nanobot✅ Native supportAPI Key
NanoClaw❌ No direct supportN/A
PicoClaw❌ NoneN/A
IronClaw✅ Via configAPI Key + encrypted storage

Trend: LLM providers standardizing on API Key authentication is the clear direction — OAuth flows are too heavyweight for CLI tools.

1.2 Doctor Auto-Migration Window Tightened

Section titled “1.2 Doctor Auto-Migration Window Tightened”

Background: openclaw doctor previously auto-fixed legacy config keys of any age. Now it only auto-migrates keys from within the last two months; older ones trigger an error instead.

Use Case: OpenClaw instances that haven’t been upgraded for a long time running openclaw doctor.

Example: If an instance hasn’t been upgraded for 3 months and its config contains old-format keys from late 2025, doctor will no longer silently fix them — it will report a validation error requiring manual intervention.

Notes:

  • ⚠️ Cluster instances may trigger this if they’ve been dormant for a while
  • Recommended: run openclaw doctor on the current version before upgrading to ensure config is up to date

Comparison: Most similar products are too new to have config migration issues. ZeroClaw has zeroclaw migrate openclaw but that’s a one-time import, not continuous migration.

Trend: A sound engineering decision — unlimited backward compatibility accumulates technical debt.

2. Providers & Models

Section titled “2. Providers & Models”

2.1 xAI / Grok: Responses API + x_search (#56048)

Section titled “2.1 xAI / Grok: Responses API + x_search (#56048)”

Background: xAI (Elon Musk’s AI company) launched their Responses API (similar to OpenAI’s Responses API), along with x_search — a tool that can search X/Twitter real-time data. Previously, OpenClaw used xAI’s older Chat Completions API.

Use Case:

  • Grok models now automatically gain x_search capability
  • Search real-time trends, tweets, and public sentiment
  • Example: Ask “What are people discussing about AI Agents on X today?” → Grok uses x_search to pull real-time tweets

Notes:

  • The xAI plugin now auto-enables from web-search and tool config — no manual plugin activation needed
  • openclaw onboard and openclaw configure --section web now include x_search configuration options
  • x_search uses the shared xAI key — no additional API key required

Comparison with Similar Products:

ProductxAI/Grokx_searchAuto Plugin Enable
OpenClaw✅ Responses API✅ Native✅
ZeroClaw✅ Via traits❌ Manual❌
Nanobot✅ Basic support❌❌
IronClaw✅Unknown❌

Trend: Provider-specific tools (x_search, Gemini’s Google Search) are proliferating. Runtimes need to auto-discover and enable these tools rather than requiring manual configuration. OpenClaw is ahead here.

2.2 MiniMax Image Generation + Model Cleanup (#54487)

Section titled “2.2 MiniMax Image Generation + Model Cleanup (#54487)”

Background: MiniMax is a Chinese AI company that launched the image-01 image generation model. Simultaneously, old models were cleaned up, retaining only M2.7.

Use Case:

  • Text-to-image: generate mode with aspect ratio control
  • Image-to-image: image-to-image editing mode
  • Example: Say “Generate a cyberpunk-style cat” in chat → calls MiniMax image-01

Notes:

  • Old models M2, M2.1, M2.5, VL-01 have been removed — instances configured with these models need updating
  • Domestic API access may require specific network configuration

Comparison: Most similar products don’t natively support image generation providers, relying on users to configure MCP or external tools. OpenClaw pushes further on multimodal support.

Trend: Agents aren’t just text interaction anymore — image generation/understanding is becoming a standard capability.

2.3 OpenAI apply_patch Enabled by Default

Section titled “2.3 OpenAI apply_patch Enabled by Default”

Background: apply_patch is OpenAI Codex’s code editing tool, previously requiring manual activation.

Use Case: Now available by default when using OpenAI or Codex models for code editing tasks.

Notes:

  • Sandbox policy aligned with write permissions — apply_patch permissions match file write permissions
  • Good news for ACP tasks using Codex in our cluster

Comparison: ZeroClaw and IronClaw haven’t implemented apply_patch yet. NanoClaw handles code editing inside containers due to its container isolation approach.

2.4 Mistral Request Standardization Fix

Section titled “2.4 Mistral Request Standardization Fix”

Background: Subtle differences between Mistral’s official API and OpenAI-compatible API request formats were causing 422 errors.

Use Case: Users connecting directly to Mistral’s official API (not via OpenRouter relay).

Notes: If you previously abandoned Mistral direct connection due to 422 errors, it’s worth trying again.

2.5 Google/Gemini Model Resolution Fix (#56567)

Section titled “2.5 Google/Gemini Model Resolution Fix (#56567)”

Background: Gemini 3.1’s pro/flash/flash-lite variants failed to resolve under different provider aliases, and flash-lite had prefix-matching order issues.

Use Case: Users configured with Google AI Studio, Vertex AI, or other Gemini provider aliases.

Notes: Fixed provider ID passthrough issues and added template-provider fallback. If Gemini flash-lite model switching wasn’t working before, it should be fine now.

2.6 Ollama thinking=off Fix (#53200)

Section titled “2.6 Ollama thinking=off Fix (#53200)”

Background: When thinkingLevel=off was set, Ollama models would still generate hidden reasoning tokens in the background, wasting compute and adding latency.

Use Case: Locally deployed Ollama running thinking-capable models (e.g., DeepSeek-R1, QwQ) where reasoning isn’t needed.

Notes: The fix now sends the think: false parameter. Important for resource-constrained devices — avoids unnecessary reasoning tokens.

Comparison: PicoClaw and ZeroClaw both support Ollama, but their thinking parameter control granularity doesn’t match OpenClaw’s.

2.7 Anthropic Stop Reason Handling (#56639)

Section titled “2.7 Anthropic Stop Reason Handling (#56639)”

Background: The Anthropic API sometimes returns non-standard stop reasons (e.g., sensitive — content safety block), which previously caused OpenClaw to crash.

Use Case: Any scenario using Claude models, especially when touching sensitive topics.

Notes: Now returned as a structured error instead of a crash. Important for cluster stability.

2.8 OpenAI Codex Image Tool Fix (#54829)

Section titled “2.8 OpenAI Codex Image Tool Fix (#54829)”

Background: Codex models were missing media-understanding provider registration, causing image analysis to fail.

Use Case: Using ACP to have Codex analyze screenshots, UI images, etc.

Notes: Also fixed generic image-runtime fallback (#54858), affecting third-party providers like OpenRouter and MiniMax Portal.

2.9 OpenAI WebSocket Reasoning Preservation (#53856)

Section titled “2.9 OpenAI WebSocket Reasoning Preservation (#53856)”

Background: In WebSocket mode, tool turns would lose reasoning replay metadata and tool-call item IDs, causing subsequent reasoning to break.

Use Case: Real-time interaction scenarios using OpenAI Responses API + WebSocket.

Notes: Two fixes (reasoning blocks restored + metadata kept intact) suggest this was a deep-seated issue.

2.10 GitHub Copilot Auth Refresh (#55360)

Section titled “2.10 GitHub Copilot Auth Refresh (#55360)”

Background: The expires_at value was treated as milliseconds when it was actually a seconds-level epoch, causing setTimeout to overflow and enter an infinite hot loop.

Use Case: Users running GitHub Copilot as a provider.

Notes: This was a performance bug — it would max out CPU. If you previously experienced system sluggishness after configuring Copilot, this was the cause.

2.11 Agent Model-Level Rate Limit Isolation (#49834)

Section titled “2.11 Agent Model-Level Rate Limit Isolation (#49834)”

Background: Previously, one model hitting 429 would block all models under the same auth profile.

Use Case: Configurations with multiple model fallbacks (e.g., Claude → GPT → Gemini).

Example: Claude hits 429, GPT should continue working, but previously the entire profile got cooled down.

Notes:

  • Cooldown strategy changed from exponential (1min → 1h) to stepped (30s / 1min / 5min) — more reasonable
  • New user-visible countdown messages
  • Important for heavily-used cluster instances

2.12 Codex Failover Improvements (#55206, #42892)

Section titled “2.12 Codex Failover Improvements (#55206, #42892)”
