Claude Code 2.1.81: —bare Mode, Mobile Approvals, and YOLO Mode

Section titled “Claude Code 2.1.81: —bare Mode, Mobile Approvals, and YOLO Mode”

2.1.81 doesn’t have any big features—just two noteworthy new flags and a pile of fixes for bugs that quietly bite you in ways you can never quite pin down. Read through each one and you’ll realize this release targets the hardest-to-notice friction in the toolchain.

Two New Flags

Section titled “Two New Flags”

--bare: Scripting Mode, Zero Overhead

Section titled “--bare: Scripting Mode, Zero Overhead”

You’re calling Claude Code with -p in CI or batch scripts, but every time you have to wait for hooks, LSP, plugin sync, and skill directory scanning. All of that makes sense in interactive mode; in an automation pipeline it’s pure waste.

--bare skips all of it:

A few conditions apply: you must provide your key via ANTHROPIC_API_KEY or apiKeyHelper in --settings—OAuth and keychain auth are unavailable in this mode. Auto-memory is also completely disabled.

The use cases are clear-cut: production pipelines, cron jobs, bulk code reviews. Anywhere you don’t need a persistent session, use --bare.

--channels: Tool Approvals Forwarded to Your Phone

Section titled “--channels: Tool Approvals Forwarded to Your Phone”

This feature requires a channel server that supports the permission capability. When that’s in place, Claude’s approval prompts for tool execution no longer block the terminal—they get sent to your phone instead.

You’re in a meeting, away from your desk, and the agent hits a step that needs confirmation. It pops up on your phone; one tap and it continues. No need to walk back to your desk.

For anyone who needs to remotely supervise an agent, this beats everything else.

Bug Fixes: A Dozen Hard-to-Explain Issues

Section titled “Bug Fixes: A Dozen Hard-to-Explain Issues”

Multi-Session OAuth Re-authentication

Section titled “Multi-Session OAuth Re-authentication”

When multiple Claude Code sessions are running simultaneously and one refreshes the OAuth token, the others would be forced to re-authenticate. Now token refreshes no longer affect other sessions.

Running multiple sessions at once is a normal workflow, and this bug would constantly interrupt you in exactly that scenario.

Two Silent Failures in Voice Mode

Section titled “Two Silent Failures in Voice Mode”
  • Retry failures would swallow the error and only show “check your network connection”—now the actual error is displayed.
  • After the server silently dropped a WebSocket connection, audio wouldn’t recover—now it automatically reconnects.

Silent failures are the hardest bugs to debug. You think it’s a network issue when really the tool is lying to you.

CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS Not Working

Section titled “CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS Not Working”

Even with this environment variable set, the structured-outputs beta header was still being sent. Proxy gateways forwarding to Vertex or Bedrock would return 400 because of it.

People actually using this variable had been getting proxy errors without knowing why. Fixed now.

Hyphens in Bash Command Strings Triggering Permission Prompts

Section titled “Hyphens in Bash Command Strings Triggering Permission Prompts”

String arguments containing hyphens (-) in commands would incorrectly trigger permission prompts. A command that should have run silently would instead require manual confirmation. These false alarms erode trust in the tool. Fixed.

Plugin Directory Deleted Mid-Session Causing Blocks

Section titled “Plugin Directory Deleted Mid-Session Causing Blocks”

If the plugin directory got deleted during a session, all subsequent submissions would hang. Plugin hooks no longer block prompt submission.

Race Condition in Background Task Output

Section titled “Race Condition in Background Task Output”

When a background agent task completed between two polling intervals, the output would hang forever. Fixed.

Worktree Session Restoration

Section titled “Worktree Session Restoration”

Restoring a session that was in a worktree now automatically switches back to that worktree. Previously it wouldn’t, and you’d have to cd manually.

/btw Dropping Pasted Content

Section titled “/btw Dropping Pasted Content”

Using /btw during an active response would fail to include the pasted text. Fixed.

Clipboard Race Condition in tmux

Section titled “Clipboard Race Condition in tmux”

Quickly Cmd+Tabbing and then pasting would sometimes paste stale content. The clipboard copy in tmux hadn’t finished before it was read. Fixed.

Several Remote Control Fixes

Section titled “Several Remote Control Fixes”
  • Session titles were always generic names—now they’re derived from the first prompt.
  • /rename didn’t sync the title for Remote Control sessions—now it does.
  • /exit couldn’t reliably archive sessions—now it can.
  • Titles auto-refresh after the third message.

Other

Section titled “Other”
  • Terminal tab titles not updating—fixed.
  • Invisible hook attachments inflating the message count in transcript mode—fixed.

A Few Improvements

Section titled “A Few Improvements”

MCP tool calls collapsed into a single line. Read/search calls used to expand every time; now they’re merged into “Queried {server}”, expandable with Ctrl+O. Cuts down on visual noise quite a bit.

! bash mode is more discoverable. When you need to run an interactive command, Claude now proactively mentions this mode exists. No more digging through docs.

Ref-tracked plugins re-clone on every load. Ensures you get the latest version, not a stale cache.

Plan mode hides the “clear context” option by default. To bring it back, add "showClearContextOnPlanAccept": true.

MCP OAuth supports CIMD / SEP-991. For servers without Dynamic Client Registration, you can now use Client ID Metadata Document for OAuth.

Windows (including WSL in Windows Terminal) disables line-by-line streaming output. Due to rendering issues. WSL in Windows Terminal is also affected.

[VSCode] Windows PATH inheritance fix. The PATH inheritance for the Bash tool when using Git Bash had a regression in v2.1.78—now fixed.

The Last Two Words

Section titled “The Last Two Words”

YOLO mode.

As always.

Claude Code 2.1.80: —channels Lets MCP Servers Push Messages Into Your Session

Section titled “Claude Code 2.1.80: —channels Lets MCP Servers Push Messages Into Your Session”

A Claude Code session has always been a conversation: you talk, the agent responds. MCP servers extended that — the agent could call external tools. But information only flowed one way, outward. The agent asked questions; servers answered them.

2.1.80 opens the reverse channel. --channels (research preview) lets MCP servers push messages into your running session. The tool that could only speak when spoken to just learned to raise its hand.

At a glance

The channel opens both ways

Section titled “The channel opens both ways”

MCP has been a one-way street. Your agent calls a tool, the server responds. That’s it. If something happens on the server side — a CI build fails, a deployment completes, a test suite finishes — the server has no way to tell the agent. You have to ask.

--channels changes this. An MCP server can now push a message into your active session without waiting to be called. Think about what that enables:

A deployment monitor MCP server watching your staging environment. Your agent is writing code. The deploy fails. The server pushes “deploy failed: missing env var DATABASE_URL on staging” directly into the session. The agent sees it, checks the config, fixes it.

A test runner MCP server that pushes results as they complete. Your agent doesn’t have to poll. It gets notified.

A team communication MCP server that pushes relevant Slack messages or PR review comments into your coding session.

This is a research preview, meaning the API surface may change. But the direction is clear: MCP is becoming a bidirectional messaging layer, not just a tool-calling protocol.

Skills learn to set their own pace

Section titled “Skills learn to set their own pace”

effort frontmatter in skills and slash commands lets the skill author override the model’s effort level when the skill is invoked.

Before this, effort was a global setting. You’d set it high for complex work, low for quick tasks, and toggle back and forth. Now the skill decides. A code formatting command runs at minimal effort because it doesn’t need deep reasoning. An architecture review skill demands maximum effort because shortcuts produce bad analysis.

This is a small YAML field with outsized impact. Skill authors can now design for the right level of reasoning rather than hoping the user has their effort setting dialed correctly.

Rate limits, visible

Section titled “Rate limits, visible”

rate_limits is a new field available to statusline scripts. It exposes Claude.ai’s 5-hour and 7-day usage windows with used_percentage and resets_at.

If you’ve ever been surprised by hitting a rate limit mid-task, this is the fix. Your statusline can now show something like “73% of 5h limit used, resets in 2h”. No more guessing.

This only applies to Claude.ai billing. API users with their own keys have different limits.

Plugins, declared inline

Section titled “Plugins, declared inline”

source: 'settings' is a new plugin marketplace source that lets you declare plugin entries directly in settings.json. No registry lookup, no install step. Write the plugin definition in your settings file, it’s loaded.

For teams that distribute internal plugins, this simplifies distribution. Push the settings.json change, everyone gets the plugin.

Combined with CLI tool usage detection for plugin tips (alongside existing file pattern matching), the plugin discovery story is getting smarter. Claude Code can now suggest plugins based on what CLI tools you’re running, not just what files exist in your project.

The resume fix that matters more than it sounds

Section titled “The resume fix that matters more than it sounds”

--resume was dropping parallel tool results. If your previous session had parallel tool calls, resuming it would show [Tool result missing] placeholders instead of the actual results.

This is worse than it sounds. Parallel tool calls are common in complex sessions — the agent reads multiple files at once, runs tests in parallel, searches across directories simultaneously. Losing those results on resume meant the agent lost context about what it had already done. It would re-read files, re-run searches, or worse, make decisions based on incomplete information.

Fixed. All tool_use/tool_result pairs now restore correctly.

Voice mode and API fixes

Section titled “Voice mode and API fixes”

Voice mode WebSocket connections were failing because Cloudflare’s bot detection was rejecting non-browser TLS fingerprints. Claude Code’s WebSocket client doesn’t look like a browser, so Cloudflare flagged it. Fixed by adjusting the TLS fingerprint handling.

Fine-grained tool streaming was returning 400 errors when used through API proxies, Bedrock, or Vertex. If you’re running Claude Code through enterprise infrastructure, this was likely hitting you. Fixed.

/remote-control was appearing in the command list for gateway and third-party provider deployments where it can’t actually function. Removed from those contexts.

Performance: 80MB lighter on large repos

Section titled “Performance: 80MB lighter on large repos”

Startup memory usage dropped by approximately 80MB on repositories with around 250,000 files. That’s a meaningful reduction. On a machine with 16GB of RAM running multiple Claude Code instances across different repos, this gives back roughly half a gigabyte.

The @ file autocomplete in large git repositories is also more responsive now. In repos with tens of thousands of files, there was a noticeable delay when typing @ to reference a file. Reduced.

UI polish

Section titled “UI polish”

Several navigation and display improvements:

/effort now shows what “auto” currently resolves to, matching the status bar indicator. Before, selecting “auto” gave you no feedback about what effort level was actually being used.

/permissions gained proper Tab and arrow key navigation within lists. Combined with the Tab/arrow fix for /sandbox, keyboard-driven navigation is now consistent across settings panels.

The background tasks panel responds to left arrow to close from the list view.

Plugin install tips simplified from a two-step flow to a single /plugin install command.

The settings fix you didn’t know you needed

Section titled “The settings fix you didn’t know you needed”

Managed settings — enabledPlugins, permissions.defaultMode, and policy-set environment variables — weren’t being applied at startup when remote-settings.json was cached from a prior session. If your organization manages Claude Code settings centrally, this meant fresh sessions could start with stale configuration.

This is the kind of bug that’s hard to diagnose because it’s intermittent. It only happens when the cached settings are different from the current ones. Fixed.

What this release signals

Section titled “What this release signals”

--channels is a research preview, but research previews in Claude Code have a track record of becoming stable features within a few releases. The fact that it shipped means the underlying architecture is ready.

The pattern across 2.1.80 is Claude Code becoming infrastructure rather than just a tool. Channels make it a message bus. Effort frontmatter makes skills self-describing. Rate limit visibility makes it observable. Inline plugin declarations make it configurable without external dependencies.

Each of these alone is a nice improvement. Together, they’re building blocks for something that looks less like a CLI and more like a development platform.

Update with claude update. If you build MCP servers, --channels is worth experimenting with now. If you write skills, add effort frontmatter. If you’ve been flying blind on rate limits, configure your statusline.

Discord or Feishu? Platform Choice for Autonomous Coding with OpenClaw ACP and YOLO Mode

Mar 20, 2026
Vibe Sparking

Same AI model. Same codebase. Same OpenClaw configuration. I type a task description into Discord, and Claude Code runs autonomously for 40 minutes --- reading files, writing code, running tests, committing changes. I type the same task into Feishu, and it executes once then goes silent. No follow-up. No threading. No session.

The difference is not the model. It is the chat platform’s architecture.

The Platform Comparison

Section titled “The Platform Comparison”

I spent a week running identical ACP workflows on both platforms. Here is what actually works:

FeatureDiscordFeishu
mode=run single-shotSupportedSupported
Thread binding (persistent sessions)SupportedNot supported
Slash commands (/acp spawn, /acp status)WorkError: “Thread bindings unavailable for feishu”
Channel-level agent routingNative (peer binding)Works but confusing UX
Multiple agents on one BotNatural (channel separation)Awkward (same group chat)
YOLO mode compatibilityFull (thread = isolated context)Partial (run mode only)

The single-shot row looks identical. Everything below it diverges.

Why YOLO Mode Is Not Optional

Section titled “Why YOLO Mode Is Not Optional”

Before comparing platforms, I need to address the elephant in the room. Claude Code in its normal interactive mode asks for permission constantly. Edit this file? Run this shell command? Install this package? In a terminal session, you tap y and move on. From a chat message, there is no terminal. There is no interactive TUI. There is nobody sitting there to approve.

I measured it during a typical refactoring session: roughly 100 permission prompts per hour. That is almost two per minute. From a chat platform, each one would be a dead end.

--dangerously-skip-permissions --- what the community calls YOLO mode --- is not a shortcut for lazy developers. It is an architectural prerequisite. OpenClaw’s acpx spawns Claude Code as a subprocess. That subprocess must run unattended. If it stops to ask permission, the chat session hangs with no way to respond.

The actual flag is --permission-mode bypassPermissions. In your agent config:

Without this flag, ACP does not function. Not “works poorly” --- does not function. Every autonomous coding workflow through every chat platform requires it.

Safety Guardrails That Actually Work

Section titled “Safety Guardrails That Actually Work”

Running with bypassed permissions sounds reckless. It is not, if you layer the right constraints.

Docker containers. Run the agent workspace inside a container. The worst case is a trashed container, not a trashed host. OpenClaw’s workspace config supports container isolation natively.

Git as rollback. Every task starts from a clean commit. If the agent produces garbage, git reset --hard takes you back. This is not theoretical safety --- I use it weekly.

Hooks still fire. This is the critical detail most people miss. PreToolUse hooks execute even in bypass mode. You can block specific operations:

The hook script can inspect the command and return a non-zero exit code to block it. Bypass mode skips the interactive permission prompt. It does not skip hooks.

--disallowedTools works in bypass mode. If the agent should never touch the database directly:

Bounded tasks. “Refactor the auth module to use JWT” works. “Make the codebase better” does not. Specificity is a safety mechanism.

Discord’s Architecture Advantage

Section titled “Discord’s Architecture Advantage”

Discord was built for persistent, threaded conversations inside channel-scoped contexts. This maps perfectly onto autonomous coding sessions.

Channels are isolation boundaries. One bot token, three channels, three different agents. #backend runs a Python specialist. #frontend runs a React expert. #infra runs a Terraform agent. Each channel has its own peer binding in openclaw.json. Users interact with the right agent without thinking about routing.

Threads are coding sessions. When you /acp spawn in a Discord channel, OpenClaw creates a thread. That thread becomes an isolated context for the agent. All messages in the thread feed into the same Claude Code session. The agent can report progress, ask clarifying questions, and receive follow-up instructions --- all within the thread.

A typical 40-minute session looks like this:

  1. User types /acp spawn with a task description
  2. OpenClaw creates a thread, starts Claude Code with YOLO mode
  3. Claude Code reads files, plans changes, starts coding
  4. Progress messages appear in the thread every few minutes
  5. User notices something in the output, sends a correction in the thread
  6. Claude Code picks up the correction and adjusts
  7. Task completes, changes are committed

That step 5 is the key. It is not fire-and-forget. It is supervised autonomy. The thread is the supervision channel.

resumeSessionId for context chaining. When a session ends, OpenClaw stores the session ID. Starting a new task in the same thread can resume from where the previous session left off. The agent remembers what it already did.

This only works because Discord threads persist. The thread ID is the anchor.

Feishu’s Limitations

Section titled “Feishu’s Limitations”

Feishu is excellent team communication software. It is not built for persistent agent sessions.

Thread binding is not implemented. When I tried /acp spawn in a Feishu group chat, the error was immediate:

No workaround. The Feishu channel plugin in OpenClaw does not support thread creation or thread-scoped message routing. Every message lands in the flat group chat timeline.

No slash commands in group chats. Feishu’s bot command model does not map cleanly to OpenClaw’s ACP command structure. The /acp prefix either does not register or conflicts with Feishu’s own command handling. What works on Discord out of the box requires custom message parsing on Feishu.

Only mode: "run" works. You can send a message, OpenClaw dispatches it to Claude Code, Claude Code runs once, and the response comes back. Single request, single response. No session persistence. No follow-up in context. Every message is a fresh conversation.

This is still useful. “Generate a utility function that validates email addresses” works fine as a single-shot task. “Refactor the authentication module across 12 files” does not --- that needs iterative context.

groupPolicy allowlist drops messages silently. This one burned an hour of debugging. Feishu defaults to groupPolicy: "allowlist". If your group chat is not explicitly on the list, messages arrive at OpenClaw and get dropped. No error. No log. Nothing. The bot appears to ignore you.

This fixes it, but the silent failure mode is hostile to anyone setting things up for the first time.

Section titled “The Real-World Decision”

I run both platforms simultaneously. Here is how I split the work:

Discord handles autonomous workflows. Multi-file refactoring. Feature implementation. Test generation. Bug investigation. Anything that takes more than one Claude Code turn. The thread-based session model means I can start a task, check back in 20 minutes, course-correct if needed, and let it continue.

Feishu handles task-driven single-shot execution. Quick code generation. Documentation lookups. Configuration file generation. One question, one answer. These work perfectly within Feishu’s message model, and the team is already there --- no need to move them to Discord for simple tasks.

The choice is not “which platform is better.” It is “which platform fits the task shape.”

If your team lives in Feishu and your tasks are bounded single-shot operations, Feishu works. You do not need Discord. Set up mode: "run", configure groupPolicy, and you have an AI coding assistant in your existing team chat.

Section titled “5 Agent Skill Design Patterns Every ADK Developer Should Know”

The Format War Is Over

Section titled “The Format War Is Over”

Thirty agent tools now read the same file format. Claude Code, Gemini CLI, Cursor, and more — they all parse the same SKILL.md layout with YAML frontmatter, the same directory structure, the same spec.

So why do most skills still break in production?

Because developers fixate on getting the YAML right and structuring directories. The formatting problem is solved. The challenge now is content design. The spec explains how to package a skill, but offers zero guidance on how to structure the logic inside it.

A skill that wraps FastAPI conventions operates completely differently from a four-step documentation pipeline, even though their SKILL.md files look identical on the outside. Same frontmatter. Same directories. Different reliability.

By studying how skills are built across the ecosystem — from Anthropic’s repositories to Vercel and Google’s internal guidelines — five recurring design patterns emerge. Each one answers a different architectural question. Each one comes with working ADK code.

Pattern 1: The Tool Wrapper

Section titled “Pattern 1: The Tool Wrapper”

A Tool Wrapper gives your agent on-demand context for a specific library. Instead of hardcoding API conventions into your system prompt, you package them into a skill. Your agent only loads this context when it actually works with that technology.

It’s the simplest pattern. The SKILL.md file listens for specific library keywords in the user’s prompt, dynamically loads your internal documentation from the references/ directory, and applies those rules as ground truth. This is how you distribute team coding guidelines or framework best practices directly into developer workflows.

When to use it: Your task needs context injection for a specific library, framework, or internal standard.

Pattern 2: The Generator

Section titled “Pattern 2: The Generator”

While the Tool Wrapper applies knowledge, the Generator enforces consistent output. If your agent generates different document structures on every run, the Generator solves this by orchestrating a fill-in-the-blank process.

It uses two optional directories: assets/ holds your output template, and references/ holds your style guide. The instructions act as a project manager — they tell the agent to load the template, read the style guide, ask the user for missing variables, and populate the document.

When to use it: You need consistent, predictable output — API docs, commit messages, project scaffolds.

Pattern 3: The Reviewer

Section titled “Pattern 3: The Reviewer”

The Reviewer separates what to check from how to check it. Rather than writing a long system prompt detailing every code smell, you store a modular rubric inside references/review-checklist.md.

When code arrives, the agent loads the checklist and scores methodically, grouping findings by severity. Swap out a Python style checklist for an OWASP security checklist, and you get a completely different audit using the same skill infrastructure.

When to use it: You need quality scoring against a checklist — PR reviews, security audits, compliance checks.

Pattern 4: Inversion

Section titled “Pattern 4: Inversion”

Agents want to guess and generate immediately. Inversion flips this. Instead of the user driving the prompt and the agent executing, the agent interviews the user first.

The key mechanism is explicit, non-negotiable gating instructions: “DO NOT start building until all phases are complete.” The agent asks structured questions sequentially, waits for answers, and refuses to synthesize output until it has a complete picture.

When to use it: You need thorough requirements gathering before any action — project planning, architecture design, onboarding flows.

Pattern 5: The Pipeline

Section titled “Pattern 5: The Pipeline”

For complex tasks, you cannot afford skipped steps. The Pipeline enforces a strict, sequential workflow with hard checkpoints.

Instructions serve as the workflow definition. Diamond gate conditions (like requiring user approval before advancing) ensure the agent cannot bypass steps or present unvalidated results. Different reference files load only at the step where they’re needed, keeping the context window clean.

When to use it: Complex multi-step tasks where order matters and validation is required at each stage.

Choosing the Right Pattern

Section titled “Choosing the Right Pattern”

Each pattern answers a different question:

QuestionPattern
Need to inject library/framework context?Tool Wrapper
Need consistent, template-based output?Generator
Need to score against a checklist?Reviewer
Need to gather requirements first?Inversion
Need strict multi-step workflow?Pipeline

Start with the question your task asks. If it spans multiple questions, compose the patterns.

Patterns Compose

Section titled “Patterns Compose”

These patterns are not mutually exclusive.

A Pipeline skill can include a Reviewer step at the end to double-check its own work. A Generator can rely on Inversion at the beginning to gather the necessary variables before filling its template. Thanks to ADK’s SkillToolset and progressive disclosure, your agent only spends context tokens on the exact patterns it needs at runtime.

This is the architectural advantage: instead of cramming complex, fragile instructions into a single system prompt, you decompose the behavior into composable building blocks. Each block is testable independently. Each block has a clear contract.

Practical Tips

Section titled “Practical Tips”

  1. Start with one pattern. Most tasks fit a single pattern cleanly. Don’t compose until you need to.

  2. Name the pattern in metadata. Adding metadata.pattern: tool-wrapper to your frontmatter makes the architecture explicit and searchable across your skill library.

  3. Keep references external. The power of Wrapper, Reviewer, and Pipeline patterns comes from loading context files on demand. Don’t inline large checklists or conventions into SKILL.md itself.

  4. Gate aggressively in Pipelines. Every checkpoint you skip is a validation you lose. The explicit “DO NOT proceed until…” instruction is the Pipeline’s most important line.

  5. Test patterns in isolation. A Generator with a broken template is a Generator problem, not a skill problem. Debug the pattern layer, not the SKILL.md layer.

Section titled “Get Started”

Thread 2: Silent failures become loud ones

Section titled “Thread 2: Silent failures become loud ones”

This is the most telling thread. Count how many fixes follow the same pattern: something failed quietly, now it fails loudly or doesn’t fail at all.

Sandbox silently disabled. When sandbox.enabled: true was set but dependencies were missing, the sandbox just… didn’t run. No error. No warning. You thought you had sandboxing. You didn’t. Now there’s a visible startup warning.

MCP deny rules ignored. deny: ["mcp__servername"] permission rules weren’t removing blocked tools from what the model could see. The model would notice the tool, try to use it, and fail. The deny rule existed but didn’t work as expected. Fixed — tools are now removed before sending to the model.

Sandbox paths broken. sandbox.filesystem.allowWrite didn’t work with absolute paths. You needed a // prefix that was undocumented. Now absolute paths work directly.

Protected directories exposed. .git, .claude, and other protected directories were writable without a prompt in bypassPermissions mode. A mode designed to trust the user was also trusting the AI with sensitive directories. Fixed.

Infinite loop. API errors could trigger stop hooks that re-fed blocking errors to the model, creating an infinite loop. The kind of bug that makes you wonder how long your machine was spinning before you noticed.

Git status pollution. git log HEAD failed with an “ambiguous argument” error inside sandboxed Bash on Linux. Stub files polluted git status in the working directory.

Session truncation. cc log and --resume silently truncated conversation history on large sessions (>5 MB) that used subagents. Your conversation history was there, but the tool only showed you part of it.

Each of these is a scenario where a developer lost time or trust because the tool didn’t tell them what was happening.

A Discord server with a dozen channels, one bot handling everything. The coding channel and the casual chat channel get the same responses. Technical questions get vague answers. Creative discussions get stuffed with code snippets.

OpenClaw has a routing system that maps different channels to different agents. Same bot token, but #code-help runs a code review specialist, #creative-writing runs a writing assistant, and #support runs a troubleshooting guide. No code required — five CLI commands and one JSON edit.

Prerequisites

Section titled “Prerequisites”
  • OpenClaw installed and running
  • Discord bot created with a valid token (if not, see the previous post: OpenClaw Discord Bot Setup)

How Routing Works

Section titled “How Routing Works”

OpenClaw’s bindings array matches in order. First match wins. Specificity from high to low:

PriorityMatch ScopeUse Case
1peer — specific channel or userPer-channel customization
2guildId — entire serverServer-level differentiation
3accountId — bot accountAccount-level default
4No match conditionGlobal fallback

Same logic as firewall rules: narrow rules must come before broad ones.

Step 1: Register the Discord Bot Account

Section titled “Step 1: Register the Discord Bot Account”

Skip if you’ve already connected Discord.

Step 2: Create Your Agents

Section titled “Step 2: Create Your Agents”

Each agent gets its own workspace and configuration directory. System prompts, model parameters, tool chains — all managed separately per agent config directory.

Want the coding channel agent to follow documentation strictly and the writing channel agent to run at higher temperature? Adjust each in their respective config directories.

Step 3: Open Group Message Permissions

Section titled “Step 3: Open Group Message Permissions”

Easy to miss. OpenClaw defaults groupPolicy to allowlist — whitelist mode. The effect: every channel message gets silently dropped. No errors, no warnings, no logs.

If the bot joins a channel and ignores every message, check this first. It’s almost always the cause.

Step 4: Edit Routing Bindings

Section titled “Step 4: Edit Routing Bindings”

Manually edit ~/.openclaw/openclaw.json and add channel-level rules to the bindings array:

One rule per channel. The id field takes the Discord channel ID.

Two ways to get a channel ID:

  • Turn on Developer Mode in Discord settings, right-click the channel, copy ID
  • CLI query: openclaw directory groups list --channel discord --account <accountId>

Ordering matters. Channel-level bindings must appear before account-level bindings for the same bot. If the account-level rule sits higher in the array, it matches first and the channel rule never fires. Same principle as CSS specificity or iptables.

Step 5: Restart the Gateway

Section titled “Step 5: Restart the Gateway”

Routing doesn’t hot-reload. After editing config, restart is required.

What It Looks Like in Practice

Section titled “What It Looks Like in Practice”

Three channels, three agents:

  • #code-help -> code-review-agent (low temperature, strict documentation adherence)
  • #creative-writing -> writing-assistant (high temperature, free style)
  • #support -> troubleshoot-agent (medium temperature, guided troubleshooting)

Three binding rules, one bot token. Whichever channel a user sends a message in, the corresponding agent handles it. Channels without specific bindings fall through to the account-level or global default agent.

Troubleshooting

Section titled “Troubleshooting”

Bot doesn’t respond in channels at all Check if groupPolicy is set to open. The default whitelist silently drops all channel messages.

Channel-level binding not working — all channels respond the same way Check the order in the bindings array. Channel rules must come before account rules.

How to get channel IDs Discord Settings > App Settings > Advanced > Developer Mode. Then right-click any channel to copy its ID.

Multi-server scenarios Use guildId for server-level routing. Channel-level peer rules have higher priority and can layer on top: a server defaults to Agent A, but a specific channel within it routes to Agent B.

Section titled “Comparison with Feishu and QQ”

OpenClaw’s routing isn’t Discord-specific. Feishu group chats and QQ group chats support the same peer-level binding. The differences:

  • Discord channels are naturally separate conversation spaces — routing them to different agents feels intuitive
  • In Feishu group chats, a bot that suddenly changes response style confuses users
  • QQ group binding uses the same logic, but permission configuration differs

Discord’s channel model and multi-agent routing are a natural fit.

Context isn’t just storage capacity. It’s the model’s attention span. Tool schemas sitting in the middle of your context are noise that the model processes on every turn.

After a week of daily use, here’s what I found.

What QClaw Is

Section titled “What QClaw Is”

QClaw is Tencent’s one-click installer built on the OpenClaw open-source framework. Download, install, scan — three steps. No command line, no environment setup. Works on both Mac and Windows.

The core pitch: remote PC control through WeChat. After binding, QClaw appears in WeChat as a “customer service message” channel. You send text, it executes on your PC. File operations, browser control, script execution, scheduled tasks — the official claim is 5,000+ skills.

The default model is a domestic Chinese LLM (Kimi 2.5), with options to switch to other domestic models.

The first time it worked, I was genuinely impressed. Sent “list the files on my desktop” — got back a file listing in seconds. It runs. No complaints there.

The Problem Lives in WeChat

Section titled “The Problem Lives in WeChat”

QClaw is not a “contact” in WeChat. It’s an “application.”

That single distinction creates a chain of friction.

No group chats. You cannot add QClaw to any WeChat group. Want the AI to process something discussed in a work group? Not possible. QClaw only talks to you in a one-on-one “application message” thread.

No message forwarding. See some text or an image in a group chat that you want QClaw to handle? You can’t forward it. WeChat’s forwarding target list doesn’t include “applications.”

Copy-paste only. To send text to QClaw, long-press to copy, switch to the QClaw conversation, paste. Images are worse — save to your photo album first, then open QClaw and send from the album.

This isn’t a QClaw bug. It’s WeChat’s platform architecture. In WeChat’s world, “contacts” are first-class citizens. “Applications” are second-class. QClaw entered as an application, and the constraints follow.

In daily use, the friction is larger than you’d expect. Your instinct says “just forward this to QClaw.” Then you remember you can’t, and you start the manual relay. After a few rounds, it gets old.

Compared to OpenClaw, Clear Feature Gaps

Section titled “Compared to OpenClaw, Clear Feature Gaps”

QClaw is built on OpenClaw, but it’s not OpenClaw. Key differences:

Model Selection

Section titled “Model Selection”

QClaw only supports domestic Chinese LLMs. You can choose Kimi, MiniMax, or configure other domestic models. Claude, GPT, and other international models are not available.

For tasks that need specific model capabilities — complex code generation, multilingual translation, long-context reasoning — this limitation directly affects output quality.

PC Side Is Read-Only

Section titled “PC Side Is Read-Only”

On your PC, QClaw shows the message history from WeChat. But the reverse doesn’t work: you cannot send messages from the PC-side QClaw back to WeChat.

View only. No reply. Communication is one-directional.

This means all commands must originate from WeChat. When you’re sitting at your computer, this design feels redundant — you’re already at the PC, why not just use OpenClaw directly?

Relationship with OpenClaw

Section titled “Relationship with OpenClaw”

QClaw reads OpenClaw’s default workspace files, memory, and skills. They share these local resources.

But there’s no message channel between them. QClaw doesn’t sync execution results back to OpenClaw’s conversation history. OpenClaw doesn’t know what QClaw did. They share a filesystem, not a communication bus.

Where QClaw Fits

Section titled “Where QClaw Fits”

Complaints aside, QClaw has genuine use cases.

You’re away from your PC and need it to do something. Forgot to email a file, need to run a script, want to check local data. Pull out your phone, send a WeChat message. This is QClaw’s smoothest scenario.

Tasks where domestic LLMs are sufficient. File organization, simple copywriting, data summarization, format conversion. These don’t need the most powerful models. Domestic LLMs handle them fine.

Scheduled tasks and push notifications. Set up automated workflows, QClaw executes on schedule, and results arrive in your WeChat. This direction works well.

The unsuitable scenarios are equally clear: anything requiring group collaboration, frequent message forwarding for processing, Claude/GPT-level model capabilities, or bidirectional PC communication.

Summary

Section titled “Summary”

QClaw lowers the deployment barrier for OpenClaw and makes WeChat an entry point for AI agents. The direction is right.

But WeChat treating it as an “application” creates daily friction that exceeds expectations. No group chats, no forwarding, mandatory manual relay — these aren’t minor issues. Combined with domestic-only model support, read-only PC side, and no message bridge to OpenClaw, the functional boundary is clear but narrow.

My recommendation: treat QClaw as a “WeChat trigger.” When you’re away from your PC and need something done remotely, send a WeChat message. Don’t try to use it as a complete AI assistant — that’s OpenClaw’s job.

Know where the boundary is, and it works fine within it.

The “can send but can’t receive” debugging saga

Section titled “The “can send but can’t receive” debugging saga”

OpenClaw 2026.3 shipped with stricter channel plugin requirements. The WeCom plugin broke in a specific, frustrating way: outbound messages worked fine. Inbound was dead silent. No error. No log entry. The callback URL returned the Control UI’s HTML page instead of “wecom webhook ok”.

Three issues conspired:

Status reporting. The health monitor queries channel status periodically. Without proper reporting (running state, account snapshots, probe results), it assumed the channel was dead and restarted it in a loop.

Gateway lifecycle. startAccount was returning immediately instead of staying alive until its abortSignal fired. Each restart spawned a new instance while old routes lingered. Race conditions.

Route registration. registerHttpRoute() needed explicit auth: "plugin" and match: "exact" in the new version. Without them, the Gateway’s SPA fallback for the Control UI captured the callback URL first. The webhook hit the React app instead of the plugin handler.

v0.3.7 fixes all three.

One real case: a developer had agentId=1000002 in their config while the WeCom console had callbacks on agentId=1000003. Outbound worked (the API is more forgiving). Inbound went to the wrong app’s handler. Swapping the ID fixed it immediately.
