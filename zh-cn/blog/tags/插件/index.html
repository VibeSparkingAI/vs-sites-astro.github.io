OpenClaw 升级踩坑：插件挂了别慌，跑两遍 update 就好

OpenClaw 升级踩坑：插件挂了别慌，跑两遍 update 就好

Section titled “OpenClaw 升级踩坑：插件挂了别慌，跑两遍 update 就好”

46 秒，核心升级完成。日志干净，版本号从 2026.3.23-2 跳到了 2026.3.24。

然后两个插件同时挂了。

QQ Bot 和微信，报的是同一个错。一个带 hash 后缀的文件找不到了。

怎么回事

Section titled “怎么回事”

install.runtime-DDmlaKdG.js 这个文件名里的 DDmlaKdG 是构建时生成的 hash。核心从旧版升到新版，重新打包，hash 变了。但第一轮跑插件更新时，进程加载的还是旧的模块映射——它去找一个已经不存在的文件。

这是一个更新顺序竞态。核心文件换了，安装器还在用老地图。

修法：再跑一遍

Section titled “修法：再跑一遍”

第二轮，核心版本没变（已经是最新），但安装器是新的了。路径对了，两个插件顺利装上：

  • @tencent-connect/openclaw-qqbot → v1.6.5
  • @tencent-weixin/openclaw-weixin → v2.0.1

38.4 秒，完事。

意外收获：插件安全扫描

Section titled “意外收获：插件安全扫描”

第二轮更新的输出里多了一堆 WARNING。之前没仔细看过，这次认真读了一遍。

OpenClaw 对每个插件做了静态代码扫描，标记两类高风险模式：

环境变量 + 网络发送。 读 env 里的 token，然后通过网络发出去。这是凭证泄露的经典路径。对消息平台插件来说，这是正常操作（得用 API key 调平台接口），但扫描器不管意图，一律报。

Shell 命令执行。 插件调用 child_process。音频转码调 ffmpeg、平台检测调 uname，都算合理。但恶意插件也能借这个口子跑任意代码。

Section titled “微信插件的告警”

腾讯官方维护的插件，这些基本都是误报。但如果你装的是第三方不知名插件，看到这些警告就该翻源码了。

OpenClaw 的思路是对的——宁可多报，不可漏报。

Section titled “配置备份”

插件更新会改主配置文件。OpenClaw 自动做了备份：

升级后行为异常，diff 这两个文件就能看出哪里变了。

manifest id 和 npm 包名不一样

Section titled “manifest id 和 npm 包名不一样”

npm 包名带 scope（@tencent-connect/），但插件内部 manifest 用短名（openclaw-qqbot）。配置文件里用的是短名。记住这个，配置时不会搞混。

升级清单

Section titled “升级清单”

OpenClaw 微信插件装好了没反应？四个坑踩完才知道

Section titled “OpenClaw 微信插件装好了没反应？四个坑踩完才知道”

Feng 按照 openclaw-weixin npm 文档 把微信插件装好了，在微信群里发了条测试消息。

OpenClaw 没反应。

看了下 gateway 日志，插件显示加载成功。openclaw status 也没报错。

问题就出在”看起来没问题”和”实际没工作”之间的那条缝里。

第一个坑：旧目录挡路

Section titled “第一个坑：旧目录挡路”

用 npx CLI 重装插件时，安装器报了一行：

这行容易被刷过去。旧目录没被覆盖，新插件根本没装进去。gateway 日志报 [plugins] openclaw-weixin failed to load，找不到 openclaw/plugin-sdk/channel-config-schema 模块。

修法： 手动删掉旧目录再装。

第二个坑：QQ 插件缺 axios

Section titled “第二个坑：QQ 插件缺 axios”

顺手也装了 openclaw-qqbot。装完 gateway 报：

QQ 插件的 package.json 里写了 axios 依赖，但安装过程没拉下来。

修法： 进插件目录手动装。

第三个坑：版本检测被污染

Section titled “第三个坑：版本检测被污染”

这个最隐蔽。

Section titled “四条教训”

浏览器：连接时序问题

Section titled “浏览器：连接时序问题”

v2026.3.22 移除了 Chrome 扩展中继，转向 existing-session 和 CDP 直连。新路径带来了新的时序假设——这些假设在某些场景下是错的。

Chrome MCP 会话挂起（#52930）。 用 existing-session 驱动附加到一个已运行的 Chrome 实例时，OpenClaw 会把初次握手信号当成”就绪”标志，立即发送指令。但浏览器标签页实际上还没准备好接受操作。v2026.3.23 改为等待附加的标签页真正可用后再继续，不再把握手完成误判为会话就绪。感谢 @vincentkoc 报告并修复。

CDP 短暂连接失败后重启（#53004）。 另一个场景：OpenClaw 启动时，本地已有一个运行中的浏览器实例，但初次可达性探测恰好超时（网络抖动、进程刚启动等）。旧逻辑会立即判定”没有可用浏览器”，触发重新拉起流程，结果两个浏览器进程并存。现在改为在短暂的初次探测失败后重试一次，确认确实不可达才启动新进程。感谢 @vincentkoc。

这两个修复加在一起，让 existing-session 模式在生产环境里变得可靠得多。

ClawHub 和 macOS 认证

Section titled “ClawHub 和 macOS 认证”

macOS 用户在 v2026.3.22 升级后普遍遇到一个问题：ClawHub 技能浏览和安装需要登录，但 OpenClaw 找不到已经保存的凭据。

根本原因是多个路径的读取逻辑没有统一。

macOS auth 配置和 XDG 路径（#53034）。 openclaw auth 登录后，凭据写入了 macOS Application Support 目录，但某些代码路径在读取时只查 XDG 配置路径，两者对不上。

ClawHub 登录路径（#52949）。 类似的问题在 ClawHub 本身的登录读取逻辑里也存在——只在某一个路径查找，另一个路径有凭据也视而不见。感谢 @scoootscooob 报告。

技能浏览的 auth token（#52949）。 网关技能浏览在发起请求时没有携带本地 ClawHub auth token，导致未授权的请求全部走公开目录。修复后，浏览私有技能目录正常工作。感谢 @vincentkoc。

这三个修复针对同一根因的不同表现：macOS 路径和 XDG 路径的二元性没有在所有读取点被一致处理。

Section titled “插件：消息工具和内存”

memory-lancedb 首次使用崩溃（#26100）。 LanceDB 内存插件在第一次被调用时，插件运行时状态里没有完成初始化，直接报错。现在改为在首次使用时懒加载完成 bootstrap。这个 issue 编号（#26100）说明这是个积压已久的老问题。

未知插件 ID 致命错误（#52992）。 如果 plugins.allow 列表里有一个插件 ID 在当前版本中不存在（比如升级后某个插件被移除或重命名），OpenClaw 会拒绝启动。这个行为太激进——一个过期的插件 ID 不应该让整个实例无法启动。现在改为输出警告继续运行。感谢 @vincentkoc。

网关：启动和稳定性

Section titled “网关：启动和稳定性”

openrouter/auto 定价无限递归（#53035）。 网关在 bootstrap 阶段刷新 openrouter/auto 的定价信息时，会触发一个递归调用链，没有终止条件。在某些环境下，这会让网关启动时卡住或直接崩溃。修复后加入了递归防护。感谢 @vincentkoc。

网关探测超时（#52927）。 网关握手成功后，还需要执行一系列 post-connect RPC 来加载详情。这些 RPC 的加载时间有时超过了外层的超时限制，导致一个实际上已经成功连接的网关被标记为”不可达”。现在等待 post-connect 详情加载完成后再判定状态。感谢 @vincentkoc。

launchd/systemd 下的锁冲突崩溃循环（#52922）。 在 macOS launchd 或 Linux systemd 托管的场景下，多个进程争抢同一把锁会触发崩溃，然后进程管理器重新拉起，再次崩溃，形成循环。修复了锁竞争的处理逻辑。感谢 @vincentkoc。

画布路由和管理端点认证。 网关的 canvas 路由之前没有要求认证，admin 的智能体会话重置端点也没有要求 admin scope。现在补上。

模型提供商

Section titled “模型提供商”

Mistral 最大 token 默认值（#52599）。 捆绑的 Mistral 模型配置里，max_tokens 默认值设得过高，超过了模型实际支持的安全输出预算。在某些请求下会触发 API 错误。v2026.3.23 降低了默认值，同时让 openclaw doctor --fix 能够自动修复旧版持久化的 Mistral 提供商配置。感谢 @vincentkoc。

Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息

Section titled “Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息”

Claude Code 的会话一直是一问一答：你说话，agent 回应。MCP 服务器扩展了这个模式，agent 可以调外部工具。但信息只往外流。agent 提问，服务器回答。

2.1.80 把反向通道打开了。--channels（研究预览）让 MCP 服务器可以主动向你正在运行的会话推送消息。一个只能被问到才说话的工具，学会了举手。

通道，双向了

Section titled “通道，双向了”

MCP 一直是单行道。你的 agent 调用工具，服务器响应。如果服务器那边发生了什么事 — CI 构建失败了、部署完成了、测试跑完了 — 服务器没法告诉 agent。你得自己去问。

--channels 改变了这件事。MCP 服务器现在可以不等调用，主动向你的活跃会话推送消息。想想这意味着什么：

一个部署监控 MCP 服务器在看你的 staging 环境。agent 在写代码。部署挂了。服务器直接推送 “deploy failed: missing env var DATABASE_URL on staging” 到你的会话。agent 看到了，检查配置，修了。

一个测试运行器 MCP 服务器在测试完成时推送结果。agent 不用轮询，收到通知就行。

一个团队沟通 MCP 服务器把相关的 Slack 消息或 PR review 评论推到你的编码会话里。

这是研究预览，API 可能会变。但方向已经明确：MCP 正在从工具调用协议变成双向消息层。

技能学会了自己定节奏

Section titled “技能学会了自己定节奏”

effort frontmatter 让技能和斜杠命令的作者在技能被调用时覆盖模型的 effort 级别。

以前 effort 是全局设置。复杂任务调高，简单任务调低，来回切。现在技能自己决定。一个代码格式化命令用最低 effort 跑，因为不需要深度推理。一个架构审查技能要求最高 effort，因为偷工减料会出烂分析。

一个小小的 YAML 字段，影响不小。技能作者可以为正确的推理深度做设计，而不是指望用户碰巧把 effort 调对了。

限速，看得见了

Section titled “限速，看得见了”

rate_limits 是状态栏脚本可用的新字段。它暴露了 Claude.ai 的 5 小时和 7 天用量窗口，包含 used_percentage 和 resets_at。

如果你曾经在任务做到一半突然撞墙，现在有解了。状态栏可以显示类似 “5h 用量 73%，2h 后重置”。不用猜了。

这只适用于 Claude.ai 计费。用自己 API key 的用户有不同的限制。

插件，内联声明

Section titled “插件，内联声明”

source: 'settings' 是一个新的插件市场来源，让你直接在 settings.json 里声明插件条目。不需要注册表，不需要安装步骤。在设置文件里写好插件定义，就加载了。

对分发内部插件的团队来说，这简化了流程。推一下 settings.json 的变更，所有人就有了。

加上插件提示现在检测 CLI 工具使用（原来只看文件模式匹配），插件发现机制在变聪明。Claude Code 现在可以根据你在跑什么命令行工具来推荐插件，而不只是看项目里有什么文件。

—resume 修复：比听起来重要得多

Section titled “—resume 修复：比听起来重要得多”

--resume 在恢复会话时丢失并行工具结果。如果之前的会话有并行工具调用，恢复后会显示 [Tool result missing] 占位符，而不是实际结果。

这比听起来严重。并行工具调用在复杂会话里很常见 — agent 同时读多个文件、并行跑测试、同时搜索多个目录。丢失这些结果意味着 agent 丢失了它已经做过什么的上下文。它会重新读文件、重新搜索，或者更糟，在信息不完整的情况下做决定。

修了。所有 tool_use/tool_result 对现在正确恢复。

语音和 API 修复

Section titled “语音和 API 修复”

语音模式的 WebSocket 连接失败，因为 Cloudflare 的机器人检测在拒绝非浏览器 TLS 指纹。Claude Code 的 WebSocket 客户端看起来不像浏览器，所以 Cloudflare 标记了它。通过调整 TLS 指纹处理修复。

精细工具流式传输通过 API 代理、Bedrock 或 Vertex 时返回 400 错误。如果你通过企业基础设施跑 Claude Code，这大概率打到你了。修了。

/remote-control 在网关和第三方提供商部署中出现在命令列表里，但在这些环境中它没法用。从这些上下文中移除了。

性能：大仓库省了 80MB

Section titled “性能：大仓库省了 80MB”

25 万文件规模的仓库，启动内存用量减少约 80MB。这是有实感的减少。在一台 16GB 内存的机器上跑多个 Claude Code 实例，省回来的加在一起大概半个 GB。

大 git 仓库里 @ 文件补全也更快了。有几万文件的仓库里，输入 @ 引用文件时以前有明显延迟。改善了。

UI 打磨

Section titled “UI 打磨”

几个导航和显示改进：

/effort 现在显示 “auto” 实际解析到什么级别，和状态栏指示器一致。以前选了 “auto” 完全不知道实际用的什么 effort。

/permissions 加上了正常的 Tab 和方向键列表内导航。加上 /sandbox 的 Tab/方向键修复，设置面板的键盘导航现在一致了。

后台任务面板支持左方向键从列表视图关闭。

插件安装提示从两步流程简化为单条 /plugin install 命令。

你可能不知道需要的设置修复

Section titled “你可能不知道需要的设置修复”

托管设置 — enabledPlugins、permissions.defaultMode、策略设置的环境变量 — 在 remote-settings.json 从上一次会话缓存后，启动时不会生效。如果你的组织集中管理 Claude Code 设置，这意味着新会话可能以过期配置启动。

这种 bug 难诊断，因为它是间歇性的。只有缓存的设置和当前的不同时才会触发。修了。

这个版本在说什么

Section titled “这个版本在说什么”

--channels 是研究预览，但 Claude Code 的研究预览有个规律：通常几个版本内就变成稳定功能。发出来了就说明底层架构准备好了。

2.1.80 的模式是 Claude Code 在从工具变成基础设施。Channels 让它成为消息总线。Effort frontmatter 让技能自描述。Rate limit 可见性让它可观测。内联插件声明让它不依赖外部就能配置。

单拿出来每个都是好的改进。放在一起看，是在搭一个东西，看起来越来越不像 CLI，越来越像开发平台。

claude update 更新。如果你写 MCP 服务器，--channels 值得现在就试。如果你写技能，给它加上 effort frontmatter。如果你一直对限速毫无感知，配置你的状态栏。

2 月 5 日到 2 月 28 日，Claude Code 连发八个版本，把自己从终端编码助手变成了多智能体开发平台——Opus 4.6、Agent Teams、Worktree 隔离、Remote Control、持久记忆、HTTP Hooks。十五天干完的活，够猛，也够粗糙。

2.1.69（3 月 4 日）干的是更难的事：让这个平台用起来舒服。技能知道自己装在哪。钩子知道是哪个 Agent 触发的。终端上能直接看到当前 effort 等级。插件改完不用重启。这些都是手感问题——手感决定了一个强大的工具到底会不会被人用下去。

git-subdir 插件源 — 指向 git 仓库里的一个子目录。一个 monorepo 里有五个插件，不用再拆成五个仓库。

worktree 字段加入状态行钩子 — 在 --worktree 会话中，钩子能拿到 name、path、branch 和原始仓库目录。CI 集成可以追踪哪个 worktree 在跑什么任务。

使用流程

Section titled “使用流程”

启动会话：

接下来会发生什么：

  1. 预检 — 检测你的框架（Next.js、Vite 等）和样式系统（Tailwind、MUI 等）

  2. 样式推断 — 从 Tailwind config、CSS 变量或主题文件读取现有设计规范

  3. 访谈 — AI 会询问以下问题：

    • 设计目标（组件 vs 页面，新建 vs 重设计）
    • 痛点和需要改进的地方
    • 视觉和交互灵感参考
    • 目标用户和关键任务

  4. 生成 — 创建 5 个不同变体，探索不同方向：

    • 信息层级
    • 布局模型（卡片、列表、表格、分栏）
    • 密度（紧凑 vs 宽松）
    • 交互模式（模态框、内联、抽屉）
    • 视觉表现

  5. 评审 — 打开 http://localhost:3000/__design_lab（或你的开发服务器端口）并排查看所有变体

  6. 反馈 — 告诉 Claude：

    • 如果某个已经很好 → 选择它，做小调整
    • 如果喜欢不同变体的部分 → 描述你喜欢每个变体的哪些方面，获得合成版本

  7. 迭代 — 重复直到满意

  8. 完成 — 所有临时文件被删除，生成 DESIGN_PLAN.md 包含实施步骤

最佳实践

Section titled “最佳实践”

在访谈中要具体。 你给出的痛点、目标用户和灵感的上下文越多，生成的变体就越有特色和有用。

参考你欣赏的产品。 “像 Linear 的密度” 或 “Stripe 的清晰度” 给 Claude 具体的方向。

不要满足于第一轮。 合成步骤才是精彩之处——描述你喜欢每个变体的哪些方面，让它们结合起来。

检查 DESIGN_PLAN.md。 完成后，这个文件包含实施步骤、组件 API、可访问性检查清单和测试指导。

引言

Section titled “引言”

在使用 Claude Code 时，你是否曾遇到这样的疑问：

  • 我的上下文还剩多少空间？
  • 哪个子代理正在执行什么任务？
  • Claude 都在用哪些工具？

Claude HUD 可以一眼回答所有这些问题。它是一个平视显示器（HUD），始终显示在输入区域下方，让你清楚地了解 Claude Code 会话中正在发生的一切。

Claude HUD 是什么？

Section titled “Claude HUD 是什么？”

Claude HUD 是一个扩展 Claude Code 状态栏 API 的插件，提供实时会话可见性。它的工作原理是：

  1. 读取 Claude Code 的原生令牌数据（非估算值）
  2. 从会话记录中解析工具/代理活动
  3. 每约 300 毫秒更新一次显示

核心优势： 与外部监控工具不同，Claude HUD 使用 Claude Code 内置的状态栏 API——这意味着它可以在任何终端中工作，无需单独的窗口或 tmux 设置，直接从源头显示准确数据。

简介

Section titled “简介”

如果你像我一样，Obsidian 知识库不仅仅是笔记应用——它是你的第二大脑、项目中心、知识库。现在想象一下，在这个工作空间中直接拥有 Claude Code 的完整 AI 智能体能力。

为什么这很重要： 与传统的聊天机器人或简单的 AI 助手不同，Claudian 赋予了 Claude 实际的自主性——它可以读取、写入和编辑你知识库中的文件，执行 bash 命令，使用工具，运行多步骤工作流，甚至通过 MCP 连接到外部服务。同时，它始终对你的笔记保持上下文感知。

Claudian 是什么？

Section titled “Claudian 是什么？”

Claudian 是一个基于 Claude Agent SDK 构建的 Obsidian 插件，将 Claude Code 的能力直接带入你的 Obsidian 工作空间。可以把它理解为：

  • 侧边栏聊天： 点击机器人图标或使用命令面板在侧边栏打开 Claude
  • 完整的智能体能力： Claude 可以在你的知识库中读取/写入文件、运行 bash 命令、执行多步骤工作流
  • 上下文感知： 自动附加当前关注的笔记，支持 @提及文件，包含选中的文本
  • 视觉支持： 通过拖放、粘贴或文件路径分析图像
  • 可扩展： 支持斜杠命令、自定义指令、技能和 MCP 服务器

核心洞察： 这不仅仅是聊天界面——这是在你的 Obsidian 中运行的 Claude Code，你的知识库就是它的工作目录。

技能一：docx-format-replicator

Section titled “技能一：docx-format-replicator”

从现有 Word 文档中提取格式，并生成具有相同格式的新文档。

使用场景

Section titled “使用场景”
  • 企业文档模板复制 - 在多个文档间保持一致的品牌风格
  • 批量文档生成 - 创建多个格式相同的文档
  • 技术规范文档系列 - 从模板生成规范文档
  • 标准化文档 - 开发任务表、报告等

技能二：video-processor

Section titled “技能二：video-processor”

从 YouTube 和其他平台下载并处理视频。支持视频下载、音频提取、格式转换和 Whisper 转录。

使用场景

Section titled “使用场景”
  • 从 YouTube 和其他平台下载视频
  • 从视频文件中提取音频
  • 将视频转换为 MP4/WebM 格式
  • 使用 Whisper 将音频/视频转录为文本

技能三：wechat-article-writer

Section titled “技能三：wechat-article-writer”

自动化微信公众号文章写作流程，包含 4 个步骤：研究、写作、标题生成和格式优化。

使用场景

Section titled “使用场景”
  • 撰写公众号文章
  • 生成爆款标题
  • 自媒体内容创作
  • 文章格式优化

工作流程

Section titled “工作流程”

该技能遵循 4 步流程：

  1. 研究 - 收集主题相关信息
  2. 写作 - 生成文章内容
  3. 标题生成 - 创建吸引人的标题
  4. 格式化 - 为微信编辑器优化格式

使用示例

Section titled “使用示例”

“帮我写一篇关于 AI 编程技巧的公众号文章”

为什么这些技能很重要

Section titled “为什么这些技能很重要”

Claude Code 的插件系统使社区贡献能够扩展工具的核心功能。happy-claude-skills 集合展示了实际应用价值：

  1. 文档自动化 - 减少手动格式化工作
  2. 媒体处理 - 将视频处理能力带入编码工作流程
  3. 内容创作 - 简化面向中文受众的文章写作流程

随着 Claude Code 生态系统的不断发展，我们可以期待更多社区插件的出现，进一步增强工具的多功能性。
