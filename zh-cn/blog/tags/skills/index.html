Matt Pocock Skills 全景调查：17 个 AI Agent 技能深度拆解

2026年4月7日
Vibe Sparking

来源：mattpocock/skills 调查日期：2026-04-07 共计 17 个 skills，覆盖规划、开发、工具链、写作四大类

一、Planning & Design（规划与设计）

Section titled “一、Planning & Design（规划与设计）”

1. write-a-prd

Section titled “1. write-a-prd”
  • 安装： npx skills@latest add mattpocock/skills/write-a-prd
  • 做什么： 通过交互式访谈 + 代码库探索，生成完整的产品需求文档（PRD），最终提交为 GitHub Issue
  • 核心流程：
    1. 收集用户对问题和方案的详细描述
    2. 探索代码库验证现状
    3. 反复追问每个决策分支，直到达成共识
    4. 设计模块划分，追求”深模块”（小接口、大实现）
    5. 按模板生成 PRD（问题描述、方案、用户故事、实施决策、模块设计）
  • 使用场景：
    • 想给项目加一个用户通知系统，但细节没想清楚——运行此 skill，它会帮你把模糊想法变成结构化文档
    • 新功能立项时，替代传统的”开个会讨论一下”

2. prd-to-plan

Section titled “2. prd-to-plan”
  • 安装： npx skills@latest add mattpocock/skills/prd-to-plan
  • 做什么： 将 PRD 拆解为多阶段实施计划，使用 tracer bullet 垂直切片，输出到 ./plans/ 目录
  • 核心流程：
    1. 确认 PRD 在上下文中
    2. 探索代码库理解架构
    3. 识别持久架构决策（路由、schema、认证方案等）
    4. 按垂直切片拆分——每个阶段切穿所有集成层（schema → API → UI → 测试）
    5. 与用户确认粒度，迭代直到满意
    6. 写入 ./plans/ Markdown 文件
  • 使用场景：
    • PRD 已就绪，需要排期和分阶段实施
    • 想确保每个开发阶段都能独立演示，而不是”最后一天才能跑起来”

3. prd-to-issues

Section titled “3. prd-to-issues”
  • 安装： npx skills@latest add mattpocock/skills/prd-to-issues
  • 做什么： 将 PRD 拆成可独立认领的 GitHub Issues，标注依赖关系和 HITL/AFK 类型
  • 核心流程：
    1. 获取 PRD（GitHub Issue 号）
    2. 可选探索代码库
    3. 拆分为垂直切片，标记 HITL（需人工决策）/ AFK（可自主完成）
    4. 与用户确认粒度、依赖、分类
    5. 按依赖顺序创建 GitHub Issues
  • 使用场景：
    • 团队多人协作，需要把大需求变成可分配的工单
    • 让 AI agent 自主执行 AFK 类型的 issue

4. grill-me

Section titled “4. grill-me”
  • 安装： npx skills@latest add mattpocock/skills/grill-me
  • 做什么： 对你的方案进行无情拷问，逐一走遍决策树每个分支，直到达成共识
  • 核心流程：
    • 一次只问一个问题
    • 每个问题附带推荐答案
    • 能通过探索代码库回答的问题，直接去看代码而非问你
  • 使用场景：
    • 打算把 monorepo 拆微服务，但边界不确定——让它拷问你
    • 任何重大技术决策前的压力测试
    • 写 RFC 之前，先过一遍”魔鬼advocate”

5. design-an-interface

Section titled “5. design-an-interface”
  • 安装： npx skills@latest add mattpocock/skills/design-an-interface
  • 做什么： 基于 John Ousterhout “Design It Twice” 原则，用并行子代理生成 3+ 种截然不同的接口设计，然后对比
  • 核心流程：
    1. 收集需求（问题、调用者、关键操作、约束）
    2. 并行启动 3+ 子代理，每个有不同约束（极简、灵活、常见场景优化等）
    3. 逐个展示设计（签名、用法示例、隐藏的复杂度）
    4. 多维度对比（接口简洁度、通用性、实现效率、模块深度）
    5. 用户选择或混合
  • 使用场景：
    • 设计缓存模块 API、插件系统、SDK 接口等关键模块
    • 避免”第一个想到的方案就是最终方案”的陷阱

6. request-refactor-plan

Section titled “6. request-refactor-plan”
  • 安装： npx skills@latest add mattpocock/skills/request-refactor-plan
  • 做什么： 通过访谈生成详细重构计划，拆成极小安全提交，提交为 GitHub Issue
  • 核心流程：
    1. 收集问题描述和初步方案
    2. 探索代码库验证
    3. 讨论替代方案
    4. 确定精确范围（改什么、不改什么）
    5. 检查测试覆盖
    6. 按 Martin Fowler “每步尽可能小”原则拆分提交计划
    7. 创建 GitHub Issue（问题、方案、提交列表、决策文档）
  • 使用场景：
    • 想把散落各处的状态管理统一为 Zustand，但怕改炸
    • 任何涉及多文件、多模块的大规模重构

7. tdd

Section titled “7. tdd”

六、设计哲学总结

Section titled “六、设计哲学总结”

Matt Pocock 的 skills 体系贯穿了几个核心理念：

  1. 垂直切片（Tracer Bullet）——贯穿 write-a-prd → prd-to-plan → prd-to-issues → tdd 的完整链路，每一步都强调端到端的薄切片而非水平分层
  2. 深模块（Deep Modules）——来自 John Ousterhout《A Philosophy of Software Design》，小接口隐藏大实现，贯穿 design-an-interface 和 improve-codebase-architecture
  3. Design It Twice——不要爱上第一个方案，并行探索多种设计
  4. 极小提交（Tiny Commits）——Martin Fowler 的重构哲学，每一步都保持代码可运行
  5. 行为测试而非实现测试——TDD skill 的核心，测试应该像规格说明一样可读、能扛住重构

推荐组合使用路径：grill-me → write-a-prd → design-an-interface → prd-to-plan → prd-to-issues → tdd

第三方 skill 不是不能装，但别上来就装。

在 OpenClaw 这种天然能读文件、跑命令、联网、操作会话的 agent 环境里，先审查、后安装不是洁癖，而是基本生存法则。

为什么 Skill Vetter 值得单独讲

Section titled “为什么 Skill Vetter 值得单独讲”

很多人第一次接触 OpenClaw skills，会把它理解成“提示词插件”或者“工具说明文件”。这理解不算错，但也不完整。

一个 skill 往往不只是告诉 agent 要怎么做事，它还可能间接影响：

  • 会读取哪些文件
  • 会运行哪些命令
  • 会不会联网
  • 会不会接触凭证、记忆文件、配置文件
  • 会不会把动作扩散到 workspace 之外

所以安装第三方 skill，本质上不是“下载一个方便的小工具”，而是在给 agent 增加一套新的行为协议。协议本身如果不安全，后面所有自动化都会被放大。

Skill Vetter 的价值，就在于把这一步前移：

Never install a skill without vetting it first.

它不是一个独立 CLI，而是一套给 agent 使用的安全审查协议：在安装 skill 之前，先读完整源码、检查红旗项、评估权限范围、输出标准化结论，再决定装不装。

Skill Vetter 是什么

Section titled “Skill Vetter 是什么”

Skill Vetter 可以理解成一个“安装前安检员”。它要求 agent 在面对未知 skill 时，不只看 README 或 SKILL.md，而是检查全部文件。

核心关注点通常包括：

  • 来源是否可信
  • 是否存在可疑外联
  • 是否读取敏感目录或隐私文件
  • 是否出现 eval / exec / 混淆代码 / base64 解码等风险行为
  • 是否请求 token、凭证、elevated 权限
  • 文件读写与联网范围是否符合最小权限原则

换句话说，它不是教你“怎么装 skill”，而是教 agent 在装之前先回答三个问题：

  1. 这个 skill 到底在干什么？
  2. 它需要多大权限？
  3. 这权限值不值得给？

一套够用的 SOP：安装任何第三方 skill 之前都走一遍

Section titled “一套够用的 SOP：安装任何第三方 skill 之前都走一遍”

如果要把 Skill Vetter 落成团队或个人标准，我建议把流程固定成下面这 6 步。

第一步：确认来源

Section titled “第一步：确认来源”

先问清楚它从哪来：

  • OpenClaw 官方内置
  • ClawHub
  • GitHub 仓库
  • 个人分享或私有链接

同时补充判断：

  • 作者是谁
  • 最近更新时间
  • 是否有人在用
  • 是否有明确用途说明

来源不是充分条件，但能快速筛掉一批低质量或来路不明的东西。

第二步：强制逐文件审查

Section titled “第二步：强制逐文件审查”

这一步最容易被偷懒，也最不该偷懒。

重点不是看它“说自己要做什么”，而是看它实际上能做什么。常见红旗包括：

  • curl / wget 指向陌生地址
  • 直接向外部服务发送数据
  • 读取 ~/.ssh、~/.aws、~/.config 等敏感目录
  • 访问 MEMORY.md、USER.md、SOUL.md、IDENTITY.md 等私有上下文
  • base64 解码、压缩包展开后再执行等掩蔽行为
  • eval() / exec() 配合外部输入
  • 修改 workspace 外系统文件
  • 额外安装未声明依赖
  • 请求 sudo / elevated 权限
  • 读取浏览器 cookie、session 或 credential 文件

有一条经验非常重要：

审的是代码，不是宣传。

README 写得再温柔，也不能代替源码审查。

第三步：评估权限边界

Section titled “第三步：评估权限边界”

审查之后，要把权限讲清楚，而不是只说一句“看起来没问题”。

至少要回答：

  • 它会读哪些文件？
  • 它会写哪些文件？
  • 它会运行哪些命令？
  • 它需要联网吗？
  • 联网对象和功能是否匹配？
  • 能不能再缩小权限？

如果一个 skill 的功能只是格式化 Markdown，却想读取整套个人记忆文件或系统配置，那就已经是明显不匹配了。

🟡 MEDIUM文件操作、浏览器、第三方 API 集成完整审查后谨慎安装

你可能一直在用错方式

Section titled “你可能一直在用错方式”

你不会雇一个高级工程师，然后一次只发一句话给他，没上下文，没流程，没团队知识积累。但我们大多数人对 AI 编码助手干的就是这件事。

Matt Pocock——Total TypeScript 背后的 TypeScript 教育者——刚把自己的 .claude 目录开源了。里面是一组结构化的「技能」，能把 Claude Code 从一个被动应答的聊天框变成一个有主见的开发搭档，懂你的工作流程。

技能到底是什么？

Section titled “技能到底是什么？”

Claude Code 支持 .claude 目录，你可以在里面定义「技能」——结构化的工作流定义，AI 被调用时会按照它执行。不是提示词，是流程。

你可以把它理解成给 AI 写的操作手册。Matt 一直在攒自己的个人收藏，现在他放到了 GitHub 上：mattpocock/skills。

有意思的不是单个技能本身，而是整个集合的组织方式。

三层架构

Section titled “三层架构”

规划层

Section titled “规划层”

三个技能处理大多数开发者跳过或草草了事的上游工作。

write-a-prd 不是生成一份模板文档。它会跟你做互动式访谈，扫描你的代码库，设计模块边界，最后把结果提交成 GitHub issue。AI 变成了你的产品思考搭档。

prd-to-issues 拿到 PRD 之后，按垂直切片拆成一个个独立可抓取的 GitHub issue。每个 issue 自成一体，拿起来就能做，不用去理依赖链。

grill-me 是最有意思的一个。它把交互完全反转了。不是你问 AI 问题，而是 AI 来盘问你的方案。一个接一个地问，直到决策树的每个分支都有答案。就像终端里住了一个不让你写代码的质疑型技术负责人。

开发层

Section titled “开发层”

工程纪律在这里体现。

tdd 跑的是真正的测试驱动开发。不是”事后补几个测试”。红灯-绿灯-重构，一次一个垂直切片。你告诉它做什么功能或修什么 bug，它来驱动循环。

triage-issue 通过遍历代码库来排查 bug，找到根因，然后提一个带 TDD 修复方案的 GitHub issue。排查和修复计划一步到位。

improve-codebase-architecture 扫描结构性改进机会。重点是加深浅层模块、提高可测试性——那种永远重要但永远不紧急、所以基本不会发生的重构工作。

工具层

Section titled “工具层”

两个技能负责安全网。

setup-pre-commit 配 Husky 预提交钩子，带 lint-staged、Prettier、类型检查和测试。标准工具链，但自动化配置意味着没理由跳过。

git-guardrails-claude-code 设置 Claude Code 钩子，在 AI 执行危险 git 命令之前拦截——push、reset —hard、clean。你的 AI 助手很强，但它也需要约束。

元层

Section titled “元层”

write-a-skill 教 AI 创建新技能，带规范结构、渐进展示和打包资源。系统是自扩展的。技能能生技能。

为什么这件事值得关注

Section titled “为什么这件事值得关注”

回头看软件开发的历史。从什么都自己写，到共享代码库。从零散脚本，到包管理器。从手动部署，到 CI/CD 流水线。

每次转变的模式一样：原来手工的、个人的东西变成了结构化的、可共享的。

技能就是 AI 辅助开发领域的这次转变。一个 tdd 技能不是一段提示词，它是一整套方法论编码成的工作流定义，任何开发者都可以安装和运行。

我们正在看到 AI 行为的包管理器的早期阶段。就像 2012 年的 npm 或 2014 年的 Docker，早期构建和分享优质包的人会影响后来所有人的工作方式。

三点。

结构而非模板。 技能给 Claude 领域知识，不是填空式模板。输出会根据你的具体情况调整，同时保持框架的严谨性。
