为什么不用端口转发？

Section titled “为什么不用端口转发？”

最初尝试了默认的 codex login（非 device-auth），它会在本地启动 HTTP 服务器（如 localhost:1455）等待 OAuth 回调。远程机器上这个端口无法被本地浏览器访问，需要设置 SSH 端口转发才能工作。

--device-auth 模式完全避免了这个问题——它使用 Device Code 流程，浏览器和 CLI 之间通过 OpenAI 服务器中转，不需要直接网络连接。推荐远程/无头机器始终使用此模式。

一、新增功能 (Added)

Section titled “一、新增功能 (Added)”

1. forceRemoteSettingsRefresh 策略设置

Section titled “1. forceRemoteSettingsRefresh 策略设置”

问题背景 企业/团队管理员通过 managed-settings.json 下发策略（权限规则、沙箱配置、插件白名单等）。此前这些设置会缓存到 remote-settings.json，CLI 启动时使用缓存，如果远端拉取失败则继续用旧缓存——这意味着已撤销的权限可能仍有效，存在安全窗口。

使用场景

  • 金融/医疗等合规敏感行业，管理员紧急撤销某人权限后，需要确保下次启动 立即生效
  • SOC2/ISO27001 审计要求「fail-closed」而非「fail-open」策略

举例

设置后：CLI 启动时阻塞等待远端配置拉取成功 → 成功才进入；失败则退出（fail-closed）。

注意事项

  • 网络不稳定时会导致 CLI 无法启动——适合企业内网环境，不适合离线开发场景
  • 建议搭配 remote-settings.json 缓存 TTL 理解使用
  • 仅对 Team/Enterprise 管理员有意义，个人用户无需关注

1.1 PreToolUse Hook 的 "defer" 决策

Section titled “1.1 PreToolUse Hook 的 "defer" 决策”

使用场景与举例：

钩子重新评估（此时可检查审批系统的状态），决定 allow 或 deny。

注意事项：

  • --resume 时如果 deferred tool input 超过 64KB 或没有 deferred marker，会卡住（本版同时修复了此问题）。
  • 需要设计好外部审批状态的轮询/回调机制。

同类对比：

1.2 CLAUDE_CODE_NO_FLICKER=1 无闪烁渲染

Section titled “1.2 CLAUDE_CODE_NO_FLICKER=1 无闪烁渲染”

变更内容： 新增环境变量，启用基于 alt-screen 的无闪烁渲染，带有虚拟化滚动回溯。

问题背景： Claude Code 的 TUI（终端 UI）在长输出流式渲染时，尤其在 iTerm2/tmux 环境下，容易出现画面闪烁和抖动。这是因为默认使用 main-screen 渲染模式，每次重绘都会影响滚动缓冲区。

使用场景：

适合：

  • 在 tmux 中运行 Claude Code 的用户
  • 使用低刷新率终端模拟器的用户
  • 长时间持续使用（编码马拉松）的场景

注意事项：

  • Alt-screen 模式下，退出后终端滚动缓冲不保留会话内容（类似 vim 退出后屏幕恢复）。
  • 标记为 “opt-in”，说明还不够成熟作为默认行为，可能存在边缘兼容性问题。

同类对比：

  • Codex CLI： 使用 Ink（React for CLI）渲染，自带 alt-screen，闪烁问题较少但自定义程度低。
  • Gemini CLI： 基于 Rich/Textual 的 Python 渲染，闪烁控制中等。

趋势： 终端 AI 工具正在从”能用”走向”好用”，渲染质量是用户体验的核心差异化。未来可能默认启用 alt-screen 并提供完整的虚拟滚动。

1.3 PermissionDenied Hook

Section titled “1.3 PermissionDenied Hook”

变更内容： 新增 PermissionDenied 钩子，在 auto mode 分类器拒绝操作后触发。返回 {retry: true} 可以让模型重试。

问题背景： Auto mode 下 Claude Code 有一个安全分类器，自动拒绝被判定为危险的操作。但有时分类是误判（false positive），尤其当命令语义复杂时。之前用户只能手动重试或切换到手动模式。

使用场景： 自定义钩子脚本检查被拒绝的命令是否在白名单中：

例如 docker compose down 可能被误判为危险删除命令，钩子可以自动允许重试。

注意事项：

  • retry: true 只是告诉模型可以重试，不等于绕过权限——模型可能换一种方式执行。
  • 滥用此钩子会削弱安全分类器的保护效果。

同类对比：

  • Codex CLI： 有 suggest / auto-edit / full-auto 三档模式，无精细钩子。

使用场景：

注意事项：

  • 非阻塞模式下，如果模型调用了尚未连接的 MCP 工具，会失败。
  • 5 秒超时可能对冷启动的 SSE 服务器过短。

同类对比：

  • Codex CLI： 不支持 MCP。
  • Gemini CLI： 支持 MCP，但没有非阻塞选项，连接失败直接跳过。

Section titled “2.3 Windows CRLF 和 Markdown 硬换行修复”

2.5 长会话内存泄漏

Section titled “2.5 长会话内存泄漏”

变更内容： 修复大 JSON 输入作为 LRU 缓存键被保留导致的内存泄漏。

问题背景： LRU 缓存使用输入内容的完整 JSON 字符串作为 key。当输入很大（如读取大文件内容）时，这些字符串常驻内存不被 GC 回收。长时间运行的会话（如 8 小时编码马拉松）会看到 Node.js 进程内存持续增长。

使用场景： 持续使用 Claude Code 数小时，读取多个大文件后，进程内存从 300MB 涨到 2GB+，终端开始卡顿。

注意事项：

  • 建议长会话定期使用 /clear 或 /compact。

同类对比：

  • Codex CLI： 使用 React/Ink 渲染，同样存在内存增长问题但表现不同。
  • Gemini CLI： Python 运行时，GC 策略不同，长会话同样可能有问题。

同类对比：

  • Codex CLI： 使用 Node.js readline，CJK 处理由系统库负责。
  • Gemini CLI： Python 的 Unicode 处理相对成熟，但类似边界问题也可能存在。

2.15 Autocompact 死循环修复 ⭐

Section titled “2.15 Autocompact 死循环修复 ⭐”

变更内容： 检测到上下文在 compact 后立即重新填满（连续 3 次），停止并报告可操作的错误，而非无限循环消耗 API 调用。

问题背景： 这是一个严重的成本和可用性 bug。当项目配置导致大量上下文被注入（如嵌套的 CLAUDE.md、大量 skill 描述），compact 后这些内容立即重新注入，触发再次 compact，形成死循环。每次 compact 都是一次 API 调用，可能在用户不知情的情况下消耗大量 token。

使用场景： 大型 monorepo 中有多层嵌套的 CLAUDE.md 文件，每次 compact 后这些文件全部重新注入，token 数立即回到阈值。循环几十次后用户发现 API 用量飙升。

注意事项：

  • 如果遇到此错误，检查是否有过多的 CLAUDE.md 嵌套或 skill 描述过长。
  • 配合本版另一个修复（2.17 CLAUDE.md 重复注入）一起理解。

同类对比：

  • Codex CLI： 无 auto compact 功能，上下文满了直接报错。
  • Gemini CLI： 上下文管理策略不同，无类似循环问题。

趋势： 自动上下文管理是长会话可用性的核心，但需要更智能的策略（如增量 compact、选择性保留）。

2.16 Prompt Cache 命中率下降修复

Section titled “2.16 Prompt Cache 命中率下降修复”

变更内容： 修复长会话中 tool schema 字节变化导致的 prompt cache miss。

问题背景： Anthropic API 的 prompt cache 依赖前缀匹配。如果 tool schema 在会话中发生微小变化（如 MCP 工具动态更新描述），会导致整个 prompt 前缀失效，cache miss，每次请求都要重新处理完整上下文，大幅增加延迟和成本。

注意事项：

  • 这是一个”隐性成本”bug——用户可能只是觉得”怎么变慢了”，不会意识到是 cache miss。

Section titled “三步上手（真的就三步）”

什么时候用 High reasoning，什么时候用 Minimal/Medium？

Section titled “什么时候用 High reasoning，什么时候用 Minimal/Medium？”

适合 High 的场景

  • 复杂重构 / 设计权衡：例如「把 MVC 项目拆成分层 + 依赖倒置，补齐测试」。需要系统性推理和多步计划。
  • 跨语言迁移：如从 Python → Go 且保留并发/错误语义。需要细致的 API/并发模型映射。
  • 疑难 bug 诊断：复杂堆栈、竞态、边界条件，靠更长的思考链更稳。

适合 Minimal/Medium 的场景

  • 脚手架、批量修 lint、重命名，追求速度且不需要长链路推理。minimal 会大幅减少推理 token、显著提速。

我在本地的推荐工作流（可直接抄）

Section titled “我在本地的推荐工作流（可直接抄）”
  1. 开场就高推理（复杂任务）

然后用 /approvals 收紧自动修改权限，重要变更逐条确认。

  1. 中途降档提速 调试通过后，输入 /model 把推理改成 medium 或 minimal，进入批量小改模式。

  2. 拆解多步任务 把一个大目标拆成多轮：设计 → 接口 → 实现 → 测试。官方也建议**“多回合、一步一回合”**，实际效果更稳。

小贴士：推理力度越高，推理 token越多，延迟可能更高；卡顿时就 /model → minimal/low。
