OpenClaw 本机升级 2026.4.5 问题记录

Section titled “OpenClaw 本机升级 2026.4.5 问题记录”

日期： 2026-04-06
升级版本： 2026.4.2 → 2026.4.5

问题概述

Section titled “问题概述”

本机执行 openclaw update 后，shell 中 openclaw -v 仍显示旧版本 2026.4.2。

根因

Section titled “根因”

本机存在两个 openclaw 安装：

路径版本来源
/opt/homebrew/bin/openclaw2026.4.5 ✅Homebrew npm global
~/.asdf/installs/nodejs/24.9.0/bin/openclaw2026.4.2 ❌asdf Node.js 24.9.0 npm global

openclaw update 只更新了 Homebrew 下的那份。用户 shell 的 PATH 中 asdf 优先级更高，所以 which openclaw 指向旧版本。

解决方案

Section titled “解决方案”

  1. 删除 asdf 下的旧 openclaw bin：

    之后 which openclaw 正确指向 /opt/homebrew/bin/openclaw（2026.4.5）。

  2. Kill 遗留的 npm install 进程： 之前尝试通过 npm install -g openclaw@latest 更新 asdf 版本，进程占用 1.1GB 内存仍未完成，手动 kill。

升级后新问题：Config Legacy Key

Section titled “升级后新问题：Config Legacy Key”

重启 gateway 时报错：

原因： 2026.4.5 将 Discord channel config 中的 allow 字段重命名为 enabled，旧配置不再兼容。

修复： 执行 openclaw doctor --fix 自动修复。

经验教训

Section titled “经验教训”
  1. 多 Node 环境注意 PATH 优先级 — asdf / nvm / homebrew 可能装了多份 openclaw，openclaw update 不会更新所有副本
  2. 升级前检查 which openclaw — 确认更新的是实际使用的那份
  3. 升级后跑 openclaw doctor — 新版本可能有 config schema 变更
  4. 统一安装源 — 删除多余副本，避免版本混乱。本机统一用 /opt/homebrew/bin/openclaw

2026年4月3日

升级概况

Section titled “升级概况”
  • 升级前版本： 2026.3.28
  • 升级后版本： 2026.4.2

升级命令很简单：

核心更新耗时约 82 秒（npm 全局更新 60s + openclaw doctor 检查 21s）。

但升级过程中踩了不少坑，记录如下。

遇到的问题

Section titled “遇到的问题”

1. 插件安全扫描拦截

Section titled “1. 插件安全扫描拦截”

新版加强了插件安全检查，自动更新插件时部分插件被拦截，报错：

  • Environment variable access combined with network send — possible credential harvesting
  • Shell command execution detected (child_process)

这是 2026.4.2 引入的安全扫描机制，对所有插件一视同仁。包含 child_process 调用或「读取环境变量 + 网络发送」组合模式的代码都会被标记为危险。

解决方式： 使用 --dangerously-force-unsafe-install 强制安装：

2. 插件重复安装冲突

Section titled “2. 插件重复安装冲突”

强制安装某个插件后，plugins list 出现了多个同名条目：

条目版本来源状态
内置版本2026.4.2stockloaded
全局强装版本1.6.5globalloaded
更早的全局安装1.5.5globaldisabled

根因： 2026.4.2 已将该插件内置到核心包中（stock 来源），版本比第三方包还新。强制安装第三方版本反而引入了低版本覆盖问题，并触发 duplicate plugin id 警告。

解决方式： 卸载多余的全局安装，保留内置版本：

教训：升级后如果插件更新失败，先用 plugins list 检查是否已内置，再决定是否强装。

3. ClawHub 与 npm 类型标记不一致

Section titled “3. ClawHub 与 npm 类型标记不一致”

尝试用 openclaw plugins install 安装某个插件时，CLI 走 ClawHub 解析路径，返回：

但该包在 npm 上是一个标准的 channel 插件。

原因： openclaw plugins install <slug> 默认走 ClawHub 解析，而 ClawHub 上该包被注册为 skill 类型。npm 和 ClawHub 是独立的分发渠道，类型标记可能不一致。

如果确实需要安装 npm 版本，应使用完整包名：

误操作教训： 按提示执行了 openclaw skills install，在 workspace/skills/ 下多装了一份 skill 副本，后续需要手动删除。

4. 插件版本号显示不一致

Section titled “4. 插件版本号显示不一致”

plugins list 显示某插件版本为 2.0.0，但磁盘上 package.json 已经是 2.0.1。

根因： plugins list 读取的是 openclaw.plugin.json（插件 manifest）中的 version 字段，而非 package.json。上游打包时 npm 版本 bump 了但忘了同步 manifest，属于上游小 bug。

临时修复： 手动更新 manifest 中的版本号即可。

5. Gateway 服务未加载

Section titled “5. Gateway 服务未加载”

升级后执行 openclaw gateway restart 提示 service not loaded。

解决： 通过 openclaw config → 选择 Daemon 重新安装 LaunchAgent：

升级经验总结

Section titled “升级经验总结”
  1. 先查再装： 插件更新失败时，先 openclaw plugins list 看是否已内置，避免低版本覆盖高版本
  2. 安全扫描是新常态： 2026.4.2 起所有插件都会被扫描，官方插件也不例外。信任的插件用 --dangerously-force-unsafe-install
  3. ClawHub ≠ npm： 同一个包在两个渠道的类型标记可能不同，注意区分 plugin 和 skill 的安装命令
  4. 版本号看 manifest： plugins list 的版本来自 openclaw.plugin.json，不是 package.json
  5. 升级后记得重启 Gateway： openclaw gateway restart，如果 service 丢失则通过 openclaw config 重新安装 Daemon

OpenClaw 升级踩坑：插件挂了别慌，跑两遍 update 就好

Section titled “OpenClaw 升级踩坑：插件挂了别慌，跑两遍 update 就好”

46 秒，核心升级完成。日志干净，版本号从 2026.3.23-2 跳到了 2026.3.24。

然后两个插件同时挂了。

QQ Bot 和微信，报的是同一个错。一个带 hash 后缀的文件找不到了。

怎么回事

Section titled “怎么回事”

install.runtime-DDmlaKdG.js 这个文件名里的 DDmlaKdG 是构建时生成的 hash。核心从旧版升到新版，重新打包，hash 变了。但第一轮跑插件更新时，进程加载的还是旧的模块映射——它去找一个已经不存在的文件。

这是一个更新顺序竞态。核心文件换了，安装器还在用老地图。

修法：再跑一遍

Section titled “修法：再跑一遍”

第二轮，核心版本没变（已经是最新），但安装器是新的了。路径对了，两个插件顺利装上：

  • @tencent-connect/openclaw-qqbot → v1.6.5
  • @tencent-weixin/openclaw-weixin → v2.0.1

38.4 秒，完事。

意外收获：插件安全扫描

Section titled “意外收获：插件安全扫描”

第二轮更新的输出里多了一堆 WARNING。之前没仔细看过，这次认真读了一遍。

OpenClaw 对每个插件做了静态代码扫描，标记两类高风险模式：

环境变量 + 网络发送。 读 env 里的 token，然后通过网络发出去。这是凭证泄露的经典路径。对消息平台插件来说，这是正常操作（得用 API key 调平台接口），但扫描器不管意图，一律报。

Shell 命令执行。 插件调用 child_process。音频转码调 ffmpeg、平台检测调 uname，都算合理。但恶意插件也能借这个口子跑任意代码。

OpenClaw 升级踩坑实录：三个包管理器打架，回滚才是正道

2026年3月24日
Vibe Sparking

OpenClaw 升级踩坑实录：三个包管理器打架，回滚才是正道

Section titled “OpenClaw 升级踩坑实录：三个包管理器打架，回滚才是正道”

晚上十一点，运行 openclaw doctor --fix，期待看到一屏绿色对勾。

屏幕上弹出三个红叉。

出了什么事

Section titled “出了什么事”

起始状态很简单：OpenClaw 2026.3.22，用 bun 全局安装，装在 /Users/vs/.bun/install/global/node_modules/openclaw，Node v25.8.1 由 Homebrew 管理。看起来没什么问题。

openclaw doctor --fix 报了三条：

#问题严重程度
1openclaw-weixin v1.0.3 加载失败：Cannot find module 'openclaw/plugin-sdk'阻断
2acpx 插件配置残留：路径不存在阻断
3Memory search 没有可用的 embedding provider功能缺失

前两个直接导致 config validation 失败。第三个暂时不影响核心功能，但也说明环境不干净。

修，但越修越坏

Section titled “修，但越修越坏”

先试最直觉的办法。

访问 http://localhost:18789/chat，返回 503。错误信息是 Control UI assets not found。Web UI 的静态资源根本没装进来。

用 Claude Code 手动清理了 openclaw.json 里的 acpx 残留配置——plugins.allow、plugins.load.paths、plugins.entries.acpx、plugins.installs.acpx，四个地方都有。

Gateway 重启后能响应了，但 Web UI 还是 503。

试了 pnpm ui:build，失败。scripts/ui.js 不在 npm 发布包里，这条路走不通。

openclaw update——已经是最新版，没有可用更新。

到这一步，开始意识到问题不在某个配置项，而在更深的地方。

包管理器坟场

Section titled “包管理器坟场”

卸载的时候才发现真正的混乱。

三个包管理器，每个都在系统里留了点什么。bun 装了二进制和 node_modules，npm 的 bin stub 可能还躺在 /opt/homebrew/bin/ 下面，Homebrew 管了 Node 本身但没管 OpenClaw。路径解析在这种环境下完全不可预测。

卸载完确认 which openclaw 返回 command not found。干净了。

Section titled “重装，但问题照旧”

用官方安装脚本重装：

这次走的是 npm 路径，装在 /opt/homebrew/lib/node_modules/openclaw，版本 2026.3.22。安装脚本自动跑了 doctor，启用了 ACP runtime。

但 openclaw-weixin 还是报 Cannot find module 'openclaw/plugin-sdk'。重新安装插件、重新运行安装脚本，结果一样。

acpx 配置残留也再次出现了——doctor 或 update 过程似乎会重新写入这些条目。

回滚：退一步走两步

Section titled “回滚：退一步走两步”

换个思路。先装一个确定能用的老版本，稳定住，再往上升。

这次 npm 走的是 asdf 管理的 Node v24.9.0，安装路径变成了 /Users/vs/.asdf/installs/nodejs/24.9.0/lib/node_modules/openclaw。

Gateway 启动了。有一条警告说配置文件是被更新版本写入的，但不影响运行。

2026.3.13 跑起来了。稳了。

过程中出了 40 多条 plugin id mismatch 警告（内置插件的 manifest id 不匹配），但升级本身完成了。Gateway 没有自动启动，手动修复：

五条教训

Section titled “五条教训”

1. 全局工具只用一个包管理器。 bun、npm、Homebrew 三套安装互相干扰，路径冲突让错误信息毫无意义。统一用 npm + asdf Node 之后，一切变得可预测。

2. 升级前备份配置。 openclaw.json 被新版写入后，旧版会报版本不匹配警告。虽然通常不阻断运行，但如果需要回滚，干净的配置备份能省很多事。

3. “回滚再升级”比”直接装最新”可靠。 先装一个已知稳定的旧版，确认能跑，再用 openclaw update 升到最新。这比跳过中间版本直接安装更安全，因为 update 路径的兼容处理比全新安装更完善。

4. 插件生态会滞后。 核心版本发了新 release，插件不一定跟得上。openclaw-weixin v1.0.3 缺少对 openclaw/plugin-sdk 的正确依赖解析，这是已知问题。遇到这种情况，先确认核心功能正常，插件的事等一等。

5. openclaw doctor --fix 是第一步，不是唯一一步。 它能诊断和自动修复一部分问题，但有些问题（比如包管理器路径冲突、插件 SDK 兼容性）超出了它的修复范围。诊断信息很有价值，修复还是要手动来。
