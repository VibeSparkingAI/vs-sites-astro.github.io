50 行需求文档，25 个文件，横跨 Rails API 和 Angular 前端。一个开发会话跑完，后端测试全绿，前端 5 个小问题每个修复不超过一分钟。

这篇文章记录的是一次真实开发经历。工具链是 Claude Code（Anthropic 的 CLI 智能体）+ BMAD 方法论的 Quick Dev Flow + YOLO 模式。目标是在 Rails 后端和 Angular 前端之间建一个完整的内容管理模块：路由、权限、富文本编辑、图片上传、集成测试，全部在一轮会话里交付。

没有逐步确认，没有中途暂停。把需求丢进去，让它自己跑完所有 story，跑通测试。

BMAD + Quick Dev Flow + YOLO 模式

Section titled “BMAD + Quick Dev Flow + YOLO 模式”

先解释几个概念。

BMAD 是 Business-Module-Architecture-Development 的缩写，一个结构化的开发方法论。它的核心思路是把业务需求拆解成模块级别的 story，每个 story 有明确的验收标准和技术边界。

Quick Dev Flow 是 BMAD 里的一条快速通道，通过 /bmad-bmm-quick-dev 命令调用。它跳过了常规流程里的多轮讨论环节，直接从需求文档生成可执行的开发任务。

YOLO 模式 是 Claude Code 的一种运行方式。开启后，Claude Code 不再每一步都停下来等你确认，而是自主执行到底。遇到需要创建文件、运行测试、安装依赖这些操作，它直接做，不问你。

三者组合的效果：BMAD 提供结构和护栏，确保生成的代码遵循项目约定；YOLO 去掉了人机交互的摩擦，把原本需要反复确认的过程压缩成一段连续执行。

需求规格

Section titled “需求规格”

这次要做的是一个内容管理模块，包含两类内容：文章（Article）和问答文档（FAQ）。

核心设计：

  • 统一的 Content 模型，用 content_type 字段区分类型
  • 完整的 CRUD 操作
  • 基于角色的权限控制
  • CMS 管理仪表盘
  • 后端 API 集成测试

需求文档总共约 50 行。没有 PRD，没有 Figma，就是一段文字描述加几个数据字段定义。

第三阶段：5 个 Bug 的修复循环

Section titled “第三阶段：5 个 Bug 的修复循环”

这是整个过程里最有意思的部分。后端有测试兜底，首次生成几乎完美。前端没有自动化测试，全靠眼睛看，问题就暴露出来了。

Bug 1：路由不匹配

Section titled “Bug 1：路由不匹配”

菜单 key 是 content-articles，但懒加载模块注册的路径前缀是 articles。点击菜单，页面空白。

原因很简单：菜单配置和路由配置是两个独立的地方，Claude Code 没有把它们对齐。改菜单 key 或改路由前缀，选一个就行。30 秒修完。

Bug 2：未知属性绑定

Section titled “Bug 2：未知属性绑定”

控制台报错 Can't bind to 'atRows' since it isn't a known property of 'at-textarea'。

Claude Code 猜测 at-textarea 组件支持 atRows 属性，实际上不支持。这个组件是项目自定义的，没有这个输入属性。删掉绑定，用 CSS 控制高度。

Bug 3：重复的编辑按钮

Section titled “Bug 3：重复的编辑按钮”

列表页面出现了两个编辑按钮。一个是表格组件的内置编辑按钮（showEdit 默认为 true），另一个是 Claude Code 额外生成的自定义编辑链接。

设置 showEdit = false，保留自定义链接。

Bug 4：富文本编辑器缺失

Section titled “Bug 4：富文本编辑器缺失”

编辑页面的内容区域只是一个普通的 textarea。需求里写了富文本编辑，但生成的代码没有引入 CKEditor。

项目里其实已经有 CKEditor 的封装组件了。Claude Code 知道需要富文本，但没发现现有的封装。手动指定用 m-ckeditor 组件替换 textarea，一分钟搞定。

Bug 5：图片上传流程不对

Section titled “Bug 5：图片上传流程不对”

m-pic-upload 组件的输出是一个 File 对象，不是 URL。Claude Code 生成的代码直接把输出当 URL 赋值给模型字段，图片显示不出来。

正确的流程是两步：先调用上传接口把 File 对象传上去拿到 URL，再把 URL 赋值给模型。这需要理解项目里的上传架构：m-pic-upload 负责选图和预览，上传逻辑在外面处理。

5 个 bug，每个定位加修复都没超过一分钟。

关键收获

Section titled “关键收获”

约定越强，YOLO 越准。 后端代码库有严格的分层约定和命名规则，Claude Code 学到以后生成的代码几乎不用改。前端的约定分散在组件属性、路由配置、菜单配置等多处，“隐性知识”更多，出错概率更高。

后端靠测试验证，前端靠人工验证。 这次后端 6 个集成测试全绿，给了很强的信心。前端没有 E2E 测试，只能打开浏览器人工检查。如果前端也有自动化测试，修复循环会更快。

修复循环才是真正的效率瓶颈。 代码生成花了几分钟，但如果没有经验判断哪里可能出问题，debug 时间会长得多。5 个 bug 里有 4 个跟项目内部约定有关，这些约定没有写在文档里，只存在于已有代码的模式中。

上传这类涉及多组件协作的功能最容易出错。 图片上传涉及选择组件、上传服务、模型绑定三个环节，Claude Code 只做了第一步就停了。跨组件的数据流需要开发者自己把关。

怎么配置这个工作流

Section titled “怎么配置这个工作流”

如果你想自己试试，步骤如下。

  1. 在项目根目录安装 BMAD 框架。它提供了一套 prompt 模板和 slash command 定义，Claude Code 能直接识别。

  2. 写好功能需求。不需要很长，关键是把数据模型、业务规则、权限要求说清楚。50 行足够。

  3. 在 Claude Code 里输入 /bmad-bmm-quick-dev，调用 Quick Dev Flow。它会读取你的需求文档，自动拆分成 story。

  4. 当 Claude Code 提示确认时，输入 YOLO 模式（在 Claude Code 设置里开启 --dangerously-skip-permissions，或者在会话中选择 YOLO）。这样它就不会每一步都停下来问你了。

  5. 等它跑完。检查后端测试是否通过，打开浏览器检查前端页面。

  6. 把发现的问题反馈给 Claude Code，让它修。通常一两轮就能收敛。

重点是第 2 步。需求写得越清楚、项目约定越显式，Claude Code 的首次输出质量越高。如果你的代码库里有统一的 Service 模式、统一的错误处理、统一的测试结构，YOLO 模式几乎可以一次性交付后端。

前端受限于组件的隐性约定，预期会有几个小问题需要手动修。但整体时间压缩是巨大的：原本可能要半天到一天的全栈功能开发，压缩到了一个会话加几分钟的 debug。

Claude Code + BMAD Quick Dev + YOLO：AI 自主修复缺陷的完整闭环实践

2026年3月12日
Vibe Sparking

从 Issue 到代码、测试、对抗性审查、文档，全程 YOLO 模式，人类只需要做决策。

背景

Section titled “背景”

我们团队在维护一个医疗 SaaS 系统（Rails API + Flutter 客户端）。某天产品提了一个 Bug：科室创建患者时，把手机号等字段改为非必填后，服务器返回”参数丢失”。

一个典型的”改个参数校验”的小需求。但从定位问题、修改代码、写测试、代码审查到文档归档，传统流程至少要半天。

这次，我用 Claude Code + BMAD Quick Dev workflow，在 YOLO 模式下，全程不到 20 分钟完成了闭环。

什么是 BMAD Quick Dev？

Section titled “什么是 BMAD Quick Dev？”

BMAD Method 是一套为 AI Agent 设计的软件开发方法论框架。其中 Quick Dev 是轻量级的快速开发工作流，专为小需求/Bug 修复设计。

它的核心是步骤文件架构（Step-file Architecture）：

每一步加载独立的 Markdown 文件，解决了 LLM 长上下文中”迷失在中间”的问题。状态通过变量（{baseline_commit}、{execution_mode} 等）在步骤间传递。

什么是 YOLO 模式？

Section titled “什么是 YOLO 模式？”

YOLO = “You Only Live Once”。在 Claude Code 中，这意味着跳过人工确认，让 AI 自主决策和执行。

在 Quick Dev 工作流中，YOLO 体现为：

  • 问你要不要先做规格？→ E（直接执行）
  • 展示计划，确认吗？→ YOLO（直接干）
  • 审查发现，怎么处理？→ F（自动修复）

人类只在关键决策点介入（比如”是否要对客户端抛错”这种业务判断），其余全部交给 AI。

实战复盘

Section titled “实战复盘”

第一步：Mode Detection

Section titled “第一步：Mode Detection”

Claude Code 读取 Issue 文件，自动判断：

  • 这是一个单 API 端点的 Bug 修复
  • 没有跨模块依赖，不需要升级到完整的 PRD 流程
  • 捕获 baseline_commit 作为后续 diff 的基准

关键设计： 工作流内置了升级检测机制。如果 AI 判断需求复杂度超过 Quick Dev 的处理范围，会自动建议切换到完整的 BMAD 流程（PRD → 架构 → 实现）。这避免了用简单工具硬做复杂事。

第二步：Context Gathering

Section titled “第二步：Context Gathering”

AI 自主完成了以下工作：

  1. 派出 Explore Agent 搜索整个代码库，定位控制器、服务层、路由、模型、测试文件
  2. 读取关键代码，理解 validate_blank? 的逻辑
  3. 识别根因：values_at(:phone, :name) 把 phone 当必填项
  4. 发现隐患：create_patient_account 依赖 patient.phone，phone 变可选后需要防护
  5. 生成执行计划并推断验收标准

整个过程 AI 自主完成，输出一份结构化的计划让人类确认。

第三步：Execute

Section titled “第三步：Execute”

三个任务顺序执行，中间不停顿：

任务 1： 修改必填参数校验

任务 2： 保护账号创建逻辑

任务 3： 编写测试用例，在 Docker 容器中运行

第四步：Self-Check

Section titled “第四步：Self-Check”

AI 对照自己生成的计划逐项核验：

  • ✅ 所有任务完成
  • ✅ 测试全部通过（含新增用例）
  • ✅ 验收标准满足
  • ✅ 代码风格与现有代码一致

第五步：Adversarial Review（对抗性审查）

Section titled “第五步：Adversarial Review（对抗性审查）”

这是整个流程中最精彩的部分。

AI 构建了从 baseline_commit 到当前的完整 diff，然后派出一个独立的 Code Reviewer Agent 进行对抗性审查。这个 Agent 没有之前的上下文，只看 diff，刻意找问题。

审查结果：

IDSeverityFinding
F1Criticalcreate_account=true + 无手机号时静默跳过，调用方无感知
F2High缺少 create_account=true + 无手机号的测试覆盖
F3Medium布尔条件括号风格不一致，影响可读性
F4Low测试断言失败时清理逻辑被跳过（已有模式）

F1 的发现直接改变了实现方案。 原本是”静默跳过账号创建”，审查后改为”抛出错误通知客户端”——这个决策是人类做的，但问题是 AI 发现的。

第六步：Resolve Findings

Section titled “第六步：Resolve Findings”

选择 [F] Fix automatically，AI 自动修复了 F1-F3，跳过了 F4（已有模式，不在本次范围）。

修复后重新跑测试：3 examples, 0 failures。

后续：人类决策驱动的迭代

Section titled “后续：人类决策驱动的迭代”

工作流结束后，人类提出了两个追加需求：

  1. “创建患者时是否关联医院科室？” → AI 分析代码后发现 hospital_department_id 不会自动填充，于是加了一行自动从医生信息继承的逻辑。

  2. “生成 QA 验证通知” → AI 用简明口语输出了验证场景，直接可以发给测试同事。

  3. “Summary and append to this issue” → AI 按 5Whys / 5W1H / PDCA / QA 格式自动归档到 Issue 文档。

关键洞察

Section titled “关键洞察”

1. AI 自主 ≠ AI 独裁

Section titled “1. AI 自主 ≠ AI 独裁”

YOLO 模式不是”AI 想怎么做就怎么做”。工作流在关键节点设置了人类决策点：

  • 需求复杂度是否需要升级？
  • 执行计划是否合理？
  • 审查发现怎么处理？
  • 业务逻辑的取舍（抛错 vs 静默跳过）

AI 负责执行和发现问题，人类负责决策。 这是高效协作的本质。

2. 对抗性审查是质量保障的关键

Section titled “2. 对抗性审查是质量保障的关键”

Step 5 的设计非常巧妙：用一个没有上下文的独立 Agent 来审查代码。这模拟了真实的 Code Review 场景——审查者不知道你的意图，只看代码本身。

本次实践中，对抗性审查发现了一个 Critical 级别的设计缺陷（静默失败），直接改变了最终实现方案。如果跳过这一步，这个问题很可能上线后才被发现。

3. 步骤文件架构解决了上下文漂移

Section titled “3. 步骤文件架构解决了上下文漂移”

传统的长 prompt 方式，AI 在执行到后半段时容易”忘记”前面的约束。BMAD 的步骤文件架构让每一步都从一个干净的状态开始加载，只继承必要的状态变量。

这不是理论上的优势——在实际使用中，每一步的输出质量都明显比”一个大 prompt 做所有事”要高。

4. 测试是 YOLO 的安全网

Section titled “4. 测试是 YOLO 的安全网”

敢用 YOLO 模式的前提是有测试兜底。本次实践中：

  • 修改代码后立即在 Docker 容器中跑集成测试
  • 每次修复审查发现后重新跑全量测试
  • 测试不仅验证正常路径，还覆盖了边界场景（无手机号 + 创建账号）

没有测试，YOLO 就是赌博。有了测试，YOLO 就是效率。

5. 文档归档不是可选项

Section titled “5. 文档归档不是可选项”

工作流结束后，AI 自动将 5Whys、5W1H、PDCA、QA 测试矩阵归档到 Issue 文档。这不是为了好看——下次类似问题出现时，任何人（包括未来的 AI Agent）都能快速理解历史决策和根因。

总结

Section titled “总结”

Claude Code + BMAD Quick Dev + YOLO 不是银弹，但它解决了一个真实的痛点：小需求的开发效率。

传统流程中，一个”改个参数校验”的需求，从理解代码、写修复、写测试、Code Review、写文档，至少半天。用这套工作流，20 分钟闭环，且代码质量不打折——因为有对抗性审查兜底。

核心理念很简单：让 AI 做 AI 擅长的事（搜索、编码、测试、审查），让人类做人类擅长的事（决策、判断、取舍）。
