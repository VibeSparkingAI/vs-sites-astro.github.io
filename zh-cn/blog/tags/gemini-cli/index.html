一、新增功能 (Added)

Section titled “一、新增功能 (Added)”

1. forceRemoteSettingsRefresh 策略设置

Section titled “1. forceRemoteSettingsRefresh 策略设置”

问题背景 企业/团队管理员通过 managed-settings.json 下发策略（权限规则、沙箱配置、插件白名单等）。此前这些设置会缓存到 remote-settings.json，CLI 启动时使用缓存，如果远端拉取失败则继续用旧缓存——这意味着已撤销的权限可能仍有效，存在安全窗口。

使用场景

  • 金融/医疗等合规敏感行业，管理员紧急撤销某人权限后，需要确保下次启动 立即生效
  • SOC2/ISO27001 审计要求「fail-closed」而非「fail-open」策略

举例

设置后：CLI 启动时阻塞等待远端配置拉取成功 → 成功才进入；失败则退出（fail-closed）。

注意事项

  • 网络不稳定时会导致 CLI 无法启动——适合企业内网环境，不适合离线开发场景
  • 建议搭配 remote-settings.json 缓存 TTL 理解使用
  • 仅对 Team/Enterprise 管理员有意义，个人用户无需关注

历次相关变更

  • 2.1.83：新增 managed-settings.d/ 分片策略目录
  • 2.1.80：修复 managed-settings 启动时未应用的问题
  • 2.1.78：修复 PreToolUse hooks 绕过 deny 规则（含企业 managed settings）

同类对比

  • Codex CLI: 无企业策略管理能力，完全依赖本地配置
  • Gemini CLI: 有 enforcedAuthType (v0.5.0) 强制认证方式，但无 fail-closed 策略刷新机制

趋势: 企业级 CLI 编码工具正在走向 MDM（移动设备管理）式的策略合规模型，fail-closed 是安全团队的标配需求。

2. 交互式 Bedrock 设置向导

Section titled “2. 交互式 Bedrock 设置向导”

问题背景 AWS Bedrock 用户配置 Claude Code 一直是痛点——需要手动设置 ANTHROPIC_BEDROCK_BASE_URL、AWS credentials、区域、模型 ID 等多个环境变量，容易出错。

使用场景

  • 企业用户通过 AWS Bedrock 使用 Claude，不走 Anthropic API 直连
  • 新员工 onboarding，无需阅读文档即可完成配置

举例 启动 Claude Code → 登录界面选「3rd-party platform」→ 进入向导：

  1. 选择 AWS 认证方式（SSO / Access Key / IAM Role）
  2. 配置 Region（us-east-1 等）
  3. 验证凭证有效性
  4. 选择/固定模型（model pinning）

注意事项

  • 仅在登录界面可用，已登录状态下需 claude auth logout 后重新进入
  • Model pinning 很重要——Bedrock 的模型 ID 格式与 Anthropic API 不同

历次相关变更

  • 2.1.84：新增 ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL_SUPPORTS 环境变量覆盖 3P 模型能力检测
  • 2.1.86：改善 Bedrock/Vertex 的 prompt cache 命中率
  • 2.1.83：改善 Bedrock SDK 冷启动延迟

同类对比

  • Codex CLI: 仅支持 OpenAI API，无第三方云平台集成
  • Gemini CLI: 深度绑定 Google Cloud（Vertex AI），配置更简单但无多云支持

趋势: 多云 LLM 接入正成为企业刚需。Claude Code 在 Bedrock、Vertex、Azure Foundry 三大云平台都有支持，领先于竞品。

3. /cost 新增 per-model 和 cache-hit 明细

Section titled “3. /cost 新增 per-model 和 cache-hit 明细”

问题背景 此前 /cost 只显示总费用。用户无法区分不同模型（Opus vs Sonnet vs Haiku）各花了多少钱，也不知道 prompt cache 命中率如何。

使用场景

  • 订阅用户（Pro/Max）想了解 token 消耗分布，优化使用策略
  • 判断是否需要调整 effort level 来节省配额

举例

注意事项

  • 仅对 subscription 用户显示（API 直付用户已有 /usage 详细信息）
  • Cache-hit 百分比能帮你判断会话是否应该 /clear

历次相关变更

  • 2.1.89：/stats 修复子代理用量未计入问题
  • 2.1.84：Token ≥1M 显示为 “1.5m” 格式
  • 2.1.80：新增 rate_limits 字段到 statusline

同类对比

  • Codex CLI: 无内置费用跟踪
  • Gemini CLI: 有 --session-summary (v0.4.0) 输出 JSON 统计，但无实时交互式费用查看

趋势: 透明的成本可观测性是 AI 开发工具的必备——谁都不想月底收到天价账单。

4. /release-notes 交互式版本选择器

Section titled “4. /release-notes 交互式版本选择器”

问题背景 此前 /release-notes 只显示当前版本的更新日志，想看其他版本需要去 GitHub。

使用场景

  • 跨版本升级后想快速了解中间错过了什么
  • 排查问题时确认某个 fix 是哪个版本引入的

注意事项

  • 纯 UX 改进，无功能性影响

同类对比: Codex/Gemini CLI 均无内置 release notes 浏览器。

1.2 CLAUDE_CODE_NO_FLICKER=1 无闪烁渲染

Section titled “1.2 CLAUDE_CODE_NO_FLICKER=1 无闪烁渲染”

变更内容： 新增环境变量，启用基于 alt-screen 的无闪烁渲染，带有虚拟化滚动回溯。

问题背景： Claude Code 的 TUI（终端 UI）在长输出流式渲染时，尤其在 iTerm2/tmux 环境下，容易出现画面闪烁和抖动。这是因为默认使用 main-screen 渲染模式，每次重绘都会影响滚动缓冲区。

使用场景：

适合：

  • 在 tmux 中运行 Claude Code 的用户
  • 使用低刷新率终端模拟器的用户
  • 长时间持续使用（编码马拉松）的场景

注意事项：

  • Alt-screen 模式下，退出后终端滚动缓冲不保留会话内容（类似 vim 退出后屏幕恢复）。
  • 标记为 “opt-in”，说明还不够成熟作为默认行为，可能存在边缘兼容性问题。

同类对比：

  • Codex CLI： 使用 Ink（React for CLI）渲染，自带 alt-screen，闪烁问题较少但自定义程度低。
  • Gemini CLI： 基于 Rich/Textual 的 Python 渲染，闪烁控制中等。

趋势： 终端 AI 工具正在从”能用”走向”好用”，渲染质量是用户体验的核心差异化。未来可能默认启用 alt-screen 并提供完整的虚拟滚动。

Section titled “1.3 PermissionDenied Hook”

使用场景： 自定义钩子脚本检查被拒绝的命令是否在白名单中：

2.5 长会话内存泄漏

Section titled “2.5 长会话内存泄漏”

变更内容： 修复大 JSON 输入作为 LRU 缓存键被保留导致的内存泄漏。

问题背景： LRU 缓存使用输入内容的完整 JSON 字符串作为 key。当输入很大（如读取大文件内容）时，这些字符串常驻内存不被 GC 回收。长时间运行的会话（如 8 小时编码马拉松）会看到 Node.js 进程内存持续增长。

使用场景： 持续使用 Claude Code 数小时，读取多个大文件后，进程内存从 300MB 涨到 2GB+，终端开始卡顿。

注意事项：

  • 建议长会话定期使用 /clear 或 /compact。

同类对比：

  • Codex CLI： 使用 React/Ink 渲染，同样存在内存增长问题但表现不同。
  • Gemini CLI： Python 运行时，GC 策略不同，长会话同样可能有问题。

2.6 超大会话文件（>50MB）删除消息崩溃

Section titled “2.6 超大会话文件（>50MB）删除消息崩溃”

变更内容： 修复从超过 50MB 的会话文件中删除消息时的崩溃。

问题背景： 会话 transcript 文件随对话增长。频繁使用工具（尤其是读取大文件）的会话很容易超过 50MB。删除消息时的全文解析和重写操作在超大文件上会导致内存溢出或超时崩溃。

2.7 LSP 服务器僵尸状态修复

Section titled “2.7 LSP 服务器僵尸状态修复”

变更内容： LSP 服务器崩溃后不再进入僵尸状态，而是在下次请求时自动重启。

问题背景： Claude Code 集成了 LSP（语言服务协议）用于代码智能（跳转定义、类型检查等）。LSP 服务器崩溃后，之前进入不可用状态，所有后续 LSP 功能静默失败直到用户手动重启会话。

使用场景： TypeScript 项目中编辑了一个导致 tsserver OOM 的巨大 .d.ts 文件，LSP 崩溃。修复前需要退出重进 Claude Code；修复后下次调用自动恢复。

同类对比：

  • Codex CLI： 不集成 LSP。
  • Gemini CLI： 不集成 LSP。
  • VS Code/Cursor： LSP 自动重启是标配功能。

趋势： Claude Code 正在朝 IDE 级别的健壮性发展。

2.8 CJK/Emoji 提示历史丢失

Section titled “2.8 CJK/Emoji 提示历史丢失”

变更内容： 修复包含 CJK 或 emoji 的提示历史条目在 ~/.claude/history.jsonl 的 4KB 边界处被静默丢弃的问题。

问题背景： JSONL 文件按 4KB 块读取。CJK 字符和 emoji 是多字节 UTF-8 编码（3-4 字节），当字符恰好横跨 4KB 边界时被截断，导致 JSON 解析失败，整条记录静默丢弃。

使用场景： 中文/日文/韩文用户频繁使用 Claude Code，发现历史提示丢失（按上箭头找不到之前的命令）。

注意事项：

  • 这是一个影响大量亚洲用户的 bug，修复意义重大。
  • 类似的 UTF-8 边界 bug 在很多工具中都存在。

同类对比：

  • Codex CLI： 使用 Node.js readline，CJK 处理由系统库负责。
  • Gemini CLI： Python 的 Unicode 处理相对成熟，但类似边界问题也可能存在。

2.9 /stats Token 统计不准确

Section titled “2.9 /stats Token 统计不准确”

问题背景： 用户依赖 /stats 监控 API 用量和成本。遗漏子代理用量意味着显著低估实际消耗，尤其在重度使用后台代理的场景下。

2.10 --resume 和 --continue 恢复问题

2.13 SDK 发送图片时系统上下文丢失

2.15 Autocompact 死循环修复 ⭐

Section titled “2.15 Autocompact 死循环修复 ⭐”

变更内容： 检测到上下文在 compact 后立即重新填满（连续 3 次），停止并报告可操作的错误，而非无限循环消耗 API 调用。

问题背景： 这是一个严重的成本和可用性 bug。当项目配置导致大量上下文被注入（如嵌套的 CLAUDE.md、大量 skill 描述），compact 后这些内容立即重新注入，触发再次 compact，形成死循环。每次 compact 都是一次 API 调用，可能在用户不知情的情况下消耗大量 token。

使用场景： 大型 monorepo 中有多层嵌套的 CLAUDE.md 文件，每次 compact 后这些文件全部重新注入，token 数立即回到阈值。循环几十次后用户发现 API 用量飙升。

注意事项：

  • 如果遇到此错误，检查是否有过多的 CLAUDE.md 嵌套或 skill 描述过长。
  • 配合本版另一个修复（2.17 CLAUDE.md 重复注入）一起理解。

同类对比：

  • Codex CLI： 无 auto compact 功能，上下文满了直接报错。
  • Gemini CLI： 上下文管理策略不同，无类似循环问题。

趋势： 自动上下文管理是长会话可用性的核心，但需要更智能的策略（如增量 compact、选择性保留）。

2.16 Prompt Cache 命中率下降修复

Section titled “2.16 Prompt Cache 命中率下降修复”

变更内容： 修复长会话中 tool schema 字节变化导致的 prompt cache miss。

问题背景： Anthropic API 的 prompt cache 依赖前缀匹配。如果 tool schema 在会话中发生微小变化（如 MCP 工具动态更新描述），会导致整个 prompt 前缀失效，cache miss，每次请求都要重新处理完整上下文，大幅增加延迟和成本。

注意事项：

  • 这是一个”隐性成本”bug——用户可能只是觉得”怎么变慢了”，不会意识到是 cache miss。

2.17 嵌套 CLAUDE.md 重复注入

Section titled “2.17 嵌套 CLAUDE.md 重复注入”

变更内容： 修复长会话中读取多文件时，嵌套 CLAUDE.md 文件被重复注入数十次的问题。

问题背景： Claude Code 会自动发现并加载项目中所有层级的 CLAUDE.md 文件。在长会话中随着文件操作增加，注入逻辑的去重机制失效，同一个 CLAUDE.md 可能被加入上下文 20-30 次。

使用场景： Monorepo 中每个包有自己的 CLAUDE.md：

长会话中频繁跨包操作，每次操作都重新注入所有 CLAUDE.md。

2.19 误导性 “Rate limit reached” 错误

Section titled “2.19 误导性 “Rate limit reached” 错误”

问题背景： 用户看到 “Rate limit reached” 会以为是临时限流，等待后重试。但实际可能是：

三十多个 Agent 工具现在读取同一种文件格式。Claude Code、Gemini CLI、Cursor 等工具全部解析同一套 SKILL.md 结构——YAML 前置信息、相同的目录布局、相同的规范。

那为什么大多数 Skill 在生产环境中仍然出问题？

因为开发者把精力都花在了写对 YAML 和整理目录上。格式问题已经解决了。现在的挑战是内容设计。规范告诉你如何打包一个 Skill，但对如何组织内部逻辑毫无指导。

一个封装 FastAPI 规范的 Skill 与一个四步文档流水线的运作方式完全不同，尽管它们的 SKILL.md 文件从外观上看一模一样。相同的前置信息，相同的目录，可靠性却天差地别。

通过研究生态系统中的各类 Skill 构建方式——从 Anthropic 的代码仓库到 Vercel 和 Google 的内部指南——五种反复出现的设计模式浮现出来。每种模式回答一个不同的架构问题，每种模式都附有可运行的 ADK 代码。

模式一：Tool Wrapper（工具封装器）

Section titled “模式一：Tool Wrapper（工具封装器）”

Tool Wrapper 让你的 Agent 在需要时按需加载某个特定库的上下文。你不必把 API 规范硬编码到系统提示词里，而是将它们打包进一个 Skill。Agent 只在实际用到该技术时才加载这份上下文。

这是最简单的模式。SKILL.md 监听用户提示词中的特定库关键词，从 references/ 目录动态加载你的内部文档，并将这些规则作为基准事实应用。这是一种将团队编码规范或框架最佳实践直接注入开发者工作流的方式。

模式二：Generator（生成器）

Section titled “模式二：Generator（生成器）”

Tool Wrapper 应用知识，Generator 则确保输出的一致性。如果你的 Agent 每次运行生成的文档结构都不一样，Generator 通过编排一个填空式流程来解决这个问题。

它使用两个可选目录：assets/ 存放输出模板，references/ 存放风格指南。指令的作用像项目经理——告诉 Agent 加载模板、读取风格指南、询问用户缺失的变量，然后填充文档。

**适用场景：**需要一致、可预测的输出——API 文档、提交信息、项目脚手架。

模式三：Reviewer（审查器）

Section titled “模式三：Reviewer（审查器）”

Reviewer 把检查什么和怎么检查分离开来。你不用在系统提示词里罗列所有代码坏味道，而是把一份模块化的评审标准存进 references/review-checklist.md。

代码到达后，Agent 加载清单并按步骤打分，按严重程度归类结果。把 Python 风格检查表换成 OWASP 安全检查表，用同一套 Skill 基础设施就能得到截然不同的审计报告。

**适用场景：**需要依照清单评分——PR 审查、安全审计、合规检查。

模式四：Inversion（反转）

Section titled “模式四：Inversion（反转）”

Agent 的本能是猜测并立即生成。Inversion 翻转了这个顺序。不是用户驱动提示词、Agent 执行，而是 Agent 先对用户展开访谈。

核心机制是明确的、不可绕过的门控指令：“在所有阶段完成之前，不得开始构建。“Agent 按顺序提出结构化问题，等待回答，在拿到完整信息之前拒绝输出任何结果。

**适用场景：**需要在行动前充分收集需求——项目规划、架构设计、入职流程。

模式五：Pipeline（流水线）

Section titled “模式五：Pipeline（流水线）”

面对复杂任务，步骤不能跳过。Pipeline 通过硬性检查点强制执行严格的顺序工作流。

指令本身就是工作流定义。菱形门控条件（例如要求用户审批后才能推进）确保 Agent 无法绕过步骤或呈现未经验证的结果。不同的参考文件只在需要它的步骤处加载，保持上下文窗口清爽。

**适用场景：**顺序严格、每个阶段都需要验证的复杂多步骤任务。

选择合适的模式

Section titled “选择合适的模式”

每种模式回答一个不同的问题：

问题模式
需要注入库或框架的上下文？Tool Wrapper
需要基于模板的一致输出？Generator
需要依照清单评分？Reviewer
需要先收集需求？Inversion
需要严格的多步骤工作流？Pipeline

从你的任务提出的问题出发。如果跨越多个问题，组合使用这些模式。

模式可以组合

Section titled “模式可以组合”

这些模式并非互斥。

一个 Pipeline Skill 可以在末尾加入 Reviewer 步骤来自我校验。一个 Generator 可以在填充模板之前借助 Inversion 收集所需变量。得益于 ADK 的 SkillToolset 和渐进式加载机制，你的 Agent 在运行时只为真正用到的模式消耗上下文 token。

这是架构上的优势：不是把复杂脆弱的指令塞进一个系统提示词，而是把行为分解成可组合的构建块。每个块可以单独测试，每个块有清晰的契约。

实践建议

Section titled “实践建议”
  1. 从单一模式开始。大多数任务干净地对应一种模式，不到需要的时候不要组合。
  2. 在元数据中标注模式。加上 metadata.pattern: tool-wrapper 让架构一目了然，也方便检索。
  3. 把参考资料放到外部文件。不要把大段检查表内联进 SKILL.md。
  4. 在 Pipeline 中设置严格的门控。每跳过一个检查点，就少一次验证机会。
  5. 单独测试每个模式。Generator 模板坏了是 Generator 的问题，不是整个 Skill 的问题。

千站一面的问题

Section titled “千站一面的问题”

每个主流大模型都是从同一批网页数据里训练出来的。同一套 Bootstrap 布局，同一套 Tailwind 模板，同一批 UI 组件库截图。你不给它具体方向，它就给你一个”网站的统计学均值”。

让 Claude 或 GPT “做一个落地页”，大概率你会拿到：

  • Inter 或系统默认字体（绝不会选什么有特色的）
  • 紫蓝渐变大 hero
  • 卡片套卡片再套卡片
  • 有色背景上搁灰色文字（对比度不达标）
  • 弹跳动效（2022 年之后就过时了）

这不是 bug。它只是在给你最大概率的输出。你告诉它太少了，它就给你最安全的答案。

词汇量才是瓶颈

Section titled “词汇量才是瓶颈”

Impeccable 的作者 Paul Bakaus 把问题说到了点上：好的设计提示词需要设计词汇。大多数开发者没有这个词汇量。

你说不出”垂直节奏再强一点”这种话，因为你没用过这个词。你不知道可以要求”用带色调的中性色替代纯灰”，因为你不知道有这个选项。你没法让 AI 用”OKLCH 色彩空间”或”模块化字号比例”，因为这些概念不在你的脑子里。

问题不在 AI 的能力，在你和 AI 之间缺了一层设计语言。

（Claude Code 待续）Zed 引入 ACP 接入外部 Agent（Gemini CLI 已上线）

2025年8月28日
Vibe Sparking

Zed 做了一个 Agent Client Protocol（ACP），把“终端里的智能体 Gemini CLI, Claude Code”等接进编辑器里。第一个落地案例就是 Gemini CLI。你继续用熟悉的 CLI，Zed 负责把它嵌到面板里、看得见改动、还能多缓冲区审阅。官方还明说，ACP 是开源（Apache 2.0），欢迎更多 Agent 和编辑器加入生态。

一句话总结（TL;DR）

Section titled “一句话总结（TL;DR）”
  • ACP = 给智能体的“LSP”：像当年的语言服务器协议一样，把 Agent 和编辑器解耦，想换就换。
  • Gemini CLI 已可直接在 Zed 用：打开 Agent 面板即可新建线程；Zed 0.201.5+ 支持。
  • 真实 CLI、非“阉割版”：Zed 后台跑 Gemini CLI，通过 ACP 对话；可在编辑器里直观看到文件与改动。
  • 开箱就能干活：没装 CLI 会自动安装；已装则走 PATH；Gemini CLI 需 ≥ 0.2.0。
  • 可自带任意 Agent：只要会说 ACP，改下配置就能接；内置调试日志。

引言

Section titled “引言”

很多人问：“我能不能在一个编辑器里切换多个 AI 编程 Agent？” Zed 这波给了答案：能。现在就能。ACP 把‘代理’和‘编辑器’分开了，Gemini CLI 率先打样，Neovim 也已跟进支持 ACP 的生态（Code Companion）。生态的门，打开了。

为什么 ACP 值得关注？

Section titled “为什么 ACP 值得关注？”

1）像 LSP 一样“解耦” 你不必为了换 Agent 换编辑器。任何讲 ACP 的 Agent 都能插进 Zed 的 UI，享受多缓冲区对比、语法高亮、以及对改动的实时可视化。数据只在本地，不经过 Zed 服务器。

2）“真实能力”+“编辑器体验” Zed 不是模拟一个“聊天窗口”，而是直接把 Gemini CLI 当子进程跑，用 JSON-RPC 通信。好处是：你得到 CLI 的全部能力，同时获得编辑器级的变更预览与导航。

3）开放生态 ACP 开源（Apache 2.0），官方还号召其他编辑器加入；Neovim 的 Code Companion 已支持 ACP 兼容 Agent。这意味着未来你可以在不同编辑器里获得类似体验。

Vibe Kanban 工具实战：一键管理 Claude、Gemini、Amp 任务

2025年7月12日
Vibe Sparking

Coding Agent（如 Claude Code、Gemini CLI、Amp 等）在工程开发中的作用愈发重要。团队发现现在花在规划、审查、协调这些人类工作上的时间，已经超过了写代码本身。

Vibe Kanban https://github.com/BloopAI/vibe-kanban，正是一款专注解决这类协作流程问题的新工具。它通过 Kanban 板界面，让你可以：

  • 快速切换编码 Agent（Claude、Gemini、Amp 等）；
  • 并行或串行调用多个 Agent，自动执行任务；
  • 以可视化方式查看 task 状态、代码审查、Dev Server 快速启动；
  • 集中管理 Agent 的 MPC 配置，提升整体协作效率；
  • 未来还能通过 MCP 服务器让 coding agent 自动创建 task ticket。

Vibe Kanban 的设计理念是：当大部分代码由 AI 写，我们人类的角色就是规划、审查、协调。这不仅是趋势，也是一种全新的开发工作方式。

⚙️ 安装+启动指南

Section titled “⚙️ 安装+启动指南”

  1. 提前配置好 Agent 比如安装并登录 Claude Code、Gemini CLI、Amp 等。

  2. 运行命令启动 Vibe Kanban

    自动寻找本地端口并打开浏览器(如http://127.0.0.1:53046），进入 Kanban 工作区。

  3. 配置 Agent 首次需在 Settings 中添加 Agent MCP（例如 Claude、Gemini、Amp 的 token/path)，后续可在 UI 中自由切换 Agent 执行任务。

  4. 创建项目 在 Kanban 界面创建新项目，添加 Task（任务），即可开始使用。

📌 核心功能详解

Section titled “📌 核心功能详解”

1. 多 Agent 并行或串行执行任务

Section titled “1. 多 Agent 并行或串行执行任务”

切换到相应 Agent 后，可为同一 Task 发起多个“Attempts”。 支持并行运行（不同分支/工作区），也支持串行执行（等待上一步完成再进行）。执行状态、日志一目了然。

2. 快速审查与 Dev Server 启动

Section titled “2. 快速审查与 Dev Server 启动”

每次 Agent 生成代码后，Vibe Kanban 会自动显示 diff 与执行输出，并提供一键启动 Dev Server 的按钮，方便实时预览。

3. 可视化任务流管理

Section titled “3. 可视化任务流管理”

采用常见的 Kanban 三列（To Do，In Progress，Done），直观睡一眼看到 Task 状态与 Agent 执行进度。 你可以为某 Task 创建多个 Attempt（尝试），并标记为成功/失败。

4. 集中配置 Agent MCP

Section titled “4. 集中配置 Agent MCP”

所有 Agent 的配置（例如 Claude、Gemini 的 token、运行命令等）都在 Settings 界面集中管理，切换使用流畅无缝。

5. Agent 自动建 Ticket（MCP 集成）

Section titled “5. Agent 自动建 Ticket（MCP 集成）”

Vibe Kanban 内建 “Vibe Kanban MCP” 服务器插件，可通过 Agent 自动生成 planner ticket。例如：

“Plan a migration from AWS to Azure and create detailed tickets…” Agent 会自动拆解任务、创建多个 Kanban 卡片，这一切都在 UI 中完成，无需人工介入。

💼 一个典型流程示例

Section titled “💼 一个典型流程示例”
  1. 在 Kanban 中创建一个 Task：例如 “实现用户登录页面”；
  2. 选择 Agent（如 Claude Code），点击 “New Attempt”；
  3. Agent 自动生成登录页面组件与后端接口；
  4. 你审查差异，运行 Dev Server，验证 UI；
  5. 发现问题，修改指示让 Agent 重试，或重新选 Agent（如 Gemini）；
  6. 标记 Attempt 成功，将 Task 移至 Done。

整个过程无需切换命令行窗口，一切在 UI 内操作，高效直观。

🧭 小结 & 为什么推荐关注

Section titled “🧭 小结 & 为什么推荐关注”

  • 对个人开发者： 极大提升启动任务、审查、调试效率，让开发更流畅、更有结构感。

  • 对小团队协作： Agent 自动拆任务、多个 Attempt 协同完成、有独立 Git worktree、可接入外部 MCP，适合团队流水线协作。

  • 投资未来能力： 随着 Agent 能力的持续提升，Vibe Kanban 能无缝适配不同 Agent，让你随时体验最新模型能力。

⏳ 尾声：AI 在编码，我们在协作

Section titled “⏳ 尾声：AI 在编码，我们在协作”

Vibe Kanban 正在开创「Agent 驱动、人人驾驭」的新范式。从写代码到 orchestrate 和 review 代码时代，我们将释放人的创造力，让 Agent Handoff 更高效、流程更清晰。推荐所有正在试用或在生产中使用 coding agents 的开发者一试。
