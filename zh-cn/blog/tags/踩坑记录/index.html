给 OpenClaw 接 Discord 机器人，Message Content Intent 的坑和绕法

2026年3月17日
Vibe Sparking

飞书上已经跑着一个 OpenClaw 智能体。能回答问题，能路由模型，能拉起 Claude Code。有人问：“Discord 上也能用吗？”

觉得应该不难。确实不难，但有坑。

这篇记录给 OpenClaw 加 Discord 通道的全过程、吃掉两个小时的一个 bug，以及让 Discord 值得折腾的那个功能。

环境

Section titled “环境”
  • macOS
  • OpenClaw 2026.3.13
  • 目标 agent：vs-dev
  • 已接入飞书，Discord 是第二通道

第一步：创建 Discord Bot

Section titled “第一步：创建 Discord Bot”

打开 Discord Developer Portal（discord.com/developers/applications）。

  1. 点 New Application，取个名字（比如 “vs-dev”）
  2. 左侧进 Bot，记下 Bot Username
  3. 点 Reset Token，复制 token——只显示一次

接下来是容易跳过、代价很大的一步：

开启 Privileged Gateway Intents

Section titled “开启 Privileged Gateway Intents”

还在 Bot 页面，往下滚到 Privileged Gateway Intents，三个全打开：

  • Presence Intent
  • Server Members Intent
  • Message Content Intent——最关键的一个

点 Save Changes。

不开 Message Content Intent 的后果：bot 在群频道里能收到消息，但读不到消息内容。@mention 检测跑不了，因为文本字段是空的。bot 会把所有群消息静默丢弃，日志里只留一行 reason: no-mention。没有报错，没有告警。

生成邀请链接

Section titled “生成邀请链接”

进 OAuth2 > OAuth2 URL Generator：

  • Scopes：bot + applications.commands
  • Bot Permissions：View Channels、Send Messages、Read Message History、Embed Links、Attach Files

复制生成的 URL，浏览器打开，选目标 Server，授权。

拿到 ID

Section titled “拿到 ID”

打开 Developer Mode（User Settings > Advanced > Developer Mode）：

  • Server ID：右键 Server 图标 > Copy Server ID
  • User ID：右键自己头像 > Copy User ID

群频道不回复

Section titled “群频道不回复”

表现： bot 连着、收到消息，但不回复。日志里是：

原因： intents:content=limited。Message Content Intent 没生效，bot 收到的消息 content 字段为空，从空字符串里检测不到 @mention。

修法（两条路一起走）：

  1. 回到 Discord Developer Portal > Bot > Privileged Gateway Intents，确认 Message Content Intent 已打开。Save。等最多 15 分钟让 Discord 传播。

  2. guild 配置里加 requireMention: false。这既是绕行方案，也是一种设计选择——配合 users 白名单，不需要 @mention 也能精确控制谁触发 bot。

如果等了 15 分钟 content=limited 还在：到 Developer Portal 里 Reset Token，更新 openclaw.json 中的 token，重启 gateway。

bot 频繁断线重连

Section titled “bot 频繁断线重连”

表现： 日志反复出现 health-monitor: restarting (reason: disconnected)。

原因： Discord WebSocket 连接不稳定，health monitor 自动重连。Intent 问题修好后通常就稳了。正常机制，不是 bug。

openclaw doctor 反复提示修改

Section titled “openclaw doctor 反复提示修改”

表现： 每次重启都提示 Moved channels.discord single-account top-level values into channels.discord.accounts.default。

处理： 跑 openclaw doctor --fix 自动修正。跑完检查一下，可能会多出一个 accounts.default 条目，需要手动清理。

109 commands exceeds limit

Section titled “109 commands exceeds limit”

表现： 日志写 discord: 109 commands exceeds limit; removing per-skill commands and keeping /skill。

影响： 没有。Discord 每个 bot 最多 100 个 slash command，OpenClaw 自动精简，保留 /skill 入口。所有 skill 通过 /skill 照常可用。

坑三：消息静默消失

Section titled “坑三：消息静默消失”

这个最耗时间。

配置全部完成，Gateway 重启后，给机器人发 “hi”。没有回复。

日志里看到：

WebSocket 连接正常。但是没有任何 im.message.receive_v1 事件进来。

排查路径：

  1. WebSocket 已连接 → 正常
  2. 事件日志为空 → 消息压根没推过来，问题在飞书那边
  3. 改 dmPolicy 为 open → 还是没消息
  4. 去飞书后台仔细检查 → 找到了

im:message.p2p_msg:readonly 这个权限状态是”未开通”。

这是”读取用户发给机器人的单聊消息”权限。没有这个权限，飞书在服务端就把事件过滤掉了。不发给长连接，不报错，不告警。消息直接丢了。

开通这个权限，发布新版本，重启 Gateway。消息立刻通了。

整个过程最难受的地方是系统给了零反馈。WebSocket 连着，配置看起来没问题，但消息就是不来。如果飞书能在事件过滤时返回一条 permission_denied 之类的提示，能省不少排查时间。

Section titled “配置检查清单”

每次配新的飞书应用时走一遍这个清单：

  • openclaw.json 中账号的 appId / appSecret 已写入
  • bindings 中 accountId 对应正确的 agentId（不是 agent）
  • dmPolicy: "open" 且 allowFrom: ["*"]（接收私聊的话）
  • 飞书后台：机器人能力已添加
  • 飞书后台：订阅方式为”长连接”，事件 im.message.receive_v1 已添加
  • 飞书后台：im:message.p2p_msg:readonly 权限已开通
  • 飞书后台：已发布最新版本
  • openclaw gateway restart 已执行

小结

Section titled “小结”

飞书接入 OpenClaw 本身不复杂，但有三个地方不按直觉来：凭据用 config set 写入而不是 --token 参数、本地扩展可能跟内置插件打架、私聊权限缺失时消息无声无息地丢。知道了坑在哪，下次配新应用几分钟就搞定。

两台 Mac 跑 OpenClaw，'Allow device to connect?' 弹个没完？四条命令治好它

2026年3月12日
Vibe Sparking

两台 Mac，一个局域网，同一套 OpenClaw。

一台当 Gateway，另一台以 node 身份连过去。连上之后，Gateway 这边冒出来一个弹窗：

Allow device to connect?

点了 Allow。过一会儿，又弹。再点，再弹。关掉窗口重开，还是弹。

这不是 bug。

为什么会弹

Section titled “为什么会弹”

OpenClaw 对设备连接有一套配对机制。规则很简单：

  • 127.0.0.1 / localhost → 本机回环，信任，不弹
  • 其他所有地址 → 外部设备，触发配对确认

两台 Mac 在同一个局域网，IP 是 192.168.x.x。对 Gateway 来说，这和互联网上随便一台机器没区别——都不是 localhost，都要走配对流程。

GitHub 上多个 issue 都确认了这个行为：非 localhost 连接必然触发 pairing。目前没有”同一子网就自动信任”的逻辑。

为什么点了 Allow 还会再弹

Section titled “为什么点了 Allow 还会再弹”

常见原因：

  1. 设备身份变了。 Gateway token 轮换、网络切换、macOS 更新，都可能导致 node 端的设备指纹变化。指纹一变，Gateway 认为是新设备或需要 repair 的旧设备，重新触发配对。
  2. pending repair 没清掉。 设备处于”等待修复确认”状态时，UI 上的 Allow 不一定能彻底解决。很多场景下只能靠 CLI 审批。
  3. token churn 循环。 近期 macOS 上有报告显示 token 反复刷新，导致 pairing required 循环出现。

一句话：UI 上点 Allow 有时候只是临时通过，没有走完整个设备生命周期。

三种拓扑方案

Section titled “三种拓扑方案”

根据你的使用场景选：

方案 A：各跑各的 localhost（推荐）

Section titled “方案 A：各跑各的 localhost（推荐）”

每台 Mac 各自运行自己的 OpenClaw 实例。channel、app、UI 只连本机 localhost。不做任何局域网 node-to-gateway 互连。

好处：localhost 连接不触发配对，弹窗从根源上消失。

适合：两台 Mac 是独立的工作环境，不需要共享 Gateway。

方案 B：保留局域网互连，CLI 批准一次

Section titled “方案 B：保留局域网互连，CLI 批准一次”

继续让一台 Mac 当 Gateway，另一台以 node 连过去。但在 Gateway 侧用上面的四步 CLI 流程把设备正式批准或清理干净。

好处：保留了集中管理的灵活性。

注意：如果设备身份频繁变化（token churn），可能需要偶尔重新处理。建议固定 Gateway token，减少身份漂移。

  2. dangerouslyDisableDeviceAuth 在最近几个版本有回归 bug，多个报告显示它不能稳定绕过设备检查。

Section titled “踩过的坑”

群聊：踩坑的地方

封禁按时解除了。但教训很清楚：QQ 的安全审核系统是真的在运行的，而且规则不太透明。反复触发会加重封禁时长。

总结

Section titled “总结”

好的地方很明确：国内直接用，不需要任何代理和 VPN；所有 OpenClaw 通道里配置最简单；语音转文字在手机端真正好用；多机器人支持，账号互相隔离；引用消息能正确解析上下文。

我的建议是直接用。这是 QQ AI 助手最快的接入路径。群聊回复保持简洁，别在群里发表格和长 Markdown。开发阶段用稳定的网络环境，别频繁重连。被封了就等，别立刻重试，那只会让情况更糟。如果群聊是你的核心场景，最好准备一个备用通信渠道。
