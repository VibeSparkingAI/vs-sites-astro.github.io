macOS SSH 登录后中文显示乱码的排查与修复

2026年4月3日
Vibe Sparking

问题现象

Section titled “问题现象”

通过 SSH 登录 macOS 主机后，使用 more 查看包含中文的 Markdown 文件，中文内容显示为乱码或被识别为 binary：

即使选择继续查看，中文也显示为乱码字符。

根因分析

Section titled “根因分析”

登录远程主机检查 locale 设置：

LANG 为空，所有 LC_* 均为 C。

C locale 只认 ASCII 单字节字符。UTF-8 编码的中文每个字符占 3 个字节，在 C locale 下会被当作非法字节序列，导致：

  • more 误判文件为 binary
  • cat 输出乱码（取决于终端模拟器是否自行处理 UTF-8）
  • less 可能部分正常（因为它有独立的字符编码处理逻辑）

为什么 macOS 会这样？

Section titled “为什么 macOS 会这样？”

macOS 的 Terminal.app 默认勾选了「Set locale environment variables on startup」，本地使用时 LANG 会被设为 en_US.UTF-8 或 zh_CN.UTF-8。但通过 SSH 登录时：

  1. SSH 客户端可能不转发 locale 变量（取决于 SendEnv 配置）
  2. 远程 sshd 可能不接受 locale 变量（取决于 AcceptEnv 配置）
  3. 用户 shell 配置文件（.zshrc / .bashrc）没有显式设置 LANG

三个条件任一不满足，远程 session 就会 fallback 到 C locale。

修复方法

Section titled “修复方法”

最可靠的方案：在远程主机的 shell 配置文件中显式设置 locale。

不依赖 SSH 的 locale 转发机制，无论从哪里登录都能生效。

额外建议

Section titled “额外建议”
  1. 优先用 less 而不是 more — less 对 UTF-8 的处理更稳健，即使 locale 有问题也经常能正确显示
  2. 不要依赖 SSH locale 转发 — SendEnv / AcceptEnv 的配置在不同系统间不一致，显式设置最可靠
  3. LC_CTYPE 是关键 — 如果只能设一个变量，设 LC_CTYPE=en_US.UTF-8，它控制字符分类和编码识别

总结

Section titled “总结”

macOS 作为 SSH 服务端时，默认不设置任何 locale 环境变量。本地使用不受影响（Terminal.app 会自动设置），但 SSH 远程登录时会 fallback 到 C locale，导致中文等多字节字符显示异常。在 shell 配置文件中显式 export LANG=en_US.UTF-8 即可彻底解决。

macOS 在背后干了什么

Section titled “macOS 在背后干了什么”

这里有个很多人不知道的细节：macOS 在休眠或重启时，会清理 /private/tmp/ 下的内容。tmux 的 socket 就放在那里。socket 没了，tmux server 自然起不来，session 自然也没了，里面跑着的 SSH 隧道当然一起凉凉。

更根本的问题是：tmux 是一个普通的用户空间进程，它没有任何机制让 macOS 在休眠后帮你重启它。你 tmux new-session 起来的东西，macOS 压根不知道它的存在，也不在乎它死没死。

所以这个问题不是”怎么让 tmux 更稳定”，而是”tmux 本来就不该干这个活”。

换个思路：launchd + autossh

Section titled “换个思路：launchd + autossh”

launchd 是 macOS 的服务管理器，系统启动时最先跑起来的进程之一，PID 1 就是它。你告诉它要运行什么、什么时候运行、崩溃了怎么办，它帮你管着。macOS 休眠、重启、重新登录，launchd 都知道该干什么。

autossh 则解决了另一个问题：SSH 连接偶尔还是会断（网络抖动、NAT 超时）。autossh 会监控连接状态，断了自动重连。两者配合，隧道基本上就是永活的。

Section titled “它是什么”

macos-use 是一个 MCP 服务器，用 Swift 写的。它让 Claude 或任何兼容 MCP 的模型，通过 macOS 的无障碍 API（Accessibility APIs）直接控制桌面应用。

关键不是截图。是语义树。

macOS 里每一个 App 的 UI 元素——按钮、输入框、菜单、列表——都暴露在无障碍 API 里，结构化的，有层次的。macos-use 读的就是这棵树。AI 看到的是「地址栏，当前值 google.com，可点击」，而不是一张 1200×800 的截图。

两台 Mac 跑 OpenClaw，'Allow device to connect?' 弹个没完？四条命令治好它

Vibe Sparking

两台 Mac，一个局域网，同一套 OpenClaw。

一台当 Gateway，另一台以 node 身份连过去。连上之后，Gateway 这边冒出来一个弹窗：

Allow device to connect?

点了 Allow。过一会儿，又弹。再点，再弹。关掉窗口重开，还是弹。

这不是 bug。

为什么会弹

Section titled “为什么会弹”

OpenClaw 对设备连接有一套配对机制。规则很简单：

  • 127.0.0.1 / localhost → 本机回环，信任，不弹
  • 其他所有地址 → 外部设备，触发配对确认

两台 Mac 在同一个局域网，IP 是 192.168.x.x。对 Gateway 来说，这和互联网上随便一台机器没区别——都不是 localhost，都要走配对流程。

GitHub 上多个 issue 都确认了这个行为：非 localhost 连接必然触发 pairing。目前没有”同一子网就自动信任”的逻辑。

为什么点了 Allow 还会再弹

Section titled “为什么点了 Allow 还会再弹”

常见原因：

  1. 设备身份变了。 Gateway token 轮换、网络切换、macOS 更新，都可能导致 node 端的设备指纹变化。指纹一变，Gateway 认为是新设备或需要 repair 的旧设备，重新触发配对。
  2. pending repair 没清掉。 设备处于”等待修复确认”状态时，UI 上的 Allow 不一定能彻底解决。很多场景下只能靠 CLI 审批。
  3. token churn 循环。 近期 macOS 上有报告显示 token 反复刷新，导致 pairing required 循环出现。

一句话：UI 上点 Allow 有时候只是临时通过，没有走完整个设备生命周期。

第二步：批准（或拒绝）pending 请求

也可以用 reject 代替 approve，效果是清掉 pending 状态。关键是别让它继续挂着。

三种拓扑方案

Section titled “三种拓扑方案”

根据你的使用场景选：

方案 A：各跑各的 localhost（推荐）

每台 Mac 各自运行自己的 OpenClaw 实例。channel、app、UI 只连本机 localhost。不做任何局域网 node-to-gateway 互连。

好处：localhost 连接不触发配对，弹窗从根源上消失。

适合：两台 Mac 是独立的工作环境，不需要共享 Gateway。

方案 B：保留局域网互连，CLI 批准一次

Section titled “方案 B：保留局域网互连，CLI 批准一次”

继续让一台 Mac 当 Gateway，另一台以 node 连过去。但在 Gateway 侧用上面的四步 CLI 流程把设备正式批准或清理干净。

好处：保留了集中管理的灵活性。

注意：如果设备身份频繁变化（token churn），可能需要偶尔重新处理。建议固定 Gateway token，减少身份漂移。

  1. allowInsecureAuth 削弱设备身份校验，官方安全通告明确指出风险。
  2. dangerouslyDisableDeviceAuth 在最近几个版本有回归 bug，多个报告显示它不能稳定绕过设备检查。

Section titled “Google Antigravity 终端沙盒：给 AI 代理装上内核级安全带”

写在前面

Section titled “写在前面”

AI 编程助手越来越能干，但也让人有点紧张——你让它跑个终端命令，它顺手把你系统文件给改了怎么办？

Google Antigravity 最近搞了个终端沙盒功能，直接用内核级隔离来解决这个事。打开后，AI 代理执行的所有终端命令都被锁在指定的工作空间里，想碰系统文件、用户目录都不行。

随着 AI 工具越来越自主，能跑复杂的多步操作，这种安全边界真的挺必要。

核心亮点

Section titled “核心亮点”
  • 通过 macOS Seatbelt (sandbox-exec) 实现内核级隔离，构建强大的安全边界
  • 文件系统限制：只能写入工作空间目录和必要的系统位置
  • 独立网络控制 — 在保持文件系统限制的同时，允许或拒绝网络访问
  • “请求审核”模式下的单命令绕过选项，提供灵活性
  • 安全模式下自动激活，默认拒绝网络访问
  • 即将支持 Linux（目前仅限 macOS）

打开沙盒

Section titled “打开沙盒”

沙盒默认是关着的，要去设置里自己开：

  1. 打开 Antigravity 设置
  2. 找到终端那块儿
  3. 把**“启用终端沙盒”**开关打开
  4. 想控制网络访问的话，再开**“沙盒允许网络”**

如果开了安全模式，沙盒会自己启动，网络访问默认被关掉。

沙盒工作原理

Section titled “沙盒工作原理”

底层技术：Seatbelt

Section titled “底层技术：Seatbelt”

Google Antigravity 利用苹果的 Seatbelt 沙盒机制 (sandbox-exec)，为进程提供内核级隔离。这与 macOS 用于沙盒化 App Store 应用的技术相同。

启用沙盒后：

  1. 文件系统：代理只能写入指定的工作空间目录，并从必要的系统位置读取
  2. 网络访问：通过”沙盒允许网络”开关独立控制
  3. 违规操作：任何超出允许边界的操作都会被立即阻止并显示清晰的错误消息

沙盒是默认开的吗？

能绕过沙盒跑命令吗？

可以。用”请求审核”模式的时候，会看到”绕过沙盒”的选项，选了就能跑这一次。这样既保持安全，又不会太死板。

支持 Linux 或 Windows 吗？

目前只有 macOS，因为用的是苹果的 Seatbelt 机制。Linux 说”即将推出”，Windows 还没消息。

跟 Docker、虚拟机有啥区别？

沙盒更轻量，只管终端命令的安全边界。Docker 那个是完整的环境隔离，不是一个层面的东西。
