远程升级 OpenClaw：旧 MacBook Pro 实战记录

2026年4月5日
Vibe Sparking

远程升级 OpenClaw：旧 MacBook Pro 实战记录

Section titled “远程升级 OpenClaw：旧 MacBook Pro 实战记录”

日期： 2026-04-05 目标主机： 旧款 MacBook Pro 2018（通过 Tailscale 组网） 升级前版本： OpenClaw 2026.4.2 升级后版本： OpenClaw 2026.4.2（已是最新） 操作方式： 从管理机通过 SSH 远程执行

背景

Section titled “背景”

OpenClaw 集群中有多台实例分布在不同主机上，日常通过 Tailscale + autossh 隧道管理。本次对旧款 MacBook Pro 2018 执行 openclaw update 升级，顺便更新插件。

踩坑：远程 SSH 下 asdf 环境加载

Section titled “踩坑：远程 SSH 下 asdf 环境加载”

目标主机使用 asdf 管理 Node.js 版本。通过 SSH 远程执行命令时，非交互式 shell 不会自动加载 asdf 环境，导致 openclaw 命令找不到。

失败尝试

Section titled “失败尝试”

解决方案

Section titled “解决方案”

使用 bash -l（login shell）让系统自动加载完整的 shell profile（包括 asdf 初始化）：

关键点：

  • -t 分配 PTY（openclaw update 有交互式进度条）
  • bash -l 启动 login shell，会读取 ~/.bash_profile / ~/.profile，asdf 初始化在这里
  • -c "..." 在 login shell 中执行命令

教训： 远程 SSH 执行依赖 asdf/nvm 等版本管理器的命令时，始终用 bash -l -c "命令" 包裹。

升级过程

Section titled “升级过程”

1. 执行 openclaw update

Section titled “1. 执行 openclaw update”

耗时约 420 秒（~7 分钟），主要时间花在 npm 包下载上。过程分三步：

  1. Updating via package manager (384s) — npm 全局包更新
  2. Running doctor checks (31s) — 健康检查，全部通过
  3. Updating plugins — 自动更新已安装的 npm 插件

结果：版本 2026.4.2 → 2026.4.2（已是最新，无实际版本变化）。

2. 插件更新情况

Section titled “2. 插件更新情况”

openclaw update 会自动尝试更新所有已安装的插件：

插件结果说明
openclaw-weixin✅ 更新至 2.1.6正常更新，仅有 2 个 suspicious 模式（未达 dangerous 级别）
openclaw-qqbot❌ 被安全策略拦截检测到 12 个 dangerous 代码模式

openclaw-qqbot 被拦截的原因

Section titled “openclaw-qqbot 被拦截的原因”

OpenClaw 2026.4.x 的安全扫描更严格了。openclaw-qqbot 插件包含以下被标记为 dangerous 的模式：

  • Environment variable access + network send（3 处）— 读取环境变量并发送网络请求，被判定为”可能的凭据窃取”
    • 实际用途：QQ Bot API 认证（appId/appSecret 从环境变量读取后发送到服务器）
  • Shell command execution (child_process)（9 处）— 调用系统命令
    • 实际用途：音频转码（ffmpeg）、平台检测、SDK 链接脚本等

这些对于一个 IM Bot 插件来说都是正常且必要的行为，但自动扫描无法区分意图。

为什么 openclaw-weixin 不需要强制安装？

Section titled “为什么 openclaw-weixin 不需要强制安装？”

openclaw-weixin 只有 2 个 suspicious 模式（较低级别），未达到 dangerous 阈值，所以不会被拦截。这说明：

  • suspicious = 警告，不阻止安装
  • dangerous = 拦截，需要 --dangerously-force-unsafe-install 强制安装

openclaw-qqbot 的 child_process 调用更多（音频转码、CLI 工具等），加上环境变量+网络发送的组合模式，超过了 dangerous 阈值。

3. 强制安装 openclaw-qqbot

Section titled “3. 强制安装 openclaw-qqbot”

安装成功，版本 1.7.1。

注意： openclaw plugins install 不会自动覆盖已存在的插件目录，需要先手动删除。

4. 重启 Gateway

Section titled “4. 重启 Gateway”

输出：Restarted LaunchAgent: gui/501/ai.openclaw.gateway

最终状态

Section titled “最终状态”
组件版本状态
OpenClaw2026.4.2✅ 最新
openclaw-qqbot1.7.1✅ 强制安装
openclaw-weixin2.1.6✅ 正常更新
Gateway—✅ 已重启
Doctor checks—✅ 全部通过

经验总结

Section titled “经验总结”
  1. asdf + SSH = 用 bash -l -c：远程执行依赖版本管理器的命令，必须用 login shell
  2. 插件更新前先删旧目录：openclaw plugins install 不支持原地覆盖
  3. 安全扫描分级：suspicious（警告）vs dangerous（拦截），IM Bot 类插件因 child_process 和环境变量+网络模式容易触发 dangerous
  4. openclaw update 会自动更新插件，但被 dangerous 拦截的插件需要单独用 --dangerously-force-unsafe-install 处理
  5. 远程升级耗时主要在 npm 下载（本次 384s / 420s），doctor checks 和插件安装相对很快
  6. config 引用了未加载插件的 channel 会导致 CLI 拒绝运行——升级插件时可能需要临时移除相关 channel 配置

根因分析

Section titled “根因分析”

LANG 为空，所有 LC_* 均为 C。

C locale 只认 ASCII 单字节字符。UTF-8 编码的中文每个字符占 3 个字节，在 C locale 下会被当作非法字节序列，导致：

  • cat 输出乱码（取决于终端模拟器是否自行处理 UTF-8）
  • less 可能部分正常（因为它有独立的字符编码处理逻辑）

为什么 macOS 会这样？

Section titled “为什么 macOS 会这样？”

macOS 的 Terminal.app 默认勾选了「Set locale environment variables on startup」，本地使用时 LANG 会被设为 en_US.UTF-8 或 zh_CN.UTF-8。但通过 SSH 登录时：

  1. SSH 客户端可能不转发 locale 变量（取决于 SendEnv 配置）
  2. 远程 sshd 可能不接受 locale 变量（取决于 AcceptEnv 配置）
  3. 用户 shell 配置文件（.zshrc / .bashrc）没有显式设置 LANG

三个条件任一不满足，远程 session 就会 fallback 到 C locale。

到底是谁死了

Section titled “到底是谁死了”

第一反应是 SSH 连接断了。但实际排查之后发现，问题根本不在 SSH。

我先验证了 SSH 本身没问题：

报错：

不是 session 消失了，是 tmux 服务进程本身没了。整个 tmux server 都不存在了。

macOS 在背后干了什么

Section titled “macOS 在背后干了什么”

这里有个很多人不知道的细节：macOS 在休眠或重启时，会清理 /private/tmp/ 下的内容。tmux 的 socket 就放在那里。socket 没了，tmux server 自然起不来，session 自然也没了，里面跑着的 SSH 隧道当然一起凉凉。

更根本的问题是：tmux 是一个普通的用户空间进程，它没有任何机制让 macOS 在休眠后帮你重启它。你 tmux new-session 起来的东西，macOS 压根不知道它的存在，也不在乎它死没死。

所以这个问题不是”怎么让 tmux 更稳定”，而是”tmux 本来就不该干这个活”。

守护进程这件事，macOS 有专门的工具：launchd。

换个思路：launchd + autossh

Section titled “换个思路：launchd + autossh”

launchd 是 macOS 的服务管理器，系统启动时最先跑起来的进程之一，PID 1 就是它。你告诉它要运行什么、什么时候运行、崩溃了怎么办，它帮你管着。macOS 休眠、重启、重新登录，launchd 都知道该干什么。

autossh 则解决了另一个问题：SSH 连接偶尔还是会断（网络抖动、NAT 超时）。autossh 会监控连接状态，断了自动重连。两者配合，隧道基本上就是永活的。

第二步：写 launchd plist

Section titled “第二步：写 launchd plist”

在 ~/Library/LaunchAgents/ 下创建一个 plist 文件。这个目录下的 plist 是用户级别的 agent，登录后自动加载，不需要 root 权限。

文件名我用 com.openclaw.tunnel-s8.plist，你可以换成自己喜欢的命名。

几个参数说明：

-M 0 禁用 autossh 自带的监控端口，改用 SSH 自己的 keepalive 机制，更简单可靠。

ServerAliveInterval=30 和 ServerAliveCountMax=3 是 SSH 的心跳配置，30 秒发一次，连续 3 次没响应就认为连接断了，触发 autossh 重连。

ExitOnForwardFailure=yes 端口转发失败时直接退出进程，让 launchd 来重启，比僵着更好。

KeepAlive=true 告诉 launchd：这个进程退出了就给我重启。

AUTOSSH_GATETIME=0 让 autossh 在首次连接失败时也尝试重连，而不是直接放弃退出。
