Claude Code 2.1.94 逐项深度分析：28 项变更全解读

2026年4月8日
Vibe Sparking

分析范围: Claude Code Changelog 2.1.94 全部 28 项变更 对比产品: OpenAI Codex CLI, Google Gemini CLI

1. 新增 Amazon Bedrock Mantle 推理支持

Section titled “1. 新增 Amazon Bedrock Mantle 推理支持”

问题背景

Section titled “问题背景”

Amazon Mantle 是 AWS 推出的新一代推理基础设施层，旨在替代传统 Bedrock 推理端点，提供更低延迟和更高吞吐量。此前 Claude Code 仅支持标准 Bedrock 端点。

使用场景与举例

Section titled “使用场景与举例”
  • 企业用户在 AWS 上运行 Claude Code，希望用 Mantle 获得更好的推理性能
  • 设置环境变量：export CLAUDE_CODE_USE_MANTLE=1，然后正常使用 Claude Code
  • 适合大规模代码生成任务（如重构整个项目），因为 Mantle 针对长上下文推理有优化

注意事项

Section titled “注意事项”
  • 需要 AWS 账号已开通 Mantle 访问权限
  • 可能与现有 Bedrock region 配置有兼容性要求
  • 环境变量方式意味着这还是实验性功能，未进入正式配置体系

历次版本相关变更

Section titled “历次版本相关变更”
  • 2.1.92: 新增交互式 Bedrock 设置向导（区域配置、凭证验证、模型固定）
  • 2.1.86: 改善 Bedrock/Vertex/Foundry 用户的 prompt cache 命中率
  • 2.1.84: 新增能力检测覆盖环境变量，允许覆盖第三方平台的能力检测

同类产品对比

Section titled “同类产品对比”
  • Claude Code: Bedrock、Vertex、Foundry、现在加 Mantle
  • Codex CLI: 仅 OpenAI API，无直接云平台集成
  • Gemini CLI: Google AI API + Vertex AI，Gemini Code Assist Enterprise

未来演进趋势

Section titled “未来演进趋势”
  • Mantle 稳定后可能成为 Bedrock 用户的默认推理路径
  • 预计后续版本会将 Mantle 集成到交互式设置向导中，而非单独环境变量

2. 付费用户默认 effort 从 medium 调整为 high

Section titled “2. 付费用户默认 effort 从 medium 调整为 high”

问题背景

Section titled “问题背景”

Claude Code 引入了 effort 概念（低/中/高），控制模型在回答时投入的”思考深度”。此前所有用户默认 medium，但付费/企业用户的体验期望更高——他们更关注质量而非 token 节省。

使用场景与举例

Section titled “使用场景与举例”
  • 之前：Team 用户使用 Claude Code 重构复杂代码，模型可能跳过深度分析
  • 现在：默认 high effort，模型会更彻底地思考、产出更完整的方案
  • 仍可通过 /effort 命令手动调低，比如快速提问时切到 low

注意事项

Section titled “注意事项”
  • 仅影响付费用户：免费/个人订阅用户不受影响
  • High effort 意味着更多 token 消耗，可能加快触达 rate limit
  • 用 /effort 可随时切换，不是永久锁定

历次版本相关变更

Section titled “历次版本相关变更”
  • 2.1.80: 新增 effort frontmatter 支持
  • 2.1.78: 新增 agent frontmatter 支持 effort
  • 2.1.76: 新增 /effort 斜杠命令

同类产品对比

Section titled “同类产品对比”
  • Claude Code: /effort 三档（low/medium/high），本版改默认值
  • Codex CLI: 无显式 effort 控制，依赖模型选择
  • Gemini CLI: 无直接等价功能，通过 model routing（Flash vs Pro）间接实现

未来演进趋势

Section titled “未来演进趋势”
  • 可能引入自适应 effort（根据问题复杂度自动调整）
  • 预计 effort 与 thinking budget 更紧密耦合

3. Slack MCP 发消息工具调用新增紧凑的可点击频道头部

Section titled “3. Slack MCP 发消息工具调用新增紧凑的可点击频道头部”

问题背景

Section titled “问题背景”

Claude Code 通过 MCP（Model Context Protocol）集成 Slack，当模型向 Slack 频道发消息时，UI 上需要清晰展示目标频道。此前可能显示原始 JSON 或不够直观。

使用场景与举例

Section titled “使用场景与举例”
  • 你让 Claude Code 给 #dev-updates 发个部署通知
  • 工具调用区域现在显示紧凑的频道名称，带有可点击链接直接跳转到该频道
  • 比之前看到原始 JSON 参数要友好得多

注意事项

Section titled “注意事项”
  • 需要 Slack MCP server 配置正确
  • 链接能否点击取决于终端是否支持超链接

未来演进趋势

Section titled “未来演进趋势”
  • 更多 MCP 工具调用将获得专属 UI 渲染（如 GitHub PR、Jira ticket 等）

4. Plugin 新增 keep-coding-instructions frontmatter 字段

Section titled “4. Plugin 新增 keep-coding-instructions frontmatter 字段”

问题背景

Section titled “问题背景”

Claude Code 的 plugin 系统允许插件产出内容（output styles）。但有时插件的输出会覆盖或冲掉编码指令配置中的规则。新增字段让插件声明”保留现有编码指令”。

使用场景与举例

Section titled “使用场景与举例”
  • 你有一个代码风格插件，它注入格式化规则
  • 设置 keep-coding-instructions: true 后，你的编码规则不会被覆盖
  • 防止插件间冲突导致代码风格指令丢失

1. managed-settings.d/ 分片策略目录

Section titled “1. managed-settings.d/ 分片策略目录”

Added managed-settings.d/ drop-in directory alongside managed-settings.json, letting separate teams deploy independent policy fragments that merge alphabetically

问题背景 企业部署 Claude Code 时，安全团队、平台团队、业务团队各自有不同的策略需求（权限规则、MCP 服务器白名单、Hook 配置等），但过去只有一个 managed-settings.json 文件。多团队写同一个文件会产生冲突和覆盖风险。

使用场景举例

  • 安全团队部署 /etc/claude-code/managed-settings.d/00-security.json（禁止 curl、wget）
  • 平台团队部署 10-platform.json（配置内部 MCP 服务器）
  • 业务团队部署 20-team-alpha.json（自定义 Hooks）
  • 按文件名字母序合并，数字前缀控制优先级

注意事项

  • 合并规则是「按字母序」，后出现的同名 key 是覆盖还是深合并需确认文档
  • 与 managed-settings.json 并存时的优先级需注意（通常 .d/ 目录优先级与主文件相同层级，按顺序合并）

演进趋势 从「单文件管理」→「分片管理」，是企业级多团队协作的标准模式。预期未来可能支持 managed-mcp.d/ 等更细粒度的分片。

Added CwdChanged and FileChanged hook events for reactive environment management (e.g., direnv)

使用场景举例

  • CwdChanged：当 Claude 切换到不同子目录时，自动执行 direnv allow 加载该目录的环境变量
  • FileChanged：当 .env 文件被修改时，自动重新加载环境配置

5. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 环境变量清理

Section titled “5. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 环境变量清理”

Added CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 to strip Anthropic and cloud provider credentials from subprocess environments (Bash tool, hooks, MCP stdio servers)

问题背景 Claude Code 运行时环境中存在 ANTHROPIC_API_KEY、AWS/GCP 凭证等敏感环境变量。当 Claude 执行 Bash 命令、触发 Hooks 或启动 MCP 服务器时，这些子进程会继承所有环境变量——如果子进程行为不可信（如来自提示注入的命令），就可能泄露凭证。

使用场景举例

  • 防止恶意 prompt 注入通过 env 或 printenv 窃取 API Key
  • 防止 MCP 服务器（可能来自不完全信任的第三方）获取云凭证
  • Hook 脚本中避免凭证泄露

注意事项

  • 默认关闭（=1 才启用），需要用户主动开启
  • 清理范围：Anthropic 相关 + 云提供商（AWS_, GCP_, AZURE_* 等）凭证
  • 如果子进程确实需要这些凭证（比如 Hook 需要调用 AWS API），开启后会中断
  • 建议企业环境通过 managed-settings.json 的 env 字段统一启用

演进趋势 这是 supply chain security 在 AI 工具链中的体现。预期未来可能会默认开启，并提供白名单机制允许特定子进程继承凭证。

Section titled “3. 拥抱全产品生命周期”

Cat Wu 说 Anthropic 内部，角色在融合。这意味着未来最值钱的人不是”前端工程师”或”后端工程师”，而是能从想法到上线一个人跑完全程的人。

的真正优势不是编程，是产品直觉——他知道什么样的东西有人买。如果你既有产品直觉又有技术深度，你的天花板比他高得多。

具体做法：下次有想法的时候，别等 PM 写 PRD。自己用 Claude Code 花一个下午做出原型，拿给用户看。Cat Wu 说这叫”原型优先，不是文档优先”。

4. 守住 AI 还做不好的领域

Section titled “4. 守住 AI 还做不好的领域”

生产环境的可靠性。安全审计。合规要求。遗留系统迁移。性能调优。这些领域有两个特点：后果严重（出错就是事故），上下文极深（需要理解整个系统的历史和约束）。

AI 在这些领域进步很快，但距离独立胜任还有距离。这是当前的护城河。

具体做法：不要回避”脏活累活”。那些别人不想碰的老系统、复杂的部署流程、诡异的线上 bug，恰恰是 Vibe Coder 做不了的事。

5. 骑在指数曲线上，不是挡在前面

Section titled “5. 骑在指数曲线上，不是挡在前面”

Cat Wu 用了一个比喻：这像是在冲浪，最重要的是别从浪上掉下来。

AI 能力每 16 个月跳升一个数量级。你不可能预测两年后 AI 会做到什么程度。但你可以确保自己是最先用上新能力的那批人，而不是最后一个感到惊讶的人。

具体做法：每次大模型更新，花半天试试它能做什么以前做不了的事。Anthropic 内部的做法是”故意让 AI 做你觉得它做不到的事，有时候它真的能做到，那就是产品需要跟上的信号”。

和你的区别

Section titled “和你的区别”

回到开头那两个故事。

1 小时做出 AppStore 第一。但他在小红书运营、需求洞察、用户心理上花的时间远超 1 小时。编码只是整个链条中最短的一环，AI 把这一环压缩到了接近零。

48 天写出 12 万行代码。但知乎分析指出他在架构上反复踩坑。一个有经验的后端工程师用同样的 AI 工具，大概率能在更短时间内做出更稳固的系统。

这就是关键：AI 消灭的是编码的体力劳动部分，放大的是你脑子里真正值钱的东西——系统理解、故障直觉、架构判断、工程品味。

问题从来不是”AI 会不会替代程序员”。

问题是：你愿不愿意从”写代码的人”变成”用 AI 解决问题的人”。

这两者之间的距离，没你想的那么远。

Claude Code 2.1.80: --channels 来了，MCP 服务器可以主动向你的会话推送消息

Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息

Section titled “Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息”

Claude Code 的会话一直是一问一答：你说话，agent 回应。MCP 服务器扩展了这个模式，agent 可以调外部工具。但信息只往外流。agent 提问，服务器回答。

2.1.80 把反向通道打开了。--channels（研究预览）让 MCP 服务器可以主动向你正在运行的会话推送消息。一个只能被问到才说话的工具，学会了举手。

通道，双向了

Section titled “通道，双向了”

MCP 一直是单行道。你的 agent 调用工具，服务器响应。如果服务器那边发生了什么事 — CI 构建失败了、部署完成了、测试跑完了 — 服务器没法告诉 agent。你得自己去问。

--channels 改变了这件事。MCP 服务器现在可以不等调用，主动向你的活跃会话推送消息。想想这意味着什么：

一个部署监控 MCP 服务器在看你的 staging 环境。agent 在写代码。部署挂了。服务器直接推送 “deploy failed: missing env var DATABASE_URL on staging” 到你的会话。agent 看到了，检查配置，修了。

一个测试运行器 MCP 服务器在测试完成时推送结果。agent 不用轮询，收到通知就行。

一个团队沟通 MCP 服务器把相关的 Slack 消息或 PR review 评论推到你的编码会话里。

这是研究预览，API 可能会变。但方向已经明确：MCP 正在从工具调用协议变成双向消息层。

技能学会了自己定节奏

Section titled “技能学会了自己定节奏”

effort frontmatter 让技能和斜杠命令的作者在技能被调用时覆盖模型的 effort 级别。

以前 effort 是全局设置。复杂任务调高，简单任务调低，来回切。现在技能自己决定。一个代码格式化命令用最低 effort 跑，因为不需要深度推理。一个架构审查技能要求最高 effort，因为偷工减料会出烂分析。

一个小小的 YAML 字段，影响不小。技能作者可以为正确的推理深度做设计，而不是指望用户碰巧把 effort 调对了。

限速，看得见了

Section titled “限速，看得见了”

rate_limits 是状态栏脚本可用的新字段。它暴露了 Claude.ai 的 5 小时和 7 天用量窗口，包含 used_percentage 和 resets_at。

如果你曾经在任务做到一半突然撞墙，现在有解了。状态栏可以显示类似 “5h 用量 73%，2h 后重置”。不用猜了。

这只适用于 Claude.ai 计费。用自己 API key 的用户有不同的限制。

插件，内联声明

Section titled “插件，内联声明”

source: 'settings' 是一个新的插件市场来源，让你直接在 settings.json 里声明插件条目。不需要注册表，不需要安装步骤。在设置文件里写好插件定义，就加载了。

对分发内部插件的团队来说，这简化了流程。推一下 settings.json 的变更，所有人就有了。

加上插件提示现在检测 CLI 工具使用（原来只看文件模式匹配），插件发现机制在变聪明。Claude Code 现在可以根据你在跑什么命令行工具来推荐插件，而不只是看项目里有什么文件。

—resume 修复：比听起来重要得多

Section titled “—resume 修复：比听起来重要得多”

--resume 在恢复会话时丢失并行工具结果。如果之前的会话有并行工具调用，恢复后会显示 [Tool result missing] 占位符，而不是实际结果。

这比听起来严重。并行工具调用在复杂会话里很常见 — agent 同时读多个文件、并行跑测试、同时搜索多个目录。丢失这些结果意味着 agent 丢失了它已经做过什么的上下文。它会重新读文件、重新搜索，或者更糟，在信息不完整的情况下做决定。

修了。所有 tool_use/tool_result 对现在正确恢复。

语音和 API 修复

Section titled “语音和 API 修复”

语音模式的 WebSocket 连接失败，因为 Cloudflare 的机器人检测在拒绝非浏览器 TLS 指纹。Claude Code 的 WebSocket 客户端看起来不像浏览器，所以 Cloudflare 标记了它。通过调整 TLS 指纹处理修复。

精细工具流式传输通过 API 代理、Bedrock 或 Vertex 时返回 400 错误。如果你通过企业基础设施跑 Claude Code，这大概率打到你了。修了。

/remote-control 在网关和第三方提供商部署中出现在命令列表里，但在这些环境中它没法用。从这些上下文中移除了。

性能：大仓库省了 80MB

Section titled “性能：大仓库省了 80MB”

25 万文件规模的仓库，启动内存用量减少约 80MB。这是有实感的减少。在一台 16GB 内存的机器上跑多个 Claude Code 实例，省回来的加在一起大概半个 GB。

大 git 仓库里 @ 文件补全也更快了。有几万文件的仓库里，输入 @ 引用文件时以前有明显延迟。改善了。

UI 打磨

Section titled “UI 打磨”

几个导航和显示改进：

/effort 现在显示 “auto” 实际解析到什么级别，和状态栏指示器一致。以前选了 “auto” 完全不知道实际用的什么 effort。

/permissions 加上了正常的 Tab 和方向键列表内导航。加上 /sandbox 的 Tab/方向键修复，设置面板的键盘导航现在一致了。

后台任务面板支持左方向键从列表视图关闭。

插件安装提示从两步流程简化为单条 /plugin install 命令。

你可能不知道需要的设置修复

Section titled “你可能不知道需要的设置修复”

托管设置 — enabledPlugins、permissions.defaultMode、策略设置的环境变量 — 在 remote-settings.json 从上一次会话缓存后，启动时不会生效。如果你的组织集中管理 Claude Code 设置，这意味着新会话可能以过期配置启动。

这种 bug 难诊断，因为它是间歇性的。只有缓存的设置和当前的不同时才会触发。修了。

这个版本在说什么

Section titled “这个版本在说什么”

--channels 是研究预览，但 Claude Code 的研究预览有个规律：通常几个版本内就变成稳定功能。发出来了就说明底层架构准备好了。

2.1.80 的模式是 Claude Code 在从工具变成基础设施。Channels 让它成为消息总线。Effort frontmatter 让技能自描述。Rate limit 可见性让它可观测。内联插件声明让它不依赖外部就能配置。

单拿出来每个都是好的改进。放在一起看，是在搭一个东西，看起来越来越不像 CLI，越来越像开发平台。

claude update 更新。如果你写 MCP 服务器，--channels 值得现在就试。如果你写技能，给它加上 effort frontmatter。如果你一直对限速毫无感知，配置你的状态栏。

大多数 changelog 条目是渐进式的。修个 bug，加个参数，省几毫秒。/remote-control 不一样。它改变了 Claude Code 这个东西本身的品类。

想想你实际怎么用 Claude Code。你启动一个任务，agent 开始工作，你在旁边看着、偶尔调整方向。有时候一个任务十分钟，有时候四十分钟。整个过程中你被钉在终端前面。不是因为你需要一直打字，而是因为你得看到发生了什么。

/remote-control 打断了这条锁链。笔记本上开始，手机上继续。沙发上看进度。等咖啡的时候批准一个文件修改。会话还是那个会话，只是屏幕换了。

让远程体验成立的配套功能

Section titled “让远程体验成立的配套功能”

/remote-control 单独拿出来已经有用，但光有它不够。我怎么知道该连哪个会话？agent 还在干活还是在等我？

这个版本还带了两个功能，刚好回答这两个问题。

VS Code 里的会话标签页现在根据你的第一条消息自动命名。不再是 “Session 1”、“Session 2”，而是 “修复 auth 中间件竞态条件”、“给搜索 API 加分页”。手机上同时开着三个会话的时候，标签名决定了你能不能快速找到对的那个。

/config 菜单里新加了一个开关，显示每个 turn 花了多长时间。远程查看时，看到 “Thought for 45s”，说明 agent 刚完成一段复杂推理。看到 “Thought for 2s”，说明它在等你。盯着终端看的时候，这些信息你靠直觉就能感知。现在换成手机远程看，需要把它变成数字。

三个功能，一个场景：不在电脑前也能干活。

认证多了一条路

Section titled “认证多了一条路”

claude auth login --console 让你通过 Anthropic Console 认证，走 API 计费通道。之前 Console 用户只能手动配 API key。现在有了正经的登录流程。

对团队来说，这简化了新人上手：跑一下 claude auth login --console，认证，完事。

性能：轻了 18MB

Section titled “性能：轻了 18MB”

启动内存减少约 18MB。一个开发者每天启动几十次，单次感知不到差别，跑多实例或者在内存紧的机器上就有感了。

非流式 API 回退加了 2 分钟单次超时。以前流式端点挂了、回退接管后，一个卡住的请求能让整个会话永远挂着。现在超时后重试。这种修复写在 changelog 里不起眼，碰到过的人知道多烦。

值得关注的 bug 修复

Section titled “值得关注的 bug 修复”

11 个 bug 修复。挑几个你大概率碰得到的。

claude -p 子进程挂起 — 用 Python 的 subprocess.run 启动 Claude Code 时没有显式传 stdin，会直接挂住。修了。一整类自动化脚本重新可用。

-p 模式下 Ctrl+C 失效 — 没法中断 print 模式会话。修了。

/btw 返回错误输出 — 流式输出过程中触发 /btw（旁问），返回的是主 agent 的输出而不是旁问的回答。修了。

语音模式启动失效 — 配置里设了 voiceEnabled: true，启动时不会自动激活，得手动切。修了。

企业用户限速不能重试 — 碰到 429 错误时没法重试。花钱买了 API 额度却被限速卡住还不能重试，对团队来说摩擦很大。修了。

会话 hook 漏触发 — 用 /resume 切换会话时 SessionEnd hook 不触发。session-end hook 里写了清理逻辑的人会踩到这个坑。修了。

/permissions 里左右方向键导航失效。键盘流开发者会注意到。修了。

自定义状态栏空白 — 工作区信任机制阻塞时，状态栏什么都不显示。现在至少会告诉你为什么。修了。

CLAUDE_CODE_DISABLE_TERMINAL_TITLE 没有阻止启动时设置终端标题。tmux 用户如果遇到标题被覆盖的怪事，就是这个 bug。修了。

VS Code 相关

Section titled “VS Code 相关”

两个 VS Code 改进（除了上面已提到的远程控制和会话标题）：

  1. 思考指示器在响应完成后显示 “Thought for Ns” 而不是只显示 “Thinking”。能看到每次回复背后花了多少时间推理。

  2. 从左侧边栏打开会话时不再缺少 session diff 按钮。如果你习惯从侧边栏查看 diff，这个功能之前是坏的。修了。

插件生态

Section titled “插件生态”

${CLAUDE_PLUGIN_DATA} 在 2.1.78 引入。这个版本加了 CLAUDE_CODE_PLUGIN_SEED_DIR 多目录支持，Unix 上用 : 分隔，Windows 上用 ;。跨项目开发插件的人可以指向多个种子目录。

加上上个版本的持久状态，插件基础设施在一步步搭起来。

这个版本在说什么

Section titled “这个版本在说什么”

把单独的条目剥掉看，2.1.79 讲的是方向。

/remote-control 加配套功能，说明 Anthropic 不打算让 Claude Code 只是一个终端工具。地铁上能看进度，会议间隙批准修改，这是它想做的事。

子进程修复和非流式超时指向另一个方向：可嵌入。写自动化脚本和 CI 流水线的人之前碰到的粗糙边角，这个版本磨掉了几个。

企业限速修复说的是用户变了。花钱买 API 额度、有合规要求的团队在用它干活了。

在用的话就更新。一直只在桌前用的，试一次 /remote-control。手机上看着 agent 干活跟坐在终端前面是两种感觉。你会发现这个工具不用你去找了，它跟着你走。

Claude Code 2.1.78: 插件有了持久状态，静默失败变成了报错

Section titled “Claude Code 2.1.78: 插件有了持久状态，静默失败变成了报错”

你的 AI 编程助手在任务中途挂了。API 触发了速率限制，turn 直接结束。没有 hook 触发，没有清理逻辑运行。你泡完咖啡回来，看到的是一个死掉的终端。

这是 2.1.77 的情况。2.1.78 加了个 StopFailure hook 事件，专门处理这种场景。changelog 里一行字，解决了一整类”到底发生了什么”的问题。

Changelog 里的暗线

Section titled “Changelog 里的暗线”

Changelog 是一种奇怪的文档。每一行都是一个修复或功能，但真正有意思的从来不是某一行，而是所有行加在一起的走向。

Claude Code 2.1.78 包含 25+ 项变更。表面看是 bug 修复版。仔细看，图景不一样：这是一个信任和可靠性版本。几乎每个改动针对的都是同一类问题——Claude Code 做了意料之外的事，或者静默失败，或者让开发者猜发生了什么。

三条线索贯穿整个更新。

线索一：插件基础设施长大了

Section titled “线索一：插件基础设施长大了”

插件获得了 ${CLAUDE_PLUGIN_DATA} 变量提供的持久状态。这个数据在插件更新后不会丢。/plugin uninstall 在删除前会弹出确认。

插件自带的 agent 获得了 frontmatter 支持：effort、maxTurns、disallowedTools。插件作者现在可以让 agent 自我约束——声明资源预算和工具限制。

这些不是面向用户的功能。是平台级基础设施。传递给插件作者的信号：在这里建设，你的状态是安全的，你的 agent 有正经的控制机制。

线索二：静默失败变成了报错

Section titled “线索二：静默失败变成了报错”

这是这份 changelog 里最说明问题的线索。数一数有多少修复遵循同一个模式：以前悄悄出错，现在大声报错，或者干脆不出错了。

沙箱静默禁用。 你设了 sandbox.enabled: true，但依赖没装好，沙箱就… 不启动。没报错。没警告。你以为有沙箱保护。实际没有。现在启动时会显示警告。

MCP deny 规则形同虚设。 deny: ["mcp__servername"] 权限规则没有把被禁止的工具从模型的视野中移除。模型能看到这个工具，尝试调用，然后失败。规则写了，但没按预期工作。修了——工具在发送给模型之前就被移除。

沙箱路径不生效。 sandbox.filesystem.allowWrite 配合绝对路径不工作，必须加 // 前缀（没人告诉你这个）。现在绝对路径直接生效。

受保护目录被暴露。 bypassPermissions 模式下，.git、.claude 等受保护目录可以被无提示写入。这个模式设计上是信任用户的，结果把对敏感目录的信任也给了 AI。修了。

死循环。 API 错误触发 stop hook，stop hook 把阻塞性错误重新喂给模型，模型又出错，又触发 hook。循环往复。你的机器在转圈，你可能好一会儿才发现。

Git 状态污染。 Linux 上沙箱 Bash 里执行 git log HEAD 报 “ambiguous argument” 错误。stub 文件出现在工作目录里污染 git status。

会话截断。 cc log 和 --resume 在大会话（>5 MB，用了 subagent 的）上静默截断对话历史。你的对话记录在，但工具只给你看了一部分。

每个都是开发者因为工具没说清发生了什么而浪费时间或失去信任的场景。

线索三：真实工作流里的边角 bug

Section titled “线索三：真实工作流里的边角 bug”

这些不是测试矩阵里的理论 bug，而是日常使用中碰到的摩擦点。

WSL2 语音模式。 在 Windows 11 的 WSLg 环境下不工作。WSL1/Win10 用户现在会看到明确的错误提示，而不是莫名其妙的沉默。

Ctrl+u。 在普通模式下按 ctrl+u 是滚屏而不是清除光标前的输入。快捷键冲突解决了——ctrl+u/ctrl+d 半页滚动移到了 transcript 模式。

语音修饰键。 ctrl+k 这类组合键式的 push-to-talk 需要按住不放才能激活。修了，现在按下立即激活。

Homebrew PATH。 macOS 上从 Dock 或 Spotlight 启动 VS Code 时，Bash 工具找不到 Homebrew 和其他依赖 PATH 的二进制文件。一个只在特定启动方式下出现的 PATH 继承问题。

颜色发白。 VS Code、Cursor、code-server 这些不声明 truecolor 支持的终端里，Claude 的橙色看起来褪色。

Worktree 加载。 --worktree 标志没有从 worktree 目录加载 skills 和 hooks。

平台信息错误。 /sandbox 的依赖标签在 macOS 上显示 Linux 的前置条件。

Git 指令设置。 CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS 和 includeGitInstructions 设置实际上没有压制系统提示中的 git status 部分。

修这些 bug 传递的信息：我们在用户真实运行的环境里测试，不只在方便测试的环境里。

流式输出更顺了

Section titled “流式输出更顺了”

响应文本现在逐行流式推送。技术上是性能改进。体验上，工具从”等待回答”变成了”看着它思考”。这种感受上的差别比省下的毫秒数更有意义。

排队的 prompt 也不再在拼接时丢失换行符——一个小格式 bug，但如果你碰到过，大概很抓狂。

几个值得知道的小改动

Section titled “几个值得知道的小改动”

自定义模型选择器。 ANTHROPIC_CUSTOM_MODEL_OPTION 环境变量可以在 /model 选择器中加一个自定义项。配套的 _NAME 和 _DESCRIPTION 后缀变量控制显示。跑自定义微调模型或代理的人会用到。

token 上限

Section titled “token 上限”

Opus 4.6 默认输出上限从之前的值提到了 64k tokens。Opus 4.6 和 Sonnet 4.6 的上限都提到了 128k。

实际影响：你在做大规模代码生成——完整模块重写、全套测试、详细架构文档——的时候，不用再被输出截断卡住了。默认翻了四倍，上限推到 128k 的话是之前默认的八倍。

allowRead 沙箱设置

Section titled “allowRead 沙箱设置”

新增 allowRead 文件系统设置，可以在 denyRead 区域内重新开放读取权限。你用 denyRead 锁了一个目录，但需要 Claude 读取里面的特定文件，allowRead 让你开精确的口子，不用解除整个限制。

/copy N

Section titled “/copy N”

/copy 支持索引了。/copy N 复制第 N 条最新的 assistant 回复。以前 /copy 只能复制最近一条。想要更早的回复，得手动滚动选中。

复合 bash 命令权限

Section titled “复合 bash 命令权限”

对 cd src && npm test 这种复合命令点”始终允许”，以前保存的是整条字符串的单一规则，而不是按子命令分开保存。结果：规则永远匹配不上，权限提示一遍遍弹。

这种 bug 很阴，因为你习惯了每次点”允许”之后就不再注意这个问题了。修了——每个子命令各自一条规则。

自动更新器内存炸弹

Section titled “自动更新器内存炸弹”

slash-command 覆盖层反复打开关闭的时候，自动更新器会启动重叠的二进制下载。每次开关都可能触发一次新下载。长 session 里频繁用 slash-command，内存累积到几十 GB。

你的 Claude Code 进程在长 session 里内存膨胀？很可能就是这个。

—resume 静默截断

Section titled “—resume 静默截断”

--resume 在静默截断最近的对话历史。根本原因：memory-extraction 写入和主 transcript 之间的竞态。提取进程和 transcript 保存在争同一份数据，transcript 有时在提取完成前就写入了，丢掉最近的条目。

这 bug 很隐蔽——你恢复 session，最近的工作不见了，但没有报错。就是消失了。

安全修复：PreToolUse hooks 绕过 deny 规则

Section titled “安全修复：PreToolUse hooks 绕过 deny 规则”

PreToolUse hooks 返回 “allow” 的时候可以绕过 deny 权限规则，包括企业托管设置。如果企业管理员通过托管设置禁止了某个工具，hook 可以通过返回 “allow” 来覆盖这个禁止。

这是安全边界的越界。hooks 应该只能加限制，不能解除限制。修了——deny 规则现在不管 hook 怎么返回都优先。

Write 工具 CRLF 处理

Section titled “Write 工具 CRLF 处理”

Write 工具在覆写 CRLF 文件或在 CRLF 目录里创建文件时会静默转换行尾。你编辑一个 Windows 风格文件，回来就变成 Unix 行尾了。混合操作系统的团队里，这制造了不必要的 diff 和合并冲突。

长 session 内存增长

Section titled “长 session 内存增长”

发生了什么

Section titled “发生了什么”

2026 年 3 月初，Claude Code 上线了原生语音输入。Anthropic 工程师 Thariq Shihipar 在 X 上宣布：“Voice mode is rolling out now in Claude Code.” 这条帖子被看了 70 多万次。

一条命令，不装插件，不配 API key，不需要第三方工具。

搞定。语音模式开了，终端里出现一行提示：

按住空格键，说话，松手。你说的话会实时变成文字，出现在提示框里。

实际怎么用

Section titled “实际怎么用”

交互方式是按住说话（push-to-talk）。按住空格录音，松手停止并转写。这是故意这么设计的——终端里不会有一直开着的麦克风，不会打字打到一半突然触发。

几个你会关心的细节：

只管输入。 Claude 回复仍然是文字，不是语音。语音是给你的提示词用的，不是 Claude 的回答。想让 Claude 用语音回复，可以用社区做的 claude-code-voice-hooks。

混合输入。 你可以先打一半字，按住空格说中间那段，再接着打。语音和键盘不冲突。逻辑用说的，变量名用打的。

懂开发术语。 语音转文字模型针对代码做过调优。camelCase、文件路径、正则、JSON key、OAuth、仓库名，它都能正确转写。你说 “getUserById”，它写的就是 “getUserById”，不是 “get user by ID”。

可以打断。 Claude 正在回复的时候，你可以按住空格说话，直接打断它。

免费。 语音转写的 token 不算在你的速率限制里。

语音不是万能的。但这些场景下它帮得上忙：

长提示词。 描述架构改动、解释 bug、讲你屏幕上看到的东西。超过两句话的内容，说比打快。

调试的时候。 “第 47 行有个 TypeError，user 变量是 undefined，但它应该在第 23 行的 useEffect 里被赋值，我觉得问题出在依赖数组是空的。“说出来 10 秒钟，打出来要一分钟。

规划和脑暴。 边想边说，语音能捕捉你的思维流，不用先在脑子里把格式排好再打字。

无障碍需求。 腱鞘炎、腕管综合征，或者任何让长时间打字变得痛苦的状况。语音把终端变成了一场对话。

打字更合适的场景： 短命令、精确语法、带特殊字符的文件路径、在开放式办公室里。

之前有什么

Section titled “之前有什么”

Claude Code 的内置语音不是第一个终端语音方案。社区先动手了：

  • voicemode — 基于 MCP，支持本地 Whisper 语音转文字 + Kokoro 文字转语音，可离线
  • claude-voice — 按住说话 + 神经网络 TTS，macOS 为主
  • Spokenly — Claude Code 的语音转文字封装

原生 /voice 不是要替代这些工具。你要离线转写、自定义 TTS、唤醒词，社区工具有原生版没有的功能。但如果你只是想”跟终端说句话”，/voice 是最省事的选择。

MCP elicitation

Section titled “MCP elicitation”

这是本次更新的头条。

到目前为止，MCP 工具调用是严格的请求-响应模式：Claude Code 发请求，服务器返回数据。如果服务器需要你提供额外信息——凭据、配置选项、操作确认——它没有办法开口。

MCP elicitation 改变了这一点。MCP 服务器现在可以在工具调用过程中发送 elicitation 请求。Claude Code 将其渲染为交互式对话框：表单字段用于结构化输入，浏览器 URL 用于 OAuth 类流程。你回应后，服务器带着你的回答继续执行。

两个新 hook 配合这个功能：

  • Elicitation 在 MCP 服务器请求输入时触发，对话框展示之前。你可以检查、修改或自动回应。
  • ElicitationResult 在你回应之后、结果发送回服务器之前触发。你可以覆盖或记录将要返回的内容。

为什么这很重要？数据库工具可以问你用哪个 schema。部署工具可以在应用变更前请求确认。认证工具可以把你重定向到登录页面，等待 token 返回。MCP 工具从被动的数据源变成了交互式的协作者。

延迟工具：compaction 后 schema 丢失

Section titled “延迟工具：compaction 后 schema 丢失”

如果你用 ToolSearch 按需加载工具（延迟工具），它们的 input schema 会在对话 compaction 后被静默丢弃。数组参数和数字参数会被拒绝，报类型错误。工具一开始能用，compaction 之后就坏了，没有明显的原因。

根本原因：compaction 序列化工具定义时没有保留完整的 schema。修复后 schema 能正确存活。

如果你遇到过 session 前半段工具正常、后半段突然报类型错误的情况，就是这个 bug。

BMAD + Quick Dev Flow + YOLO 模式

Section titled “BMAD + Quick Dev Flow + YOLO 模式”

设置 showEdit = false，保留自定义链接。

Bug 4：富文本编辑器缺失

Section titled “Bug 4：富文本编辑器缺失”

Bug 5：图片上传流程不对

Section titled “Bug 5：图片上传流程不对”

m-pic-upload 组件的输出是一个 File 对象，不是 URL。Claude Code 生成的代码直接把输出当 URL 赋值给模型字段，图片显示不出来。

正确的流程是两步：先调用上传接口把 File 对象传上去拿到 URL，再把 URL 赋值给模型。这需要理解项目里的上传架构：m-pic-upload 负责选图和预览，上传逻辑在外面处理。

5 个 bug，每个定位加修复都没超过一分钟。

后端靠测试验证，前端靠人工验证。 这次后端 6 个集成测试全绿，给了很强的信心。前端没有 E2E 测试，只能打开浏览器人工检查。如果前端也有自动化测试，修复循环会更快。

修复循环才是真正的效率瓶颈。 代码生成花了几分钟，但如果没有经验判断哪里可能出问题，debug 时间会长得多。5 个 bug 里有 4 个跟项目内部约定有关，这些约定没有写在文档里，只存在于已有代码的模式中。

怎么配置这个工作流

Section titled “怎么配置这个工作流”

如果你想自己试试，步骤如下。

  1. 在项目根目录安装 BMAD 框架。它提供了一套 prompt 模板和 slash command 定义，Claude Code 能直接识别。

  2. 写好功能需求。不需要很长，关键是把数据模型、业务规则、权限要求说清楚。50 行足够。

  3. 在 Claude Code 里输入 /bmad-bmm-quick-dev，调用 Quick Dev Flow。它会读取你的需求文档，自动拆分成 story。

  5. 等它跑完。检查后端测试是否通过，打开浏览器检查前端页面。

重点是第 2 步。需求写得越清楚、项目约定越显式，Claude Code 的首次输出质量越高。如果你的代码库里有统一的 Service 模式、统一的错误处理、统一的测试结构，YOLO 模式几乎可以一次性交付后端。

前端受限于组件的隐性约定，预期会有几个小问题需要手动修。但整体时间压缩是巨大的：原本可能要半天到一天的全栈功能开发，压缩到了一个会话加几分钟的 debug。

两种死法

Section titled “两种死法”

两个独立的 bug 都能让你的会话彻底卡死。

权限提示 CPU 死循环。 Claude Code 弹出复杂 bash 命令的权限提示时，可能进入一个紧密循环，CPU 直接打满 100%。界面冻住，没法回应提示，也没法取消。只能强制杀掉进程。修复消除了复杂命令结构触发的循环条件。

技能文件死锁。 大量技能文件同时变更——典型场景是在有很多 .claude/skills/ 文件的仓库里执行 git pull——Claude Code 会死锁。两个内部系统互相等待，谁也不让步。结果就是完全冻住，没有任何错误消息。修复去掉了循环依赖。

这类 bug 让人对工具产生怀疑。不是因为频率高，而是一旦碰上，除了杀进程没有别的办法。

多会话 bash 输出丢失

Section titled “多会话 bash 输出丢失”

在同一个项目目录里开两个 Claude Code 会话，bash 工具的输出可能会丢。一个会话的输出静默消失。原因是会话共享输出通道时的文件级冲突。

修复后每个会话有独立的输出路径。如果你习惯在同一个项目开多个终端，之前遇到命令似乎没有输出的情况，大概率就是这个 bug。

修复后泛化模型名称会解析到各平台最新可用版本。再加上默认 Opus 从 4.1 升到 4.6，你的代理现在真的在用你指定的模型了。

Section titled “modelOverrides”

企业用户之前用各种 hack 绕这个限制。现在有了正式的配置方式。

Section titled “Claude Code 2.1.74: 内存泄漏修复、OAuth 修复、RTL 文本修复”

你的 Claude Code 进程一直在悄悄吃内存。不是因为 prompt 变长了，也不是 context 膨胀了。流式 API 响应的缓冲区在你提前终止生成时没有被释放。在 Node.js/npm 代码路径上，RSS 会无限增长。2.1.74 修了这个，还有一批其他 bug——听起来都很常规，直到你碰上其中一个。

内存泄漏

Section titled “内存泄漏”

这是本次更新的头条。在 Node.js/npm 代码路径上，流式 API 响应的缓冲区在 generator 提前终止时不会被释放。你中途取消一次生成，缓冲区就留在那里。长时间会话中反复发生，RSS 就无限增长。

修复方式很直接：generator 终止时正确释放缓冲区。如果你在多小时会话中观察到 Claude Code 进程的内存持续攀升，这很可能就是原因。

这和 2.1.72 修的原生 bash 解析器内存泄漏不同。那个是命令解析期间累积的，这个是响应流期间累积的。两个 bug 导致同一个症状——进程越用越重。

MCP OAuth：两个独立问题

Section titled “MCP OAuth：两个独立问题”

MCP OAuth 认证有两个 bug，每个都能让你的集成静默失败。

端口冲突卡死。 OAuth 回调端口被占用时，认证会无限挂起。没有报错，没有超时，进程就在那里等一个永远不会到达的回调。修复后会检测冲突并给出明确错误信息。

Token 刷新失败。 部分 OAuth 服务器（Slack 是典型）用 HTTP 200 状态码返回错误。刷新逻辑把所有 200 响应当成功处理，所以 refresh token 过期后不会触发重新认证，集成就静默中断了。修复后会检查响应体的实际内容。

如果你的 MCP 集成用了几周后突然不工作了，大概率是这个原因。

托管策略绕过

Section titled “托管策略绕过”

安全修复。管理员设置的托管策略 ask 规则，可以被用户级别的 allow 规则或技能的 allowed-tools 声明绕过。层级关系现在被强制执行：托管策略优先级最高，不管用户或技能怎么声明。

对企业部署来说，管理员设定的策略边界就应该被严格遵守。

Agent 模型配置

Section titled “Agent 模型配置”

完整模型 ID（如 claude-opus-4-5）在 agent frontmatter 的 model: 字段和 --agents JSON 配置中会被静默忽略。agent 会回退到默认模型，没有任何警告。现在 agent 接受和 --model 标志相同的模型值。

如果你给 agent 指定了模型 ID 却发现它用的不是你指定的模型，就是这个 bug。

macOS 语音模式

Section titled “macOS 语音模式”

macOS 原生二进制缺少 audio-input 授权。如果你的终端从未被授予麦克风权限，语音模式会静默失败——没有报错，没有权限提示，你按下说话键什么都不会发生。

二进制现在包含该授权，macOS 会正常弹出麦克风访问请求。

SessionEnd hooks 超时

Section titled “SessionEnd hooks 超时”

SessionEnd hooks 在退出时不管 hook.timeout 怎么设置都会在 1.5 秒后被杀掉。如果你的清理 hook 需要超过 1.5 秒，它会被静默终止。超时时间现在可以通过 CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS 配置。

RTL 文本渲染

覆盖行为的变更对插件开发者来说是个改进：开发时你的本地副本优先。

Claude Code 2.1.72: 60+ 修复、effort 重新设计、12 倍缓存优化

Section titled “Claude Code 2.1.72: 60+ 修复、effort 重新设计、12 倍缓存优化”

一份 changelog 里塞了六十多个条目。没有新模型，没有范式转换。就是一个团队盯着自己的 bug 追踪器、性能仪表盘和用户反馈队列，决定一次性清理干净。

先看数据

Section titled “先看数据”
指标详情
Bug 修复60+ 项，覆盖沙箱、hooks、插件、语音、会话
包体积缩小约 510 KB
Prompt 缓存成本SDK query() 调用最高降低 12 倍
Bash 解析切换到原生模块，启动更快，内存泄漏归零
Effort 等级从 4 级简化为 3 级（去掉了 max）
并行工具容错Read/WebFetch/Glob 失败不再连带取消兄弟调用

这是 Claude Code 发布过的最大补丁版本。规模本身就说明了这个工具现在覆盖的面有多广。

Effort 重新设计

Section titled “Effort 重新设计”

effort 系统从四个等级变成三个：low、medium、high。“max” 被砍掉了。图标也换了：空心圆代表 low，半实心圆代表 medium，实心圆代表 high。状态栏的常驻图标换成了一个短暂提示，出现后自动消失。

砍掉 “max” 是一个值得留意的设计决策。四个等级制造了一种虚假的精确感。用户在 “high” 和 “max” 之间纠结，实际使用中两者的差异并不明显。三个等级更贴合人们对任务复杂度的实际认知。

12 倍 prompt 缓存修复

Section titled “12 倍 prompt 缓存修复”

SDK query() 调用中有个 bug，导致 prompt 缓存失效的频率远高于预期。修复后，基于 Claude Code SDK 构建的应用输入 token 成本最高降低 12 倍。如果你通过 SDK 跑 Claude Code 并且注意到账单偏高，这就是原因。

这种修复不会让演示变好看，但会让财务部门安心。

原生 bash 解析器

Section titled “原生 bash 解析器”

bash 命令解析器被重写为原生模块。两个具体改进：启动初始化更快（不再需要 JS 解析器预热），以及消除了一个在长时间会话中累积的内存泄漏。

如果你经常连续跑 Claude Code 好几个小时，可能注意过进程内存慢慢增长。这个泄漏就是原因之一。

沙箱与权限加固

Section titled “沙箱与权限加固”

权限系统在这个版本得到了认真的修缮：

  • 通配符权限规则现在能正确匹配包含 heredoc、嵌入换行符或无参数的命令
  • sandbox.excludedCommands 能配合环境变量前缀工作
  • “Always allow” 不再为嵌套 CLI 工具建议过于宽泛的前缀
  • Deny 规则在所有命令形式下一致生效
  • 某些本应触发提示的文件写操作现在会正确提示
  • 对允许列表目录（如 /tmp/claude/）的输出重定向不再产生多余提示

这些不是理论上的漏洞。它们是真正配置了自定义沙箱规则、在 bash 中使用 heredoc、运行嵌套 CLI 工具的用户发现的实际间隙。

Hooks 恢复可靠

Section titled “Hooks 恢复可靠”

Hooks 系统在之前几个版本有些不稳定。这次修了六个问题：

  1. transcript_path 在恢复或分叉的会话中指向了错误目录
  2. Agent prompt 在每次 settings 写入时被静默删除
  3. PostToolUse 的 block 原因显示了两遍
  4. 异步 hooks 在 bash read -r 时收不到 stdin
  5. 验证错误消息展示的示例本身就通不过验证
  6. hooks-enabled 技能被模型调用时，skill hooks 每个事件触发两次

第 2 条尤其折磨人。你的 agent prompt 会在任何 settings 变更后消失，没有报错，没有警告。

跨平台插件修复

Section titled “跨平台插件修复”

插件系统修了五个问题，其中几个是 Windows 特有的：

  • 在 Windows OneDrive 文件夹中安装不再报 EEXIST 错误
  • 存在项目级安装时，marketplace 不再阻止用户级安装
  • CLAUDE_CODE_PLUGIN_CACHE_DIR 不再创建字面量 ~ 目录
  • 包含 marketplace 专有字段的 plugin.json 不再加载失败
  • 不带 .git 后缀的 marketplace git URL 现在能正常工作（Azure DevOps、AWS CodeCommit）

OneDrive 的修复是个好例子，这种 bug 在测试环境里永远找不到。OneDrive 同步制造的文件系统状态和正常安装完全不同。只有真实的 Windows 用户在自己的 home 目录里安装插件时才会遇到。

并行工具调用不再级联失败

Section titled “并行工具调用不再级联失败”

之前，如果 Read、WebFetch 或 Glob 在并行执行时失败，会取消所有兄弟工具调用。现在只有 Bash 错误才会级联。其他工具独立失败。

这个改动在架构上很重要。并行工具调用是 Claude Code 保持速度的关键方式——同时跑多个文件读取或网页请求。让一个失败杀掉整个批次太悲观了。新行为：如果一个文件不存在，其他读取照常完成。

语音模式清理

Section titled “语音模式清理”

五项语音修复：

  • 偶发的输入延迟消除
  • 松开 push-to-talk 后不再误报 “No speech detected”
  • 过期转录文本不再在提交后重新填充输入框
  • 仓库名和常见开发术语（regex、OAuth、JSON）的转录准确度提升
  • 技术词汇的语音识别整体改善

转录准确度的修复值得单独说。你说 “regex” 或 “OAuth” 时如果转录不对，后续的工具调用就会跑偏。

会话和 UI 修复

Section titled “会话和 UI 修复”

会话管理的长尾修复：

  • --continue 在 --compact 后正确恢复到最近的节点
  • Ctrl+B 后台查询不再丢失转录或在 /clear 后损坏新对话
  • /clear 只终止前台任务，后台 agent 继续运行
  • /model 在 Claude 工作时也能显示结果
  • Plan 模式权限提示中，数字键正确输入而非选择菜单
  • Escape 键在取消查询后不再失灵
  • 双击 Ctrl+C 即使有后台 agent 也能退出
  • 会话标题正确处理多行首条消息
  • 排队消息正确显示附带的图片

配置和工作流改进

Section titled “配置和工作流改进”

几项生活质量提升：

  • /config 现在 Escape 取消、Enter 保存关闭、Space 切换设置
  • 上箭头历史在多会话并行时优先显示当前会话的消息
  • /plan 接受可选的描述参数（/plan fix the auth bug），直接进入 plan 模式并开始
  • /copy 中按 w 键将选中内容直接写入文件，绕过剪贴板（SSH 场景下很实用）
  • CLAUDE.md 中的 HTML 注释（<!-- ... -->）在自动注入时对 Claude 隐藏，用 Read 工具读取时仍然可见
  • CLAUDE_CODE_DISABLE_CRON 环境变量可在会话中途停止定时任务

/plan 的快捷参数和 /copy 的文件写入都是小改动，但压缩了常见工作流。CLAUDE.md 注释行为更微妙——你现在可以在 CLAUDE.md 里留给人看的备注，Claude 正常运行时不会看到，但主动读取文件时仍然能访问。

Section titled “一次发 60+ 修复意味着什么”

Claude Code 2.1.71：/loop 让你的终端自己盯活

Section titled “Claude Code 2.1.71：/loop 让你的终端自己盯活”

Claude Code 学会定闹钟了。

2.1.71 加了 /loop，在会话里定时跑 prompt。输入 /loop 5m check the deploy，然后去干别的。每五分钟 Claude 自己查一次，有变化就告诉你。就这一个功能，Claude Code 的定位变了。

主角：/loop 和 cron 调度

Section titled “主角：/loop 和 cron 调度”

/loop 把自然语言的时间间隔转成 cron 表达式，后台跑。

支持的单位：s（秒，会向上取整到分钟）、m（分钟）、h（小时）、d（天）。不写间隔默认 10 分钟一次。

还能套别的命令：

每 20 分钟自动跑一次 PR review。

一次性提醒直接用自然语言：

底层三个工具：

工具用途
CronCreate用 5 字段 cron 表达式建任务
CronList列出所有活跃任务
CronDelete用 8 位 ID 取消任务

一个会话最多 50 个定时任务。任务在你的对话轮次之间触发，不会打断 Claude 正在回复的内容。时间用本地时区。任务 3 天后自动过期。

有个设计选择值得说：定时任务是会话级的。关掉终端就没了。这是故意的。持久化调度走 Desktop 定时任务或 GitHub Actions。会话级的好处是出问题影响范围小。

语音按键可以改了

Section titled “语音按键可以改了”

voice:pushToTalk 现在能在 keybindings.json 里配。默认还是空格键，但你可以改成 meta+k 这类组合键，打字的时候完全不会误触。

之前用语音模式写代码，空格键一键两用，经常打字打到一半触发语音。这个改动解决了这个痛点。

Bash 白名单扩了

Section titled “Bash 白名单扩了”

这些命令不再弹权限确认框：

fmt、comm、cmp、numfmt、expr、test、printf、getconf、seq、tsort、pr

大部分是 POSIX 文本处理工具。加了之后 Claude 做字符串处理、数字格式化、文件比较不会再打断你。

Bug 修复清单

Section titled “Bug 修复清单”

会话稳定性：

  • 长时间会话里 stdin 卡死，按键没反应但进程还活着。用过一两个小时突然 Claude 不响应了的，就是这个问题

  • /plugin marketplace add owner/repo@ref 里 @ 符号解析错误，以前只有 # 能用
  • /permissions 工作区页签里同一个目录带不带尾部斜杠算两条记录

界面清理：

这个版本说明了什么

Section titled “这个版本说明了什么”

最近几个版本的 Claude Code 有两条线在走。

一条是从被动变主动。之前加了后台 agent，现在加了定时任务。方向很明确：Claude Code 想做一个运行时环境，不只是一个对话窗口。

另一条是 bug 修复越来越细。长会话的 stdin 卡死、多个代理连接器的 OAuth 竞争条件、fork 对话的 plan 文件冲突。这些 bug 只有用户量大了、使用场景复杂了才会出现。说明用户群已经过了尝鲜阶段。

/loop 加上这批稳定性修复，意味着你可以让 Claude Code 在更长时间内无人看管地跑。这改变了你和它的工作方式。

2025 年，Claude Code 发了 176 次更新。从 2 月的公测到 12 月的 v2.0，平均两天一次。

你大概率一次都没仔细看过。我也是。

有个叫 Oikon 的开发者不一样。他把 176 次更新从头到尾读了一遍，写了篇总结。他的结论是：context engineering（上下文工程）是贯穿始终的主线。

我觉得他说对了一半。另一半他没展开——这 176 次更新不是功能清单，是一张施工图。Anthropic 在造的东西，比「代码助手」大得多。

换个角度看更新日志

Section titled “换个角度看更新日志”

前段时间 @yan5xu 发了条推文，分享了一套拆解工作的方法论。核心观点：任何工作都是同一个闭环。

调研 → 决策 → 规划 → 执行 → 反馈 → 复盘

不管你做运营、做开发、做自媒体还是做财务，把工作拆开往这六步里放，一定放得进去。关键是看清楚每一步：你在做判断，还是在当搬运工。

他还提了三层模型：

  • 经理（LLM）：理解意图，制定计划
  • 章程（代码和脚本）：写一次，跑无数次
  • 员工（工具和接口）：按指令执行，不思考

三层接通，Agent 就能跑完整个闭环。三层没接通，LLM 再聪明，也是关在小黑屋里的经理——看不见外面，改变不了任何事。

用这个框架去看 Claude Code 的更新日志，有意思的事情就出现了。

三层模型在 Claude Code 里长什么样

Section titled “三层模型在 Claude Code 里长什么样”

回到经理、章程、员工三层：

经理层 = Claude（LLM 本身）

Claude 读懂你的意图。你说「把这个 API 从 REST 迁移到 GraphQL」，它能拆解成步骤、选择工具、安排执行顺序。Plan Mode 让它先想清楚再动手，不会一上来就瞎改。

章程层 = CLAUDE.md + Skills + Hooks

CLAUDE.md 是项目记忆。代码规范、架构约定、常用命令，写一次，每次会话自动加载。Skills 是可复用的工作流模板，测试、代码审查、部署，打包好，一个命令触发。Hooks 是质量关卡，提交前自动跑 lint，执行命令前检查安全。不需要 LLM 参与，纯确定性逻辑。

员工层 = MCP + Bash + Subagents + Plugins

MCP 让 Claude 连接到你用的所有东西：数据库、Jira、GitHub、Sentry、Slack，300 多个集成。Bash 工具让它直接在终端跑命令。Subagents 是独立的 Claude 实例，各自处理子任务，互不干扰。Plugins 把这些打包成可分发的单元。装一个插件，LSP、MCP、Skills、Hooks 全到位。

三层都在了。而且每一层在 2025 年都经历了多轮迭代。

创造者自己怎么用

Section titled “创造者自己怎么用”

Boris Cherny 是 Claude Code 的创造者，Anthropic 的 Head of Claude Code。之前在 Meta 当了五年 Principal Engineer，写过 Programming TypeScript。

他日常工作的方式：同时开 15 到 20 个 Opus 会话。本地终端开 5 个，Anthropic 网站上再开 5 到 10 个。每个会话跑在独立的 git worktree 上，互不干扰。他把这个叫做「最大的生产力解锁」。

这不是在「使用工具」。这是在管理一个团队。

他还提到两个方向是 Claude Code 团队正在推进的：长时间运行任务（Long-running tasks）和集群能力（Swarm）。都已经到了 demo 阶段。

长时间运行任务意味着 Agent 不再需要你盯着。启动一个迁移任务，关上终端，去开会。回来的时候任务跑完了，结果等着你审查。

集群意味着多个 Agent 协同工作。不是一个 Agent 顺序执行多个任务，是多个 Agent 并行处理一个大任务的不同部分。

2026 年初发生了什么

Section titled “2026 年初发生了什么”

进入 2026 年，更新节奏没有放慢：

  • Sandbox 模式上线，Bash 工具在 Linux 和 Mac 上有了安全沙箱，Agent 执行命令不再裸奔
  • HTTP Hooks 落地，Hooks 不再限于本地 shell 命令，可以 POST JSON 到远程 URL，接收 JSON 响应
  • 企业级 MCP 管控，IT 团队可以设置 MCP 允许列表和拒绝列表
  • 语音输入支持 20 种语言
  • Plugins 搜索和 SHA 锁定——插件生态开始正规化
  • Sonnet 4.6 上线——更好的 Agent 搜索性能，更少的 token 消耗，100 万 token 上下文窗口
  • Opus 4 和 4.1 退役——用户自动迁移到 Opus 4.6

每一条都在加固那三层：经理更聪明（Sonnet 4.6），章程更完善（HTTP Hooks），员工更安全（Sandbox）。

那张表，轮到你自己填了

Section titled “那张表，轮到你自己填了”

回到 @yan5xu 的方法论。他说得很对：设计一个 Agent，本质上就是填一张表。

调研：你的数据从哪来？有没有 API？能不能自动拉？

决策：你的分类标准是什么？边界情况怎么处理？

规划：输出什么格式？发到哪里？

执行：调哪个接口？操控哪个页面？

反馈：怎么确认执行到位？出错怎么报警？

复盘：这次的偏差，怎么变成下次的自动规则？

Claude Code 更新日志告诉你的是：这张表的每一格，现在都有了填的工具。MCP 填调研和执行，Plan Mode 填决策和规划，Hooks 填反馈，CLAUDE.md 填复盘。

你要做的只有一件事：把你自己的工作拆进这六步里，看看哪步你还在当管道。

从最让你烦的那一步开始。不一定是最耗时的，但一定是每天堵在最前面、让你迟迟不想启动的那一步。

先把这一步交给 Agent。等到那个早上，打开电脑，发现那件事已经做完了——不是「效率提升了」，是「这件事消失了」。

有了这个感受，后面的事情水到渠成。

你的 AI 智能体技能写错了，这里是修法

Section titled “你的 AI 智能体技能写错了，这里是修法”

你写技能的方式一直有问题。

不是小问题，是根子上就不对。多数开发者写 AI 智能体技能的思路跟写给初级开发者的文档一样——堆上下文、加标题、塞几个例子，然后祈祷智能体能搞定。结果呢？上下文窗口撑爆、触发器乱飞、输出忽好忽坏。

Minko Gechev 最近发了个叫 skills-best-practices 的仓库，认真对待了这个问题。他的核心观点很直接：技能不是文档，是程序。运行时是 LLM。

技能的结构

Section titled “技能的结构”

每个技能只有一种结构：

不要 README。不要 changelog。不要库代码。运行时用不到的文件就是浪费。

SKILL.md 是大脑——放高层流程和导航。references 放 API 文档和速查表。scripts 处理容易出错、重复性高的操作，这类任务里变异就是 bug。assets 存模板让智能体复制。就这些。

发现机制是技能成败的关键

Section titled “发现机制是技能成败的关键”

智能体决定是否加载你的技能之前，只看两样东西：name 和 description。总共 1024 个字符决定你的技能存在还是不存在。

烂描述：“React 技能。”

好描述：“使用 Tailwind CSS 创建和构建 React 组件。当用户想更新组件样式或 UI 逻辑时使用。不适用于 Vue、Svelte 或原生 CSS 项目。”

注意负触发。你得告诉智能体什么时候不该启动。不写的话，你的 Angular 迁移技能会在 React 项目上跳出来。

name 字段也有规矩：1-64 个字符，只允许小写字母、数字、连字符，不能连续用连字符，而且名字必须和父目录名一致。angular-testing 就得放在 angular-testing/SKILL.md 里。

上下文窗口就是内存，得管理

Section titled “上下文窗口就是内存，得管理”

指南管这叫”按需加载”（Just-in-Time Loading）。参考资料在智能体用到的时候再拉进来。SKILL.md 保持精简：只放流程和导航。把 schema、API 文档、速查表搬到 references/，模板搬到 assets/。在 SKILL.md 里明确写出什么时候读哪个文件：“具体错误码见 references/auth-flow.md。”

子目录只放一层。references/schema.md 可以。references/db/v1/schema.md 不行。

这就是给按 token 计费的运行时做内存管理。

给机器写，不是给人写

Section titled “给机器写，不是给人写”

三条规则会改变你写技能指令的方式：

编号步骤。 工作流定义成严格的顺序序列。决策分支要画清楚：“第 2 步：如果需要 source map 就运行 ng build --source-map。否则跳到第 3 步。“不留模糊空间。

用具体模板代替描述。 智能体擅长模式匹配。assets/ 里的一个 JSON 模板比几段文字描述管用得多。别描述——直接展示。

第三人称祈使句。 “提取文本……”而不是”你应该提取……”也不是”我将提取……”这种表述能让智能体行为更稳定。

概念命名要统一。用领域原生词汇。Angular 里就说”template”，别说”html""markup""view”。一致性减少智能体混淆。

把脆弱的工作交给脚本

Section titled “把脆弱的工作交给脚本”

不要让 LLM 每次运行技能都从头写复杂的解析逻辑。在 scripts/ 目录里放一个测试过的 Python 或 Bash 脚本，设计成小型 CLI。

关键细节：脚本的错误信息要写得具体、人能读懂。脚本失败时输出”Error: Unable to resolve CommonJS dependency ‘lodash’ — try adding it to the Vite optimizeDeps.include array”，智能体就能自己纠正。只返回退出码 1 没有消息，智能体就卡住了。

别创建浪费 token 的文件

Section titled “别创建浪费 token 的文件”

技能是给智能体用的，不是给人看的。指南明确列出不该创建的东西：

  • 文档文件：README.md、CHANGELOG.md、INSTALLATION_GUIDE.md 都不要
  • 冗余逻辑：智能体已经能可靠处理的任务，把指令删掉
  • 库代码：技能里只放小型单用途脚本，长期维护的库放别的地方

技能目录里的每个文件都消耗上下文。对谁能进来要狠心。

用 LLM 测试技能

Section titled “用 LLM 测试技能”

这部分让这份指南跟一般的”最佳实践”清单拉开了距离。

发现验证。 把你的 YAML 前置信息粘贴到一个新的 LLM 对话里。让它生成三个应该触发你技能的提示词和三个不应该触发的。如果描述分不清，就重写。再进一步——用真实任务去提示智能体，检查它选了哪个技能、为什么选。

逻辑验证。 把整个 SKILL.md 和目录结构喂给 LLM。让它针对一个具体任务一步步模拟执行。每一步写出它在做什么、读哪个文件或运行哪个脚本——最关键的是标记出每个它被迫猜测的地方。这些”执行阻塞点”就是指令中的歧义，会导致生产环境里的不一致输出。

对抗测试。 角色互换。让 LLM 当 QA 测试员来攻击你的技能。“如果 esbuild 脚本在 CommonJS 依赖上失败了怎么办？如果用户的 angular.json 有自定义 Webpack builder、Vite 不支持呢？我对 Node 环境做了什么隐含假设？“先别改——只收集问题。

架构精炼。 回答完对抗性问题后，让 LLM 重构你的技能。把密集内容从 SKILL.md 推到 references/ 和 assets/ 里。加错误处理部分。执行渐进式披露，保持上下文窗口精简。

指南还提到了 SkillsBench——一个评估技能的基准——可以用来构建自己的评估体系。

终局

Section titled “终局”

Gechev 的仓库里有一个元技能：用来创建其他技能的技能。这是方向——智能体给智能体写指令，由智能体验证。

现在还没到那一步。但是把技能当成一等软件制品来对待——有架构、有测试、有部署纪律——这就是”偶尔帮上忙”和”稳定交付”之间的分水岭。

AI 编程智能体的驾驭术：为什么上下文工程比换模型管用

Section titled “AI 编程智能体的驾驭术：为什么上下文工程比换模型管用”

你的团队上个月引入了一个 AI 编程智能体。第一周感觉很兴奋。到第三周，规律变得清晰：有时候智能体写出的代码拿来就能用，有时候代码看着合理但经不起审查。三个地方出现重复逻辑。utils 里明明有现成的工具函数，它从头写了一个新的。循环里藏着一个 N+1 查询。

你开始怀疑是不是选错了模型。

不是。模型从来不是问题。

大多数团队忽略的关键

Section titled “大多数团队忽略的关键”

Julian de Angelis 在 MercadoLibre（拉丁美洲最大的科技公司）负责 AI 编程智能体的推广，覆盖了近 20000 名开发者和上千个代码仓库。他在这个规模上得出的结论：

你的 AI 编程智能体就像入职第一天的新人。聪明、积极、手速快，但对你的代码库、编码规范和系统架构一无所知。

你不会给一个新工程师扔一张 Jira 卡片写着”修这个 bug”然后就走了。你会做入职培训：给文档，介绍技术栈，讲清楚代码风格，说明发布流程，开通工具权限，安排人做代码审查。

这个入职体系就是 de Angelis 所说的”智能体驾驭系统”（agent harness）——围绕智能体搭建的一整套结构化控制，决定它知道什么、能做什么、输出怎么验证。背后的底层学科叫上下文工程（context engineering）：设计和控制 LLM 在生成任何内容之前所能看到的一切。

没人说的那个约束条件

Section titled “没人说的那个约束条件”

所有主流 AI 编程智能体——Claude Code、Cursor、Codex——都在跑同一个基本循环：

读取 -> 规划 -> 编码 -> 验证 -> 迭代

智能体读你的文件，规划方案，写代码，跑测试，失败了就回头重来。每轮迭代，上下文窗口都在增长。系统提示词、工具定义、对话历史、文件内容、终端输出、智能体自己生成的代码——全部堆积在一个有限的工作空间里。

让人意外的部分来了：上下文窗口用到大约 60% 的时候，继续塞入更多上下文反而会让智能体表现更差。这种现象叫上下文腐化（context rot）。即使窗口扩到 100 万 token，这个问题依然存在。每一个花在冗长工具输出或过长规则文件上的 token，都是从实际任务的可用空间里偷走的。

好的驾驭系统围绕这个现实来设计：在正确的时机注入正确的上下文，其余一概不放。

四个真正管用的杠杆

Section titled “四个真正管用的杠杆”

1. 自定义规则

Section titled “1. 自定义规则”

CLAUDE.md、cursor/rules、AGENTS.md 这类文件会在每次交互开始时注入智能体的上下文。这是最容易上手的杠杆。

该写什么：

  • 技术栈和架构模式
  • 命名规范和代码风格
  • 测试要求（“所有单元测试必须使用表驱动输入”）
  • 代码库里常见的坑
  • 你已经看到智能体反复犯的错误

不该写什么：

  • 整份 API 文档（太长，浪费上下文）
  • 正确的废话（“写干净的代码”）
  • 自相矛盾的规则

实操建议：

  • 控制在 500 行以内。精准比全面更有用。
  • 按关注点拆分成多个文件：架构、测试、代码风格、安全。智能体只加载需要的部分。
  • 放几个具体示例。模型从例子中学到的东西比抽象指令多得多。
  • 把它当成活文档。智能体每次犯错，就更新规则。几周之后这个文件会变得非常有效。

2. MCP 服务

Section titled “2. MCP 服务”

MCP（Model Context Protocol）服务是给智能体扩展文件读写之外能力的插件。没有它们，智能体只能看到仓库里有什么。有了它们，智能体能够：

  • 查询数据库，理解表结构和数据
  • 搜索内部文档和知识库
  • 查找 API 接口约定
  • 和 CI/CD 流水线交互
  • 访问 Figma 上的设计稿
  • 用真实系统验证自己的输出

MCP 服务弥合了智能体和组织知识之间的鸿沟。让它获取人类开发者日常使用的同一套资源。

3. 技能（Skills）

Section titled “3. 技能（Skills）”

技能给智能体注入新的能力和领域知识。一个技能是一个目录，包含入口文件，可以捆绑模板、示例输出、参考文档和可执行脚本。

设计上的巧妙之处：只有一段简短描述常驻上下文，让智能体知道有这个技能可用。完整内容仅在技能被调用时加载——用户手动触发或智能体检测到相关性后自动加载。按需加载意味着技能可以写得足够详细，而不会长期占用上下文空间。

技能分两种：

  • 知识型技能注入上下文：编码规范、设计模式、业务领域知识
  • 任务型技能提供具体操作步骤

真正的威力在于技能能捆绑并执行脚本，在独立的子智能体（拥有干净上下文窗口）中运行，还能互相组合。可编程、上下文感知、可组合的智能体行为单元。

4. 规格驱动开发（Spec-Driven Development）

Section titled “4. 规格驱动开发（Spec-Driven Development）”

这个杠杆会改变你和智能体交互的整个方式。

看看这个提示词：“做一个新功能，从后台管理添加新商品。”

看起来很简单。但什么都没说清楚：用什么技术栈，后台在哪里，API 接口怎么定，数据存哪里，幂等性怎么处理，权限控制怎么做。

智能体会读代码库，规划一个合理的方案，产出一个能跑的 MVP。你添加一个商品，成功了。你再点一次”添加”，同一个商品插入了两次。用 ID 做幂等”应该是”常识。在你们的业务里，只有特定角色能添加商品”应该是”常识。

问题不在智能体，在于输入太粗糙。瓶颈卡在椅子和屏幕之间。

规格驱动开发的解法是：在智能体写代码之前，先写详细的规格文档。功能做什么，怎么和现有代码集成，边界情况有哪些，验收标准是什么，测试计划怎么安排。规格文档本身就是驾驭系统——它把架构决策、执行指南和审查标准浓缩成一份文档，一次性工程化了智能体的整个上下文窗口。

而且，你可以用智能体来写规格文档。

反馈闭环

Section titled “反馈闭环”

四个杠杆定义了智能体知道什么、能做什么。让整个系统收敛的关键是反馈闭环：测试、代码检查、类型检查、构建脚本。每一个产出”通过/失败”信号的工具都是自我纠正机制。

智能体钩子（agent hooks）让这件事变得强制可执行。钩子是在智能体生命周期特定节点自动执行的用户定义命令。把验证逻辑挂到 Stop 钩子上，智能体在检查通过之前无法结束。不是它可能忽略的建议，而是一道硬性关卡。

可用的结构化反馈越多，需要的人工干预就越少。

MercadoLibre 的 20000 人实战手册

Section titled “MercadoLibre 的 20000 人实战手册”

9 种以上技术栈，上千个遗留仓库，多个业务领域。以下是他们在实际规模上验证有效的做法：

按技术栈标准化规则。 在组织层面维护一套经过精心调校的自定义规则，覆盖每个技术栈、内部类库和代码审查标准。各团队继承基础规则后叠加仓库级定制。精确度的把控很关键——规则太细会把遗留项目搞坏，太松会放过未经批准的第三方库（安全隐患）。

内部 MCP 服务。 接入内部云平台能力、内部 SDK、通过 RAG 提供的业务上下文，以及持续更新的应用文档。

自定义代码审查智能体。 在 CI 流水线中运行的独立审查智能体，分析每一个 PR——不管是人写的还是 AI 生成的。输出按优先级排序，工程师先看到最关键的问题。人类审查者把精力放在架构设计上，不用再花时间抓代码风格违规。审查周期缩短，代码质量更一致，安全网的扩展跟着 PR 数量走，不跟着审查人数走。

从这里开始

Section titled “从这里开始”

如果你还没搭建智能体驾驭系统，从最简单的杠杆开始：自定义规则。创建一个 CLAUDE.md 或等效文件，写入你的编码规范、常见陷阱，加两个代码库里好模式和坏模式的具体例子。

跑一周。智能体每次产出不对的东西，加一条规则。月底回头看，这个文件对结果的改善会超过任何一次模型升级。

在 AI 编程智能体这场竞赛里，赢的不是用最新模型的团队，而是有最好驾驭系统的团队。

自动驾驶代码库：后台智能体与下一代企业软件交付

2026年3月2日
Vibe Sparking

大多数人睡觉的时候，Cursor 的 AI 系统生成了大约 8000 个提交。那是 8 小时内的数字。连续 7 天，这套系统累计了 1000 万次工具调用，同时运行着几百个智能体，峰值速度大约是每小时 1000 个提交。现场的工程师没有在写代码。他们盯着监控面板，调整方向。

这就是自动驾驶代码库。它已经存在了。

你以前叫它「Bot」，但它变了

Section titled “你以前叫它「Bot」，但它变了”

自动化代码我们早就有了。构建服务器、代码规范流水线、依赖更新机器人。这些是脚本系统，执行预定义好的步骤。

后台智能体不同的地方只有一个：它们会推理。

一个后台智能体被安全漏洞通告触发时，不走流程图。它读 CVE 描述，找到受影响的代码，生成修复方案，对着修复方案跑测试，然后创建一个 PR 解释它改了什么、为什么这么改。每一步都有决策。工程师审查输出结果。

「执行脚本」和「做决策」之间的这道缝隙，就是整件事情的核心。

Cursor 验证了什么

Section titled “Cursor 验证了什么”

Cursor 在 2026 年初发布了自动驾驶代码库的研究。数字值得认真看一遍。

一套多智能体系统不间断运行了 7 天。峰值：每小时约 1000 个提交。总计：1000 万次工具调用。这个项目是一个浏览器，不是 demo。几百个智能体同时在做真实的工程工作。

让这套系统跑起来的架构并不是一开始就想到的。早期的方案都失败了。

单个强模型（Opus 4.5）会跑偏，「经常在距离完成还很远的时候宣布成功」。等权限的多智能体共享状态文件的方案，由于锁竞争把 20 个有效智能体压缩成了 1-3 个。智能体为了减少冲突开始回避复杂任务。两种方案都无法扩展。

最终跑通的是一个层级结构：

  • 根规划者掌控整体范围，不写代码
  • 递归子规划者细分工作，同时保持所有权
  • 独立工作者在代码库的独立副本上运行，完成后交付
  • 信息向上流动，不需要全局同步

单个智能体失败不会连锁崩溃。这套系统具有反脆弱性。

系统还接受了一个小的常量错误率。让分布式智能体快速修复错误，比完全预防错误更有效率。智能体 A 搞崩了构建，智能体 B 发现了并修好。终极 CI/CD，CI 本身能修它找到的 bug。

三个塑造架构的提示词洞察：

  1. 约束比指令有效。「不允许有 TODO，不允许有不完整的实现」比描述性指导更有效。
  2. **别用清单思维。**给出高层意图并赋予自主权，比给出详细任务列表效果更好。
  3. 量化范围。「生成 20-100 个任务」比「生成很多任务」传递的意图更清晰。

研究者的原话是：「智能体有巨大的工程能力，但会把指令执行到底，不管指令好不好。」

基础设施的问题

Section titled “基础设施的问题”

在笔记本上跑几个智能体不是后台智能体。企业级后台智能体需要三件事。

隔离计算。 每个智能体得到自己的沙盒环境，按需启动，任务结束后销毁。没有可以在任务之间污染的共享状态，没有并行工作流之间的资源争抢。

事件路由。 必须有什么东西决定什么时候触发哪个智能体。新的 PR、安全通告、CI 失败、计划好的依赖审计。事件路由层监听这些信号，带着合适的上下文和范围分发智能体。

治理。 权限和爆炸半径控制，智能体能碰什么、不能碰什么。每个操作的审计日志。PR 是合并前必经的人工审查关卡。失败隔离，一个智能体的状态不传播到其他智能体。

关于安全的核心认识：智能体的安全性取决于它周围的基础设施。一个治理良好、爆炸半径有限的智能体，比一个拥有无限制生产权限的工程师更安全。PR 仍然是人工审查的关键节点，这一点不变。

角色在变

Section titled “角色在变”

background-agents.com 的说法很准确：开发者从「在循环中」变成「在循环上」。

传统模式里，开发者在循环中，逐字逐行写代码，每个决策都亲手做。后台智能体模式里，开发者在循环上，设定方向、审查输出、校准智能体行为、处理智能体解决不了的判断题。

变得更重要的技能：

提示词设计和约束设计。 什么约束能让智能体稳定产出？「不允许不完整的实现」比「把任务做完」更有效。学会该说什么、不该说什么是一门手艺。

为智能体工作设计系统架构。 怎么组织代码库让智能体能独立工作？小的、自包含的模块。清晰的接口契约。最少的横切依赖。这些不是新原则，但在智能体是主要工作者时变得更关键。

在正确深度上做审查。 智能体的「技术正确」方案可以引入「语境错误」，能编译、能通过测试，但偏离了意图。能抓住这个的开发者有价值。只是橡皮图章盖章的开发者没有价值。

信任标定。 知道什么时候让智能体跑、什么时候介入。读懂智能体跑偏的信号。根据任务设定合适的自主度。

写代码本身变成很多技能之一，而不是定义性技能。

现在长什么样

Section titled “现在长什么样”

今天已经落地的后台智能体用例：

依赖更新。 智能体按计划审计所有依赖，为安全的次版本更新生成 PR，为主版本更新读 changelog 并标记破坏性变更请人工审核。不是开 issue 的机器人，是理解这次升级的智能体。

CVE 修复。 安全通告触发，智能体定位受影响代码，生成修复，测试，创建 PR 并附上漏洞和修复说明。从披露到审查就绪的 PR：分钟级，不是一个迭代周期。

CI/CD 迁移。 老的构建流水线要迁移到新平台。智能体逐文件处理转换，每步都测试。工程师审查方案，批准输出。没有人需要手动重写 200 条流水线步骤。

测试覆盖率扩展。 智能体分析覆盖率缺口，为未覆盖路径写测试，验证正确性后提交审查。有针对性的覆盖，不是随机生成测试。

代码规范落地。 新的代码规范要在多个代码库推行。智能体一致地应用它们，没有把工作分发给一整个团队的协调成本。

这些都不需要智能体做产品决策。范围清晰、输出可审查、边界明确，这是模式：后台智能体处理那些「清晰到可以规范」且「重要到值得始终如一地做」的工作。

不那么舒服的那部分

Section titled “不那么舒服的那部分”

智能体会把指令执行到底，不管指令好不好。

Cursor 直接记录了这个。模糊的指令让智能体追求偏门特性。明确的规范改善了结果。当单个执行者同时收到太多目标，它会出现功能障碍：随机停下来、拒绝委派、提前宣布完成。

这意味着人的工作变成：成为智能体工作的好架构师。把问题组织得让智能体能解决。提供产生好结果的约束。设定清晰的范围边界。用足够深的领域知识审查，能抓到那个通过了所有测试但仍然是错的东西。

能做好这件事的开发者比打字快的开发者更有价值。

从哪里开始

Section titled “从哪里开始”

不需要完整的后台智能体平台才能开始培养这些技能。

用 Claude Code、Cursor 或 GitHub Copilot Agent 模式跑更长的自主任务，练习审查输出。注意智能体什么时候产出「技术正确但语境错误」的结果，那是你在培养审查技能。

把下个项目设计成更干净的模块边界和更清晰的接口。不是因为智能体现在就在读你的代码，而是练习让智能体工作可靠的架构原则。

给 AI 编程工具写提示词时，关注约束而不是指令。「不得在未经明确批准的情况下添加新依赖」是约束。「添加依赖前仔细想想」不是。

关注后台智能体基础设施的进展。隔离计算、事件路由、治理，企业工具正在这三个方向聚集。

结语

Section titled “结语”

自动驾驶代码库不是未来状态。对特定工作负载，依赖维护、安全补丁、规范落地、测试覆盖率，它今天就在运行。

基础设施问题：隔离计算、事件路由、治理。三者缺一，你有的是个强力的笔记本助手，不是后台智能体。

角色问题：在循环上，不是在循环中。审查、校准、指挥。架构智能体工作，而不是执行它。

定位问题：这套结构里哪些技能重要？约束设计、系统架构、深度审查、信任标定。

学会这样工作的开发者，有效产出比优化打字速度的开发者大得多。这个转变正在进行。
