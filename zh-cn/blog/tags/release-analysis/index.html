📌 版本概览

2026.3.24正式版18 项 Changes + 16 项 Fixes，涵盖 OpenAI 兼容、Teams 全面重构、技能管理 UX 大改、多平台消息修复
2026.3.24-beta.2预发布正式版的 3 项 Fix 子集 + 1 项测试隔离修复，作为 RC 验证轮次

beta.2 的 4 项修复全部被正式版吸收（Outbound media、Node 22 floor、CLI/update preflight），额外的 Tests/security audit 项是 CI 内部修复，未列入正式版 changelog。

一、Changes（功能变更）

Section titled “一、Changes（功能变更）”

1. Gateway/OpenAI compatibility

Section titled “1. Gateway/OpenAI compatibility”

变更内容： 新增 /v1/models、/v1/embeddings 端点，并在 /v1/chat/completions 和 /v1/responses 中透传显式 model 参数。

问题背景： OpenClaw 的 Gateway 暴露了一个兼容 OpenAI 的 HTTP API，让第三方客户端（如 Cursor、Continue、LibreChat、Dify）可以把 OpenClaw 当作 OpenAI 代理使用。但之前缺少 /v1/models（客户端用来枚举可用模型）和 /v1/embeddings（RAG 管线必需），导致很多客户端接入时报错或功能残缺。

使用场景举例：

  • 你在 Dify 中配置一个自定义 OpenAI 端点指向 http://localhost:3000/v1，之前 Dify 调 /v1/models 会 404，现在能正常拉取模型列表
  • LangChain 的 OpenAIEmbeddings 类发请求到 /v1/embeddings，之前会失败，现在 OpenClaw 可以代理到后端 embedding 模型
  • 在 /v1/chat/completions 请求体里指定 "model": "claude-opus-4-6"，之前可能被忽略用默认模型，现在会正确转发

注意事项：

  • /v1/models 返回的列表取决于 Gateway 配置的 provider/模型，不是 OpenAI 的全量模型
  • /v1/embeddings 需要后端有配置好的 embedding 模型（如 text-embedding-3-small），否则会返回错误
  • model override 透传意味着客户端可以覆盖 agent 默认模型——如果你做了权限管控需注意

同类对比：

产品OpenAI 兼容层模型枚举Embedding 支持
OpenClaw✅ 完整✅ 新增✅ 新增
LiteLLM✅ 核心卖点✅✅
LocalAI✅✅✅
Ollama✅ 部分✅✅
TypingMind❌ 纯前端N/AN/A

LiteLLM 是这个赛道的标杆——专门做 OpenAI 兼容代理。OpenClaw 补齐这些端点后，作为”AI agent 平台 + API 代理”的定位更完整。

未来趋势： OpenAI 兼容层正在成为 AI infra 的事实标准接口。预计 OpenClaw 后续还会补齐 /v1/assistants、/v1/threads（Assistants API 兼容）以及 Realtime API 的 WebSocket 代理。

2. Agents/tools: /tools 可视化改进

Section titled “2. Agents/tools: /tools 可视化改进”

变更内容： /tools 命令现在只显示当前 agent 实际可用的工具，默认紧凑视图 + 可选详细模式；Control UI 新增”Available Right Now”区域。

问题背景： 之前 /tools 列出所有已注册的工具，包括因权限/配置问题实际不可用的。用户会困惑：“为什么我能看到 web_search 但用不了？” 这个改动把”已注册”和”当前可用”区分开来。

使用场景举例：

  • 你给某个 agent 配了 workspaceOnly 沙箱，/tools 现在只显示沙箱内可用的工具，不再列出被策略禁用的
  • Control UI 里一眼看到绿色的”Available Right Now”列表，不用猜测哪些工具当前能调用

注意事项：

  • 紧凑视图可能隐藏了你需要的细节（参数签名等），需要时切换到 detailed mode
  • 如果你发现某个工具”消失”了，可能是配置/权限问题而非 bug

同类对比：

  • Copilot Studio / GPTs：工具列表在配置界面可见，但运行时不区分”可用/不可用”
  • LangChain Agent：工具绑定在代码层面，没有运行时可视化
  • Semantic Kernel：有 plugin 可用性检查但无前端展示

OpenClaw 这种”运行时工具可用性透明化”在同类产品中算领先的 UX 设计。

未来趋势： 工具可观测性（tool observability）会越来越重要。预计后续会加入工具调用频率统计、延迟监控、失败率 dashboard。

3. Microsoft Teams：迁移到官方 SDK + AI UX 最佳实践

Section titled “3. Microsoft Teams：迁移到官方 SDK + AI UX 最佳实践”

变更内容： 从自定义 Teams 集成迁移到官方 Teams SDK，并实现流式 1:1 回复、欢迎卡片、提示词推荐、反馈/反思、状态更新、打字指示器、原生 AI 标签。

问题背景： Teams 作为企业协作平台，拥有约 3.2 亿月活用户。之前 OpenClaw 的 Teams 集成是基于 Bot Framework 的低层实现，缺少微软推荐的 AI agent UX 模式。微软在 2025 年发布了 Teams AI Library 和 AI Agent UX Guidelines，这次迁移全面对齐了这些规范。

使用场景举例：

一、总判断

Section titled “一、总判断”

OpenClaw 2026.4.9 不是“炫新功能版”，而是一个很典型的“把 Memory、Auth、Security、跨端一致性一口气往产品级再推一大步”的版本。

如果说 2026.4.8 更像“把系统跑起来、把部署链理顺”，那 2026.4.9 是在补运行时可信度、记忆可治理性、插件生态可扩展性，以及多端发布工程化。

这版变化可以归成 6 条主线：

  1. Memory/Dreaming 从“实验能力”走向“可追溯、可回放、可治理”
  2. Security 继续收紧，重点堵“交互后绕过检查”“不可信输入污染运行时”“远端文本伪装成系统消息”
  3. Provider/Auth 正在从 core 内建逻辑，迁移为插件自描述能力
  4. QA 正从“能测”走向“能并行比较人格/模型行为差异”
  5. 多端工程化增强，尤其 iOS、Android、Windows 与 npm 包完整性
  6. 聊天路由、回复链路、流式输出的一堆小坑被补平，说明 OpenClaw 已进入大规模真实使用后的“边角可靠性修复期”

一句话总结：

2026.4.9 的核心价值，不是让 OpenClaw 更“会做事”，而是让它更像一个长期可运营、可审计、可安全扩展的 agent runtime。

二、逐项深度拆解

Section titled “二、逐项深度拆解”

1. Memory/Dreaming：grounded REM backfill、historical rem-harness、diary commit/reset、durable-fact extraction、live short-term promotion

Section titled “1. Memory/Dreaming：grounded REM backfill、historical rem-harness、diary commit/reset、durable-fact extraction、live short-term promotion”

这是在把 Dreaming/Memory 体系 从“只消费当前新产生的记忆”推进到“可以把旧 daily notes 重新喂回系统，并安全地产生 Dreams 和 durable memory”。

过去这类 agent memory 容易有个老问题：新对话能进记忆，旧日志只是静态文件；如果后来改了记忆提取逻辑，历史日志就无法高质量重放，于是会出现“短期记忆一套，长期记忆另一套”的双栈问题。这版就是在解决这个结构性问题。

如果你之前几周或几个月的 memory/YYYY-MM-DD.md 里积了大量历史信息，现在 dreaming 或 durable fact 提取器升级了，你就可以把旧记忆重新回灌，统一进入新的 memory pipeline，还能让整个过程可 reset、可 commit、可 trace。

这类功能很强，但也最容易出问题，比如历史污染、重复提取、错误归因，以及回灌量过大带来的 memory 噪声。所以这版同时加了 grounded lane、diary commit/reset、更干净的 durable-fact extraction 和后续 hardening。这说明作者很清楚，这不是“多一条功能”，而是“高风险认知写入链路”。

2. Control UI/Dreaming：structured diary view、timeline navigation、backfill/reset、traceable summaries、grounded Scene lane

Section titled “2. Control UI/Dreaming：structured diary view、timeline navigation、backfill/reset、traceable summaries、grounded Scene lane”

把上面那套 memory/dreaming 能力，真正做成 人能看、能操作、能审计 的 UI，是这版另一个大信号。

很多 agent memory 系统的问题不在“没有功能”，而在看不见它记了什么，不知道它为什么记这个，不知道哪些是 staged、grounded、promoted，也没法 reset 某段 backfill，或者判断 hallucinated durable fact 从哪来的。

现在如果你在 Control UI 里沿 timeline 看某天 diary 进入 backfill、生成 summary、拆出 claim、进入 grounded lane、再到 promotion 候选，这其实就是把“memory 可解释性”做成界面。后面很可能继续出现 memory lineage graph、durable fact 审核流、fact confidence 和 conflict resolution 等能力。

3. QA/Lab：character-vibes evaluation reports、model selection、parallel runs

Section titled “3. QA/Lab：character-vibes evaluation reports、model selection、parallel runs”

这是 人格/风格/行为层的 QA 工具化。

以前 QA 多数测的是功能对不对、输出有没有报错、工具有没有调用成功。但 agent 产品越来越像“角色化系统”，于是问题变成：这个模型更稳还是更啰嗦？新 system prompt 会不会让人格变油腻？两个模型在同一角色上，哪个更符合预期 vibe？

这说明 OpenClaw 已经不满足于“模型能跑”，而是在做“人格行为工程”。后面大概率会继续有 regression vibe baselines、per-agent personality snapshots、cross-model style drift detection，以及 failover 后人格一致性检查。

4. Plugins/Provider Auth：providerAuthAliases

Section titled “4. Plugins/Provider Auth：providerAuthAliases”

让 provider manifest 自己声明 auth alias，多个 provider 变体可以共享 env vars、auth profiles、config-backed auth 和 onboarding choices，是非常正确的架构方向。

过去常见问题是 core 里要写死“这个 provider 跟那个 provider 实际共用一套认证”，兼容变体要重复接线，onboarding 时每个 provider 都要单独硬编码逻辑，最后会让 core 越来越胖。

但这个方向的安全风险也很明显，比如 alias 冲突、不可信插件冒充 bundled provider auth choice，或者错误地把 operator secret 流给 workspace plugin。所以这版同时有 onboarding auth collision fix 和 trust 过滤相关修复，说明这不是单纯的 DX 优化，而是可扩展性与信任边界一起收口。

5. iOS version pin / release train

Section titled “5. iOS version pin / release train”

把 iOS release versioning 固定到明确的 CalVer，并允许 TestFlight 在同一 short version 上迭代，直到维护者明确推进下一版 gateway，这对产品发布工程很关键。

移动端最烦的是版本节奏和后端节奏不同步。gateway 更新很快，iOS 发版慢，又受 TestFlight 和 App Store 节奏影响。如果版本号策略混乱，维护和发布列车会很痛苦。

6. 关键修复：Security、Routing、Packaging 一起补边角

Section titled “6. 关键修复：Security、Routing、Packaging 一起补边角”

这版最重要的 fixes，主要集中在几条线上：

  • Browser/Security：交互驱动导航后重新执行 blocked-destination safety checks，补 SSRF 和隔离绕过
  • dotenv hardening：阻止不可信 workspace .env 覆盖 runtime-control env vars，堵配置污染
  • Remote exec sanitize：把远端 node exec summaries 作为不可信 system events 处理，避免伪装成可信系统消息
  • Plugin onboarding auth collision：防止不可信插件撞名官方 auth choice，减少 secret 截获与混淆 setup 风险
  • Android pairing：围绕 stale auth、fresh pairing、stored device tokens、后台 auto-retry 等细节继续修补
  • Routing/Reply/Streaming：NO_REPLY、ANNOUNCE_SKIP、partial streaming、external route preservation 等边角问题一起修平
  • Packaging/SDK：npm packaging、packed tarball 测试、Plugin SDK public contracts、Windows update heap headroom 等工程化补强

这些修复表面看很碎，实则都在做同一件事：把内部控制信号、外部输入和用户可见输出彻底分层。

四、和竞品的系统级对比

Section titled “四、和竞品的系统级对比”
  • OpenClaw vs NanoClaw：NanoClaw 像一把干净的战术刀，OpenClaw 更像一整套指挥系统，风险更高，但上限也更高。

1) Memory/dreaming: grounded REM backfill lane

Section titled “1) Memory/dreaming: grounded REM backfill lane”

背景问题

以前很多 agent memory 都有几个老问题：

  • 历史 daily notes 在磁盘里，但不会自动回流进长期记忆
  • 新旧 memory 路径分裂，形成“第二套记忆栈”
  • durable fact 提炼不干净，噪音多
  • 回灌历史数据时不可追踪、不可回滚

这版具体解决什么

这次最重要的一点是：

旧 daily notes 终于能以 grounded 的方式回放进 Dreams 和 durable memory，且不需要再维护第二套 memory stack。

也就是把历史数据纳入同一条 memory promotion 流水线。

使用场景

  1. 老 workspace 补历史记忆
  2. 迁移实例后重建 Dreams / durable fact
  3. 运营型 agent 从历史日志中提炼稳定事实

举例

比如 manager agent 过去 30 天 daily note 里反复出现：

  • 某个 tunnel 切换 IP 后必须更新 known_hosts
  • 某些 provider 在特定 transport 下容易超时
  • 某些 channel 的 reply fallback 有重复发问题

这版 dreaming backfill 理想情况下会把这些重复出现的信息提炼成 durable facts，而不是永远埋在日记里。

注意事项

  • backfill 是高价值能力，但风险也高
  • 容易产生过度 promotion、旧错误固化、source attribution 混乱
  • 建议先小范围回放，开 trace，人工审阅 durable fact

历次版本相关变化

  • 2026.4.2/4.5 更像搭 dreaming/promotion 的基础设施
  • 2026.4.9-beta.1 开始补齐历史回放、grounded lane、commit/reset、traceability

同类产品对比

  • OpenClaw：已进入多阶段记忆巩固系统
  • NanoClaw / PicoClaw：更偏日志归档或简单 memory store
  • Nanobot：常见 embeddings/vector recall，但不一定有 staged memory consolidation
  • IronClaw：可能偏 audit/workflow，更企业化
  • ZeroClaw：偏极简 runtime，通常不会引入复杂 dreaming 层

八、结论

Section titled “八、结论”

值得升级，但不是”无脑升”的版本。

  • 如果配置很多 legacy path、自定义模板很多、对 exec 安全边界要求高 → 升级前必须做一轮配置审计
