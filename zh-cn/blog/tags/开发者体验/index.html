Claude Code 2.1.83 Changelog 逐项调研分

2026年3月25日
Vibe Sparking

一、新增功能 (Added)

Section titled “一、新增功能 (Added)”

1. managed-settings.d/ 分片策略目录

Section titled “1. managed-settings.d/ 分片策略目录”

Added managed-settings.d/ drop-in directory alongside managed-settings.json, letting separate teams deploy independent policy fragments that merge alphabetically

问题背景 企业部署 Claude Code 时，安全团队、平台团队、业务团队各自有不同的策略需求（权限规则、MCP 服务器白名单、Hook 配置等），但过去只有一个 managed-settings.json 文件。多团队写同一个文件会产生冲突和覆盖风险。

使用场景举例

  • 安全团队部署 /etc/claude-code/managed-settings.d/00-security.json（禁止 curl、wget）
  • 平台团队部署 10-platform.json（配置内部 MCP 服务器）
  • 业务团队部署 20-team-alpha.json（自定义 Hooks）
  • 按文件名字母序合并，数字前缀控制优先级

注意事项

  • 合并规则是「按字母序」，后出现的同名 key 是覆盖还是深合并需确认文档
  • 与 managed-settings.json 并存时的优先级需注意（通常 .d/ 目录优先级与主文件相同层级，按顺序合并）
  • 类似 Linux 的 /etc/sudoers.d/、/etc/apt/sources.list.d/ 模式

演进趋势 从「单文件管理」→「分片管理」，是企业级多团队协作的标准模式。预期未来可能支持 managed-mcp.d/ 等更细粒度的分片。

2. CwdChanged 和 FileChanged Hook 事件

Section titled “2. CwdChanged 和 FileChanged Hook 事件”

Added CwdChanged and FileChanged hook events for reactive environment management (e.g., direnv)

问题背景 开发者在 monorepo 或多项目环境中工作时，切换目录会导致环境变量（如 .envrc/direnv）、工具链版本（如 .node-version）变化。之前 Claude Code 无法感知这些变化，可能用错误的环境执行命令。

使用场景举例

  • CwdChanged：当 Claude 切换到不同子目录时，自动执行 direnv allow 加载该目录的环境变量
  • FileChanged：当 .env 文件被修改时，自动重新加载环境配置
  • 结合 Hook 自动切换 Node/Python 版本

注意事项

  • FileChanged 的监控粒度（是 inotify/fsevents 级别还是 Claude 工具触发级别）需确认
  • 高频文件变化可能触发大量 Hook 调用，注意性能
  • 与 ConfigChange Hook 不同：ConfigChange 关注 Claude Code 自身配置变化，这两个关注工作目录和项目文件变化

演进趋势 Hook 事件不断细化，从生命周期事件（SessionStart/End）→ 工具事件（PreToolUse/PostToolUse）→ 现在的环境事件（CwdChanged/FileChanged）。趋势是让 Claude Code 成为一个完全可编程的开发环境。

3. sandbox.failIfUnavailable 设置

Section titled “3. sandbox.failIfUnavailable 设置”

Added sandbox.failIfUnavailable setting to exit with an error when sandbox is enabled but cannot start, instead of running unsandboxed

问题背景 这是对 v2.1.78 安全修复的进一步强化。之前如果沙箱依赖缺失，Claude Code 会静默降级为无沙箱运行——这是一个严重的安全隐患，尤其在企业环境中。v2.1.78 改为显示警告，但进程仍然继续。现在提供了「硬失败」选项。

使用场景举例

  • 企业管理员在 managed-settings.json 中设置 "sandbox": {"enabled": true, "failIfUnavailable": true}
  • CI/CD 环境中确保沙箱必须工作，否则构建失败
  • 安全敏感项目中作为合规要求

注意事项

  • 默认值应该是 false（不破坏向后兼容）
  • 建议企业环境始终开启此选项
  • 需确保沙箱依赖（Linux: bubblewrap/bwrap; macOS: sandbox-exec）已正确安装

演进趋势 安全策略从「默认宽松」→「可选严格」→ 预期最终会「默认严格」。这是 defense-in-depth 的体现。

4. disableDeepLinkRegistration 设置

Section titled “4. disableDeepLinkRegistration 设置”

Added disableDeepLinkRegistration setting to prevent claude-cli:// protocol handler registration

问题背景 Claude Code 安装时会注册 claude-cli:// 协议处理器（用于 IDE 集成、Remote Control 等）。在某些环境下（共享服务器、容器、CI/CD），注册协议处理器是不需要的甚至有害的（安全攻击面、与其他实例冲突）。

使用场景举例

  • Docker 容器中运行 Claude Code（无桌面环境）
  • CI/CD 管道中的自动化使用
  • 企业锁定环境中通过 managed settings 禁止

注意事项

  • 禁用后 IDE deep link 功能（如从 VSCode 打开 Claude Code 会话）将不可用
  • 对 headless/服务端使用无影响

演进趋势 更多「可选禁用」的开关出现，体现了 Claude Code 从「开发者工具」向「企业级平台」的演进——需要更精细的功能开关。

5. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 环境变量清理

Section titled “5. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 环境变量清理”

Added CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 to strip Anthropic and cloud provider credentials from subprocess environments (Bash tool, hooks, MCP stdio servers)

问题背景 Claude Code 运行时环境中存在 ANTHROPIC_API_KEY、AWS/GCP 凭证等敏感环境变量。当 Claude 执行 Bash 命令、触发 Hooks 或启动 MCP 服务器时，这些子进程会继承所有环境变量——如果子进程行为不可信（如来自提示注入的命令），就可能泄露凭证。

使用场景举例

演进趋势 这是 supply chain security 在 AI 工具链中的体现。预期未来可能会默认开启，并提供白名单机制允许特定子进程继承凭证。

Section titled “--bare：脚本模式，去掉所有开销”

你在 CI 或批处理脚本里用 -p 调 Claude Code，但每次都要等 hooks、LSP、插件同步、skill 目录扫描。这些在交互模式下有意义，在自动化管道里是纯浪费。

--bare 直接跳过这些：

Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息

Section titled “Claude Code 2.1.80: —channels 来了，MCP 服务器可以主动向你的会话推送消息”

Claude Code 的会话一直是一问一答：你说话，agent 回应。MCP 服务器扩展了这个模式，agent 可以调外部工具。但信息只往外流。agent 提问，服务器回答。

2.1.80 把反向通道打开了。--channels（研究预览）让 MCP 服务器可以主动向你正在运行的会话推送消息。一个只能被问到才说话的工具，学会了举手。

通道，双向了

Section titled “通道，双向了”

MCP 一直是单行道。你的 agent 调用工具，服务器响应。如果服务器那边发生了什么事 — CI 构建失败了、部署完成了、测试跑完了 — 服务器没法告诉 agent。你得自己去问。

--channels 改变了这件事。MCP 服务器现在可以不等调用，主动向你的活跃会话推送消息。想想这意味着什么：

一个部署监控 MCP 服务器在看你的 staging 环境。agent 在写代码。部署挂了。服务器直接推送 “deploy failed: missing env var DATABASE_URL on staging” 到你的会话。agent 看到了，检查配置，修了。

一个测试运行器 MCP 服务器在测试完成时推送结果。agent 不用轮询，收到通知就行。

一个团队沟通 MCP 服务器把相关的 Slack 消息或 PR review 评论推到你的编码会话里。

这是研究预览，API 可能会变。但方向已经明确：MCP 正在从工具调用协议变成双向消息层。

技能学会了自己定节奏

Section titled “技能学会了自己定节奏”

effort frontmatter 让技能和斜杠命令的作者在技能被调用时覆盖模型的 effort 级别。

以前 effort 是全局设置。复杂任务调高，简单任务调低，来回切。现在技能自己决定。一个代码格式化命令用最低 effort 跑，因为不需要深度推理。一个架构审查技能要求最高 effort，因为偷工减料会出烂分析。

一个小小的 YAML 字段，影响不小。技能作者可以为正确的推理深度做设计，而不是指望用户碰巧把 effort 调对了。

限速，看得见了

Section titled “限速，看得见了”

rate_limits 是状态栏脚本可用的新字段。它暴露了 Claude.ai 的 5 小时和 7 天用量窗口，包含 used_percentage 和 resets_at。

如果你曾经在任务做到一半突然撞墙，现在有解了。状态栏可以显示类似 “5h 用量 73%，2h 后重置”。不用猜了。

这只适用于 Claude.ai 计费。用自己 API key 的用户有不同的限制。

插件，内联声明

Section titled “插件，内联声明”

source: 'settings' 是一个新的插件市场来源，让你直接在 settings.json 里声明插件条目。不需要注册表，不需要安装步骤。在设置文件里写好插件定义，就加载了。

对分发内部插件的团队来说，这简化了流程。推一下 settings.json 的变更，所有人就有了。

加上插件提示现在检测 CLI 工具使用（原来只看文件模式匹配），插件发现机制在变聪明。Claude Code 现在可以根据你在跑什么命令行工具来推荐插件，而不只是看项目里有什么文件。

—resume 修复：比听起来重要得多

Section titled “—resume 修复：比听起来重要得多”

--resume 在恢复会话时丢失并行工具结果。如果之前的会话有并行工具调用，恢复后会显示 [Tool result missing] 占位符，而不是实际结果。

这比听起来严重。并行工具调用在复杂会话里很常见 — agent 同时读多个文件、并行跑测试、同时搜索多个目录。丢失这些结果意味着 agent 丢失了它已经做过什么的上下文。它会重新读文件、重新搜索，或者更糟，在信息不完整的情况下做决定。

修了。所有 tool_use/tool_result 对现在正确恢复。

语音和 API 修复

Section titled “语音和 API 修复”

语音模式的 WebSocket 连接失败，因为 Cloudflare 的机器人检测在拒绝非浏览器 TLS 指纹。Claude Code 的 WebSocket 客户端看起来不像浏览器，所以 Cloudflare 标记了它。通过调整 TLS 指纹处理修复。

精细工具流式传输通过 API 代理、Bedrock 或 Vertex 时返回 400 错误。如果你通过企业基础设施跑 Claude Code，这大概率打到你了。修了。

/remote-control 在网关和第三方提供商部署中出现在命令列表里，但在这些环境中它没法用。从这些上下文中移除了。

Section titled “性能：大仓库省了 80MB”

25 万文件规模的仓库，启动内存用量减少约 80MB。这是有实感的减少。在一台 16GB 内存的机器上跑多个 Claude Code 实例，省回来的加在一起大概半个 GB。

大 git 仓库里 @ 文件补全也更快了。有几万文件的仓库里，输入 @ 引用文件时以前有明显延迟。改善了。

几个导航和显示改进：

/effort 现在显示 “auto” 实际解析到什么级别，和状态栏指示器一致。以前选了 “auto” 完全不知道实际用的什么 effort。

Section titled “你可能不知道需要的设置修复”

托管设置 — enabledPlugins、permissions.defaultMode、策略设置的环境变量 — 在 remote-settings.json 从上一次会话缓存后，启动时不会生效。如果你的组织集中管理 Claude Code 设置，这意味着新会话可能以过期配置启动。

这种 bug 难诊断，因为它是间歇性的。只有缓存的设置和当前的不同时才会触发。修了。

Section titled “这个版本在说什么”

--channels 是研究预览，但 Claude Code 的研究预览有个规律：通常几个版本内就变成稳定功能。发出来了就说明底层架构准备好了。

Claude Code 2.1.78 包含 25+ 项变更。表面看是 bug 修复版。仔细看，图景不一样：这是一个信任和可靠性版本。几乎每个改动针对的都是同一类问题——Claude Code 做了意料之外的事，或者静默失败，或者让开发者猜发生了什么。

三条线索贯穿整个更新。

线索一：插件基础设施长大了

Section titled “线索一：插件基础设施长大了”

插件获得了 ${CLAUDE_PLUGIN_DATA} 变量提供的持久状态。这个数据在插件更新后不会丢。/plugin uninstall 在删除前会弹出确认。

插件自带的 agent 获得了 frontmatter 支持：effort、maxTurns、disallowedTools。插件作者现在可以让 agent 自我约束——声明资源预算和工具限制。

这些不是面向用户的功能。是平台级基础设施。传递给插件作者的信号：在这里建设，你的状态是安全的，你的 agent 有正经的控制机制。

线索二：静默失败变成了报错

Section titled “线索二：静默失败变成了报错”

这是这份 changelog 里最说明问题的线索。数一数有多少修复遵循同一个模式：以前悄悄出错，现在大声报错，或者干脆不出错了。

沙箱静默禁用。 你设了 sandbox.enabled: true，但依赖没装好，沙箱就… 不启动。没报错。没警告。你以为有沙箱保护。实际没有。现在启动时会显示警告。

MCP deny 规则形同虚设。 deny: ["mcp__servername"] 权限规则没有把被禁止的工具从模型的视野中移除。模型能看到这个工具，尝试调用，然后失败。规则写了，但没按预期工作。修了——工具在发送给模型之前就被移除。

沙箱路径不生效。 sandbox.filesystem.allowWrite 配合绝对路径不工作，必须加 // 前缀（没人告诉你这个）。现在绝对路径直接生效。

受保护目录被暴露。 bypassPermissions 模式下，.git、.claude 等受保护目录可以被无提示写入。这个模式设计上是信任用户的，结果把对敏感目录的信任也给了 AI。修了。

死循环。 API 错误触发 stop hook，stop hook 把阻塞性错误重新喂给模型，模型又出错，又触发 hook。循环往复。你的机器在转圈，你可能好一会儿才发现。

Git 状态污染。 Linux 上沙箱 Bash 里执行 git log HEAD 报 “ambiguous argument” 错误。stub 文件出现在工作目录里污染 git status。

会话截断。 cc log 和 --resume 在大会话（>5 MB，用了 subagent 的）上静默截断对话历史。你的对话记录在，但工具只给你看了一部分。

每个都是开发者因为工具没说清发生了什么而浪费时间或失去信任的场景。

线索三：真实工作流里的边角 bug

Section titled “线索三：真实工作流里的边角 bug”

这些不是测试矩阵里的理论 bug，而是日常使用中碰到的摩擦点。

WSL2 语音模式。 在 Windows 11 的 WSLg 环境下不工作。WSL1/Win10 用户现在会看到明确的错误提示，而不是莫名其妙的沉默。

Ctrl+u。 在普通模式下按 ctrl+u 是滚屏而不是清除光标前的输入。快捷键冲突解决了——ctrl+u/ctrl+d 半页滚动移到了 transcript 模式。

语音修饰键。 ctrl+k 这类组合键式的 push-to-talk 需要按住不放才能激活。修了，现在按下立即激活。

Homebrew PATH。 macOS 上从 Dock 或 Spotlight 启动 VS Code 时，Bash 工具找不到 Homebrew 和其他依赖 PATH 的二进制文件。一个只在特定启动方式下出现的 PATH 继承问题。

颜色发白。 VS Code、Cursor、code-server 这些不声明 truecolor 支持的终端里，Claude 的橙色看起来褪色。

Worktree 加载。 --worktree 标志没有从 worktree 目录加载 skills 和 hooks。

平台信息错误。 /sandbox 的依赖标签在 macOS 上显示 Linux 的前置条件。

Git 指令设置。 CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS 和 includeGitInstructions 设置实际上没有压制系统提示中的 git status 部分。

修这些 bug 传递的信息：我们在用户真实运行的环境里测试，不只在方便测试的环境里。

流式输出更顺了

Section titled “流式输出更顺了”

响应文本现在逐行流式推送。技术上是性能改进。体验上，工具从”等待回答”变成了”看着它思考”。这种感受上的差别比省下的毫秒数更有意义。

排队的 prompt 也不再在拼接时丢失换行符——一个小格式 bug，但如果你碰到过，大概很抓狂。

几个值得知道的小改动

Section titled “几个值得知道的小改动”

自定义模型选择器。 ANTHROPIC_CUSTOM_MODEL_OPTION 环境变量可以在 /model 选择器中加一个自定义项。配套的 _NAME 和 _DESCRIPTION 后缀变量控制显示。跑自定义微调模型或代理的人会用到。

会话性能。 恢复大会话时的内存占用和启动时间有改善。

ANTHROPIC_BETAS。 这个环境变量在用 Haiku 模型时被静默忽略。修了。

VS Code 相关

这个版本到底在说什么

Section titled “这个版本到底在说什么”

MCP 工具的隐性成本

Section titled “MCP 工具的隐性成本”

用 Claude Code 接了多个 MCP 服务器的人，大概率碰到过这个问题但没意识到。每个 MCP 服务器在启动时会把完整的工具定义塞进上下文 — 工具名、描述、参数 schema、示例，全部塞进来。一个服务器吃 2000 到 5000 token。我接了十几个：Chrome DevTools、Kubernetes、微信公众号、文言发布、Context7、Exa 搜索、Dart 开发工具、sequential-thinking，还有别的。加起来就是 3 万到 5 万 token 的开销，还没开始干活呢。

Opus 4.6 有百万上下文窗口，你可能觉得 5 万 token 不算什么。短任务确实无所谓。但那种真正出活的长会话 — 跨文件调 bug、跑测试、反复改设计、发内容 — 每个 token 都是注意力。schema 噪音越多，模型花在你实际代码上的注意力就越少。

按需加载：工具变成菜单

Section titled “按需加载：工具变成菜单”

然后我注意到会话的系统提示里有个东西：<available-deferred-tools>。147 个工具名排成一列。只有名字，没有 schema，没有参数定义。

需要某个工具的时候，Claude 调一次 ToolSearch，把完整定义拉过来，用完就完了。

从大约 5 万 token 降到 735 token。工具相关的上下文开销砍了 98%。

百万上下文下为什么还要在意这个

Section titled “百万上下文下为什么还要在意这个”

你可能想，百万窗口里 5 万 token 算什么。问题不在容量，在注意力。

长上下文模型的研究一直在说同一件事：上下文中间的信息比头尾的信息更容易被忽略。一堆工具 schema 静静地躺在上下文中段，就是每轮对话都要处理的噪音。

按需加载把这些噪音整个拿掉，直到真正需要。你从写博客切到调 Chrome 扩展，chrome-devtools 的 schema 就在你当前对话附近出现 — 而不是埋在几千 token 之前的某个角落。

Section titled “Claude Code 2.1.77: Opus 4.6 输出上限拉到 128k，其他全在修 bug”

Opus 4.6 单次响应最多能输出 128k tokens 了。默认 64k，是之前大多数人用的四倍。一口气生成一整个模块、一套完整测试、一次大规模重构，不用担心输出被截断。

token 上限

Section titled “token 上限”

Opus 4.6 默认输出上限从之前的值提到了 64k tokens。Opus 4.6 和 Sonnet 4.6 的上限都提到了 128k。

实际影响：你在做大规模代码生成——完整模块重写、全套测试、详细架构文档——的时候，不用再被输出截断卡住了。默认翻了四倍，上限推到 128k 的话是之前默认的八倍。

allowRead 沙箱设置

Section titled “allowRead 沙箱设置”

新增 allowRead 文件系统设置，可以在 denyRead 区域内重新开放读取权限。你用 denyRead 锁了一个目录，但需要 Claude 读取里面的特定文件，allowRead 让你开精确的口子，不用解除整个限制。

/copy N

Section titled “/copy N”

/copy 支持索引了。/copy N 复制第 N 条最新的 assistant 回复。以前 /copy 只能复制最近一条。想要更早的回复，得手动滚动选中。

复合 bash 命令权限

Section titled “复合 bash 命令权限”

对 cd src && npm test 这种复合命令点”始终允许”，以前保存的是整条字符串的单一规则，而不是按子命令分开保存。结果：规则永远匹配不上，权限提示一遍遍弹。

这种 bug 很阴，因为你习惯了每次点”允许”之后就不再注意这个问题了。修了——每个子命令各自一条规则。

自动更新器内存炸弹

Section titled “自动更新器内存炸弹”

slash-command 覆盖层反复打开关闭的时候，自动更新器会启动重叠的二进制下载。每次开关都可能触发一次新下载。长 session 里频繁用 slash-command，内存累积到几十 GB。

你的 Claude Code 进程在长 session 里内存膨胀？很可能就是这个。

—resume 静默截断

Section titled “—resume 静默截断”

--resume 在静默截断最近的对话历史。根本原因：memory-extraction 写入和主 transcript 之间的竞态。提取进程和 transcript 保存在争同一份数据，transcript 有时在提取完成前就写入了，丢掉最近的条目。

这 bug 很隐蔽——你恢复 session，最近的工作不见了，但没有报错。就是消失了。

安全修复：PreToolUse hooks 绕过 deny 规则

Section titled “安全修复：PreToolUse hooks 绕过 deny 规则”

PreToolUse hooks 返回 “allow” 的时候可以绕过 deny 权限规则，包括企业托管设置。如果企业管理员通过托管设置禁止了某个工具，hook 可以通过返回 “allow” 来覆盖这个禁止。

这是安全边界的越界。hooks 应该只能加限制，不能解除限制。修了——deny 规则现在不管 hook 怎么返回都优先。

Write 工具 CRLF 处理

Section titled “Write 工具 CRLF 处理”

Write 工具在覆写 CRLF 文件或在 CRLF 目录里创建文件时会静默转换行尾。你编辑一个 Windows 风格文件，回来就变成 Unix 行尾了。混合操作系统的团队里，这制造了不必要的 diff 和合并冲突。

Section titled “长 session 内存增长”

MCP elicitation

Section titled “MCP elicitation”

这是本次更新的头条。

到目前为止，MCP 工具调用是严格的请求-响应模式：Claude Code 发请求，服务器返回数据。如果服务器需要你提供额外信息——凭据、配置选项、操作确认——它没有办法开口。

MCP elicitation 改变了这一点。MCP 服务器现在可以在工具调用过程中发送 elicitation 请求。Claude Code 将其渲染为交互式对话框：表单字段用于结构化输入，浏览器 URL 用于 OAuth 类流程。你回应后，服务器带着你的回答继续执行。

两个新 hook 配合这个功能：

  • Elicitation 在 MCP 服务器请求输入时触发，对话框展示之前。你可以检查、修改或自动回应。
  • ElicitationResult 在你回应之后、结果发送回服务器之前触发。你可以覆盖或记录将要返回的内容。

为什么这很重要？数据库工具可以问你用哪个 schema。部署工具可以在应用变更前请求确认。认证工具可以把你重定向到登录页面，等待 token 返回。MCP 工具从被动的数据源变成了交互式的协作者。

BMAD + Quick Dev Flow + YOLO 模式

Section titled “BMAD + Quick Dev Flow + YOLO 模式”

先解释几个概念。

BMAD 是 Business-Module-Architecture-Development 的缩写，一个结构化的开发方法论。它的核心思路是把业务需求拆解成模块级别的 story，每个 story 有明确的验收标准和技术边界。

Quick Dev Flow 是 BMAD 里的一条快速通道，通过 /bmad-bmm-quick-dev 命令调用。它跳过了常规流程里的多轮讨论环节，直接从需求文档生成可执行的开发任务。

YOLO 模式 是 Claude Code 的一种运行方式。开启后，Claude Code 不再每一步都停下来等你确认，而是自主执行到底。遇到需要创建文件、运行测试、安装依赖这些操作，它直接做，不问你。

如果你想自己试试，步骤如下。

  1. 在项目根目录安装 BMAD 框架。它提供了一套 prompt 模板和 slash command 定义，Claude Code 能直接识别。

  2. 写好功能需求。不需要很长，关键是把数据模型、业务规则、权限要求说清楚。50 行足够。

  3. 在 Claude Code 里输入 /bmad-bmm-quick-dev，调用 Quick Dev Flow。它会读取你的需求文档，自动拆分成 story。

  4. 当 Claude Code 提示确认时，输入 YOLO 模式（在 Claude Code 设置里开启 --dangerously-skip-permissions，或者在会话中选择 YOLO）。这样它就不会每一步都停下来问你了。

  5. 等它跑完。检查后端测试是否通过，打开浏览器检查前端页面。

  6. 把发现的问题反馈给 Claude Code，让它修。通常一两轮就能收敛。

重点是第 2 步。需求写得越清楚、项目约定越显式，Claude Code 的首次输出质量越高。如果你的代码库里有统一的 Service 模式、统一的错误处理、统一的测试结构，YOLO 模式几乎可以一次性交付后端。

前端受限于组件的隐性约定，预期会有几个小问题需要手动修。但整体时间压缩是巨大的：原本可能要半天到一天的全栈功能开发，压缩到了一个会话加几分钟的 debug。

你的 Claude Code 进程一直在悄悄吃内存。不是因为 prompt 变长了，也不是 context 膨胀了。流式 API 响应的缓冲区在你提前终止生成时没有被释放。在 Node.js/npm 代码路径上，RSS 会无限增长。2.1.74 修了这个，还有一批其他 bug——听起来都很常规，直到你碰上其中一个。

内存泄漏

Section titled “内存泄漏”

这是本次更新的头条。在 Node.js/npm 代码路径上，流式 API 响应的缓冲区在 generator 提前终止时不会被释放。你中途取消一次生成，缓冲区就留在那里。长时间会话中反复发生，RSS 就无限增长。

修复方式很直接：generator 终止时正确释放缓冲区。如果你在多小时会话中观察到 Claude Code 进程的内存持续攀升，这很可能就是原因。

这和 2.1.72 修的原生 bash 解析器内存泄漏不同。那个是命令解析期间累积的，这个是响应流期间累积的。两个 bug 导致同一个症状——进程越用越重。

MCP OAuth：两个独立问题

Section titled “MCP OAuth：两个独立问题”

MCP OAuth 认证有两个 bug，每个都能让你的集成静默失败。

端口冲突卡死。 OAuth 回调端口被占用时，认证会无限挂起。没有报错，没有超时，进程就在那里等一个永远不会到达的回调。修复后会检测冲突并给出明确错误信息。

Token 刷新失败。 部分 OAuth 服务器（Slack 是典型）用 HTTP 200 状态码返回错误。刷新逻辑把所有 200 响应当成功处理，所以 refresh token 过期后不会触发重新认证，集成就静默中断了。修复后会检查响应体的实际内容。

如果你的 MCP 集成用了几周后突然不工作了，大概率是这个原因。

托管策略绕过

Section titled “托管策略绕过”

安全修复。管理员设置的托管策略 ask 规则，可以被用户级别的 allow 规则或技能的 allowed-tools 声明绕过。层级关系现在被强制执行：托管策略优先级最高，不管用户或技能怎么声明。

对企业部署来说，管理员设定的策略边界就应该被严格遵守。

Agent 模型配置

Section titled “Agent 模型配置”

完整模型 ID（如 claude-opus-4-5）在 agent frontmatter 的 model: 字段和 --agents JSON 配置中会被静默忽略。agent 会回退到默认模型，没有任何警告。现在 agent 接受和 --model 标志相同的模型值。

如果你给 agent 指定了模型 ID 却发现它用的不是你指定的模型，就是这个 bug。

macOS 语音模式

Section titled “macOS 语音模式”

macOS 原生二进制缺少 audio-input 授权。如果你的终端从未被授予麦克风权限，语音模式会静默失败——没有报错，没有权限提示，你按下说话键什么都不会发生。

二进制现在包含该授权，macOS 会正常弹出麦克风访问请求。

SessionEnd hooks 超时

Section titled “SessionEnd hooks 超时”

SessionEnd hooks 在退出时不管 hook.timeout 怎么设置都会在 1.5 秒后被杀掉。如果你的清理 hook 需要超过 1.5 秒，它会被静默终止。超时时间现在可以通过 CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS 配置。

RTL 文本渲染

Section titled “RTL 文本渲染”

如果你经常连续跑 Claude Code 好几个小时，可能注意过进程内存慢慢增长。这个泄漏就是原因之一。

Section titled “沙箱与权限加固”

这些不是理论上的漏洞。它们是真正配置了自定义沙箱规则、在 bash 中使用 heredoc、运行嵌套 CLI 工具的用户发现的实际间隙。
