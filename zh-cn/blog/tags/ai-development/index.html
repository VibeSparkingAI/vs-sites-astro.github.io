关键发现

Section titled “关键发现”

架构评审 发现其他事件类型的去重块存在完全相同的漏洞——4个评审子代理中有3个独立发现了这个问题，互相印证。

性能评审 发现：

  • 去重查询缺少复合索引，每次同步都会全表扫描
  • events.present? 会加载所有匹配事件到内存，应使用 .exists?
  • 1.year.ago 在循环内每次迭代都重新计算

安全评审 发现：

  • 新增的 .where("events.created_at >= ?", cycle_cutoff) 使用参数化查询，安全
  • 但同文件存在预先的 SQL 字符串插值风险

Vibe Sparking

BMAD 6.2.0：干掉一整套架构的版本升级

Section titled “BMAD 6.2.0：干掉一整套架构的版本升级”

我问了一个很简单的问题：“这两个 BMAD skill 有什么区别？“答案让我重新审视了对 AI 开发工具的整个理解。

两个 skill 都生成 product brief，都在同一个框架里。一个有六个步骤，另一个有五个阶段、四个子 Agent、三种执行模式，还有一个 replaces-skill 字段，像判决书一样指向前者。

两个 Skill，同一件事，两个世界

Section titled “两个 Skill，同一件事，两个世界”

BMAD 6.2.0 在 analysis workflow 文件夹里附带了两个 skill：bmad-create-product-brief 和 bmad-product-brief-preview。同样的任务，同一个框架。我以为第二个不过是小版本迭代的预览版。打开 bmad-manifest.json，看到了 replaces-skill 字段。

一个在取代另一个。

旧方式：Step-File 架构

Section titled “旧方式：Step-File 架构”

原版 bmad-create-product-brief 像表单向导一样运转。Step 01 到 Step 06，严格顺序，不能跳过。每个步骤需要用户确认才能解锁下一步。单个 Agent 处理全部内容。没有网络调研。状态通过 stepsCompleted 存在 frontmatter 里。能跑，能用，可预期。

它也是一段碰巧用了 AI 的脚本。结构是人设计的，节奏是人掌控的，过程是人主导的。

新方式：基于 Prompt 的多 Agent 编排

Section titled “新方式：基于 Prompt 的多 Agent 编排”

替代品 bmad-product-brief-preview 和前任几乎没有相似之处。五个阶段代替六个步骤，但这是最无趣的变化。

四个子 Agent 并发运行：

  • artifact-analyzer 扫描现有项目文档
  • web-researcher 抓取外部市场数据
  • opportunity-reviewer 评估商业潜力
  • skeptic-reviewer 压力测试各项假设

三种执行模式：

  • guided（默认）用于交互式使用
  • yolo 用于带模拟专家输入的自主执行
  • headless 用于完全自主、无人参与的执行

它能编辑已有的 brief，而不只是新建。接受 --create、--edit、--optimize、--distillate、--inputs、--headless 等参数。输出是 LLM distillate——一个经过 token 优化的 brief 版本，专门设计用来喂给下游 AI 工作流，比如 PRD 生成。

对比一览

Section titled “对比一览”
维度旧版（create-product-brief）新版（product-brief-preview）
架构Step-file，固定顺序Prompt-based，灵活阶段
执行模式一种（仅交互式）三种（guided / yolo / headless）
AI 协作单 Agent四个并发子 Agent
网络调研无有
Headless 支持无有
编辑已有 brief无有
AI 对 AI 输出无有（LLM distillate）

每一行说的都是同一个故事。旧 skill 是在自动化人的工作流。新 skill 是定义一个目标，让 Agent 自己商量怎么做。

背后的模式

Section titled “背后的模式”

我一直在观察 AI 工具领域的这种转变。第一代工具把人在做的事情搬过来，在每个步骤加上 AI——自行车装了个电机。第二代工具问的是：这东西为什么非得是自行车？

Step-file 架构说的是：“这里有六件事要做，按这个顺序做，每步都要等批准。”

Prompt-based 架构说的是：“这是我们要产出的东西，这些是能帮上忙的专家，开始吧。”

这不是版本升级，是范式切换。

为什么这改变了能构建什么

Section titled “为什么这改变了能构建什么”

Step-file skill 无法 headless 运行，因为每个步骤都等着人按 ‘C’ 继续。Multi-agent skill 可以，因为 Agent 之间自己协商。

Step-file skill 无法在做 artifact 分析的同时并行做网络调研，因为第 3 步结束才能开始第 4 步。新 skill 可以，因为子 Agent 在设计上就是并发的。

LLM distillate 或许是最能说明问题的细节。旧 skill 产出的是给人读的内容。新 skill 产出的是给人和下游 AI Agent 同时消费的内容。它在为 AI 对 AI 的通信做设计——product brief 喂给 PRD 生成器，PRD 生成器喂给 story 创建器，story 创建器喂给开发 Agent。输出格式不是事后才想的；它是一个关于受众是谁（或者是什么）的架构决策。

“Guided → YOLO → Headless”成熟度曲线

Section titled ““Guided → YOLO → Headless”成熟度曲线”

三种执行模式不只是个功能，它描述了一条成熟度曲线：

  1. Guided：人来驱动，AI 辅助（辅助轮）
  2. YOLO：AI 驱动，带模拟专家输入，人来审查（受监督的自主）
  3. Headless：AI 独立运行，产出结果，继续前进（完全自主）

如果你的 AI 工具只支持 guided 模式，它就是第一代。从 guided 跳到 headless 不是量变，它要求工具在架构层面具备自我驱动的能力。Step-file 工具跨不过这道坎，multi-agent 工具可以。

对实践者的意义

Section titled “对实践者的意义”

别再用功能清单评估 AI 工具了，从架构开始看。

一个有三种执行模式和并发子 Agent 的工具，“好过”step-file 工具，不是快车好过慢车那种好法。是汽车好过马那种好法。能力的差距不是量级的，是类别的。

下次更新框架时，别只确认旧工作流还能不能跑。检查一下框架有没有已经超越你的思维模型。BMAD manifest 里的 replaces-skill 字段，不只是在废弃一个脚本，它在废弃一整种关于 AI 与人如何协作的思考方式。

建议

Section titled “建议”

新项目：用 bmad-product-brief-preview。

审视自己的工具：问一下，当世界已经转向 agent orchestration，你是不是还在构建 step-file 架构。

9.4 架构决策的关键启示

Section titled “9.4 架构决策的关键启示”
  1. 离线优先不是选项，是必需品。 本地 SQLite 作为 Source of Truth，API 失败不影响用户体验。
  2. Feature-Based 组织优于 Type-Based。 按功能模块组织代码，而非按 models/views/controllers 分类，减少跨目录依赖。
  3. sealed class 是 Dart 错误处理的最佳实践。 Result<T, AppError> 模式强制调用方处理所有情况。
  4. 统一响应格式从第一天就定义。 {"data": ..., "meta": ...} + {"error": {"code": ..., "message": ...}} 让前后端协作无摩擦。
  5. 测试用 SQLite 替代 PostgreSQL。 API 测试使用内存 SQLite，零配置即可运行，极大降低了 CI 复杂度。

一、 为什么要做这次测评？(Motivation)

Section titled “一、 为什么要做这次测评？(Motivation)”

在 AI 辅助编程领域，Claude Opus 4.5 曾是无可争议的王者，但其高昂的成本（约 $15/百万输入，$75/百万输出）让高频开发者望而却步。DeepSeek V3 虽然便宜，但在处理超长上下文（>128K tokens）时偶尔会遇到瓶颈。

我希望通过开发 HeartPetBond 这款 App，验证 DeepSeek V3 的强力挑战者 —— 智谱 GLM-4.7 在实际工程中的表现：

  • 长上下文能力：标称 200K Tokens Context，能否撑起整个项目的文档和代码库？
  • 输出长度：128K Tokens Output，能否一次性生成复杂的 Flutter 页面？
  • 稳定性与幻觉：在长达数天的持续开发中，是否会出现逻辑崩溃？
  • 性价比：相比 Opus 4.5，它能为独立开发者省下多少钱？

挑战背景：在使用 DeepSeek V3 配合 Claude Code + BMAD 开发时，当上下文超过 128K 时曾遇到如下报错： API Error: 400 ... maximum context length is 131072 tokens... 而 GLM-4.7 的 200K 上下文或许正是破局的关键。

我有 10 年以上的 Flutter 开发经验，此前已成功利用 Claude Code + BMAD 自动生成了 MoneyMind App。这次，我要看看“国产之光”能否胜任同样的挑战。

Section titled “⚠️ 局限 (Cons)”
