背景

Section titled “背景”

3月底，运营团队收到用户反馈：某型号医疗输液设备（编号 EQ-7830）的两条输注事件（bolus_delivery）在运营管理后台上没有显示。用户提供了两条事件的原始遥测数据：

这是一个涉及设备数据同步、后端去重逻辑、前端数据展示的跨系统问题。我们使用 Claude Code 配合 BMAD Quick Dev 工作流和多个 MCP Server，完成了从排查到修复的全过程。

根因确认

Section titled “根因确认”

去重逻辑（production 分支）：

根因：医疗输液设备的序列计数器是2字节（最大65535），大约每2年循环一次。当计数器回绕后，产生了与2年前完全相同的 raw_payload 遥测帧。去重查询没有 event_date 也没有时间窗口，于是旧事件被误认为是当前事件的”重复”，导致新事件被丢弃。

Git 历史追溯

Section titled “Git 历史追溯”

Claude Code 进一步追溯了 event_date 被移除的历史：

移除的原因：另一台设备（EQ-5217）出现了重复事件问题。由于解析器用 Date.current 推断年份（设备原始遥测帧不包含年份），同一天的多次同步可能产生不同的 event_date，导致去重失效。所以改用 raw_payload（稳定的原始遥测帧）替代 event_date。

这意味着简单地加回 event_date 会重新引入旧问题。需要一个同时解决两个问题的方案。

第三阶段：修复方案设计与实现

Section titled “第三阶段：修复方案设计与实现”

三层防御策略

Section titled “三层防御策略”

这个方案同时解决了：

  • 原问题（EQ-5217）：同日重复同步 → raw_payload 在1年窗口内仍能捕获
  • 当前问题（EQ-7830）：序列回绕 → 2年前的旧事件超出1年窗口，不再误判

第四阶段：/code-review 四路并行对抗性评审

Section titled “第四阶段：/code-review 四路并行对抗性评审”

修复完成后，通过 /code-review 技能启动了 4个并行的评审子代理：

评审架构

Section titled “评审架构”

每个子代理独立运行，互不干扰，最终汇总为统一报告。

关键发现

Section titled “关键发现”

架构评审 发现其他事件类型的去重块存在完全相同的漏洞——4个评审子代理中有3个独立发现了这个问题，互相印证。

性能评审 发现：

  • 去重查询缺少复合索引，每次同步都会全表扫描
  • events.present? 会加载所有匹配事件到内存，应使用 .exists?
  • 1.year.ago 在循环内每次迭代都重新计算

安全评审 发现：

  • 新增的 .where("events.created_at >= ?", cycle_cutoff) 使用参数化查询，安全
  • 但同文件存在预先的 SQL 字符串插值风险

最终修复清单

Section titled “最终修复清单”

根据评审结果，共修复 7 项：

#修复项类型
1bolus_delivery 去重：加 event_date + 时间窗口核心修复
2其他事件类型去重：同样修复一致性

经验总结

Section titled “经验总结”

  1. MCP 接入数据库是排查的加速器。3 条 SQL 就定位了根因，省去了大量猜测和日志翻查。

  2. Git 历史追溯不可省略。event_date 被移除是有原因的，如果不了解历史就加回去，会重新引入旧 bug。

  3. 并行对抗性评审能发现盲点。4 个独立评审子代理中，3 个都发现了其他事件类型的同源漏洞——这是单人 review 很容易遗漏的。

  4. 自动化测试要模拟真实场景。测试中用 2.years.ago 模拟旧事件，用当天日期模拟当前事件，精确覆盖了时间窗口的边界条件。

  5. 修复前确认数据安全。测试运行在事务中自动回滚，migration 使用 CONCURRENTLY 不锁表——生产环境零风险。
