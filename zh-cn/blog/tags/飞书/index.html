OpenClaw v2026.3.22：史上最大版本，10 个破坏性变更，80+ 贡献者，安全全面加固

2026年3月23日
Vibe Sparking

OpenClaw v2026.3.22：史上最大版本

Section titled “OpenClaw v2026.3.22：史上最大版本”

一个 release tag 里塞了 10 个破坏性变更。如果你在生产环境跑 OpenClaw，先别急着 npm update。

这不是一次普通的功能堆叠。v2026.3.22 是 OpenClaw 清理遗留包袱、重新定义自己的版本。旧的 Chrome 扩展中继、CLAWDBOT_* 环境变量、.moltbot 状态目录、单体式的 extension-api——全部砍掉，没有兼容层。

80 多位贡献者参与了这次发布。

破坏性变更：先看这里

Section titled “破坏性变更：先看这里”

ClawHub 优先安装。 openclaw plugins install <package> 现在先查 ClawHub，查不到才回退到 npm。如果你之前直接从 npm 装插件，行为会变。

Chrome 扩展中继移除。 旧的 Chrome extension relay 路径、捆绑的扩展资源、driver: "extension" 配置、browser.relayBindHost 全部删除。运行 openclaw doctor --fix 迁移浏览器配置。Docker、headless、沙箱和远程浏览器流程不受影响。

图片生成标准化。 image_generate 工具统一了图片创建和编辑路径。旧的 nano-banana-pro 文档和示例已移除。之前复制过那个示例配置的，改用 agents.defaults.imageGenerationModel。

全新 plugin SDK。 公共插件 SDK 现在是 openclaw/plugin-sdk/*，openclaw/extension-api 已删除，没有兼容垫片。捆绑插件必须使用注入的运行时来执行主机端操作。

消息发现 API 变更。 ChannelMessageActionAdapter.describeMessageTool(...) 成为共享消息工具发现的唯一方式。旧的 listActions、getCapabilities、getToolSchema 已移除。

Matrix 插件重写。 基于官方 matrix-js-sdk 的全新 Matrix 插件。从旧版 Matrix 插件升级需要按迁移指南操作。

遗留环境变量清除。 所有 CLAWDBOT_* 和 MOLTBOT_* 环境变量名在运行时、安装器和测试工具中被移除。改用对应的 OPENCLAW_* 名称。

遗留状态目录清除。 .moltbot 状态目录和 moltbot.json 的自动检测/迁移回退已移除。还在用 ~/.moltbot 的，把数据移到 ~/.openclaw 或者设置 OPENCLAW_STATE_DIR。

exec 环境沙箱加固。 阻止宿主 exec 环境中的 JVM 注入（MAVEN_OPTS、SBT_OPTS、GRADLE_OPTS、ANT_OPTS）、glibc 可调参数利用（GLIBC_TUNABLES）和 .NET 依赖解析劫持（DOTNET_ADDITIONAL_DEPS）。Gradle 初始化脚本重定向限制为仅覆盖方式。

Discord Carbon reconcile。 原生命令部署默认切换到 Carbon reconcile，Discord 重启不再通过 OpenClaw 的本地部署路径反复搅动斜杠命令。

插件生态：ClawHub 和捆绑包

Section titled “插件生态：ClawHub 和捆绑包”

ClawHub 成为一等公民。新增 openclaw skills search|install|update 流程，openclaw plugins install clawhub:<package> 支持带更新元数据的安装。

市场支持。 Claude 市场注册解析、plugin@marketplace 安装、市场列表和更新支持已上线。

捆绑包兼容。 兼容 Codex、Claude 和 Cursor 的捆绑包发现和安装支持。捆绑包技能映射为 OpenClaw 技能，Claude 捆绑包的 settings.json 默认值应用到嵌入式 Pi。

Hook 管理。 hook-pack 的安装和更新通过 openclaw plugins 路由，openclaw hooks 专注于 hook 可见性和逐个 hook 的控制。

插件命令。 新增所有者门控的 /plugins 和 /plugin 聊天命令，用于插件列表、显示和启用/禁用。

模型和提供商

Section titled “模型和提供商”

OpenAI 默认切换。 默认 OpenAI 设置模型切换到 openai/gpt-5.4，Codex 保持 openai-codex/gpt-5.4。聊天、图片、TTS、转录和嵌入的默认值集中在一个共享模块中。

GPT-5.4 家族扩展。 原生前向兼容支持 gpt-5.4-mini 和 gpt-5.4-nano。

Anthropic Vertex。 新增通过 Google Vertex AI 使用 Claude 的核心 anthropic-vertex 提供商支持，包括 GCP 认证和发现。

Chutes 提供商。 新增捆绑的 Chutes 提供商，带插件拥有的 OAuth/API-key 认证和动态模型发现。

网络搜索提供商。 Exa、Tavily、Firecrawl 作为捆绑的网络搜索插件加入，各自带有专用工具和配置路径。

MiniMax M2.7。 默认模型从 M2.5 升级到 M2.7，新增 M2.7-highspeed，/fast 模式映射到 highspeed 变体。MiniMax API 和 OAuth 插件表面合并为单一默认启用的 minimax 插件。

xAI Grok 更新。 捆绑的 Grok 目录同步到当前 Pi 支持的 ID、限制和定价。/fast 映射到当前 xAI Grok fast 模型家族。

智谱 GLM 更新。 捆绑的 GLM 目录同步到当前 Pi 元数据，包括 4.5/4.6 模型家族和更新的定价。

小米 MiMo V2。 小米提供商切换到 /v1 OpenAI 兼容端点，新增 MiMo V2 Pro 和 MiMo V2 Omni。

智能体和会话

Discord 还是飞书？OpenClaw ACP 自主编程的平台选择与 YOLO 模式

2026年3月20日
Vibe Sparking

同一条指令，发到两个平台。

Discord 频道里，我 @ 了机器人：“给 UserService 写完整的单元测试，覆盖边界情况，写完跑一遍确认全过。” 然后切去干别的事。40 分钟后回来，Thread 里已经堆了十几条进度消息——创建了 12 个测试文件，跑了两轮修复，最后一条是测试报告截图，全绿。代码已经 commit 到分支上。

飞书群里，同样的指令，同一个 OpenClaw 配置，同一个 Claude Code 后端。任务也完成了，测试也写了。但整个过程是一次性的：消息发出去，Claude Code 跑完，结果回来，结束。我想追问”把那个 edge case 再加几个”，只能重新发一条消息触发一个全新的进程。上一轮的上下文？不在了。

差别不在 Agent 能力，在平台。

两个平台跑同一套 ACP，体验完全不同

Section titled “两个平台跑同一套 ACP，体验完全不同”

我把这几天踩坑的结果整理成表：

能力Discord飞书
mode=run 单次执行支持支持
Thread 绑定（持久会话）支持不支持
Slash 命令（/acp spawn、/acp status）正常报错：“Thread bindings unavailable for feishu”
频道级 Agent 路由原生支持（peer 绑定）能用但体验混乱
一个 Bot 挂多个 Agent自然（频道隔离）别扭（同一个群聊）
YOLO 模式兼容性完整（Thread = 隔离上下文）部分（仅 run 模式）

核心差距在 Thread 绑定。Discord 的 Thread 是平台原生概念——一个 Thread 就是一个独立的消息流，OpenClaw 把它映射成一个持久的编程会话。飞书有话题功能，但 OpenClaw 的飞书 Channel 插件没有实现 Thread 绑定，源码里写得很明确："Thread bindings unavailable for feishu"。

这意味着 Discord 上可以做到：发一条指令启动任务 → Agent 在 Thread 里报进度 → 我在同一个 Thread 追问或修正 → Agent 继续跑。整个过程是连续的对话。

飞书上只有：发指令 → 等结果 → 结束。想继续？再发一条，新进程，新上下文。用 resumeSessionId 可以把前一次的会话 ID 传进去，Claude Code 能加载之前的记忆，但这需要你手动管理 session ID 的链条。跟 Discord 里自动维持的 Thread 上下文比，差着一个抽象层。

聊天驱动编程，绕不开 YOLO 模式

Section titled “聊天驱动编程，绕不开 YOLO 模式”

说完平台差异，说一个更根本的问题。

Claude Code 在正常模式下，每次要读文件、写文件、执行命令，都会弹一个权限确认。一个小时内弹上百次。在终端里你可以按 y 确认，有节奏地跟着走。但从聊天界面驱动呢？

没有交互式 TUI。没有地方让你按 y。

OpenClaw 的 ACP 后端 acpx 是把 Claude Code 作为子进程启动的。子进程没有终端，没有 stdin 可以输入确认。如果不跳过权限检查，进程启动后第一个文件读取就卡住了，永远等着一个不会到来的确认。

所以 --dangerously-skip-permissions（或等效的 --permission-mode bypassPermissions）不是”图省事”，是架构上的硬性要求。没有它，聊天驱动编程这件事根本不成立。

YOLO 不等于裸奔

Section titled “YOLO 不等于裸奔”

跳过权限检查听着吓人，但实际风险可以控制到很低。

Docker 隔离。把 Agent 的工作区跑在容器里，最坏情况是容器炸了，宿主机不受影响。OpenClaw 支持配置 workspace 路径，指向容器内挂载的目录就行。

Git 是最好的回滚。Agent 写的每一行代码都在 Git 仓库里。不满意？git reset --hard HEAD~1。干净利落，没有后遗症。我习惯让 Agent 在独立分支上工作，合不合并我说了算。

PreToolUse Hooks 仍然生效。这点很多人不知道——bypass 模式跳过的是交互式确认，不是 Hook 系统。你可以在 .claude/settings.json 里配置 PreToolUse hook，比如禁止 rm -rf /，禁止修改特定目录。这些规则在 bypass 模式下照样拦截。

--disallowedTools 可用。想禁止 Agent 用某些工具？--disallowedTools 参数在 bypass 模式下正常工作。注意别用 --allowedTools，那个在 bypass 模式下有 bug，行为不符合预期。

任务边界要窄。“给 UserService 写单元测试”是好指令。“把代码库整体优化一下”是灾难。Agent 越自由，出错的搜索空间越大。限定模块、限定操作类型、限定输出格式，这些约束本身就是安全措施。

Discord 的架构优势

Section titled “Discord 的架构优势”

回到平台选择。Discord 之所以跑 ACP 效果好，是因为它的几个原生概念刚好对上了自主编程的需求。

频道是天然隔离边界。一个 Bot Token 接入一个 Discord 服务器，不同频道绑定不同 Agent。#backend 频道背后是后端代码库的 Agent，#frontend 是前端的，#infra 管基础设施。互不干扰，peer binding 配置一下就完事。

Thread 是持久编程会话。每个 Thread 内部，OpenClaw 维护一个 session。消息上下文在 Thread 生命周期内一直存在。40 分钟的自主编程过程中，Agent 发的进度消息、我的追加指令、Agent 的响应，全在一个 Thread 里，上下文连贯。

resumeSessionId 自动链接。Thread 内的后续消息自动携带上一次的 session ID，Claude Code 进程启动时带上 --resume 参数，加载之前的对话历史。不需要手动传 ID，平台层自动处理。

飞书的限制在哪

Section titled “飞书的限制在哪”

飞书不是不能用，我前几天的飞书 ACP 实战里已经跑通了完整流程。但它有明确的天花板。

Thread 绑定未实现。这是最大的限制。尝试在飞书群里用 /acp spawn 启动持久会话，直接报错。OpenClaw 的飞书插件代码里，Thread 相关的方法全部抛出 “unavailable” 异常。这不是配置问题，是功能缺失。

没有 Slash 命令。Discord 的 Slash 命令是平台级 API，OpenClaw 注册了 /acp spawn、/acp status、/acp stop 等命令。飞书没有对等的机制，群聊里的 / 命令全靠文本解析模拟，容易出问题。

mode: "session" 不工作。飞书上只能用 mode: "run"——发一条消息，起一个 Claude Code 进程，跑完退出。mode: "session" 需要 Thread 绑定支持，而 Thread 绑定在飞书上不存在。

resumeSessionId 能用但要手动。飞书上也可以通过消息内容传递 session ID 来实现链式调用。但你得自己记住上一次的 session ID，在下一条消息里带上。实操中很容易断链。

groupPolicy 默认白名单。飞书的 groupPolicy 默认是 allowlist，消息会被静默丢弃。不报错、不提示。第一次用的人大概率会被这个坑住，以为 Bot 挂了。记得设成 open。

怎么选

Section titled “怎么选”

结论很直接。

要自主编程、要持久会话、要 Agent 跑几十分钟不用管——用 Discord。Thread 绑定 + YOLO 模式 + 频道隔离，这套组合目前是 OpenClaw ACP 体验最完整的方案。

团队已经在飞书上协作、不想换平台——飞书也能用。mode: "run" + resumeSessionId 手动链式调用，一样能完成编程任务。每次任务是独立的，像发工单一样用。对很多场景来说够了。

两者可以并行。同一个 OpenClaw 实例可以同时接 Discord 和飞书，bindings 里配好路由就行。我现在的用法就是这样：需要长时间自主编程的任务发 Discord，快速问答和小任务发飞书群。工具为场景服务，不用站队。

真正重要的不是选哪个平台，是理解 YOLO 模式在这个架构里扮演什么角色。没有它，聊天窗口发出去的编程指令只是一个没有回应的请求。有了它——加上容器隔离、Git 回滚、Hook 守卫这些配套措施——聊天窗口才真正变成了一个编程界面。

平台能换。这个架构约束换不了。

  • /acp spawn、/acp status 等斜杠命令在飞书群里不可用

  1. WebSocket 已连接 → 正常
  2. 事件日志为空 → 消息压根没推过来，问题在飞书那边
  3. 改 dmPolicy 为 open → 还是没消息
  4. 去飞书后台仔细检查 → 找到了

im:message.p2p_msg:readonly 这个权限状态是”未开通”。

这是”读取用户发给机器人的单聊消息”权限。没有这个权限，飞书在服务端就把事件过滤掉了。不发给长连接，不报错，不告警。消息直接丢了。

开通这个权限，发布新版本，重启 Gateway。消息立刻通了。

整个过程最难受的地方是系统给了零反馈。WebSocket 连着，配置看起来没问题，但消息就是不来。如果飞书能在事件过滤时返回一条 permission_denied 之类的提示，能省不少排查时间。

配置检查清单

Section titled “配置检查清单”

每次配新的飞书应用时走一遍这个清单：

  • openclaw.json 中账号的 appId / appSecret 已写入
  • bindings 中 accountId 对应正确的 agentId（不是 agent）
  • dmPolicy: "open" 且 allowFrom: ["*"]（接收私聊的话）
  • 飞书后台：机器人能力已添加
  • 飞书后台：订阅方式为”长连接”，事件 im.message.receive_v1 已添加
  • 飞书后台：im:message.p2p_msg:readonly 权限已开通
  • 飞书后台：已发布最新版本
  • openclaw gateway restart 已执行

小结

Section titled “小结”

飞书接入 OpenClaw 本身不复杂，但有三个地方不按直觉来：凭据用 config set 写入而不是 --token 参数、本地扩展可能跟内置插件打架、私聊权限缺失时消息无声无息地丢。知道了坑在哪，下次配新应用几分钟就搞定。
