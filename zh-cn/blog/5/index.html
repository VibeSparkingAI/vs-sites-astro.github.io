Claude Code 2.1.85 深度解析：逐项分析 × 同类对比 × 演进趋势

2026年3月27日
Vibe Sparking

版本概览

Section titled “版本概览”

2.1.85 是一次”平台成熟度”版本——9 项新功能 + 17 项修复 + 4 项性能优化，核心主题是：MCP 生态规范化、Hook 系统企业化、终端体验打磨、以及大会话稳定性。

新功能逐项解析

Section titled “新功能逐项解析”

1. MCP 多服务器环境变量 (CLAUDE_CODE_MCP_SERVER_NAME / CLAUDE_CODE_MCP_SERVER_URL)

Section titled “1. MCP 多服务器环境变量 (CLAUDE_CODE_MCP_SERVER_NAME / CLAUDE_CODE_MCP_SERVER_URL)”

问题背景： 之前写 MCP header helper 脚本时，一个 helper 脚本只能硬编码为一个特定 MCP 服务器服务。如果你有 5 个 MCP 服务器，你就需要 5 个几乎一样的 helper 脚本。

使用场景举例：

  • 企业里有 jira-mcp、confluence-mcp、sentry-mcp 三个服务器，它们都需要注入同样格式的 OAuth Bearer token header
  • 现在可以写一个通用 helper：#!/bin/bash echo "Authorization: Bearer $(get_token $CLAUDE_CODE_MCP_SERVER_NAME)"
  • 运行时 Claude Code 自动注入当前服务器的 name 和 url

注意事项： helper 脚本需要能根据 server name/url 动态返回不同的 token，不要用全局固定值。

同类对比：

产品MCP header 定制能力
Claude Code环境变量注入，一个 helper 服务多 server
Codex CLI不支持 MCP（OpenAI 走自有插件体系）
Gemini CLI支持 MCP，但 header 自定义能力不如 Claude Code 精细

趋势： MCP header 定制是为了适配企业内部的认证网关和 zero-trust 网络架构。未来可能演进为声明式 auth config（类似 Kubernetes ServiceAccount token 自动挂载）。

2. Hook 条件执行 (if 字段，使用权限规则语法)

Section titled “2. Hook 条件执行 (if 字段，使用权限规则语法)”

问题背景： 之前的 hook 系统是”全量触发”——每次 PreToolUse 都会 fork 一个进程跑 hook 脚本，即使那个 hook 只关心 git 命令。频繁 fork 进程 = 延迟 + CPU 浪费。

使用场景举例：

只在执行 git 相关的 Bash 命令时才触发，其他所有 Bash 调用（npm、python 等）直接跳过。

注意事项：

  • if 语法复用权限规则的模式匹配（Bash(git *) 意思是 Bash 工具且参数匹配 git *）
  • 不匹配的 hook 不会 spawn 任何进程，纯字符串匹配跳过
  • 注意通配符 * 的范围，Bash(rm *) 会匹配 rm -rf /

同类对比：

产品Hook 条件过滤
Claude Code权限规则语法的 if 条件
Codex CLI有 hook 系统但无条件过滤，通过 sandbox policy 分层控制
Gemini CLI无 hook 系统，通过 tool policy 做粗粒度控制

趋势： Hook 系统正在向”轻量级 policy engine”演进，条件匹配 -> 条件链 -> 最终变成类似 OPA/Rego 的策略引擎。

3. 定时任务时间戳标记（/loop, CronCreate 的 transcript 标记）

Section titled “3. 定时任务时间戳标记（/loop, CronCreate 的 transcript 标记）”

问题背景： 使用 /loop 或 cron 定时执行任务时，transcript 里看不到任务是什么时候触发的。事后排查问题时，无法区分是手动触发还是定时触发，也无法判断时间线。

使用场景举例：

  • 你设置 /loop 每 10 分钟检查一次 CI 状态
  • 现在 transcript 里会出现 [2026-03-27 14:30:00 UTC — /loop triggered] 这样的标记
  • 回顾 session 时一目了然哪些是自动触发的

注意事项： 时间戳用的是 UTC，如果你需要本地时间，需要自行换算。

同类对比：

产品定时任务审计
Claude Codetranscript 内嵌时间戳
Codex CLI无内置 loop/cron 机制
Gemini CLItask tracker 刚集成进系统 prompt，暂无时间标记

趋势： AI Agent 的可审计性（auditability）是企业采购的硬性要求。未来会演变为 OpenTelemetry span 级别的追踪。

4. 图片粘贴尾随空格（[Image #N] 后加空格）

Section titled “4. 图片粘贴尾随空格（[Image #N] 后加空格）”

背景： 粘贴图片后，[Image #1] 占位符后面紧跟用户输入文字，导致 tokenizer 可能把占位符和文字粘在一起解析。

使用场景： 粘贴截图后继续输入 “fix this CSS”，之前会变成 [Image #1]fix this CSS，现在变成 [Image #1] fix this CSS。

注意事项： 微小但对多模态交互的鲁棒性很重要。

同类对比： 三家产品都有类似的图片粘贴支持，这是 polish 级细节，不构成竞争差异。

5. Deep Link 扩容至 5000 字符

Section titled “5. Deep Link 扩容至 5000 字符”

问题背景： claude-cli://open?q=... deep link 之前限制较短，无法传递复杂的预填充 prompt。CI/CD 工具、IDE 插件想通过 deep link 打开 Claude Code 并传入完整上下文时会被截断。

使用场景举例：

  • CI pipeline 失败时自动生成一个 deep link：claude-cli://open?q=This%20build%20failed%20with%20error...（附带完整错误日志）
  • 团队内部 wiki 嵌入一键调试链接
  • 超长 prompt 会显示 “scroll to review” 警告，防止盲目执行

注意事项： 5000 字符是 URL 编码后的长度，实际内容会更短。浏览器对 URL 总长度也有限制。

同类对比：

产品Deep Link / URL Scheme
Claude Codeclaude-cli://open?q=...，5000 字符

注意事项：

怎么回事

Section titled “怎么回事”

install.runtime-DDmlaKdG.js 这个文件名里的 DDmlaKdG 是构建时生成的 hash。核心从旧版升到新版，重新打包，hash 变了。但第一轮跑插件更新时，进程加载的还是旧的模块映射——它去找一个已经不存在的文件。

这是一个更新顺序竞态。核心文件换了，安装器还在用老地图。

Section titled “修法：再跑一遍”

  • @tencent-weixin/openclaw-weixin → v2.0.1

意外收获：插件安全扫描

Section titled “意外收获：插件安全扫描”

第二轮更新的输出里多了一堆 WARNING。之前没仔细看过，这次认真读了一遍。

OpenClaw 对每个插件做了静态代码扫描，标记两类高风险模式：

环境变量 + 网络发送。 读 env 里的 token，然后通过网络发出去。这是凭证泄露的经典路径。对消息平台插件来说，这是正常操作（得用 API key 调平台接口），但扫描器不管意图，一律报。

Shell 命令执行。 插件调用 child_process。音频转码调 ffmpeg、平台检测调 uname，都算合理。但恶意插件也能借这个口子跑任意代码。

1. managed-settings.d/ 分片策略目录

Section titled “1. managed-settings.d/ 分片策略目录”

Added managed-settings.d/ drop-in directory alongside managed-settings.json, letting separate teams deploy independent policy fragments that merge alphabetically

问题背景 企业部署 Claude Code 时，安全团队、平台团队、业务团队各自有不同的策略需求（权限规则、MCP 服务器白名单、Hook 配置等），但过去只有一个 managed-settings.json 文件。多团队写同一个文件会产生冲突和覆盖风险。

使用场景举例

  • 安全团队部署 /etc/claude-code/managed-settings.d/00-security.json（禁止 curl、wget）
  • 平台团队部署 10-platform.json（配置内部 MCP 服务器）
  • 业务团队部署 20-team-alpha.json（自定义 Hooks）
  • 按文件名字母序合并，数字前缀控制优先级

注意事项

  • 合并规则是「按字母序」，后出现的同名 key 是覆盖还是深合并需确认文档
  • 与 managed-settings.json 并存时的优先级需注意（通常 .d/ 目录优先级与主文件相同层级，按顺序合并）
  • 类似 Linux 的 /etc/sudoers.d/、/etc/apt/sources.list.d/ 模式

演进趋势 从「单文件管理」→「分片管理」，是企业级多团队协作的标准模式。预期未来可能支持 managed-mcp.d/ 等更细粒度的分片。

2. CwdChanged 和 FileChanged Hook 事件

Section titled “2. CwdChanged 和 FileChanged Hook 事件”

Added CwdChanged and FileChanged hook events for reactive environment management (e.g., direnv)

问题背景 开发者在 monorepo 或多项目环境中工作时，切换目录会导致环境变量（如 .envrc/direnv）、工具链版本（如 .node-version）变化。之前 Claude Code 无法感知这些变化，可能用错误的环境执行命令。

使用场景举例

  • CwdChanged：当 Claude 切换到不同子目录时，自动执行 direnv allow 加载该目录的环境变量
  • FileChanged：当 .env 文件被修改时，自动重新加载环境配置
  • 结合 Hook 自动切换 Node/Python 版本

注意事项

  • FileChanged 的监控粒度（是 inotify/fsevents 级别还是 Claude 工具触发级别）需确认
  • 高频文件变化可能触发大量 Hook 调用，注意性能
  • 与 ConfigChange Hook 不同：ConfigChange 关注 Claude Code 自身配置变化，这两个关注工作目录和项目文件变化

演进趋势 Hook 事件不断细化，从生命周期事件（SessionStart/End）→ 工具事件（PreToolUse/PostToolUse）→ 现在的环境事件（CwdChanged/FileChanged）。趋势是让 Claude Code 成为一个完全可编程的开发环境。

Section titled “3. sandbox.failIfUnavailable 设置”

  • 安全敏感项目中作为合规要求

注意事项

  • 默认值应该是 false（不破坏向后兼容）
  • 建议企业环境始终开启此选项
  • 需确保沙箱依赖（Linux: bubblewrap/bwrap; macOS: sandbox-exec）已正确安装

问题背景 Claude Code 运行时环境中存在 ANTHROPIC_API_KEY、AWS/GCP 凭证等敏感环境变量。当 Claude 执行 Bash 命令、触发 Hooks 或启动 MCP 服务器时，这些子进程会继承所有环境变量——如果子进程行为不可信（如来自提示注入的命令），就可能泄露凭证。

  • 清理范围：Anthropic 相关 + 云提供商（AWS_, GCP_, AZURE_* 等）凭证
  • 如果子进程确实需要这些凭证（比如 Hook 需要调用 AWS API），开启后会中断
  • 建议企业环境通过 managed-settings.json 的 env 字段统一启用

Section titled “OpenClaw 微信插件装好了没反应？四个坑踩完才知道”

Feng 按照 openclaw-weixin npm 文档 把微信插件装好了，在微信群里发了条测试消息。

OpenClaw 没反应。

看了下 gateway 日志，插件显示加载成功。openclaw status 也没报错。

问题就出在”看起来没问题”和”实际没工作”之间的那条缝里。

第一个坑：旧目录挡路

Section titled “第一个坑：旧目录挡路”

用 npx CLI 重装插件时，安装器报了一行：

这行容易被刷过去。旧目录没被覆盖，新插件根本没装进去。gateway 日志报 [plugins] openclaw-weixin failed to load，找不到 openclaw/plugin-sdk/channel-config-schema 模块。

修法： 手动删掉旧目录再装。

第二个坑：QQ 插件缺 axios

Section titled “第二个坑：QQ 插件缺 axios”

顺手也装了 openclaw-qqbot。装完 gateway 报：

QQ 插件的 package.json 里写了 axios 依赖，但安装过程没拉下来。

修法： 进插件目录手动装。

第三个坑：版本检测被污染

Section titled “第三个坑：版本检测被污染”

这个最隐蔽。

QQ 插件的 node_modules/openclaw 不是 symlink，是一个完整的目录副本，版本号是 1.6.5。OpenClaw 的版本检测代码扫描 node_modules 时，先碰到了这个副本，把 1.6.5 当成了系统版本。

结果微信插件注册时报错：

实际系统装的是 2026.3.22，但检测逻辑被 QQ 插件里那份副本骗了。

修法： 删掉副本，换成 symlink 指向真正的安装路径。

第四个坑：插件 OK 但没配账号

Section titled “第四个坑：插件 OK 但没配账号”

三个问题修完，openclaw status 显示 openclaw-weixin 状态 OK。

但还是收不到消息。

查了日志，没有 getUpdates 轮询。再看配置文件，channels.openclaw-weixin 是 {}。插件装好了，账号没挂上去。

Token 存在 ~/.openclaw/openclaw-weixin/accounts/ 目录里，但 config 没引用它们。

修法： 手动补配置。

两个微信账号都能收发消息了。

QQ 插件的后续

Section titled “QQ 插件的后续”

QQ 插件目前还有 SDK 兼容性问题 —— applyAccountNameToChannelSection 这个导出不匹配，账号暂时没配。等上游修。

四条教训

Section titled “四条教训”

1. 重装插件前先删旧目录。 安装器不会自动覆盖，会静默跳过。

2. 第三方插件的 node_modules/openclaw 如果是目录副本，会干扰其他插件。 改成 symlink 指向系统安装路径。这个问题不在你的配置里，在插件的打包方式里。

3. 插件加载成功不等于在收消息。 openclaw status 只检查插件是否注册，不检查 channel 是否有账号配置。要看日志里有没有 getUpdates 轮询。

4. 排查”没反应”类问题，从日志入手，别猜。 四个问题叠在一起，每个的表现都是”没反应”。只有看日志才能分层。

/office-hours：从想法到设计文档

然后它搜索了市场竞争格局。发现了真正的竞品：ClawHost（单实例部署）、NanoClaw（Docker Sandbox 容器化隔离）、Docker 自己的 cagent 项目。但没有一个做”OpenClaw 管理 OpenClaw”的舰队管理模式。

这重新定义了整个构建顺序：CLI 优先，魔法优先，UI 其次。

产出物是一份完整的设计文档，包含问题陈述、三种实现方案、前提假设、跨模型视角和推荐方案，全部写入 ~/.gstack/projects/，供下游技能自动消费。

macOS 在背后干了什么

Section titled “macOS 在背后干了什么”

这里有个很多人不知道的细节：macOS 在休眠或重启时，会清理 /private/tmp/ 下的内容。tmux 的 socket 就放在那里。socket 没了，tmux server 自然起不来，session 自然也没了，里面跑着的 SSH 隧道当然一起凉凉。

更根本的问题是：tmux 是一个普通的用户空间进程，它没有任何机制让 macOS 在休眠后帮你重启它。你 tmux new-session 起来的东西，macOS 压根不知道它的存在，也不在乎它死没死。

所以这个问题不是”怎么让 tmux 更稳定”，而是”tmux 本来就不该干这个活”。

守护进程这件事，macOS 有专门的工具：launchd。

换个思路：launchd + autossh

Section titled “换个思路：launchd + autossh”

launchd 是 macOS 的服务管理器，系统启动时最先跑起来的进程之一，PID 1 就是它。你告诉它要运行什么、什么时候运行、崩溃了怎么办，它帮你管着。macOS 休眠、重启、重新登录，launchd 都知道该干什么。

autossh 则解决了另一个问题：SSH 连接偶尔还是会断（网络抖动、NAT 超时）。autossh 会监控连接状态，断了自动重连。两者配合，隧道基本上就是永活的。

Section titled “浏览器：连接时序问题”

v2026.3.22 移除了 Chrome 扩展中继，转向 existing-session 和 CDP 直连。新路径带来了新的时序假设——这些假设在某些场景下是错的。

CDP 短暂连接失败后重启（#53004）。 另一个场景：OpenClaw 启动时，本地已有一个运行中的浏览器实例，但初次可达性探测恰好超时（网络抖动、进程刚启动等）。旧逻辑会立即判定”没有可用浏览器”，触发重新拉起流程，结果两个浏览器进程并存。现在改为在短暂的初次探测失败后重试一次，确认确实不可达才启动新进程。感谢 @vincentkoc。

这两个修复加在一起，让 existing-session 模式在生产环境里变得可靠得多。

根本原因是多个路径的读取逻辑没有统一。

macOS auth 配置和 XDG 路径（#53034）。 openclaw auth 登录后，凭据写入了 macOS Application Support 目录，但某些代码路径在读取时只查 XDG 配置路径，两者对不上。

ClawHub 登录路径（#52949）。 类似的问题在 ClawHub 本身的登录读取逻辑里也存在——只在某一个路径查找，另一个路径有凭据也视而不见。感谢 @scoootscooob 报告。

技能浏览的 auth token（#52949）。 网关技能浏览在发起请求时没有携带本地 ClawHub auth token，导致未授权的请求全部走公开目录。修复后，浏览私有技能目录正常工作。感谢 @vincentkoc。

这三个修复针对同一根因的不同表现：macOS 路径和 XDG 路径的二元性没有在所有读取点被一致处理。

在模糊中制造清晰。 模型进步快，可能性爆炸式增长，大家很容易迷失在”能做”和”该做”之间。PM 要把这团迷雾切开。

1小时登顶AppStore，48天写出12万行代码：专业程序员的出路在哪？

Section titled “1小时登顶AppStore，48天写出12万行代码：专业程序员的出路在哪？”

去年一个人不会写代码，用 Cursor 花了1个多小时做出一款叫”小猫补光灯”的 App。就是那种纯色屏幕补光的工具，没什么技术含量。但它冲上了 AppStore 付费榜第一，小红书拿了百万浏览，卖了上百万。

最近打开 B 站，的新视频跳出来：《过去的 48 天我经历了什么》。这位前 ZEALER 创始人用 Claude Code 从零搞了一个多智能体 AI Agent 系统，20 万行总代码，12 万行有效代码，包含智能日历和记账的融合架构。

我看了看自己刚提交的 PR。改了三天，两百多行。

来自两个方向的冲击

Section titled “来自两个方向的冲击”

把这两件事放在一起看，你会发现专业程序员正被两股力量夹击。

第一股：AI 从上方碾压。 Anthropic 的 METR 测量显示，Opus 4.6 大约有 50% 的概率能独立完成人类需要近 12 小时的软件任务。16 个月前，同类模型只能处理 21 分钟级别的工作。这是 41 倍的能力跳跃。不是线性增长，是指数级的。你今天写的代码，明天 AI 写得更快、错误更少。

第二股：普通人从下方涌入。 不是个例。他从 GPT-4 到 Cursor，前前后后做了十几二十个项目。他运营的 AI 编程社群里，没有编程背景的人用 Vibe Coding 做出能跑的产品越来越常见。也不是专业程序员，但 48 天的输出量超过很多小型开发团队一个季度的产出。

V2EX 上有人说：“大概率花钱找团队写的。“这种反应可以理解，但其实是一种自我安慰。就算这次是找人写的，下一次呢？再下一次呢？工具在变好，门槛在消失。这个趋势不会停。

焦虑的方向搞错了

Section titled “焦虑的方向搞错了”

很多程序员看到这些新闻，第一反应是恐慌：我的饭碗要没了。

但仔细想想，这种恐慌指向了一个错误的问题。问题不是”AI 会不会替代程序员”，而是”编程这件事本身正在变成什么”。

做小猫补光灯赚了钱，不是因为他的代码写得好。他甚至不懂代码。他赚钱是因为他发现了一个需求：自拍补光，然后用最快的方式把产品丢到市场上测试。产品感觉对了就上架，感觉不对就扔掉，一个下午验证一个想法。

那个 48 天项目，技术社区讨论最多的不是他的代码质量。知乎上的深度分析指出，他在架构上走了不少弯路——早期用 ReAct 死循环模式反复碰壁，后来才切到 Plan & Execute 流水线。但关键是：他最终跑通了。一个非专业程序员，用 AI 工具完成了一个多智能体系统的完整交付。

用户不关心你的代码是手写的还是 AI 生成的。用户关心问题有没有被解决。

Anthropic 产品负责人说了什么

Section titled “Anthropic 产品负责人说了什么”

Anthropic Claude Code 产品负责人 Cat Wu 最近写了一篇文章叫《Product Management on the AI Exponential》。里面有几句话值得反复读：

角色在融合。设计师在提交代码，工程师在做产品决策，产品经理在构建原型和评估。

当产品经理能在一个下午从想法到可用原型，“如果我们试试…”和”来，试试这个”之间的距离几乎消失了。

做简单的事。如果你的产品巧妙地绕过了模型的某个局限，等下一个模型发布，这个 workaround 就变成了不必要的复杂度。实现越简单，新能力到来时切换就越容易。

这段话翻译成程序员能听懂的版本：你花三天精心设计的抽象层，下个月新模型一出，可能直接就不需要了。你的价值不在于写出多精巧的代码，而在于你能不能快速理解问题、快速验证方案、快速在变化中调整。

Cat Wu 还提到一个原则：先验证能力上限，再优化成本。 过早砍 token 是常见错误。这和写代码的道理一样——先确认方向对，再考虑优化。

五条路，不是退路

Section titled “五条路，不是退路”

说完让人不舒服的部分，说说出路。这不是鸡汤，每一条都有具体的对应动作。

1. 做 AI 增强的 10x 工程师

Section titled “1. 做 AI 增强的 10x 工程师”

用 Cursor 1 小时做出一个 App。但他做不出一个高并发的支付系统、一个分布式消息队列、一个需要在 99.99% 可用性下运行的核心服务。你能。

区别在于：你的专业知识让你能用 AI 工具做出更复杂、更可靠、更大规模的东西。AI 不是来替代你的，是来给你装上涡轮增压的。

具体做法：把 Claude Code 或 Cursor 嵌入你的日常工作流。不是偶尔用一下，是每个任务都用。让 AI 处理模板代码、测试生成、文档编写，你专注于架构决策和边界情况。

2. 往上走，做系统思考者

Section titled “2. 往上走，做系统思考者”

Vibe Coding 能生成代码，但生成不了系统设计。一个非程序员可以让 AI 写出一个能跑的 API，但他很难让 AI 设计出一个在百万用户量级下不倒的架构。

你在数据库选型、缓存策略、服务拆分、容错设计上的十年经验，AI 工具放大的是这些知识的应用效率，不是让这些知识变得不值钱。

具体做法：从”写代码的人”重新定义自己为”设计系统的人”。花更多时间在架构评审、技术方案对比、故障模式分析上。这些是 AI 辅助的领域，不是 AI 接管的领域。

3. 拥抱全产品生命周期

Section titled “3. 拥抱全产品生命周期”

Cat Wu 说 Anthropic 内部，角色在融合。这意味着未来最值钱的人不是”前端工程师”或”后端工程师”，而是能从想法到上线一个人跑完全程的人。

的真正优势不是编程，是产品直觉——他知道什么样的东西有人买。如果你既有产品直觉又有技术深度，你的天花板比他高得多。

具体做法：下次有想法的时候，别等 PM 写 PRD。自己用 Claude Code 花一个下午做出原型，拿给用户看。Cat Wu 说这叫”原型优先，不是文档优先”。

4. 守住 AI 还做不好的领域

Section titled “4. 守住 AI 还做不好的领域”

生产环境的可靠性。安全审计。合规要求。遗留系统迁移。性能调优。这些领域有两个特点：后果严重（出错就是事故），上下文极深（需要理解整个系统的历史和约束）。

AI 在这些领域进步很快，但距离独立胜任还有距离。这是当前的护城河。

具体做法：不要回避”脏活累活”。那些别人不想碰的老系统、复杂的部署流程、诡异的线上 bug，恰恰是 Vibe Coder 做不了的事。

5. 骑在指数曲线上，不是挡在前面

Section titled “5. 骑在指数曲线上，不是挡在前面”

Cat Wu 用了一个比喻：这像是在冲浪，最重要的是别从浪上掉下来。

AI 能力每 16 个月跳升一个数量级。你不可能预测两年后 AI 会做到什么程度。但你可以确保自己是最先用上新能力的那批人，而不是最后一个感到惊讶的人。

具体做法：每次大模型更新，花半天试试它能做什么以前做不了的事。Anthropic 内部的做法是”故意让 AI 做你觉得它做不到的事，有时候它真的能做到，那就是产品需要跟上的信号”。

和你的区别

Section titled “和你的区别”

回到开头那两个故事。

1 小时做出 AppStore 第一。但他在小红书运营、需求洞察、用户心理上花的时间远超 1 小时。编码只是整个链条中最短的一环，AI 把这一环压缩到了接近零。

48 天写出 12 万行代码。但知乎分析指出他在架构上反复踩坑。一个有经验的后端工程师用同样的 AI 工具，大概率能在更短时间内做出更稳固的系统。

这就是关键：AI 消灭的是编码的体力劳动部分，放大的是你脑子里真正值钱的东西——系统理解、故障直觉、架构判断、工程品味。

问题从来不是”AI 会不会替代程序员”。

问题是：你愿不愿意从”写代码的人”变成”用 AI 解决问题的人”。

这两者之间的距离，没你想的那么远。

  • 压缩安全。 孤立的 tool_result 块在压缩后被修复，长工具循环在下次模型调用前触发溢出恢复。
  • 内存刷新。 内存写入的转录哈希去重在回退重试间保持激活，不再写入重复条目。

2026年3月22日
Vibe Sparking

AI 能读代码、改文件、搜网页，但它操控不了你桌面上的 App。打开 Slack 发条消息、在 Finder 整理文件、往 Xcode 里粘段代码——这些事 AI 一直是旁观者。

macos-use 把这堵墙拆了。

它是什么

Section titled “它是什么”

macos-use 是一个 MCP 服务器，用 Swift 写的。它让 Claude 或任何兼容 MCP 的模型，通过 macOS 的无障碍 API（Accessibility APIs）直接控制桌面应用。

关键不是截图。是语义树。

macOS 里每一个 App 的 UI 元素——按钮、输入框、菜单、列表——都暴露在无障碍 API 里，结构化的，有层次的。macos-use 读的就是这棵树。AI 看到的是「地址栏，当前值 google.com，可点击」，而不是一张 1200×800 的截图。

这不是新技术。VoiceOver 用了这套 API 几十年了。新的是：现在 AI 也能用。

六个工具

Section titled “六个工具”
工具做什么
open_application_and_traverse打开任意 App，读取 UI 树
click_and_traverse点击坐标，返回变化了什么
type_and_traverse往输入框打字
press_key_and_traverse按键，支持 Cmd、Shift 等修饰键
scroll向任意方向滚动
refresh_traversal重读当前 UI 状态

每次操作之后，默认返回一个 diff——哪些元素增加了，哪些删了，哪些改了。AI 知道自己的操作产生了什么效果，不用猜。

为什么不用截图

Section titled “为什么不用截图”

截图方案有两个根本问题，一个表面问题。

Token 消耗先谈。一张 1080p 截图扔给模型，context 直接涨一大块。macos-use 返回的是 JSON 文件路径，UI 树存到 /tmp/macos-use/，不往 context 里堆。

更深的是稳定性。像素识别依赖分辨率、缩放比、深色模式、字体渲染。换台显示器或者切换深色模式，之前标注的坐标可能全错。无障碍树是结构化数据，跟像素没有关系。

表面问题是语义。截图里的按钮，AI 需要猜它叫什么、是否可点。无障碍树直接告诉你：AXButton, label="发送", enabled=true。没有推断，没有猜测。

Section titled “注意事项”

坐标是相对窗口的，不是屏幕绝对坐标。click_and_traverse 的 x/y 以目标 App 的窗口为基准，窗口移动后之前记的坐标要重算。

没有 Windows 和 Linux 版本。Swift + macOS Accessibility APIs 是平台绑定的，暂时只有 Mac。

Vibe Sparking

引言：为什么选择 Bruno？

Section titled “引言：为什么选择 Bruno？”

上一篇文章介绍了如何用 AI 一句话生成 Postman Collection。但很多团队正在从 Postman 迁移到 Bruno——一个开源、离线优先、纯文本存储的 API 客户端。

核心区别在于存储格式：

维度PostmanBruno
存储云端 JSON（单文件，可达数千行）本地 .bru 文本文件（每个请求一个文件）
版本控制JSON diff 可读性差纯文本 diff，PR Review 友好
协作依赖 Postman Cloud 同步直接提交到 Git 仓库
离线使用受限完全离线
环境变量JSON 嵌套结构独立 .bru 文件

Bruno 的 .bru 文件天然适合代码仓库——每个 API 请求是一个独立文件，环境变量是独立文件，改动一个参数只产生一行 diff。这对 Code Review 和 CI/CD 集成至关重要。

但问题也随之而来：Bruno 的 .bru 格式是一种自定义 DSL，不像 JSON 那样通用——手动编写更容易出格式错误。

本文记录了如何用 BMAD Quick Dev 在同一个会话中，继 Postman Collection 之后，再生成一整套 Bruno API 文档——包括多环境配置、鉴权链、请求参数、测试脚本和内联文档。

一、同一上下文，不同输出格式

Section titled “一、同一上下文，不同输出格式”

1.1 零重复分析

Section titled “1.1 零重复分析”

  • 鉴权流程（OAuth token + user_session_key 双层机制）
  • 响应信封格式（{status: {code, message}, data: {...}}）
  • 搜索参数命名（search[like_*]、search[*]）
  • 内容模型字段（Content + QaItem）
  • 前端调用方式（ContentService 的 GET 参数格式）

1.2 AI 的额外分析

Section titled “1.2 AI 的额外分析”

但 AI 并非简单地 “格式转换”。它额外做了以下工作：

  1. 检查现有目录结构：发现 bruno/carehealth-api/ 已存在但为空（仅 bruno.json 和 collection.bru），确认不会覆盖
  2. 检查是否有现有 .bru 文件作为格式参考——没有，所以从 Bruno DSL 规范生成
  3. 设计目录层级：api/auth/（鉴权前置）+ api/contents/（业务接口），符合 Bruno 的文件夹即分组约定
  4. 创建多环境文件：environments/local.bru、sit.bru、prod.bru——Postman 用 JSON 内嵌环境变量，Bruno 用独立文件

关键差异：

5.1 复用效率

Section titled “5.1 复用效率”

关键数据：生成 Bruno 版本时，AI 没有重新阅读任何源文件。

Postman 版本需要读取 8 个文件（控制器、模型、Service、鉴权拦截器、响应拦截器、环境配置、视图模板、前端组件）。Bruno 版本复用了全部上下文，仅花时间在格式转换和目录结构设计上。

这就是 BMAD Quick Dev 在长会话中的复利效应：每一次分析都为后续任务积累可复用的理解。

六、与 UI 自动化测试的三位一体

Section titled “六、与 UI 自动化测试的三位一体”

在这个完整的开发会话中，AI 产出了三种互补的工件：

工件用途受众
Playwright E2E验证前端表单、导航、组件交互QA / CI

三者共享同一套源码理解，但服务于不同的质量保障场景。

七、实践建议

Section titled “七、实践建议”

7.1 什么时候优先选 Bruno？

Section titled “7.1 什么时候优先选 Bruno？”
  • API 文档需要版本控制：团队要求接口变更可追溯
  • CI/CD 中运行 API 测试：Bruno CLI (bru run) 支持命令行执行
  • 离线开发环境：无法访问 Postman Cloud
  • Code Review 包含 API 变更：.bru diff 远比 JSON diff 可读

7.2 什么时候保留 Postman？

Section titled “7.2 什么时候保留 Postman？”
  • 团队已深度使用 Postman Cloud：迁移成本高
  • 需要 Mock Server、Monitor 等高级功能
  • 非技术成员需要 GUI 操作

7.3 两者并存策略

Section titled “7.3 两者并存策略”

在这个会话中，AI 生成了两种格式。它们可以并存：

  • Bruno（.bru）提交到 Git 仓库 → 作为 API 文档的 “源代码”
  • Postman（.json）用于团队共享和 CI → 从 Bruno 导出或独立维护

八、结语

Section titled “八、结语”

Bruno 的 .bru 格式代表了一种理念：API 文档应该和代码一样被版本控制、审查和测试。

BMAD Quick Dev 让这个理念的落地成本趋近于零——你不需要学习 .bru DSL 的语法细节，不需要手动创建目录结构，不需要记住 bru.setEnvVar 和 pm.collectionVariables.set 的区别。你只需要说一句 “生成 Bruno 格式”，AI 会处理剩下的一切。

更重要的是，在一个足够长的开发会话中，这些不同格式的产出共享同一次源码分析的成本。第一次分析鉴权流程花了 30 秒读取 8 个文件；此后生成 Postman、Bruno、Playwright Mock 的鉴权配置，都是零成本的知识转换。

这就是 AI 辅助开发的理想形态：理解一次，输出多次，格式自适应。
