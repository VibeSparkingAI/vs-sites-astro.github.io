引言：API 文档的 “最后一公里” 问题

Section titled “引言：API 文档的 “最后一公里” 问题”

后端接口开发完成后，团队常常面临一个尴尬的局面：

代码写好了，测试通过了，但前端同事问你：“接口文档呢？Postman Collection 有吗？”

你知道你应该写。你也知道一份好的 Postman Collection 不仅是文档，更是可执行的契约——它能一键验证接口是否正常、参数是否正确、鉴权流程是否完整。但手动编写一份包含鉴权链、示例响应、自动变量传递的 Collection，往往需要 30-60 分钟。

如果 AI 能从现有代码中自动推断出完整的 Postman Collection 呢？

3.1 控制器不存在时的应对

Section titled “3.1 控制器不存在时的应对”

这个案例有一个特殊之处：目标控制器在当前部署的容器中并不存在。AI 在容器内执行 rails routes | grep content 返回零结果后，并没有停下来说 “无法生成”，而是：

  1. 从同类控制器（advices_controller.rb）提取 RESTful 约定
  2. 从前端 Service（content.service.ts）确认调用端点和参数格式
  3. 从数据模型（content.ts）确认字段结构
  4. 从鉴权拦截器（token.interceptor.ts）确认请求签名方式

这种 “从消费者倒推生产者” 的方法，在后端接口尚未部署的阶段尤其有价值——前端团队可以拿着这份 Collection 进行 Mock 联调。

3.2 响应格式的精确推断

Section titled “3.2 响应格式的精确推断”

AI 注意到了 ResponseInterceptor 中的一个关键细节：

成功响应会被解构——data 的内容被展开到顶层。但在 Postman 的示例响应中，AI 保留了原始信封格式 {status, data}，因为 Postman 接收到的是 HTTP 响应原文，ResponseInterceptor 只在 Angular 内部生效。

通道，双向了

Section titled “通道，双向了”

MCP 一直是单行道。你的 agent 调用工具，服务器响应。如果服务器那边发生了什么事 — CI 构建失败了、部署完成了、测试跑完了 — 服务器没法告诉 agent。你得自己去问。

--channels 改变了这件事。MCP 服务器现在可以不等调用，主动向你的活跃会话推送消息。想想这意味着什么：

一个部署监控 MCP 服务器在看你的 staging 环境。agent 在写代码。部署挂了。服务器直接推送 “deploy failed: missing env var DATABASE_URL on staging” 到你的会话。agent 看到了，检查配置，修了。

一个测试运行器 MCP 服务器在测试完成时推送结果。agent 不用轮询，收到通知就行。

一个团队沟通 MCP 服务器把相关的 Slack 消息或 PR review 评论推到你的编码会话里。

这是研究预览，API 可能会变。但方向已经明确：MCP 正在从工具调用协议变成双向消息层。

技能学会了自己定节奏

Section titled “技能学会了自己定节奏”

effort frontmatter 让技能和斜杠命令的作者在技能被调用时覆盖模型的 effort 级别。

以前 effort 是全局设置。复杂任务调高，简单任务调低，来回切。现在技能自己决定。一个代码格式化命令用最低 effort 跑，因为不需要深度推理。一个架构审查技能要求最高 effort，因为偷工减料会出烂分析。

一个小小的 YAML 字段，影响不小。技能作者可以为正确的推理深度做设计，而不是指望用户碰巧把 effort 调对了。

限速，看得见了

Section titled “限速，看得见了”

rate_limits 是状态栏脚本可用的新字段。它暴露了 Claude.ai 的 5 小时和 7 天用量窗口，包含 used_percentage 和 resets_at。

如果你曾经在任务做到一半突然撞墙，现在有解了。状态栏可以显示类似 “5h 用量 73%，2h 后重置”。不用猜了。

这只适用于 Claude.ai 计费。用自己 API key 的用户有不同的限制。

Section titled “插件，内联声明”

source: 'settings' 是一个新的插件市场来源，让你直接在 settings.json 里声明插件条目。不需要注册表，不需要安装步骤。在设置文件里写好插件定义，就加载了。

对分发内部插件的团队来说，这简化了流程。推一下 settings.json 的变更，所有人就有了。

加上插件提示现在检测 CLI 工具使用（原来只看文件模式匹配），插件发现机制在变聪明。Claude Code 现在可以根据你在跑什么命令行工具来推荐插件，而不只是看项目里有什么文件。

Section titled “—resume 修复：比听起来重要得多”

--resume 在恢复会话时丢失并行工具结果。如果之前的会话有并行工具调用，恢复后会显示 [Tool result missing] 占位符，而不是实际结果。

这比听起来严重。并行工具调用在复杂会话里很常见 — agent 同时读多个文件、并行跑测试、同时搜索多个目录。丢失这些结果意味着 agent 丢失了它已经做过什么的上下文。它会重新读文件、重新搜索，或者更糟，在信息不完整的情况下做决定。

频道级 Agent 路由原生支持（peer 绑定）能用但体验混乱
一个 Bot 挂多个 Agent自然（频道隔离）别扭（同一个群聊）
YOLO 模式兼容性完整（Thread = 隔离上下文）部分（仅 run 模式）

核心差距在 Thread 绑定。Discord 的 Thread 是平台原生概念——一个 Thread 就是一个独立的消息流，OpenClaw 把它映射成一个持久的编程会话。飞书有话题功能，但 OpenClaw 的飞书 Channel 插件没有实现 Thread 绑定，源码里写得很明确："Thread bindings unavailable for feishu"。

这意味着 Discord 上可以做到：发一条指令启动任务 → Agent 在 Thread 里报进度 → 我在同一个 Thread 追问或修正 → Agent 继续跑。整个过程是连续的对话。

飞书上只有：发指令 → 等结果 → 结束。想继续？再发一条，新进程，新上下文。用 resumeSessionId 可以把前一次的会话 ID 传进去，Claude Code 能加载之前的记忆，但这需要你手动管理 session ID 的链条。跟 Discord 里自动维持的 Thread 上下文比，差着一个抽象层。

聊天驱动编程，绕不开 YOLO 模式

Section titled “聊天驱动编程，绕不开 YOLO 模式”

说完平台差异，说一个更根本的问题。

Claude Code 在正常模式下，每次要读文件、写文件、执行命令，都会弹一个权限确认。一个小时内弹上百次。在终端里你可以按 y 确认，有节奏地跟着走。但从聊天界面驱动呢？

没有交互式 TUI。没有地方让你按 y。

OpenClaw 的 ACP 后端 acpx 是把 Claude Code 作为子进程启动的。子进程没有终端，没有 stdin 可以输入确认。如果不跳过权限检查，进程启动后第一个文件读取就卡住了，永远等着一个不会到来的确认。

所以 --dangerously-skip-permissions（或等效的 --permission-mode bypassPermissions）不是”图省事”，是架构上的硬性要求。没有它，聊天驱动编程这件事根本不成立。

打开这个，Claude Code 子进程就不再请求权限确认，直接执行所有工具调用。

YOLO 不等于裸奔

Section titled “YOLO 不等于裸奔”

跳过权限检查听着吓人，但实际风险可以控制到很低。

Docker 隔离。把 Agent 的工作区跑在容器里，最坏情况是容器炸了，宿主机不受影响。OpenClaw 支持配置 workspace 路径，指向容器内挂载的目录就行。

Git 是最好的回滚。Agent 写的每一行代码都在 Git 仓库里。不满意？git reset --hard HEAD~1。干净利落，没有后遗症。我习惯让 Agent 在独立分支上工作，合不合并我说了算。

PreToolUse Hooks 仍然生效。这点很多人不知道——bypass 模式跳过的是交互式确认，不是 Hook 系统。你可以在 .claude/settings.json 里配置 PreToolUse hook，比如禁止 rm -rf /，禁止修改特定目录。这些规则在 bypass 模式下照样拦截。

--disallowedTools 可用。想禁止 Agent 用某些工具？--disallowedTools 参数在 bypass 模式下正常工作。注意别用 --allowedTools，那个在 bypass 模式下有 bug，行为不符合预期。

任务边界要窄。“给 UserService 写单元测试”是好指令。“把代码库整体优化一下”是灾难。Agent 越自由，出错的搜索空间越大。限定模块、限定操作类型、限定输出格式，这些约束本身就是安全措施。

Discord 的架构优势

Section titled “Discord 的架构优势”

回到平台选择。Discord 之所以跑 ACP 效果好，是因为它的几个原生概念刚好对上了自主编程的需求。

频道是天然隔离边界。一个 Bot Token 接入一个 Discord 服务器，不同频道绑定不同 Agent。#backend 频道背后是后端代码库的 Agent，#frontend 是前端的，#infra 管基础设施。互不干扰，peer binding 配置一下就完事。

Thread 是持久编程会话。每个 Thread 内部，OpenClaw 维护一个 session。消息上下文在 Thread 生命周期内一直存在。40 分钟的自主编程过程中，Agent 发的进度消息、我的追加指令、Agent 的响应，全在一个 Thread 里，上下文连贯。

resumeSessionId 自动链接。Thread 内的后续消息自动携带上一次的 session ID，Claude Code 进程启动时带上 --resume 参数，加载之前的对话历史。不需要手动传 ID，平台层自动处理。

飞书的限制在哪

Section titled “飞书的限制在哪”

飞书不是不能用，我前几天的飞书 ACP 实战里已经跑通了完整流程。但它有明确的天花板。

Thread 绑定未实现。这是最大的限制。尝试在飞书群里用 /acp spawn 启动持久会话，直接报错。OpenClaw 的飞书插件代码里，Thread 相关的方法全部抛出 “unavailable” 异常。这不是配置问题，是功能缺失。

没有 Slash 命令。Discord 的 Slash 命令是平台级 API，OpenClaw 注册了 /acp spawn、/acp status、/acp stop 等命令。飞书没有对等的机制，群聊里的 / 命令全靠文本解析模拟，容易出问题。

mode: "session" 不工作。飞书上只能用 mode: "run"——发一条消息，起一个 Claude Code 进程，跑完退出。mode: "session" 需要 Thread 绑定支持，而 Thread 绑定在飞书上不存在。

resumeSessionId 能用但要手动。飞书上也可以通过消息内容传递 session ID 来实现链式调用。但你得自己记住上一次的 session ID，在下一条消息里带上。实操中很容易断链。

groupPolicy 默认白名单。飞书的 groupPolicy 默认是 allowlist，消息会被静默丢弃。不报错、不提示。第一次用的人大概率会被这个坑住，以为 Bot 挂了。记得设成 open。

怎么选

Section titled “怎么选”

结论很直接。

要自主编程、要持久会话、要 Agent 跑几十分钟不用管——用 Discord。Thread 绑定 + YOLO 模式 + 频道隔离，这套组合目前是 OpenClaw ACP 体验最完整的方案。

团队已经在飞书上协作、不想换平台——飞书也能用。mode: "run" + resumeSessionId 手动链式调用，一样能完成编程任务。每次任务是独立的，像发工单一样用。对很多场景来说够了。

两者可以并行。同一个 OpenClaw 实例可以同时接 Discord 和飞书，bindings 里配好路由就行。我现在的用法就是这样：需要长时间自主编程的任务发 Discord，快速问答和小任务发飞书群。工具为场景服务，不用站队。

真正重要的不是选哪个平台，是理解 YOLO 模式在这个架构里扮演什么角色。没有它，聊天窗口发出去的编程指令只是一个没有回应的请求。有了它——加上容器隔离、Git 回滚、Hook 守卫这些配套措施——聊天窗口才真正变成了一个编程界面。

平台能换。这个架构约束换不了。

BMAD 6.2.0：干掉一整套架构的版本升级

Section titled “BMAD 6.2.0：干掉一整套架构的版本升级”

我问了一个很简单的问题：“这两个 BMAD skill 有什么区别？“答案让我重新审视了对 AI 开发工具的整个理解。

两个 skill 都生成 product brief，都在同一个框架里。一个有六个步骤，另一个有五个阶段、四个子 Agent、三种执行模式，还有一个 replaces-skill 字段，像判决书一样指向前者。

两个 Skill，同一件事，两个世界

Section titled “两个 Skill，同一件事，两个世界”

BMAD 6.2.0 在 analysis workflow 文件夹里附带了两个 skill：bmad-create-product-brief 和 bmad-product-brief-preview。同样的任务，同一个框架。我以为第二个不过是小版本迭代的预览版。打开 bmad-manifest.json，看到了 replaces-skill 字段。

一个在取代另一个。

旧方式：Step-File 架构

Section titled “旧方式：Step-File 架构”

原版 bmad-create-product-brief 像表单向导一样运转。Step 01 到 Step 06，严格顺序，不能跳过。每个步骤需要用户确认才能解锁下一步。单个 Agent 处理全部内容。没有网络调研。状态通过 stepsCompleted 存在 frontmatter 里。能跑，能用，可预期。

它也是一段碰巧用了 AI 的脚本。结构是人设计的，节奏是人掌控的，过程是人主导的。

新方式：基于 Prompt 的多 Agent 编排

Section titled “新方式：基于 Prompt 的多 Agent 编排”

替代品 bmad-product-brief-preview 和前任几乎没有相似之处。五个阶段代替六个步骤，但这是最无趣的变化。

四个子 Agent 并发运行：

  • artifact-analyzer 扫描现有项目文档
  • web-researcher 抓取外部市场数据
  • opportunity-reviewer 评估商业潜力
  • skeptic-reviewer 压力测试各项假设

三种执行模式：

  • guided（默认）用于交互式使用
  • yolo 用于带模拟专家输入的自主执行
  • headless 用于完全自主、无人参与的执行

它能编辑已有的 brief，而不只是新建。接受 --create、--edit、--optimize、--distillate、--inputs、--headless 等参数。输出是 LLM distillate——一个经过 token 优化的 brief 版本，专门设计用来喂给下游 AI 工作流，比如 PRD 生成。

对比一览

Section titled “对比一览”
维度旧版（create-product-brief）新版（product-brief-preview）
架构Step-file，固定顺序Prompt-based，灵活阶段
执行模式一种（仅交互式）三种（guided / yolo / headless）
AI 协作单 Agent四个并发子 Agent
网络调研无有
Headless 支持无有
编辑已有 brief无有
AI 对 AI 输出无有（LLM distillate）

每一行说的都是同一个故事。旧 skill 是在自动化人的工作流。新 skill 是定义一个目标，让 Agent 自己商量怎么做。

背后的模式

Section titled “背后的模式”

我一直在观察 AI 工具领域的这种转变。第一代工具把人在做的事情搬过来，在每个步骤加上 AI——自行车装了个电机。第二代工具问的是：这东西为什么非得是自行车？

Step-file 架构说的是：“这里有六件事要做，按这个顺序做，每步都要等批准。”

Prompt-based 架构说的是：“这是我们要产出的东西，这些是能帮上忙的专家，开始吧。”

这不是版本升级，是范式切换。

为什么这改变了能构建什么

Section titled “为什么这改变了能构建什么”

Step-file skill 无法 headless 运行，因为每个步骤都等着人按 ‘C’ 继续。Multi-agent skill 可以，因为 Agent 之间自己协商。

Step-file skill 无法在做 artifact 分析的同时并行做网络调研，因为第 3 步结束才能开始第 4 步。新 skill 可以，因为子 Agent 在设计上就是并发的。

LLM distillate 或许是最能说明问题的细节。旧 skill 产出的是给人读的内容。新 skill 产出的是给人和下游 AI Agent 同时消费的内容。它在为 AI 对 AI 的通信做设计——product brief 喂给 PRD 生成器，PRD 生成器喂给 story 创建器，story 创建器喂给开发 Agent。输出格式不是事后才想的；它是一个关于受众是谁（或者是什么）的架构决策。

“Guided → YOLO → Headless”成熟度曲线

Section titled ““Guided → YOLO → Headless”成熟度曲线”

三种执行模式不只是个功能，它描述了一条成熟度曲线：

  1. Guided：人来驱动，AI 辅助（辅助轮）
  2. YOLO：AI 驱动，带模拟专家输入，人来审查（受监督的自主）
  3. Headless：AI 独立运行，产出结果，继续前进（完全自主）

如果你的 AI 工具只支持 guided 模式，它就是第一代。从 guided 跳到 headless 不是量变，它要求工具在架构层面具备自我驱动的能力。Step-file 工具跨不过这道坎，multi-agent 工具可以。

对实践者的意义

Section titled “对实践者的意义”

别再用功能清单评估 AI 工具了，从架构开始看。

一个有三种执行模式和并发子 Agent 的工具，“好过”step-file 工具，不是快车好过慢车那种好法。是汽车好过马那种好法。能力的差距不是量级的，是类别的。

下次更新框架时，别只确认旧工作流还能不能跑。检查一下框架有没有已经超越你的思维模型。BMAD manifest 里的 replaces-skill 字段，不只是在废弃一个脚本，它在废弃一整种关于 AI 与人如何协作的思考方式。

建议

Section titled “建议”

新项目：用 bmad-product-brief-preview。

审视自己的工具：问一下，当世界已经转向 agent orchestration，你是不是还在构建 step-file 架构。

11 个 bug 修复。挑几个你大概率碰得到的。

会话 hook 漏触发 — 用 /resume 切换会话时 SessionEnd hook 不触发。session-end hook 里写了清理逻辑的人会踩到这个坑。修了。

自定义状态栏空白 — 工作区信任机制阻塞时，状态栏什么都不显示。现在至少会告诉你为什么。修了。

CLAUDE_CODE_DISABLE_TERMINAL_TITLE 没有阻止启动时设置终端标题。tmux 用户如果遇到标题被覆盖的怪事，就是这个 bug。修了。

Claude Code 2.1.78: 插件有了持久状态，静默失败变成了报错

Section titled “Claude Code 2.1.78: 插件有了持久状态，静默失败变成了报错”

你的 AI 编程助手在任务中途挂了。API 触发了速率限制，turn 直接结束。没有 hook 触发，没有清理逻辑运行。你泡完咖啡回来，看到的是一个死掉的终端。

这是 2.1.77 的情况。2.1.78 加了个 StopFailure hook 事件，专门处理这种场景。changelog 里一行字，解决了一整类”到底发生了什么”的问题。

Changelog 里的暗线

Section titled “Changelog 里的暗线”

Changelog 是一种奇怪的文档。每一行都是一个修复或功能，但真正有意思的从来不是某一行，而是所有行加在一起的走向。

Claude Code 2.1.78 包含 25+ 项变更。表面看是 bug 修复版。仔细看，图景不一样：这是一个信任和可靠性版本。几乎每个改动针对的都是同一类问题——Claude Code 做了意料之外的事，或者静默失败，或者让开发者猜发生了什么。

三条线索贯穿整个更新。

线索一：插件基础设施长大了

Section titled “线索一：插件基础设施长大了”

插件获得了 ${CLAUDE_PLUGIN_DATA} 变量提供的持久状态。这个数据在插件更新后不会丢。/plugin uninstall 在删除前会弹出确认。

插件自带的 agent 获得了 frontmatter 支持：effort、maxTurns、disallowedTools。插件作者现在可以让 agent 自我约束——声明资源预算和工具限制。

这些不是面向用户的功能。是平台级基础设施。传递给插件作者的信号：在这里建设，你的状态是安全的，你的 agent 有正经的控制机制。

线索二：静默失败变成了报错

Section titled “线索二：静默失败变成了报错”

这是这份 changelog 里最说明问题的线索。数一数有多少修复遵循同一个模式：以前悄悄出错，现在大声报错，或者干脆不出错了。

沙箱静默禁用。 你设了 sandbox.enabled: true，但依赖没装好，沙箱就… 不启动。没报错。没警告。你以为有沙箱保护。实际没有。现在启动时会显示警告。

MCP deny 规则形同虚设。 deny: ["mcp__servername"] 权限规则没有把被禁止的工具从模型的视野中移除。模型能看到这个工具，尝试调用，然后失败。规则写了，但没按预期工作。修了——工具在发送给模型之前就被移除。

沙箱路径不生效。 sandbox.filesystem.allowWrite 配合绝对路径不工作，必须加 // 前缀（没人告诉你这个）。现在绝对路径直接生效。

受保护目录被暴露。 bypassPermissions 模式下，.git、.claude 等受保护目录可以被无提示写入。这个模式设计上是信任用户的，结果把对敏感目录的信任也给了 AI。修了。

死循环。 API 错误触发 stop hook，stop hook 把阻塞性错误重新喂给模型，模型又出错，又触发 hook。循环往复。你的机器在转圈，你可能好一会儿才发现。

Git 状态污染。 Linux 上沙箱 Bash 里执行 git log HEAD 报 “ambiguous argument” 错误。stub 文件出现在工作目录里污染 git status。

会话截断。 cc log 和 --resume 在大会话（>5 MB，用了 subagent 的）上静默截断对话历史。你的对话记录在，但工具只给你看了一部分。

每个都是开发者因为工具没说清发生了什么而浪费时间或失去信任的场景。

线索三：真实工作流里的边角 bug

Section titled “线索三：真实工作流里的边角 bug”

这些不是测试矩阵里的理论 bug，而是日常使用中碰到的摩擦点。

WSL2 语音模式。 在 Windows 11 的 WSLg 环境下不工作。WSL1/Win10 用户现在会看到明确的错误提示，而不是莫名其妙的沉默。

Ctrl+u。 在普通模式下按 ctrl+u 是滚屏而不是清除光标前的输入。快捷键冲突解决了——ctrl+u/ctrl+d 半页滚动移到了 transcript 模式。

语音修饰键。 ctrl+k 这类组合键式的 push-to-talk 需要按住不放才能激活。修了，现在按下立即激活。

Homebrew PATH。 macOS 上从 Dock 或 Spotlight 启动 VS Code 时，Bash 工具找不到 Homebrew 和其他依赖 PATH 的二进制文件。一个只在特定启动方式下出现的 PATH 继承问题。

颜色发白。 VS Code、Cursor、code-server 这些不声明 truecolor 支持的终端里，Claude 的橙色看起来褪色。

Worktree 加载。 --worktree 标志没有从 worktree 目录加载 skills 和 hooks。

平台信息错误。 /sandbox 的依赖标签在 macOS 上显示 Linux 的前置条件。

Section titled “流式输出更顺了”

响应文本现在逐行流式推送。技术上是性能改进。体验上，工具从”等待回答”变成了”看着它思考”。这种感受上的差别比省下的毫秒数更有意义。

多轮提取。 第一遍没抓到有用内容，会放宽条件重试。Readability 失败了就算了，defuddle 会想办法。

MCP 工具的隐性成本

Section titled “MCP 工具的隐性成本”

用 Claude Code 接了多个 MCP 服务器的人，大概率碰到过这个问题但没意识到。每个 MCP 服务器在启动时会把完整的工具定义塞进上下文 — 工具名、描述、参数 schema、示例，全部塞进来。一个服务器吃 2000 到 5000 token。我接了十几个：Chrome DevTools、Kubernetes、微信公众号、文言发布、Context7、Exa 搜索、Dart 开发工具、sequential-thinking，还有别的。加起来就是 3 万到 5 万 token 的开销，还没开始干活呢。

Opus 4.6 有百万上下文窗口，你可能觉得 5 万 token 不算什么。短任务确实无所谓。但那种真正出活的长会话 — 跨文件调 bug、跑测试、反复改设计、发内容 — 每个 token 都是注意力。schema 噪音越多，模型花在你实际代码上的注意力就越少。

一个 Bot Token，多个 Agent：OpenClaw Discord 频道级路由配置

2026年3月18日
Vibe Sparking

Discord 服务器上十几个频道，一个 Bot 管全场。编程频道和闲聊频道收到同一种回复，技术问题得到的是泛泛而谈，创意讨论却被塞了一堆代码。

问题不在 Agent 不够好，在于一个 Agent 不该干所有人的活。

OpenClaw 有一套路由机制，可以把不同频道指向不同 Agent。同一个 Bot Token，#code-help 背后是代码审查专家，#creative-writing 跑的是写作助手，#support 则是排障引导员。配置过程不需要写代码，五步 CLI 操作加一次 JSON 编辑。

前提

Section titled “前提”
  • OpenClaw 已安装并正常运行
  • Discord Bot 已创建并拿到 Token（如果还没搞定，先看上一篇：给 OpenClaw 接 Discord 机器人）
  • 至少准备两个 Agent 配置（否则路由没意义）

路由的核心逻辑

Section titled “路由的核心逻辑”

OpenClaw 的 bindings 数组是按顺序匹配的，第一个命中的规则生效。匹配精度从高到低：

优先级匹配范围适用场景
1peer — 具体频道或用户频道级定制
2guildId — 整个服务器服务器级区分
3accountId — Bot 账号账号级默认
4无匹配条件全局兜底

和防火墙规则一样，窄规则必须排在宽规则前面。

第一步：注册 Discord Bot 账号

Section titled “第一步：注册 Discord Bot 账号”

如果之前已经接过 Discord，跳过。

Section titled “第二步：创建 Agent”

每个 Agent 有自己的工作区和配置目录。系统提示词、模型参数、工具链——全在配置目录里分开管。

想让编程频道的 Agent 严格遵循文档风格、写作频道的 Agent 提高 temperature——在各自的配置目录调就行。

第三步：打开群组消息权限

Section titled “第三步：打开群组消息权限”

这一步容易漏掉。OpenClaw 的 groupPolicy 默认是 allowlist，也就是白名单模式。效果是：频道消息全部被静默丢弃，不报错、不提示、不记录。

Section titled “第四步：编辑路由绑定”

手动编辑 ~/.openclaw/openclaw.json，在 bindings 数组中加入频道级规则：

每个频道一条规则。id 填 Discord 频道 ID。

获取频道 ID 两种方式：

  • Discord 设置里打开”开发者模式”，右键频道，复制 ID
  • 命令行查询：openclaw directory groups list --channel discord --account <账号ID>

顺序问题： 频道级绑定必须放在同一 Bot 账号的账号级绑定之前。如果账号级规则在上面，它先命中，频道级规则永远不会触发。和 CSS 选择器优先级或 iptables 是同一个道理。

Section titled “实际效果”

假设你有三个频道和三个 Agent：

  • #code-help -> code-review-agent（低 temperature，严格遵循项目文档）
  • #creative-writing -> writing-assistant（高 temperature，风格自由）
  • #support -> troubleshoot-agent（中等 temperature，引导式排障）

三条 binding 规则，同一个 Bot Token。用户在哪个频道发消息，就由对应的 Agent 处理。其他没有专门绑定的频道，走账号级或全局默认 Agent。

常见问题

Section titled “常见问题”

Bot 在频道里没有任何反应 先检查 groupPolicy 是不是 open。默认白名单会静默丢弃所有频道消息。

频道级绑定没生效，所有频道回复风格相同 检查 bindings 数组里的顺序。频道级规则必须在账号级规则前面。

频道 ID 怎么拿 Discord 设置 > 外观 > 开发者模式打开。之后右键任何频道可以复制 ID。

多服务器场景 用 guildId 做服务器级路由。频道级 peer 规则优先级更高，两者可以叠加：某个服务器走 Agent A，但里面的特定频道走 Agent B。

和飞书、QQ 的对比

Section titled “和飞书、QQ 的对比”

OpenClaw 的路由机制不限于 Discord。飞书群聊、QQ 群聊都支持同样的 peer 级别绑定。区别在于：

  • Discord 的频道天然就是独立会话空间，路由到不同 Agent 不需要额外解释
  • 飞书群聊里同一个机器人换了回复风格，用户可能会困惑
  • QQ 群聊的 peer 绑定逻辑相同，但权限配置入口不同

Discord 的频道模型和多 Agent 路由是天然搭配。

微信控制电脑？QClaw 用了一周，聊聊真实感受

Vibe Sparking

在微信里给 PC 发一条消息，电脑自动执行命令。

QClaw 做到了。扫个二维码绑定微信，从此微信聊天窗口变成了远程终端。你在地铁上、在饭桌旁、在任何打开微信的地方，都能让家里或办公室的电脑干活。

用了一周之后，我想说说真实感受。

QClaw 是什么

Section titled “QClaw 是什么”

QClaw 是腾讯电脑管家团队基于 OpenClaw 开源框架做的一键安装包。下载、安装、扫码，三步搞定。不用命令行，不用配环境，Mac 和 Windows 都支持。

它的核心卖点是微信远程操控。绑定之后，QClaw 在微信里以「客服消息」的形式出现。你给它发文字，它在 PC 上执行。文件操作、浏览器控制、脚本运行、定时任务——官方说覆盖 5000+ Skills。

内置的默认模型是国产大语言模型（比如 Kimi 2.5），也可以换成其他国产模型。

第一次用的时候确实有点兴奋。发了句「帮我看看桌面上有哪些文件」，几秒后微信收到了文件列表。能跑起来，这点没问题。

问题出在微信这边

Section titled “问题出在微信这边”

QClaw 在微信里不是一个「联系人」。它是一个「应用」。

这一个区别，导致了一连串的麻烦。

不能加群。 你没法把 QClaw 拉进任何微信群。想在工作群里让 AI 帮忙处理点什么？做不到。它只能在一对一的「应用消息」里跟你说话。

不能转发消息。 在群里看到一段文字、一张图，想转发给 QClaw 处理？不行。微信的消息转发目标列表里，「应用」不会出现。

只能复制粘贴。 要把文字发给 QClaw，得先长按复制，再切到 QClaw 对话窗口粘贴。图片更麻烦——先保存到相册，再从 QClaw 对话里选图发送。

这不是 QClaw 的 bug。这是微信平台架构决定的。在微信的世界里，「联系人」是一等公民，「应用」是二等公民。QClaw 作为应用接入，天然受限。

日常用的时候，这个摩擦感比想象中大。你会本能地想「直接转发给它处理」，然后发现做不到，只好手动中转。多几次之后就有点烦了。

和 OpenClaw 比，功能上有明显差距

Section titled “和 OpenClaw 比，功能上有明显差距”

QClaw 基于 OpenClaw，但不等于 OpenClaw。几个关键区别：

模型选择

Section titled “模型选择”

QClaw 只支持国内大语言模型。可以选 Kimi、MiniMax 等，也能自定义配置其他国产模型。但 Claude、GPT 这些不在选项里。

对于需要特定模型能力的任务——比如复杂代码生成、多语言翻译、长上下文推理——这个限制会直接影响结果质量。

PC 端只读

Section titled “PC 端只读”

在 PC 上打开 QClaw，你能看到微信端发来的消息记录。但反过来不行：你没法从 PC 端的 QClaw 给微信发消息。

只能看，不能回。沟通是单向的。

这意味着所有指令必须从微信端发起。坐在电脑前的时候，这个设计显得多余——你都在电脑前了，为什么不直接用 OpenClaw？

与 OpenClaw 的关系

Section titled “与 OpenClaw 的关系”

QClaw 会读取 OpenClaw 默认的工作区文件、记忆和技能。两者共享这些本地资源。

但它们之间没有消息通道。QClaw 不会把执行结果同步回 OpenClaw 的对话，OpenClaw 也不知道 QClaw 做了什么。是共享文件系统，不是共享通讯。

适合什么场景

Section titled “适合什么场景”

吐槽完了，说说 QClaw 适合干什么。

人不在电脑前，需要电脑做点事。 比如出门了才想起来要把某个文件发到邮箱、要跑个脚本、要查个本地数据。拿出手机，微信发一句话搞定。这是它最顺畅的场景。

用国内大模型就够的任务。 文件整理、简单文案生成、数据汇总、格式转换。这些不需要最强的模型，国产模型完全胜任。

定时任务和推送。 设定好的自动化流程，QClaw 到点执行，结果通过微信推送给你。这个方向其实挺好用。

不适合的场景也很明确：需要群协作的、需要频繁转发内容处理的、需要 Claude 或 GPT 级别模型的、需要 PC 端双向通讯的。

总结

Section titled “总结”

QClaw 降低了 OpenClaw 的部署门槛，让微信成为了 AI 智能体的入口。这个方向是对的。

但微信把它当「应用」处理，导致日常使用的摩擦远超预期。不能加群、不能转发、必须手动中转，这些限制不是小问题。加上模型只支持国产、PC 端单向只读、与 OpenClaw 没有消息桥接，功能边界清晰但也窄。

我的建议：把 QClaw 当作一个「微信触发器」来用。人不在电脑前，需要远程跑点东西，发条微信就行。别试图把它当成完整的 AI 助手——那是 OpenClaw 的活。

那为什么大多数 Skill 在生产环境中仍然出问题？

因为开发者把精力都花在了写对 YAML 和整理目录上。格式问题已经解决了。现在的挑战是内容设计。规范告诉你如何打包一个 Skill，但对如何组织内部逻辑毫无指导。

一个封装 FastAPI 规范的 Skill 与一个四步文档流水线的运作方式完全不同，尽管它们的 SKILL.md 文件从外观上看一模一样。相同的前置信息，相同的目录，可靠性却天差地别。

模式一：Tool Wrapper（工具封装器）

Section titled “模式一：Tool Wrapper（工具封装器）”

Tool Wrapper 让你的 Agent 在需要时按需加载某个特定库的上下文。你不必把 API 规范硬编码到系统提示词里，而是将它们打包进一个 Skill。Agent 只在实际用到该技术时才加载这份上下文。

这是最简单的模式。SKILL.md 监听用户提示词中的特定库关键词，从 references/ 目录动态加载你的内部文档，并将这些规则作为基准事实应用。这是一种将团队编码规范或框架最佳实践直接注入开发者工作流的方式。

模式二：Generator（生成器）

Section titled “模式二：Generator（生成器）”

Tool Wrapper 应用知识，Generator 则确保输出的一致性。如果你的 Agent 每次运行生成的文档结构都不一样，Generator 通过编排一个填空式流程来解决这个问题。

它使用两个可选目录：assets/ 存放输出模板，references/ 存放风格指南。指令的作用像项目经理——告诉 Agent 加载模板、读取风格指南、询问用户缺失的变量，然后填充文档。

**适用场景：**需要一致、可预测的输出——API 文档、提交信息、项目脚手架。

模式三：Reviewer（审查器）

Section titled “模式三：Reviewer（审查器）”

Reviewer 把检查什么和怎么检查分离开来。你不用在系统提示词里罗列所有代码坏味道，而是把一份模块化的评审标准存进 references/review-checklist.md。

代码到达后，Agent 加载清单并按步骤打分，按严重程度归类结果。把 Python 风格检查表换成 OWASP 安全检查表，用同一套 Skill 基础设施就能得到截然不同的审计报告。

**适用场景：**需要依照清单评分——PR 审查、安全审计、合规检查。

模式四：Inversion（反转）

Section titled “模式四：Inversion（反转）”

Agent 的本能是猜测并立即生成。Inversion 翻转了这个顺序。不是用户驱动提示词、Agent 执行，而是 Agent 先对用户展开访谈。

核心机制是明确的、不可绕过的门控指令：“在所有阶段完成之前，不得开始构建。“Agent 按顺序提出结构化问题，等待回答，在拿到完整信息之前拒绝输出任何结果。

**适用场景：**需要在行动前充分收集需求——项目规划、架构设计、入职流程。

模式五：Pipeline（流水线）

Section titled “模式五：Pipeline（流水线）”

面对复杂任务，步骤不能跳过。Pipeline 通过硬性检查点强制执行严格的顺序工作流。

指令本身就是工作流定义。菱形门控条件（例如要求用户审批后才能推进）确保 Agent 无法绕过步骤或呈现未经验证的结果。不同的参考文件只在需要它的步骤处加载，保持上下文窗口清爽。

**适用场景：**顺序严格、每个阶段都需要验证的复杂多步骤任务。

选择合适的模式

Section titled “选择合适的模式”

每种模式回答一个不同的问题：

问题模式
需要注入库或框架的上下文？Tool Wrapper
需要基于模板的一致输出？Generator
需要依照清单评分？Reviewer
需要先收集需求？Inversion
需要严格的多步骤工作流？Pipeline

从你的任务提出的问题出发。如果跨越多个问题，组合使用这些模式。

模式可以组合

Section titled “模式可以组合”

这些模式并非互斥。

一个 Pipeline Skill 可以在末尾加入 Reviewer 步骤来自我校验。一个 Generator 可以在填充模板之前借助 Inversion 收集所需变量。得益于 ADK 的 SkillToolset 和渐进式加载机制，你的 Agent 在运行时只为真正用到的模式消耗上下文 token。

这是架构上的优势：不是把复杂脆弱的指令塞进一个系统提示词，而是把行为分解成可组合的构建块。每个块可以单独测试，每个块有清晰的契约。

实践建议

Section titled “实践建议”
  1. 从单一模式开始。大多数任务干净地对应一种模式，不到需要的时候不要组合。
  2. 在元数据中标注模式。加上 metadata.pattern: tool-wrapper 让架构一目了然，也方便检索。
  3. 把参考资料放到外部文件。不要把大段检查表内联进 SKILL.md。
  4. 在 Pipeline 中设置严格的门控。每跳过一个检查点，就少一次验证机会。
  5. 单独测试每个模式。Generator 模板坏了是 Generator 的问题，不是整个 Skill 的问题。

你家人不会打开那个面板。

企业微信的桥接思路

Section titled “企业微信的桥接思路”

插件把 AI 对话接入企业微信（WeCom）。企业微信管理后台有个「微信插件」功能——开启后用个人微信扫个二维码，你的 AI 智能体就变成了微信里可以直接聊天的联系人。

不用装新应用，不用记网址。微信本来就开着。

从只能发文字到五种消息类型

Section titled “从只能发文字到五种消息类型”

插件最早是 dingxiang-me 的 OpenClaw-Wechat v0.1.0——只能收发文字。Xueheng-Li fork 之后开始扩展。

v0.3.7 的能力：

类型接收发送说明
文本支持支持超长消息按 UTF-8 字节边界自动分段（2048 字节限制）
图片支持支持收到图片自动走 AI Vision 识别
语音支持不支持三级语音识别降级链

文件支持支持.txt/.md/.json/.pdf 等可读格式自动提取内容交给 AI

企业微信不渲染 Markdown，所以插件在发送前自动把 Markdown 转成纯文本。

语音识别：三级降级

Section titled “语音识别：三级降级”

微信上发语音很常见。插件用三级降级链处理：

  1. 企业微信自带识别 — 用腾讯返回的 Recognition 字段
  2. 远程 Qwen3-ASR — 如果有 GPU 服务器，跑 asr_server.py，0.6B 参数的模型，支持 52 种语言和 22 种中文方言。RTX 4090D 上短语音大约 2-4 秒。
  3. 本地 FunASR — CPU、Apple MPS 或 CUDA 都能跑，慢一点但不依赖远程服务器。

音频流程：从企业微信下载 AMR，FFmpeg 转 16kHz WAV，然后交给可用的语音模型。某一级挂了，下一级接上。没有单点故障。

对话记忆

Section titled “对话记忆”

v0.3.6 之前，每条消息都是独立对话。AI 不记得你 30 秒前说了什么。

修复方案用了 OpenClaw SDK 自己的历史管理方法——recordPendingHistoryEntry 加 buildPendingHistoryContextFromMap。每次调用 AI 前重建最近 20 条消息作为上下文。这跟官方 Telegram、Discord 渠道的实现方式一样。

/clear 清空历史，/status 看当前消息数。

「能发不能收」的调试过程

Section titled “「能发不能收」的调试过程”

OpenClaw 2026.3 对渠道插件的要求更严格了。企业微信插件坏掉了，而且坏法很折磨人：往用户发消息没问题，但用户回复的消息完全收不到。没有报错，没有日志。callback 地址返回的是 Control UI 的 HTML 页面，不是 “wecom webhook ok”。

三个问题叠在一起造成了这个现象。

状态上报。 健康监控定期查询渠道状态。插件没有正确上报运行态信息（running 状态、账户快照、探测结果），监控器认定渠道已停止，反复执行重启。

Gateway 生命周期。 startAccount 调完就返回了，没有等 abortSignal。每次重启生成新实例，旧实例的路由还在。竞态条件。

路由注册。 registerHttpRoute() 在新版本里需要显式传 auth: "plugin" 和 match: "exact"。缺了这两个参数，Gateway 的 SPA fallback 先捕获了 callback URL，请求打到了 React 前端应用上。webhook 请求根本没到插件。

v0.3.7 同时修了这三个问题。

AgentId 绑错的坑

Section titled “AgentId 绑错的坑”

代码修完之后，有人还是遇到同样的症状。原因是配置问题：企业微信后台可以创建多个自建应用，每个应用有独立的 AgentId、Secret、Token、EncodingAESKey。这四个值必须来自同一个应用。

一个真实案例：某开发者的 openclaw.json 里写的是 agentId=1000002，但企业微信后台配置回调的应用是 agentId=1000003。发消息能到（API 比较宽容），收消息走的是另一个应用的回调，根本对不上。换了 ID 就好了。

BMAD Method v6 是什么

Section titled “BMAD Method v6 是什么”

BMAD Method 一开始是一套 AI 驱动开发的结构化方法——给编码智能体定规矩，让它们按章办事。到了 v6，它变成了一个平台。

区别在哪？以前是整体安装，全有或全无。v6 是一个核心引擎加上模块生态。你按需选模块，配置好 IDE，安装器处理剩下的事。它给 AI 编码智能体定义了结构、角色和工作流技能，让输出有规范，不用每次从头发挥。

平台目前有这些模块：

  • BMM — 敏捷 AI 驱动开发（项目管理、冲刺规划、PRD）
  • BMB — BMad 构建器（创建自定义智能体、工作流、模块）
  • CIS — 创意智能套件（叙事、头脑风暴、设计思维）
  • TEA — 测试架构师（测试设计、自动化、CI 集成）
  • GDS — 游戏开发工作室（游戏设计文档、玩法测试、游戏架构）
  • WDS — Whiteport 设计工作室（UX 工作流、设计系统、产品简报）

每个模块带自己的技能、智能体和工作流模板。按项目需求组合。

  2. 读取实际 DOM（Playwright 截图、ARIA 快照、error-context.md）

你的 Claude Code 进程在长 session 里内存膨胀？很可能就是这个。

Section titled “—resume 静默截断”

这 bug 很隐蔽——你恢复 session，最近的工作不见了，但没有报错。就是消失了。

安全修复：PreToolUse hooks 绕过 deny 规则

Section titled “安全修复：PreToolUse hooks 绕过 deny 规则”

PreToolUse hooks 返回 “allow” 的时候可以绕过 deny 权限规则，包括企业托管设置。如果企业管理员通过托管设置禁止了某个工具，hook 可以通过返回 “allow” 来覆盖这个禁止。

这是安全边界的越界。hooks 应该只能加限制，不能解除限制。修了——deny 规则现在不管 hook 怎么返回都优先。

Section titled “Write 工具 CRLF 处理”

Section titled “长 session 内存增长”

progress 消息在长时间运行的 session 里会在 compaction 后存活。每条状态更新都会积累，穿过 compaction 周期持续存在，内存越来越大。跑几个小时的 session 里这个量不小。

性能

Section titled “性能”

两个有针对性的改进：

macOS 启动快了约 60ms，办法是把钥匙串凭证读取和模块加载并行化，不再串行等待。

大 session 的 --resume 最多快 45%，峰值内存减少约 100-150MB。fork-heavy 的 session 受益最大。

2.1.77 释放的信号

Section titled “2.1.77 释放的信号”

三个新功能，25+ 个 bug 修复，两个性能改进。比例本身就说明了方向。

token 上限提升是实打实的——128k 输出 tokens 意味着 Opus 4.6 和 Sonnet 4.6 的单次响应可以装下一个完整的、生产级的模块。对代码生成工作流来说，这是能力层面的变化。

安全修复很关键。hooks 绕过企业 deny 规则这种 bug 会侵蚀托管部署的信任基础。修了，而且确立了一个原则：deny 规则说了算。

其他的都是一个团队认真看 bug 报告的结果。自动更新器的内存炸弹、resume 的竞态截断、粘贴处理器、CRLF 转换、CJK 渲染、tmux 剪贴板——每一个都在以细小而具体的方式把某个人的工作日搞差一点。现在都修了。

如果你还在 2.1.76，更新。如果你跳过了 2.1.76，更新。这个版本让工具在日常使用中更可靠。
