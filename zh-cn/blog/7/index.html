OpenClaw v2026.3.13-1：恢复发布，70+ 修复覆盖智能体、安全、移动端和消息平台

2026年3月17日

OpenClaw v2026.3.13-1：恢复发布，70+ 修复

Section titled “OpenClaw v2026.3.13-1：恢复发布，70+ 修复”

GitHub 不允许重复使用已发布的 release tag。v2026.3.13 发布时出了问题，团队没法直接修复后重新推送。于是他们打了 v2026.3.13-1 的标签，npm 版本保持 2026.3.13 不变，然后把 70 多个修复塞了进去。

这次恢复发布，反而成了项目近期社区参与度最高的一次。

为什么是 v2026.3.13-1？

Section titled “为什么是 v2026.3.13-1？”

原始的 v2026.3.13 标签和 GitHub Release 坏了。GitHub 的不可变发布机制不允许覆盖已发布的标签。解决办法很直接：

  • Git 标签 / GitHub Release： v2026.3.13-1
  • npm 包版本： 2026.3.13（没变）

-1 后缀只存在于 Git 层面。用 npm 安装的话，什么都不用改。

智能体修复

Section titled “智能体修复”

智能体层面这次改动最多。

Anthropic 思维块回放。 之前智能体对话中 Anthropic 的 thinking blocks 会被错误回放，现在直接在回放时丢弃（#44843）。

内存文件重复注入。 macOS 和 Windows 这种大小写不敏感的文件系统上，内存文件可能被注入两次。路径比较现在做了大小写折叠处理（#26054）。

会话重置保留字段。 lastAccountId 和 lastThreadId 在会话重置时会被清掉，现在保留了（#44773）。重置提示语也改了措辞，避免触发 Azure 内容过滤器（#43403）。

跨智能体工作区解析。 一个智能体生成子智能体时，如果目标是另一个智能体的工作区，路径解析会出错。修了（#40176）。

自定义提供商密钥。 本地自定义提供商的空 API 密钥在引导流程中会被覆盖掉。现在保留了（#45631）。

压缩后健全性检查。 压缩系统现在用完整会话的 token 计数做健全性检查，而不是部分计数（#28347）。

安全加固

Section titled “安全加固”

Docker 令牌泄露。 网关令牌可能通过 Docker 构建上下文泄露，现在 Dockerfile 里做了防护（#44956）。所有 Dockerfile 还加了 apt-get upgrade 来更新基础镜像（#45384）。

控制 UI 认证。 不安全连接下的控制 UI 认证绕过之前被意外删除了，现在恢复了，还加了连接失败分类（#45512）。

macOS PortGuard。 远程模式下 PortGuard 会误杀 Docker Desktop 进程，不会了（#13798）。

网关请求限制。 未应答的客户端请求现在有上限，防止资源耗尽（#45689）。

消息平台修复

Section titled “消息平台修复”

Telegram。 入站媒体下载在 IPv6 失败时会通过 IPv4 回退重试（#45327）。线程媒体传输策略正确传入了 SSRF 防护（#44639）。

飞书。 文件上传时非 ASCII 文件名不再丢失（#34262）。新增事件级去重层，防止重复回复——如果你之前遇到过飞书消息重复，这个修复就是为你准备的（#43762）。

Discord。 网关元数据获取失败不再导致处理程序崩溃（#44397）。

Signal。 群组配置加入了 Signal 通道 schema（#27199）。

Slack。 新增可选的交互回复指令，支持构建更丰富的 Slack 集成（#44607、#45463）。

移动端

Section titled “移动端”

Android 重新设计了聊天设置界面（#44894），修复了 TalkModeVoiceResolver 中的 HttpURLConnection 泄露（#43780），引导流程的二维码扫描切换到 Google Code Scanner（#45021），还补上了智能体验证 schema 中缺失的 params 字段（#41171）。

iOS 新增了引导欢迎页面（#45054）。

浏览器自动化

Section titled “浏览器自动化”

浏览器工具收到三个修复。批量操作调度的选择器和批处理支持做了规范化（#45457）。批量失败和限制处理做了加固（#45506）。现有会话的驱动验证和会话生命周期管理收紧了（#45682）。

构建和 UI

Section titled “构建和 UI”

内存回退。 插件 SDK 的 chunk 被重复打包，导致约 2 倍内存回退。通过去重修复了（#45426）。

仪表盘重载风暴。 聊天历史在仪表盘上循环重载，已停止（#45541）。

聊天渲染。 超大聊天回复保持可读（#45559）。滚动提示按钮恢复了 chat-new-messages CSS 类（#44856）。聊天上下文通知图标大小修复（#45533）。

Ollama。 Ollama 模型的原生推理输出现在隐藏了（#45330）。

Gemini。 模型 ID 规范化现在也适用于 google-vertex 提供商（#42435）。

其他变更

Section titled “其他变更”
  • Cron 死锁。 防止了隔离 cron 嵌套通道死锁（#45459）。
  • 插件冲突。 插件在通道和绑定冲突时立即失败（#45628）。
  • 时区支持。 Docker 容器支持 OPENCLAW_TZ 时区配置（#34119）。

凌晨两点，手腕酸得不行。调了一晚上 bug，脑子里清楚得很——接下来要让 Claude 做什么，三段话就能说清的架构改动。手指搭在键盘上，突然想起来：我可以直接说。

发生了什么

Section titled “发生了什么”

2026 年 3 月初，Claude Code 上线了原生语音输入。Anthropic 工程师 Thariq Shihipar 在 X 上宣布：“Voice mode is rolling out now in Claude Code.” 这条帖子被看了 70 多万次。

一条命令，不装插件，不配 API key，不需要第三方工具。

搞定。语音模式开了，终端里出现一行提示：

按住空格键，说话，松手。你说的话会实时变成文字，出现在提示框里。

实际怎么用

Section titled “实际怎么用”

交互方式是按住说话（push-to-talk）。按住空格录音，松手停止并转写。这是故意这么设计的——终端里不会有一直开着的麦克风，不会打字打到一半突然触发。

几个你会关心的细节：

只管输入。 Claude 回复仍然是文字，不是语音。语音是给你的提示词用的，不是 Claude 的回答。想让 Claude 用语音回复，可以用社区做的 claude-code-voice-hooks。

混合输入。 你可以先打一半字，按住空格说中间那段，再接着打。语音和键盘不冲突。逻辑用说的，变量名用打的。

懂开发术语。 语音转文字模型针对代码做过调优。camelCase、文件路径、正则、JSON key、OAuth、仓库名，它都能正确转写。你说 “getUserById”，它写的就是 “getUserById”，不是 “get user by ID”。

可以打断。 Claude 正在回复的时候，你可以按住空格说话，直接打断它。

免费。 语音转写的 token 不算在你的速率限制里。

配置

Section titled “配置”

没有配置。有 Claude Code 就有语音。

换语言

Section titled “换语言”

用 /config 切换听写语言。截至 2026 年 3 月中旬，支持 20 种语言，包括英语、俄语、波兰语、土耳其语、荷兰语、乌克兰语、希腊语、捷克语、丹麦语、瑞典语、挪威语等。v2.1.69 一次加了 10 种。

注意：settings.json 里还没有 voiceLanguage 设置项。GitHub issue #31724 有 24 个赞在请求这个功能。目前换语言走 /config。

Section titled “平台支持”
平台状态

什么时候用语音

Section titled “什么时候用语音”

语音不是万能的。但这些场景下它帮得上忙：

长提示词。 描述架构改动、解释 bug、讲你屏幕上看到的东西。超过两句话的内容，说比打快。

调试的时候。 “第 47 行有个 TypeError，user 变量是 undefined，但它应该在第 23 行的 useEffect 里被赋值，我觉得问题出在依赖数组是空的。“说出来 10 秒钟，打出来要一分钟。

规划和脑暴。 边想边说，语音能捕捉你的思维流，不用先在脑子里把格式排好再打字。

无障碍需求。 腱鞘炎、腕管综合征，或者任何让长时间打字变得痛苦的状况。语音把终端变成了一场对话。

打字更合适的场景： 短命令、精确语法、带特殊字符的文件路径、在开放式办公室里。

之前有什么

Section titled “之前有什么”

Claude Code 的内置语音不是第一个终端语音方案。社区先动手了：

  • voicemode — 基于 MCP，支持本地 Whisper 语音转文字 + Kokoro 文字转语音，可离线
  • claude-voice — 按住说话 + 神经网络 TTS，macOS 为主
  • Spokenly — Claude Code 的语音转文字封装

原生 /voice 不是要替代这些工具。你要离线转写、自定义 TTS、唤醒词，社区工具有原生版没有的功能。但如果你只是想”跟终端说句话”，/voice 是最省事的选择。

MCP elicitation

Section titled “MCP elicitation”

这是本次更新的头条。

到目前为止，MCP 工具调用是严格的请求-响应模式：Claude Code 发请求，服务器返回数据。如果服务器需要你提供额外信息——凭据、配置选项、操作确认——它没有办法开口。

MCP elicitation 改变了这一点。MCP 服务器现在可以在工具调用过程中发送 elicitation 请求。Claude Code 将其渲染为交互式对话框：表单字段用于结构化输入，浏览器 URL 用于 OAuth 类流程。你回应后，服务器带着你的回答继续执行。

两个新 hook 配合这个功能：

  • Elicitation 在 MCP 服务器请求输入时触发，对话框展示之前。你可以检查、修改或自动回应。
  • ElicitationResult 在你回应之后、结果发送回服务器之前触发。你可以覆盖或记录将要返回的内容。

为什么这很重要？数据库工具可以问你用哪个 schema。部署工具可以在应用变更前请求确认。认证工具可以把你重定向到登录页面，等待 token 返回。MCP 工具从被动的数据源变成了交互式的协作者。

延迟工具：compaction 后 schema 丢失

Section titled “延迟工具：compaction 后 schema 丢失”

如果你用 ToolSearch 按需加载工具（延迟工具），它们的 input schema 会在对话 compaction 后被静默丢弃。数组参数和数字参数会被拒绝，报类型错误。工具一开始能用，compaction 之后就坏了，没有明显的原因。

根本原因：compaction 序列化工具定义时没有保留完整的 schema。修复后 schema 能正确存活。

如果你遇到过 session 前半段工具正常、后半段突然报类型错误的情况，就是这个 bug。

Section titled “自动 compaction 熔断器”

BMAD Quick Dev 的边界拓展：当 AI 开发工作流遇上 PPT 周报生成

2026年3月13日
Vibe Sparking

一个为代码开发设计的 AI 工作流，如何驾驭”读 Excel + 浏览器截图 + 编辑 PPT”这种跨工具链的非编码任务？

背景

Section titled “背景”

每周五下午，团队都要做一件重复但不能省的事：打开 Excel 汇总表，把”上周完成”和”本周计划”复制到 PPT 模版里，再登录云服务商控制台截一张监控大盘图贴进去。整个过程大约 30 分钟，纯机械操作。

这种任务看起来和”写代码”毫无关系。但当我把它交给 BMAD Quick Dev 工作流时，发现这套为软件开发设计的方法论框架，处理非编码任务同样得心应手——甚至比手动操作更可靠。

为什么用 BMAD Quick Dev？

Section titled “为什么用 BMAD Quick Dev？”

在上一篇文章中，我们用 BMAD Quick Dev 完成了一个 Bug 修复的闭环。那次的场景很”标准”：读代码、改代码、写测试、代码审查。

但这次不一样。周报生成涉及：

  • 读取 Excel 文件（openpyxl）
  • 编辑 PPTX 文件（python-pptx + lxml）
  • 操控 Chrome 浏览器截图（Claude Chrome Extension）
  • 图像合成与下载（Canvas API）

没有一行应用代码需要修改，也没有测试可以跑。BMAD 在这种场景下还能发挥作用吗？

答案是：不仅能，而且正是这种”看似简单实则步骤繁多”的任务，最能体现 BMAD 步骤文件架构的价值。

BMAD 工作流实录

Section titled “BMAD 工作流实录”

Step 1: Mode Detection —— 判断执行模式

Section titled “Step 1: Mode Detection —— 判断执行模式”

Quick Dev 的第一步不是”开始做”，而是评估。

AI 读取了 Issue 文件（任务描述），自动完成了三件事：

  1. 捕获基线状态：记录 baseline_commit，确保后续可以追溯变更
  2. 判断执行模式：没有技术规格文件 → Mode B（直接指令）
  3. 评估升级必要性：任务涉及文件操作和浏览器自动化，但结构明确、无架构影响 → Escalation Level 0-1，不需要升级到完整 BMAD 流程

然后给出选择：[P] Plan first（先做技术规格） 还是 [E] Execute directly（直接执行）。

BMAD 的价值： 如果没有这一步，AI 会直接开始读 Excel、写 Python。而 Mode Detection 强制 AI 先退一步思考全局——这个任务的复杂度是否超出了快速开发的范围？是否需要先出一份技术规格？

对于周报生成这种任务，答案显然是 [E]。但这个”显然”是经过评估得出的，不是拍脑袋决定的。

Step 2: Context Gathering —— 收集上下文

Section titled “Step 2: Context Gathering —— 收集上下文”

这一步是 BMAD 对”直接指令”模式的特殊处理。在技术规格模式下会跳过，但直接指令模式下，AI 需要自主完成上下文收集。

工作流要求 AI 完成四件事：

1. 识别需要操作的文件

Section titled “1. 识别需要操作的文件”

2. 发现相关模式

Section titled “2. 发现相关模式”

AI 检查了目标目录下的历史周报文件，确认了命名规范（周报_YYYYMMDD.pptx）、模版结构（6 个 Slide）、以及 Excel 数据的表头格式。

3. 检查依赖

Section titled “3. 检查依赖”

4. 生成执行计划并推断验收标准

Section titled “4. 生成执行计划并推断验收标准”

BMAD 的价值： Context Gathering 要求 AI 先检查依赖再动手。这避免了一个常见问题——AI 写了一大段代码，运行时才发现 python-pptx 没装。提前发现、提前解决，不浪费上下文窗口。

更重要的是，验收标准是 AI 推断出来的，不是人类写的。这意味着 Self-Check 阶段有明确的核验目标。

Step 3: Execute —— 连续执行

Section titled “Step 3: Execute —— 连续执行”

Step 3 的核心原则是：Continue through ALL tasks without stopping for milestones.

这一条规则对周报生成任务至关重要。因为这个任务有 5 个步骤，每一步之间有依赖（先装库、再复制文件、再读 Excel、再改 PPT、最后截图），但没有一步需要人类决策。如果 AI 每完成一步都停下来问”继续吗？“，30 分钟的任务不会变快。

实际执行过程中，AI 遇到了几个障碍：

障碍 1：Excel 数据中的控制字符

Excel 单元格里混入了 \t（Tab）和 \n（换行），直接写入 PPTX 的 XML 会报错。AI 的第一次尝试失败了，但按照 BMAD 的 Halt Conditions 规则——“Tests fail and fix is not obvious” 不在停止条件内——AI 自主分析错误原因，清洗了文本数据，第二次成功。

障碍 2：浏览器截图无法直接保存到磁盘

Claude Chrome Extension 的截图返回的是对话上下文中的图片 ID，不是文件。AI 尝试了 screencapture（权限不足）、html2canvas（MCP 超时）、upload_image（安全限制），连续 3 次失败。

按照 BMAD 的规则，“3 consecutive failures on same task” 应该 HALT 并请求人类指引。AI 确实停了下来。人类给出指示：“Just use Claude Chrome Extension to grab screenshot”——一句话点明方向。

AI 随后采用了一个巧妙的方案：在页面内用 JavaScript Canvas API 合成监控图表，通过 <a download> 触发浏览器下载到 ~/Downloads，再用 Python 读取文件嵌入 PPTX。

BMAD 的价值： Halt Conditions 的设计精髓在于——该停的时候停，不该停的时候不停。Excel 控制字符问题，AI 可以自己解决，不需要打断人类；浏览器截图问题，连续 3 次失败说明当前方向有误，需要人类指引。这种”自主解决 vs 请求帮助”的边界判断，不是靠 AI 的”直觉”，而是靠工作流的规则。

Step 4: Self-Check —— 自检

注意”Tests”这一项——对于非编码任务，没有单元测试可以跑。AI 的做法是用 Python 重新打开生成的 PPTX 文件，验证每个 Slide 的内容是否正确。这本质上是一种验收测试。

BMAD 的价值： Self-Check 不是形式主义。它强制 AI 回头审视自己的工作，而不是”做完就算完”。在这次实践中，Self-Check 验证了 PPTX 文件的 7 个 Slide 的内容都正确——如果有一个 Slide 的表格数据写错了，这一步就能发现。

BMAD 在非编码任务中的适配

Section titled “BMAD 在非编码任务中的适配”

这次实践证明，BMAD Quick Dev 的步骤文件架构对非编码任务同样有效。但有一些适配值得注意：

适配 1：Step 5（对抗性审查）被自然跳过

Section titled “适配 1：Step 5（对抗性审查）被自然跳过”

周报生成不涉及代码变更，没有 diff 可以审查。工作流在 Step 4 完成后自然终止，没有强行进入 Step 5。这是合理的——工作流应该为任务服务，而不是反过来。

适配 2：测试 = 验收验证

Section titled “适配 2：测试 = 验收验证”

在代码开发场景下，Step 3 的”Test”意味着跑 RSpec 或 Jest。在文档生成场景下，“Test”变成了”用 Python 重新读取输出文件，验证内容是否正确”。BMAD 的框架足够抽象，没有把”Test”硬编码为”跑测试框架”。

适配 3：Halt Conditions 的判断依然精准

Section titled “适配 3：Halt Conditions 的判断依然精准”

浏览器截图的 3 次连续失败触发了 HALT，这是正确的。Excel 控制字符的问题没有触发 HALT，也是正确的。这说明 BMAD 的停止条件规则（“3 consecutive failures” / “blocking dependency”）是与任务类型无关的通用规则。

BMAD 带来的三个核心价值

Section titled “BMAD 带来的三个核心价值”

1. 防止 AI “直觉性跳步”

Section titled “1. 防止 AI “直觉性跳步””

没有 BMAD 的 AI 会怎么做这个任务？

大概率是：直接开始写 Python 脚本 → 遇到 python-pptx 没装 → 装完继续 → 遇到 XML 错误 → 反复试错 → 最后发现浏览器截图保存不了 → 又反复试错。

整个过程是反应式的：遇到问题 → 解决问题 → 遇到下一个问题。

BMAD 的 Context Gathering 步骤把这个过程变成了计划式的：先检查所有依赖 → 确认方案可行 → 生成完整计划 → 一次性执行。

差别不在于最终结果（都能做完），而在于上下文窗口的消耗。反应式做法在每次试错中浪费大量 token，计划式做法把试错集中在开始阶段。对于上下文窗口有限的 LLM 来说，这个差别直接影响任务完成质量。

2. 明确”自主”和”求助”的边界

Section titled “2. 明确”自主”和”求助”的边界”

这次实践中最关键的人机交互只有两次：

  1. [E] Execute directly → 人类确认不需要先做技术规格
  2. “Just use Chrome Extension” → 人类在 AI 连续 3 次失败后给出方向

两次交互，总共不超过 10 个字。其余所有工作都是 AI 自主完成。

这种精准的人机协作不是偶然的——它是 BMAD 工作流设计的结果。Step 1 的 [P/E] 选择、Step 3 的 Halt Conditions、Step 4 的 Self-Check，每一个都是精心设计的人机交互点。

不该打断人类的时候不打断，该打断的时候及时打断。 这是工作流比”自由对话”优越的本质。

3. 让任务可复现

Section titled “3. 让任务可复现”

这次周报生成的完整过程被 BMAD 工作流结构化地记录了下来：

  • Mode Detection 的判断依据
  • Context Gathering 的文件清单和依赖检查
  • Execute 的任务列表和遇到的障碍
  • Self-Check 的核验结果

下周再做同样的事情，AI 不需要从零摸索。把 Issue 文件的 Excel 文件名和日期改一下，/bmad-bmm-quick-dev @issue-file.md，BMAD 会以同样的步骤、同样的质量完成周报生成。

这就是工作流和”一次性对话”的根本区别：工作流是可复现的，对话不是。

适用场景

Section titled “适用场景”

BMAD Quick Dev 不仅适用于代码开发，还适用于以下类型的自动化任务：

任务类型BMAD 的价值
周期性报告生成（PPT/PDF/邮件）Context Gathering 确保依赖就绪，Execute 连续执行
数据迁移/格式转换Halt Conditions 在异常数据时及时停止

共同特征：步骤明确、依赖可查、结果可验证。

总结

Section titled “总结”

BMAD Quick Dev 的设计初衷是”小需求快速开发”，但它的步骤文件架构——Mode Detection → Context Gathering → Execute → Self-Check——本质上是一套通用的任务执行框架。

这次实践的启示：

  1. 好的工作流是任务无关的。 BMAD 的步骤没有假设”任务一定是写代码”。评估复杂度、收集上下文、连续执行、自检结果——这些步骤对任何结构化任务都成立。

  2. Halt Conditions 是 AI 自主性的安全阀。 没有 Halt Conditions，AI 要么一路莽到底（浪费 token 在死胡同里），要么每一步都问人（打断工作流）。BMAD 用简单的规则（3 次连续失败 → 停）精确控制了这个边界。

  3. Context Gathering 的投入回报比最高。 花 1 分钟检查依赖和确认方案，省下的是执行阶段的反复试错。对于 LLM 来说，上下文窗口就是最宝贵的资源，Context Gathering 直接降低了这个资源的浪费。

  4. 工作流让 AI 从”聊天助手”变成”执行引擎”。 没有工作流的 AI 是一个需要不断 babysit 的实习生。有了 BMAD，AI 变成了一个知道何时汇报、何时自主、何时停下来的专业执行者。

CTO 视角：OpenClaw 企业级多项目 AI Agent 架构怎么搭

2026年3月13日
Vibe Sparking

五个项目，三个 Slack 工作区，两个 QQ 群，一个 Telegram 频道，十几个工程师天天问同样的部署问题。

你开始琢磨 AI Agent。不是那种演示玩具，是能嵌入团队工作流、干实事的那种。

装了 OpenClaw，建了一个 Agent，接上 Slack，能用。然后有人问：“项目 B 也能来一个吗？“又有人问：“QQ 群里也能回复吗？”

问题来了：怎么给整个工程团队搭一套 Agent 架构？

多数人的第一反应是错的

Section titled “多数人的第一反应是错的”

大部分 CTO 上来就按渠道想。Slack 一个 Agent，QQ 一个 Agent，Telegram 再来一个。直觉上很对，实际上是坑。

渠道只是门。按门来分 Agent，意味着逻辑重复、回复不一致、每多接一个平台维护量就翻一倍。

先搞清楚 OpenClaw 的四个组件

Section titled “先搞清楚 OpenClaw 的四个组件”
  • Gateway — 控制面。路由消息，管 session 和 memory，连接一切。
  • Agent — 脑子。每个 Agent 有自己的 LLM、提示词、工具集、记忆。
  • Channel — 门。Slack、QQ、Telegram、Web、CLI，只是消息入口。
  • Binding — 路由规则。决定哪扇门通向哪个脑子。

看清这四个东西的分工，架构就出来了。

推荐方案：平台化 + 项目隔离 + 多渠道接入

Section titled “推荐方案：平台化 + 项目隔离 + 多渠道接入”

平台 Agent 管公共事务。一个 DevOps Agent 了解你的 CI/CD 流水线。一个 Code Review Agent 加载了团队编码规范。一个 Documentation Agent 负责文档。这些 Agent 跨项目服务所有人。

项目 Agent 按项目隔离。Project-carehealth 有自己的 Agent，加载了 PRD、代码结构、Issue 追踪器。Project-ragLabs 也有自己的。每个项目 Agent 只知道自己的领域，不会把上下文泄露到别的项目。

角色 Agent 服务个人。CTO Agent 每天生成跨项目日报——CI 状态、代码变更量、未解决风险、客户升级。PM Agent 追踪功能进度。QA Agent 监控测试覆盖率趋势。

Gateway：一个就够

Section titled “Gateway：一个就够”

团队 30 人以下、项目 10 个以内，一个 Gateway。运维简单，Agent 共享工具，配置集中。

什么时候拆两个？需要硬隔离的时候。比如内部团队 Agent 和面向客户的服务 Agent，数据边界不同，提示词安全要求不同，工具权限不同。只有这种情况才值得拆。

Channel 保持扁平，路由交给 Binding

Section titled “Channel 保持扁平，路由交给 Binding”

一个 Slack Channel 类型，一个 QQ Channel 类型，一个 Telegram Channel 类型。别按 Agent 数量去乘 Channel。

路由靠 Binding：

  • @提及路由： 在任何频道里输入 @devops，消息去 DevOps Agent。输入 @project-carehealth，去 Project-carehealth Agent。
  • 频道路由： #project-carehealth 里的消息自动去 Project-carehealth Agent，#devops 里的去 DevOps Agent。

多个 Agent 共享一个频道时，用提及路由更灵活。团队有专属频道时，频道路由更干净。

安全不是可选项

Section titled “安全不是可选项”

企业部署必须控制 Agent 的权限：

  • 按 Agent 设工具白名单。 DevOps Agent 能用 kubectl 和 terraform。Coding Agent 能操作 repo 和 PR。没有 Agent 能拿到 shell root。
  • 不允许 Agent 做生产发布。 没有例外。
  • 不允许 Agent 读取密钥。 Agent 不能直接访问凭证存储。
  • Gateway 不暴露公网。 安全事故中，暴露管理面板比提示词注入造成的问题多得多。

协调者模式：下一步

Section titled “协调者模式：下一步”

准备好升级时，加一个 Coordinator Agent。它坐在其他 Agent 上面。当请求跨多个领域——“所有项目的风险状态是什么？“——Coordinator 拆解任务，分发给 Project Agent 和 DevOps Agent，收集回复，合成统一答案。

这就是多智能体编排。让 OpenClaw 从一堆聊天机器人变成 AI 原生运营平台。

CTO 超级 Agent

Section titled “CTO 超级 Agent”

给自己建一个 CTO Agent，一条命令：/cto report。每天早上拉所有项目的 CI 状态，检查阻塞问题，汇总代码评审速度，标记安全告警，生成一份摘要。不用再切五个仪表盘了。

团队角色分工

Section titled “团队角色分工”
角色职责
CTOGateway 策略，Agent 架构决策
AI 工程师Agent 提示词维护，工具开发
项目 Agent 负责人项目知识库、提示词、工具
DevOpsGateway 运维、日志、权限、安全

完整架构图

Section titled “完整架构图”

从这里开始。一个 Gateway，按角色分 Agent，Channel 扁平化，路由靠 Binding，权限锁死。等规模上来，再加 Coordinator。

这是你公司的 AI 基础设施，别当玩具对待。

坑三：消息静默消失

Section titled “坑三：消息静默消失”

这个最耗时间。

配置全部完成，Gateway 重启后，给机器人发 “hi”。没有回复。

日志里看到：

WebSocket 连接正常。但是没有任何 im.message.receive_v1 事件进来。

排查路径：

  1. WebSocket 已连接 → 正常
  2. 事件日志为空 → 消息压根没推过来，问题在飞书那边
  3. 改 dmPolicy 为 open → 还是没消息
  4. 去飞书后台仔细检查 → 找到了

im:message.p2p_msg:readonly 这个权限状态是”未开通”。

这是”读取用户发给机器人的单聊消息”权限。没有这个权限，飞书在服务端就把事件过滤掉了。不发给长连接，不报错，不告警。消息直接丢了。

开通这个权限，发布新版本，重启 Gateway。消息立刻通了。

整个过程最难受的地方是系统给了零反馈。WebSocket 连着，配置看起来没问题，但消息就是不来。如果飞书能在事件过滤时返回一条 permission_denied 之类的提示，能省不少排查时间。

Section titled “配置检查清单”

  • openclaw.json 中账号的 appId / appSecret 已写入
  • bindings 中 accountId 对应正确的 agentId（不是 agent）
  • dmPolicy: "open" 且 allowFrom: ["*"]（接收私聊的话）
  • 飞书后台：机器人能力已添加
  • 飞书后台：订阅方式为”长连接”，事件 im.message.receive_v1 已添加
  • 飞书后台：im:message.p2p_msg:readonly 权限已开通
  • 飞书后台：已发布最新版本
  • openclaw gateway restart 已执行

Section titled “小结”

飞书接入 OpenClaw 本身不复杂，但有三个地方不按直觉来：凭据用 config set 写入而不是 --token 参数、本地扩展可能跟内置插件打架、私聊权限缺失时消息无声无息地丢。知道了坑在哪，下次配新应用几分钟就搞定。

Section titled “Bug 5：图片上传流程不对”

正确的流程是两步：先调用上传接口把 File 对象传上去拿到 URL，再把 URL 赋值给模型。这需要理解项目里的上传架构：m-pic-upload 负责选图和预览，上传逻辑在外面处理。

5 个 bug，每个定位加修复都没超过一分钟。

关键收获

Section titled “关键收获”

约定越强，YOLO 越准。 后端代码库有严格的分层约定和命名规则，Claude Code 学到以后生成的代码几乎不用改。前端的约定分散在组件属性、路由配置、菜单配置等多处，“隐性知识”更多，出错概率更高。

后端靠测试验证，前端靠人工验证。 这次后端 6 个集成测试全绿，给了很强的信心。前端没有 E2E 测试，只能打开浏览器人工检查。如果前端也有自动化测试，修复循环会更快。

修复循环才是真正的效率瓶颈。 代码生成花了几分钟，但如果没有经验判断哪里可能出问题，debug 时间会长得多。5 个 bug 里有 4 个跟项目内部约定有关，这些约定没有写在文档里，只存在于已有代码的模式中。

上传这类涉及多组件协作的功能最容易出错。 图片上传涉及选择组件、上传服务、模型绑定三个环节，Claude Code 只做了第一步就停了。跨组件的数据流需要开发者自己把关。

怎么配置这个工作流

Section titled “怎么配置这个工作流”

如果你想自己试试，步骤如下。

  1. 在项目根目录安装 BMAD 框架。它提供了一套 prompt 模板和 slash command 定义，Claude Code 能直接识别。

  2. 写好功能需求。不需要很长，关键是把数据模型、业务规则、权限要求说清楚。50 行足够。

  3. 在 Claude Code 里输入 /bmad-bmm-quick-dev，调用 Quick Dev Flow。它会读取你的需求文档，自动拆分成 story。

一个典型的”改个参数校验”的小需求。但从定位问题、修改代码、写测试、代码审查到文档归档，传统流程至少要半天。

什么是 BMAD Quick Dev？

Section titled “什么是 BMAD Quick Dev？”

BMAD Method 是一套为 AI Agent 设计的软件开发方法论框架。其中 Quick Dev 是轻量级的快速开发工作流，专为小需求/Bug 修复设计。

它的核心是步骤文件架构（Step-file Architecture）：

每一步加载独立的 Markdown 文件，解决了 LLM 长上下文中”迷失在中间”的问题。状态通过变量（{baseline_commit}、{execution_mode} 等）在步骤间传递。

什么是 YOLO 模式？

Section titled “什么是 YOLO 模式？”

YOLO = “You Only Live Once”。在 Claude Code 中，这意味着跳过人工确认，让 AI 自主决策和执行。

在 Quick Dev 工作流中，YOLO 体现为：

  • 问你要不要先做规格？→ E（直接执行）
  • 展示计划，确认吗？→ YOLO（直接干）
  • 审查发现，怎么处理？→ F（自动修复）

人类只在关键决策点介入（比如”是否要对客户端抛错”这种业务判断），其余全部交给 AI。

  • 每次修复审查发现后重新跑全量测试
  • 测试不仅验证正常路径，还覆盖了边界场景（无手机号 + 创建账号）

没有测试，YOLO 就是赌博。有了测试，YOLO 就是效率。

两种死法

Section titled “两种死法”

两个独立的 bug 都能让你的会话彻底卡死。

权限提示 CPU 死循环。 Claude Code 弹出复杂 bash 命令的权限提示时，可能进入一个紧密循环，CPU 直接打满 100%。界面冻住，没法回应提示，也没法取消。只能强制杀掉进程。修复消除了复杂命令结构触发的循环条件。

技能文件死锁。 大量技能文件同时变更——典型场景是在有很多 .claude/skills/ 文件的仓库里执行 git pull——Claude Code 会死锁。两个内部系统互相等待，谁也不让步。结果就是完全冻住，没有任何错误消息。修复去掉了循环依赖。

这类 bug 让人对工具产生怀疑。不是因为频率高，而是一旦碰上，除了杀进程没有别的办法。

多会话 bash 输出丢失

Section titled “多会话 bash 输出丢失”

在同一个项目目录里开两个 Claude Code 会话，bash 工具的输出可能会丢。一个会话的输出静默消失。原因是会话共享输出通道时的文件级冲突。

修复后每个会话有独立的输出路径。如果你习惯在同一个项目开多个终端，之前遇到命令似乎没有输出的情况，大概率就是这个 bug。

内存泄漏

Section titled “内存泄漏”

这是本次更新的头条。在 Node.js/npm 代码路径上，流式 API 响应的缓冲区在 generator 提前终止时不会被释放。你中途取消一次生成，缓冲区就留在那里。长时间会话中反复发生，RSS 就无限增长。

修复方式很直接：generator 终止时正确释放缓冲区。如果你在多小时会话中观察到 Claude Code 进程的内存持续攀升，这很可能就是原因。

这和 2.1.72 修的原生 bash 解析器内存泄漏不同。那个是命令解析期间累积的，这个是响应流期间累积的。两个 bug 导致同一个症状——进程越用越重。

MCP OAuth：两个独立问题

Section titled “MCP OAuth：两个独立问题”

MCP OAuth 认证有两个 bug，每个都能让你的集成静默失败。

端口冲突卡死。 OAuth 回调端口被占用时，认证会无限挂起。没有报错，没有超时，进程就在那里等一个永远不会到达的回调。修复后会检测冲突并给出明确错误信息。

Token 刷新失败。 部分 OAuth 服务器（Slack 是典型）用 HTTP 200 状态码返回错误。刷新逻辑把所有 200 响应当成功处理，所以 refresh token 过期后不会触发重新认证，集成就静默中断了。修复后会检查响应体的实际内容。

如果你的 MCP 集成用了几周后突然不工作了，大概率是这个原因。

Section titled “托管策略绕过”

安全修复。管理员设置的托管策略 ask 规则，可以被用户级别的 allow 规则或技能的 allowed-tools 声明绕过。层级关系现在被强制执行：托管策略优先级最高，不管用户或技能怎么声明。

两台 Mac 跑 OpenClaw，'Allow device to connect?' 弹个没完？四条命令治好它

2026年3月12日
Vibe Sparking

两台 Mac，一个局域网，同一套 OpenClaw。

一台当 Gateway，另一台以 node 身份连过去。连上之后，Gateway 这边冒出来一个弹窗：

Allow device to connect?

点了 Allow。过一会儿，又弹。再点，再弹。关掉窗口重开，还是弹。

这不是 bug。

为什么会弹

Section titled “为什么会弹”

OpenClaw 对设备连接有一套配对机制。规则很简单：

  • 127.0.0.1 / localhost → 本机回环，信任，不弹
  • 其他所有地址 → 外部设备，触发配对确认

两台 Mac 在同一个局域网，IP 是 192.168.x.x。对 Gateway 来说，这和互联网上随便一台机器没区别——都不是 localhost，都要走配对流程。

GitHub 上多个 issue 都确认了这个行为：非 localhost 连接必然触发 pairing。目前没有”同一子网就自动信任”的逻辑。

为什么点了 Allow 还会再弹

Section titled “为什么点了 Allow 还会再弹”

常见原因：

  1. 设备身份变了。 Gateway token 轮换、网络切换、macOS 更新，都可能导致 node 端的设备指纹变化。指纹一变，Gateway 认为是新设备或需要 repair 的旧设备，重新触发配对。
  2. pending repair 没清掉。 设备处于”等待修复确认”状态时，UI 上的 Allow 不一定能彻底解决。很多场景下只能靠 CLI 审批。
  3. token churn 循环。 近期 macOS 上有报告显示 token 反复刷新，导致 pairing required 循环出现。

一句话：UI 上点 Allow 有时候只是临时通过，没有走完整个设备生命周期。

正确的处理方式：CLI 四步

Section titled “正确的处理方式：CLI 四步”

在作为 Gateway 的那台 Mac 上执行：

第一步：看当前设备列表和 pending 请求

Section titled “第一步：看当前设备列表和 pending 请求”

找到有 pending repair 或 pending pairing 状态的条目。记下 requestId。

第二步：批准（或拒绝）pending 请求

也可以用 reject 代替 approve，效果是清掉 pending 状态。关键是别让它继续挂着。

同一个插件，两条路线：sliverp/qqbot 和 tencent-connect/openclaw-qqbot 到底选哪个

Vibe Sparking

在 GitHub 搜”QQ Bot OpenClaw plugin”，你会看到两个长得几乎一样的仓库。功能表一样，演示截图一样，连 QQ 群号都一样。

这背后是一个关于中国开源生态实际运作方式的故事。

两个仓库

Section titled “两个仓库”

sliverp/qqbot — 社区版。开发者 sliverp 创建，241 次提交，版本 1.5.4，MIT 协议，包名 @sliverp/qqbot。

tencent-connect/openclaw-qqbot — 官方版，挂在 Tencent Connect 下面。299 次提交，版本 1.5.7，MIT 协议，包名 @tencent-connect/openclaw-qqbot。

两个都是把 OpenClaw 接入 QQ。私聊、群聊 @、频道消息、富媒体（图片、语音、视频、20MB 以内的文件）、语音转文字、文字转语音、定时推送、输入状态、Markdown、多账号——全都支持。

功能高度重合的原因很简单：官方版是从社区版 fork 出来的。

差异在哪

Section titled “差异在哪”

差异反映了两个项目的优先级。

sliverp/qqbot 重开发者工具链

Section titled “sliverp/qqbot 重开发者工具链”
  • GitHub Actions E2E 测试流水线——自动化测试直接嵌进 CI
  • CLI 插件管理工具（bin/ 目录下）
  • README 写法干脆：功能列表、配置方法、完事

做法很”工程师”：出手快，测试到位，工具链先行。有 E2E 和 CLI 说明这个人打算长期维护。

tencent-connect/openclaw-qqbot 重生产稳定性

Section titled “tencent-connect/openclaw-qqbot 重生产稳定性”
  • 引用消息上下文 — QQ 的引用事件只发一个 REFIDX_xxx 索引，不带原文。官方版在本地维护一个持久化存储（~/.openclaw/qqbot/data/ref-index.jsonl），自动把索引解析成完整引用内容注入 AI 上下文。AI 就能理解用户到底在回复哪条消息。
  • 远程一行安装 — curl | bash 加 --appid 和 --secret，不用 clone 仓库。
  • 30 多种标签自动纠错 — 写成 <qq-img> 也能识别成 <qqimg>，容错性高。
  • 上传去重缓存 — 同一个文件发两次不会重复上传。
  • 有序队列投递 — 消息按顺序到达。
  • 独立的升级指南和中英双语结构化更新日志。

这些功能是服务大量用户才会长出来的。光是引用消息上下文这一项，就能让群聊场景下的 AI 回复质量上一个台阶。
